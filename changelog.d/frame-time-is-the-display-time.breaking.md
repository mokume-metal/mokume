窓に出して動かしている間の実時間の時計で、`time` と `deltaTime` が表すものが、「`draw()` が走った時刻」から「**その枚が表示される予定の時刻**」に変わりました ([#2390](https://github.com/mokume-metal/mokume/issues/2390))。ディスプレイが渡す表示の目標時刻 (`targetTimestamp`) を、その枚の時刻にします。

これまでは、main がイベントや SwiftUI・タイマーで数ミリ秒遅れると、そのぶんが `deltaTime` の揺れとして作品に見え、表示の時刻とずれた細かなカクつきになっていました。60 Hz の窓で main が 5 ミリ秒ごとに 0〜3 ミリ秒塞がる場面では、`deltaTime` の標準偏差が 0.87 ミリ秒 (最大の外れ 5.3 ミリ秒) だったのが、0.002 ミリ秒ほどになります。表示が刻みを飛ばした枚は、飛んだ枚数ぶん `deltaTime` が跳び、`time` は表示の時刻と合ったまま進みます。

- 表示の時刻と合うのは、その刻みに間に合った枚です。描き終えるのが遅れた枚は後の刻みで表示されますが、`time` は予定のままです
- 共有面 (`mokume watch` のプレビュー) の `time` は、スケッチ側の画面の刻みの予定の時刻です。揺れは窓と同じく取れますが、道具の窓に出る時刻とは 1〜2 刻みずれうります
- 表示のリフレッシュが止まって予備のタイマーが進めた回と、名乗りのメニューが開いている間にプレビューを動かす回は、これまでどおり現在時刻で進みます。どちらの回でも `time` は前の枚より小さくなりません
- 最初の枚は、これまでどおり `time` が 0、`deltaTime` が目標の 1 フレームぶんです。`setup()` にかかった時間は 2 枚目に乗りません
- 窓の数字 (fps・1 枚の ms) と観測の応答の `frameRate`・`frameTimeMs` は、これまでどおり描いた時刻で数えます
- フレームの時計 (`SketchSettings.clock` を `.frames` にした窓・書き出し・観測の指定秒) の値は変わりません

移行: 多くの作品は何も直す必要がなく、`deltaTime` で動かしているものは滑らかになります。`deltaTime` の揺れに合わせて何かを補正していたり、`time` と `draw()` の実行時刻 (`Date()` や `CACurrentMediaTime()` など) を突き合わせていたりするコードは、`time` が表示の予定の時刻 (実行時刻より先の、表示の刻みに揃った値) になった前提で見直してください。実行時刻と合わせたい処理は、`Date()` などを直に読みます。
