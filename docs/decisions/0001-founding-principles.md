# ADR-0001: 設計原則

## 状態

採用 (2026-08-26)

## 文脈

mokume は macOS / Apple Silicon 専用のクリエイティブコーディング環境として、これから設計と実装を始める。最初のコードを書く前に、以後のすべての設計判断 (個別 ADR) が従う原則を確定しておく。

原則は 2 群に分ける。**製品の原則**は「この道具は何であるか」を定め、**開発の原則**は「どう作り続けるか」を定める。作品を作る人間と、協働する AI エージェントの両方を一級の利用者・開発者として想定する。

## 決定

以下の 10 原則をプロジェクトの土台とする。個別の設計判断がこれらと衝突する場合、原則の側を変えるには本 ADR の改訂を要する。

### 製品の原則

1. **スケッチの気楽さを最優先する** — スケッチは 1 ファイルから始められ、ボイラープレート・並行性の注釈・ビルド設定をユーザーコードに要求しない。「書いてから絵が出るまで」の時間を常に短く保ち、実行中のコード変更の反映 (ホットリロード) を一級機能として扱う。ライブラリ内部の複雑さがスケッチの書き味に漏れ出す設計は、内部がどれほど正しくても採らない。

2. **同一入力は同一の絵を生む (決定論)** — 同じコード・同じシード・同じフレーム番号からは、バイト単位で同じ画像が得られることを設計目標にする。乱数はシード可能、時間はフレームに紐づく。決定論は作品の再現・自動検証 (golden image)・AI との協調すべての土台であり、これを壊す機能は導入時に代償を明示する。

3. **AI エージェントは一級の利用者・開発者** — 実行中スケッチの観測 (描画結果と内部状態の取得)・入力注入・ヘッドレス実行をコア要件とする。プロセス間の通信形式は schema を正典とし、実装が schema に従う (逆ではない)。API リファレンスは機械可読な形で常に生成される。人間と AI が同じ道具・同じ情報で作品を作れる状態を保つ。

4. **実需が機能を駆動する** — 機能の追加は、実際の作品制作で踏まれた必要によって正当化する。想定だけの API を先回りで作らない。リファレンス作品の制作をライブラリ開発と並走させ、そこで困ったことがロードマップの源泉になる。

5. **macOS / Apple Silicon 専用・最新世代への一本化・外部依存は最小** — 対象プラットフォームを絞り、Swift・Metal は単一の最新世代に一本化する (採用する世代の具体は個別 ADR で確定する)。旧世代との並走サポートは持たず、互換ビルドを検証する CI も持たない。依存は Apple 標準フレームワークを第一選択とし、外部パッケージは代替が無い場合に限る。

### 開発の原則

6. **単一リポジトリ・単一バージョン・自動リリース** — ライブラリ・CLI・プロジェクトテンプレートは 1 つのリポジトリで開発し、1 つのバージョンタグで常に同時に出荷する (バージョン間の整合検査という問題クラスを発生させないため)。リリースは自動で回し、出荷を人手の儀式にしない。1.0 までは 0.x として破壊的変更を許容し、早すぎる安定化をしない。バイナリ配布物を必要とする拡張だけは別リポジトリに置く (SwiftPM の binaryTarget は、使わない product 経由でも利用者に artifact をダウンロードさせるため)。

7. **git に生成物とバイナリをコミットしない** — 生成できるもの (API リファレンス・索引など) は CI が生成して配信し、ローカルでは `make` でオンデマンド生成する。画像・動画・モデル等のバイナリは外部ホスティングへ置き URL で参照する。「コミットされた生成物の鮮度を検査する」という機構をそもそも持たない。

8. **検証は規約でなく構造で保証する** — CI の検査は `make ci-check` の 1 入口に集約し、CI 定義はそれを呼ぶだけにする (ローカルと CI の乖離を構造的に不可能にする)。main へのマージは merge queue を通し、「main は常に検証済み」を機械が保証する。ファイルの帰属 (著作権とライセンス) は機械検査し、帰属不明のファイルは存在した時点で CI が落ちる。**描画に影響する変更は絵で検証する** — 視覚的証跡 (before/after) を PR に残し、決定論 (原則 2) に基づく golden image 比較を自動検証に育てる。問題が再発したら、文書ルールの追記ではなく機構 (CI・hook・lint) で塞ぐ。

9. **正典は GitHub に置き、変更は Issue から始める** — 設計判断は `docs/decisions/` の ADR、作業の経過と発見は Issue / PR に記録する。ADR は自己完結で書き、読者に外部の文脈を要求しない。変更は Issue 起票 (目的・完了条件) から始め、ブランチ → PR (`Closes #N`) → merge の順で進める。複数工程の仕事は親 Issue + sub-issue で構成し、本文のチェックリストでは管理しない。文書は「どれが正か」を常に 1 つに保ち、同じ内容の二重管理を作らない。

10. **言語を強制しない** — メンテナは日本語で作業する (このリポジトリの規約文書・コミット・PR・Issue は基本日本語で書かれる)。これはメンテナ自身の実践であって、リポジトリが要求するルールではない。どの言語での Issue 起票・コントリビューションも妨げない。コードの識別子は英語とする。

## 影響

- 個別の設計判断 (モジュール構成・並行性規範・色規範・ビュー層・パラメータ API・採用する Swift/Metal 世代など) は、本原則に沿う形で番号付き ADR として順次確定する。
- 原則 1 と 3 は緊張しうる (内部の並行性・観測機構がユーザーコードへ漏れやすい)。個別 ADR では「スケッチの書き味を損なわない形で成立するか」を必ず検査する。
- 原則 2 により、決定論を壊す要素 (実時間依存・非シード乱数・非同期の描画順) は既定で採用しない。必要な場合は opt-in にする。
- 原則 4 により、リファレンス作品の制作トラックをライブラリ開発と並走させる (体制は別途 Issue で設計する)。
- 原則 6 により、CLI の配布 (Homebrew) はこのリポジトリのリリースタグを起点に組む。
- 原則 7 により、リポジトリの肥大要因は構造的に排除されるが、生成・配信のパイプラインを CI に持つコストを引き受ける。
- 原則 8 により、検証機構の導入 (`make ci-check`・merge queue・帰属検査) が最初の整備対象になる。視覚検証の自動化 (golden image) はレンダラ実装後の整備対象。
- 原則 10 により、ドキュメントは当面日本語で書かれる。公開文書の多言語展開は必要になった時点で別の ADR として判断する。
