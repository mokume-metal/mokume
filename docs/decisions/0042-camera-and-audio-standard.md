# ADR-0042: カメラと音を標準の機能として持つ — 呼べば入る受け口・置き場・共通の土台

## 状態

採用 (2026-10-03) / 改訂あり (本文の「改訂 (日付)」見出し)

## 文脈

### 地図はカメラと音を標準に置いたが、形は決めていない

[ADR-0041](0041-standard-scope-map.md) の地図は、カメラと音 (入力の解析・ファイル再生) を標準の区分に置いた。地図が決めるのは領域が本体に入るかどうかだけで、**利用者からどう見えるか・どこに置くか・中で何を共有するか**は決めていない ([#1957](https://github.com/mokume-metal/mokume/issues/1957))。

受け口の作法は [ADR-0028](0028-external-inputs.md) が先に引いてある (差込口を通る・入れ物 2 種・機材の選び方・許可の状態・外の画素は `Image`・注入の道・決定論の名乗り)。ただし、どれも実装を持たない。**組み込みで入り口 (`Inlet`) に準拠している型は、いま 0 個である。** カメラと音は最初の利用者になり、その形がシリアル・OSC・MIDI・動画の再生 (同じ地図の標準) の型紙になる。

### 前身のライブラリで繰り返したくないこと

前身のライブラリもカメラと音を本体に持ち、作例で最も使われた周辺機能だった (カメラ 5 本・音 2 本)。そこで起きたことのうち、ここで決めないと再発するものを挙げる。

| 前身で起きたこと | 何が要るか |
|---|---|
| 毎フレームの口が領域ごとに違った (`update()` / `read()` / `poll()`)。呼び忘れるとどれも黙って何も起きず、手動と自動を併用すると 2 回進んだ | 毎フレーム進める口を 1 本にする |
| 失敗の伝え方が領域ごとに違った (throws / `lastError` / コールバック / フラグ)。カメラは作った時点で始まり、音は始まらなかった | 状態の型を 1 つにする |
| カメラの時刻も MIDI・OSC の時刻も捨てたので、書き出しと同期できなかった ([metaphor#563](https://github.com/shinyaoguri/metaphor/issues/563)) | 時刻を 1 本にする |
| 外から来た絵を専用の型 (`MTLTexture?`) で渡したので、立体に貼れなかった ([metaphor#701](https://github.com/shinyaoguri/metaphor/issues/701)) | ADR-0028 決定 5 (外の画素は `Image`) を守る |
| 見せる値と測る値を同じ名前にした。`volume` が振幅 0.354 で飽和して戻せなかった ([metaphor#941](https://github.com/shinyaoguri/metaphor/issues/941)) | 生の値と正規化した値を別の名前にする |
| 音などを本体に依存しない層に置いたので、本体の型への準拠と便利な口を束ねの入口に置くしかなく、リファレンスから消えた ([metaphor#565](https://github.com/shinyaoguri/metaphor/issues/565)) | 本体の上に載る層に置く |
| 11 の product に分けたが、作例 343 ファイルのうち 341 が束ねの入口 (`import metaphor`) しか使わなかった | 利用者に product を選ばせない |

### いまの本体は、呼び出しの途中で差込口を足せない

差込口の登録は、スケッチの組み立て時に 1 回だけ行われる (`SketchRuntime` が `Sketch.plugins` を読む)。呼び出しの途中で並びに入れるのは書き出しの係 (`FrameRecorder`) だけで、その道は本体の内側 (private) にしかない。

Processing / p5.js の `createCapture()` のように「呼べば使える」形にするには、**実行中に差込口を足し・外す口が要る。** 内側にだけ作ると、組み込みにできて外のパッケージにできないことが増える ([ADR-0024](0024-extension-seams.md) 決定 10 が防ぐもの)。

### 外の画素を `Image` に書く公開の道は 1 本ある

[#487](https://github.com/mokume-metal/mokume/issues/487) で `Image.write(_ picture: DisplayImage)` を入れた。1920×1080 の 1 フレームを GPU へ送るまでで 2.20 ms で、外のパッケージ (Syphon の受け取り) もこの道を通っている。GPU のテクスチャを直に受ける口を足せばこの 2.2 ms も消せるが、予算に収まっているので足していない。下位の描画資源が公開の面に出るのは `OutputFrame.texture` の 1 点のままである。

### OS の受け口は、待ち行列とスレッドを向こうが決める

- カメラの受け取り (`AVCaptureVideoDataOutput`) は、待ち行列を引数に取る
- 音の入力と出力は、OS の realtime スレッドで呼ばれる。そこでは確保・ロック待ち・dispatch ができない ([WWDC19 510](https://developer.apple.com/videos/play/wwdc2019/510/))

[ADR-0010](0010-concurrency-model.md) 決定 4 は `DispatchQueue` を新たに導入しないと決め、例外をファイルの見張り 1 本に限っている。カメラと音を入れると、この例外が 1 本ではなくなる。

### 許可は、実行の形によって振る舞いが違う

カメラとマイクは OS の許可 (TCC) を要する。

- 許可は、アクセスした「責任を負うプロセス」に付く。端末から起動した実行ファイルでは、端末アプリが責任を負う ([Apple Forums 756510](https://developer.apple.com/forums/thread/756510))
- 一方、前身では、束ねない実行でダイアログが出ず、未決定のまま止まった ([metaphor#685](https://github.com/shinyaoguri/metaphor/issues/685)。15 秒でサンプル 0、`.app` なら 12 秒で 94 枚)
- 拒否・未回答のあいだ、音は無音・映像は黒になり、エラーにならない
- `.app` には `NSCameraUsageDescription` / `NSMicrophoneUsageDescription` が要る。hardened runtime なら entitlement (`com.apple.security.device.camera` / `audio-input`) が無いとダイアログも出ずに拒否される。ad-hoc 署名は、ビルドし直すたびに許可が外れる ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements))

**束ねない実行 (`mokume run`) を実測すると、ダイアログは出て、許可は起動した端末アプリに付いた** ([#1957](https://github.com/mokume-metal/mokume/issues/1957) の実測、2026-10-03)。開始時はカメラ・マイクとも未決定で、起動から最初の値が届くまで (ダイアログに答える時間を含む) がマイク 1.9 秒・カメラ 4.2 秒、以後カメラは毎秒 30 枚・マイクは途切れずに届いた。[ADR-0028](0028-external-inputs.md) 決定 4 の「許可のダイアログは束ねたアプリにしか出ない」は、この実測と食い違う。前身の「ダイアログが出ずに止まる」は再現しておらず、起動の仕方によっては起こりうるものとして残る。

## 決定

### 1. カメラと音は、呼べば使える標準の機能にする。`plugins` には書かせない

根拠は [ADR-0041](0041-standard-scope-map.md) の地図 (標準の区分) である。

```swift
final class Mirror: Sketch {
    var camera: Capture?
    func setup() { camera = createCapture() }       // 呼んだときだけ機材を開く
    func draw() {
        if let camera { image(camera.image, 0, 0) } // camera.image は普通の Image
    }
}
```

名前は例である。決めるのは実装の Issue で、Processing / p5.js に倣う ([ADR-0020](0020-api-naming-and-surface.md) 決定 1)。

- **呼んだときだけ機材を開く。** `import mokume` しただけでカメラが点いたり、許可のダイアログが出たりしない
- **標準の機能は呼び出しの形だけを持つ。** 同じ機能を `Sketch.plugins` にも載せられる形は作らない。書き方が 2 つあると、両方に書いたときにどちらが勝つかを誰も言えない ([ADR-0024](0024-extension-seams.md) 決定 4 と同じ理由)
- **この作法は地図の他の標準 (動画の再生・シリアル・OSC・MIDI ほか) にもそのまま効く。** カメラと音だけの取り決めにしない

**`plugins` に書くプラグインの形は採らない。** 毎回 `var plugins: [any Plugin] { [camera] }` の 1 行が要り ([ADR-0001](0001-founding-principles.md) 原則 1 の気楽さに反する)、載せ忘れると黙って何も起きない — 前身の「呼び忘れ」と同じ種類の失敗になる。`Sketch.plugins` は外から足す機能の並びで、標準の機能の置き場ではない。

> 破れたとき: 載せ忘れたカメラが黙って黒い絵を返す。原因がスケッチの書き方なのか許可なのか機材なのかを、外から言い当てられない。

### 2. 実行中に差込口を足し・外す口を、MokumeCore の公開の面に置く

決定 1 の「呼べば使える」は、呼び出しの中で差込口を並びに入れることで実現する。そのための口を MokumeCore に**公開で**置く。

- **公開にする。** 外のパッケージも同じ書き味 (`createSyphonServer()` のような) を作れる。呼べば入る手軽さを、組み込みだけの特権にしない ([ADR-0024](0024-extension-seams.md) 決定 10)
- **並びは本体の中で 1 本のまま。** 呼び出しで入ったものも `plugins` で宣言したものも、同じ並びに入る ([ADR-0024](0024-extension-seams.md) 決定 4)。書き出しの係が「頼まれている間だけ並びに居る」形 ([ADR-0023](0023-frame-stages-and-outputs.md) 決定 5) を、入り口にも開く
- **読み込み時の自動登録はしない。** 並びに入るのは呼んだときだけである ([ADR-0024](0024-extension-seams.md) 決定 5)
- **開けなかったときは黙らない。** 扱いは宣言で入れたものと同じ ([ADR-0024](0024-extension-seams.md) 決定 7)。ただし、機材が無いことは失敗ではなく状態として持つ (決定 4)。後から挿されるからである
- 口の名前と、手放したときに並びから外れる時点は、実装の Issue で決める

> 破れたとき: 本体の内側にだけ道があり、外のパッケージは `plugins` の 1 行を要求し続ける。組み込みにできて外にできないことが、外からは見えないまま増える。

### 3. 置き場は本体の上に載る別ターゲット。MokumeCore の `public` だけで書く

```
MokumeDiagnostics ← MokumeCore ← (カメラ・音のターゲット) ← mokume (束ねの入口が再輸出する)
```

- **[ADR-0016](0016-package-structure.md) 決定 1 の「コア依存」の層に置く。** ADR-0016 は改訂しない
- **MokumeCore の `public` だけを使う。** `package` 可視性には触れない。差込口と決定 2 の口が、外から本当に使えることの証明になる
- **ターゲットの一覧はこの ADR で固定しない。** 決めるのは「外とやりとりする領域はコア依存の層に置き、MokumeCore の `public` だけを使う」という規則だけである。束ねの入口が再輸出するので、割り方は利用者に見えず、後から併合・分割しても書き味は変わらない。最初はカメラと音の 2 本で始め、後の領域は着手時に既存へ入れるか新しく切るかを決める
- **利用者が選んで import する product にはしない。** `import mokume` だけで届く。前身では、分けた product がほとんど使われなかった
- **`extension Sketch` の便利な口は、そのターゲット自身に置く。** 束ねの入口に置くと、リファレンスから消える (前身で起きた)

MokumeCore の中のフォルダでなく別ターゲットにする理由は 2 つある。

1. `public` だけで書くことが、ビルドで強制される
2. OS のコールバックのためのコードと realtime のコードを本体から隔離できる (決定 7)

> 破れたとき: カメラが MokumeCore の内側の都合に寄りかかり、外のパッケージには同じものが書けなくなる。あるいは本体に依存しない層に置かれ、本体の型への準拠を書く場所を失う。

### 4. 共通の土台を MokumeCore に置く。地図の他の領域も同じ土台を使う

[ADR-0028](0028-external-inputs.md) の決定 2・4・6 を、次の 5 つの部品として具体化する。

| 土台 | 中身 | ADR-0028 |
|---|---|---|
| 受け渡しの 3 層 | (a) OS のコールバック層 (`nonisolated`。クロージャは `@Sendable`) → (b) 入れ物 → (c) `supply()` がフレームの開始時に 1 回だけ取り出す | 決定 2 |
| 毎フレームの口は 1 本 | 利用者は `update()` のような口を呼ばない。`Inlet.supply()` だけが進める | 決定 1 |
| 時刻は 1 本 | 届いた値はすべて host time (`mach_absolute_time`) を持ち、フレームへの割り当てでフレームの時刻に直す。カメラ・音・MIDI の時刻はどれも host time に揃えられる | — |
| 供給元を差し替えられる | 実機 / 記録の再生 / 合成した値を、同じ口に差し込む。差し込む位置は OS のコールバック層の直後 | 決定 6 |
| 状態の型を 1 つにする | 許可待ち / 拒否 / 動作中 / 機材なし / 切断と、最後に値が届いた時刻。観測の面 ([ADR-0018](0018-observation-and-control-surface.md)) から読める | 決定 3・4 |

- **機材が無いことは状態で持ち、`open()` で投げて外さない。** 後から挿されたときに戻れる
- **供給元の差し替えが、機材の無い検査と決定論的な書き出しの両方を成り立たせる。** 差し替えた先では許可を要求しない
- ADR-0028 決定 8 の「足す日にやることの表」は、カメラと音では次のように埋まる。実装の Issue は、この表を完了条件に写す

| ADR-0028 | カメラ | 音 (入力) |
| --- | --- | --- |
| 1 差込口 | `Inlet` に準拠する。本体に同梱する (本 ADR) | 同左 |
| 2 入れ物 | 最新の 1 つ (フレームは溜めない) | 最新の窓 (リングバッファ) |
| 3 機材 | 一覧・識別子での選択・使えなくなったことが読める | 入力の機材の一覧と選択 (Core Audio)・抜かれたことが読める |
| 4 許可 | 状態と最後に届いた時刻。束ねた形でも確かめる | 同左 |
| 5 画素 | `Image` に書く (決定 5) | — |
| 6 注入 | 自分で作った画素の列を差し込む | 音声ファイル・合成したサンプル列を差し込む |
| 7 名乗り | 台帳に入れるのは注入で回すときだけ | 音声ファイルで回すときは水準 2 を名乗れる (決定 6) |

- 届き続ける値を `AsyncSequence` で公開する ([ADR-0010](0010-concurrency-model.md) 決定 5) か、フレームで読む値として持つかの使い分けは、下の改訂 (2026-10-06) で決まった

> 破れたとき: 領域ごとに毎フレームの口・失敗の伝え方・時刻の持ち方が分かれる。前身で起きたことが、地図の領域の数だけ繰り返される。

#### 改訂 (2026-10-06) — 届き続ける値は、フレームで読む値として持つ

音の入力の実装 ([#1978](https://github.com/mokume-metal/mokume/issues/1978)) で、上で実装の Issue に回した使い分けを決めた。

- **カメラの絵と音の解析の結果は、フレームで読む値として持つ。** `supply()` がフレームの開始時に 1 回取り出し (カメラは最新の 1 枚、音は最新の窓)、入り口の型の値 (`Capture.image`・`AudioIn.level` ほか) に書く。`AsyncSequence` にはしない
- 取りこぼすと意味が変わる出来事の列 (OSC・MIDI のメッセージ) は、`AsyncSequence` のまま残す
- 理由と、例を外した経緯は [ADR-0010](0010-concurrency-model.md) 決定 5 の改訂 (2026-10-06) に置く

### 5. 外の画素は `Image.write(DisplayImage)` の道を通す。GPU の道は、計測で足りなくなったら足す

カメラの絵は、[#487](https://github.com/mokume-metal/mokume/issues/487) の公開の道で `Image` に書く。外のパッケージ (Syphon の受け取り) と同じ道である。

- **下位の描画資源を、面に新しく出さない。** 露出は `OutputFrame.texture` の 1 点のまま ([ADR-0024](0024-extension-seams.md) 決定 8・[ADR-0028](0028-external-inputs.md) 決定 5)
- 受け取る画素の形式 (420v / 420f で受けて変換するか、32BGRA で受けるか) は、実装で計測して決める ([TN3121](https://developer.apple.com/documentation/technotes/tn3121-selecting-a-pixel-format-for-an-avcapturevideodataoutput) は 420v / 420f を既定に勧めている)
- **フレームの予算に収まらないと計測で示されたら、GPU のテクスチャを直に受ける道を足す。** 足すときは決定 3 のとおり MokumeCore の `public` に置き、外のパッケージも使えるようにする ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) の順序)
- 長く持つと機材のメモリが枯れる sample buffer は、入れ物に最新の 1 枚だけを持ち、`supply()` は新しい 1 枚が来たときだけ書く

**当初の案は、`CVMetalTextureCache` でコピーせずに Metal へ渡すことだった** (#1957)。しかし、それを MokumeCore の `public` だけで書くには下位の描画資源を面に出すことになり、決定 3 と ADR-0024 決定 8 の両方に反する。コピーの費用は #487 で予算内と測れているので、先にこちらを採る。

> 破れたとき: カメラのためだけに `MTLTexture` を受ける口が面に増える。それを使えるのは組み込みだけになるか、外の語彙が面に散る。

### 6. 音の範囲は、解析・再生・合成まで。音の流れは音のターゲットが持つ

**範囲は次の 3 つで、Processing Sound と並ぶところまでとする。**

1. マイク入力の解析
2. 音声ファイルの再生と、再生中の音の解析
3. 合成とエフェクト (オシレータ・ノイズ・エンベロープ・フィルタ・簡単なエフェクト)

DAW にはしない。Audio Unit のホストは持たない ([#1972](https://github.com/mokume-metal/mokume/issues/1972))。

- **再生と合成は、同じ音の流れに入る音源として設計する。** 音の流れは音のターゲットが持ち、**本体に 3 つ目の差込口は作らない** ([ADR-0024](0024-extension-seams.md) 決定 1)。音は絵のフレームの前でも後でもなく、OS の音の時計で進むためである
- **解析は純粋な関数にする。** 入力はサンプル列と窓の終わりの時刻、出力はスペクトル・RMS である。実機ではリングバッファの最新の窓を、書き出しでは音声ファイルの「その時刻の窓」を、同じ関数に通す
- **書き出しでは、音声ファイルを解析して動くスケッチは [ADR-0025](0025-determinism-levels.md) の水準 2 を名乗れる。** 音声ファイルの窓はフレームの時刻から一意に決まるので、外の時間に依らない ([ADR-0028](0028-external-inputs.md) 決定 7 の注入と同じ扱い)
- **生の値 (RMS・dB・スペクトルの大きさ) と、0〜1 に正規化した値を別の名前にする**
- 入力の機材は Core Audio で選ぶ (macOS に AVAudioSession は無い)。AVFAudio の呼び出しは薄い層に閉じ込める (macOS 27 SDK で `installTap` などが非推奨になり、`installAudioTap` へ移る)
- 検査は manual rendering (オフライン) モードで走らせる。機材に触れずに、決定論的に走る

**当初の案は、入力の解析だけを先に入れ、再生と合成は後で扱いを決めることだった** (#1957)。変えた理由は 2 つある。

- 地図 (ADR-0041) が既にファイル再生を標準にしていて、その下限は Processing である。Processing Sound は合成とエフェクトまで持つ (#1972)
- 「曲を鳴らしながら、その曲を解析して絵を動かす」(p5.sound の `song.play()` と `fft.analyze()`) が最もよくある形で、再生が無いとこれが書けない

> 破れたとき: 音に反応する映像を書き出すたびに、実時間で鳴らして録るしかなくなる。書き出しの結果が回ごとに違う。

### 7. OS の受け口が待ち行列やスレッドを決めるものは、ファイルの見張りと同じ条件で認める

カメラの受け取りの待ち行列と、音の realtime スレッドは、[ADR-0010](0010-concurrency-model.md) 決定 4 の追補 (ファイルの見張り) と同じく、**並列の設計ではなく OS の受け口の形**である。次の条件をすべて満たすときに限って認める。

1. **受ける点でしかない。** 待ち行列やスレッドの上で受けたものは、入れ物 (決定 4) に入れるところまでで手を離す。並列の処理を組まない
2. **境界を越えるのは `Sendable` な値か合図だけ。** OS の型 (`CMSampleBuffer` など) を越えさせない
3. **利用者に漏らさない。** コールバックは internal に留め、公開の面に出さない ([ADR-0010](0010-concurrency-model.md) 決定 5)
4. **realtime スレッドでは、確保・ロック待ち・dispatch をしない。** 事前に確保したリングバッファ (書き手 1・読み手 1) へ書くだけにする
5. **置くのは決定 3 の別ターゲットだけ。** MokumeCore の例外は、ファイルの見張りの 1 本のまま増やさない

OS のコールバックを受ける型は明示的に `nonisolated` にする。既定の隔離が main actor のターゲットでは、そうしないと動的な隔離検査 (SE-0423) で落ちうる。

> 破れたとき: 受け口の待ち行列の上で処理が育ち、決定 4 が禁じた自前の並列が「OS の都合」の名目で増える。

### 8. 許可と束ねは CLI が持つ

- **`mokume bundle` が `NSCameraUsageDescription` / `NSMicrophoneUsageDescription` を入れる。** 文言は作者が `mokume-app.json` に書く。hardened runtime なら entitlement も付ける。差込口が権限を宣言する仕組みは作らない ([ADR-0024](0024-extension-seams.md) 決定 9)
- **ad-hoc 署名では、ビルドし直すたびに許可が外れることを文書にする**
- **CI と注入で動かすときは、許可を要求しない** (決定 4 の供給元の差し替え)
- **束ねない実行では、許可はスケッチではなく起動した端末アプリに付く** (文脈の実測)。同じ端末から動かすスケッチはどれも 1 度の許可で済み、端末アプリを替えると改めて求められる。CLI は特別な手当てをせず、この振る舞いを文書にする
- **許可が未決定のまま値が来ないときは、1 度だけ知らせる。** 3 秒経っても値が 0 で許可が未決定なら、どのアプリの許可を見ればよいかを診断に出す (前身 [metaphor#699](https://github.com/shinyaoguri/metaphor/issues/699) の形)。実測ではダイアログが出たが、出ない起動の仕方 (前身の例) のために残す

> 破れたとき: 束ねた `.app` だけが、ダイアログも出ずに黒い絵を返す。作った手元では動くので、配った先でしか気付かない。

## 影響

- **`import mokume` の公開の面が増える。** 増えた口には [ADR-0020](0020-api-naming-and-surface.md) の規範検査 (`make api`) がそのまま効く。ただし `scripts/api-surface.py` はいま MokumeCore だけを見ているので、カメラ・音のターゲットを足す実装で、見る範囲を複数のモジュールへ広げる
- **組み込みで `Inlet` に準拠する最初の型が、カメラになる。** ADR-0028 の決定 3・4・6 は、ここで初めて実地に掛かる
- **GPU を通る検査 (カメラの画素を `Image` に書くところ) は、専用機で走る** ([ADR-0019](0019-drawing-verification.md) 決定 7)。音の解析は GPU を要らないので、GitHub のランナーでも走る
- **実装の順番と進み具合は Issue が持つ。** 実装の Issue は [#1959](https://github.com/mokume-metal/mokume/issues/1959) の下に置いた
  1. 共通の土台を、カメラを最初の利用者にして作る (決定 2・4・5 の実装) — [#1977](https://github.com/mokume-metal/mokume/issues/1977)
  2. 音の入力の解析 (マイクと音声ファイル) — [#1978](https://github.com/mokume-metal/mokume/issues/1978)
  3. 音声ファイルの再生と、再生中の音の解析 — [#1979](https://github.com/mokume-metal/mokume/issues/1979)
  4. 合成とエフェクト — [#1980](https://github.com/mokume-metal/mokume/issues/1980)
  5. 許可の文言と entitlement を束ねで入れる (決定 8) — [#1981](https://github.com/mokume-metal/mokume/issues/1981)
- **ホットリロード (`mokume watch`) で走らせ直すたびに、機材を開き直す。** 開き直しの費用が書き味を損なうかは、1 の実装で確かめる
- `mokume-audio` / `mokume-camera` の外のリポジトリをどうするかは、本 ADR の範囲外 ([ADR-0041](0041-standard-scope-map.md) 影響節)
