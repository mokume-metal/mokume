# ADR-0020: API の名前と面の規範

## 状態

採用 (2026-08-28)

## 文脈

いま公開している API は 91 宣言で、その大半は描画の骨格と観測の面が占める。2D の道具を揃えると**この数は 3 倍以上になる**。

名前の決め方はどこにも書かれていない。判断は API 1 本ごとの裁量に委ねられており、この状態で面を広げると、**同じ意味の操作が違う綴りで並ぶ状態が固定される**。「切る」操作が `noFill()` と `disableShadows()` と `clearEffects()` と `shadows(false)` の 4 通りで書かれている面を想像すればよい。どれも単体では妥当で、混ざったときだけ悪い。

そして混ざった後に直すのは、利用者のコードが壊れる変更になる。1.0 未満は破壊的変更を minor で出せる ([ADR-0009](0009-platform-floor-and-toolchain.md)) が、**出せることと、出してよいことは違う**。名前は書き手の指に残るものなので、揺らすたびに信頼を削る。

### この面には二層ある

利用者が最初に触るのはスケッチの中から直接呼ぶ形で、その下に描画の面がある。

```swift
func draw() {
    background(...)   // ← 利用者が触る層
    circle(x, y, d)
}
canvas.circle(x, y, d)  // ← 下の層。道具や検査はここを直接使う
```

二層あること自体は妥当で、**層ごとに正しい作法が違う**。上は手軽さが第一で、書き味は先行するクリエイティブコーディング環境の語彙に揃っているほど学習が要らない。下は Swift のコードとして読まれるので、Swift の慣行に従うほうがよい。

### 既に重複が始まっている

現状、直接呼べる描画 12 本 (`background` / `fill` / `stroke` / `strokeWeight` / `rect` / `circle` / `line` / `translate` / `rotate` / `scale` / `push` / `pop`) は、下の層と**同じ説明文を持っている**。いまは転送するだけなので中身も一致しているが、片方だけ直す変更が 1 度でも入れば食い違う。そして食い違いは、生成した API 一覧を読むエージェントに直接届く。

## 決定

### 1. 名前は、手本があればそれに従い、無ければ Swift の慣行に従う

- **手本がある**とは、Processing または p5.js のリファレンスに**同名または同義の API が存在する**ことをいう。その場合は**名前と引数の順序**をそのまま採る
- 手本が無いものは Swift API Design Guidelines に従う
- **この規則が効くのは利用者が最初に触る層だけ**。下の層は常に Swift の慣行を正とする

判定はリファレンスを引くだけで済み、裁量が入らない。この規則により `noFill()` と `loadImage(from:)` が同じライブラリに同居することは「不統一」ではなく**二層の設計**として説明でき、新しい API を足すときの判断も自動になる。

下の層が上の層の転送先である場合に限り、同じ名前・同じ引数ラベルを許す — 転送の対称性を検査で確かめられる形を保つためで、**下の層の新規 API は Guidelines に完全準拠**とする。

### 2. オンオフは 1 系統で表す

- 手本があれば手本の綴り (`noFill()` の形)
- 手本が無ければ**真偽値を 1 つ取る関数**を 1 本置く

`enable*` / `disable*` の対も、`set*` / `clear*` の対も作らない。系統が増えるのは「どちらの綴りか予測する規則」が無いときであり、規則を 1 本に決めればその余地が消える。

### 3. 状態は 2D と 3D に等しく効く

変換とスタイルは、**描く対象の次元によって作用先が変わらない**。

いま 3D は無い。それでもここで宣言するのは、後から揃える変更が**シグネチャを変えずに描画結果だけを変える**種類の変更になるからである。利用者のコードはコンパイルが通ったまま、絵だけが変わる。この形の変更は移行の手立てが乏しく、事前に宣言しておく以外に払わない方法がない。

一方にしか意味を持たない状態 (光・投影・奥行きの扱いなど) は、**API 自身が名前で示す**。例外を作るときは本 ADR を改訂する — 散文の但し書きで運用しない。

### 4. 説明文の正本は、利用者が最初に触る層に置く

下の層には「転送である」ことだけを書き、意味の説明を重ねない。

同じ説明を 2 か所に置けば必ず食い違い、しかもその食い違いは**生成した API 一覧を通してエージェントの書くコードに届く**。正本を 1 つに決めるのは、[ADR-0001](0001-founding-principles.md) 原則 9 (同じ内容の二重管理を作らない) を API の説明文へ適用したものである。

### 5. 失敗の伝え方は、呼ばれ方で決める

| 種類 | 伝え方 |
|---|---|
| フレームごとに呼ばれるもの (描画) | **投げない。** 受け口で値を検証し、警告を出して安全な既定へ倒す (何もしない・範囲に丸める) |
| 資源の生成・初期化 | 型のついたエラーを投げる |
| 読み取り (画素・状態・寸法) | **決して落ちない。** 値が無ければ空を返す |

描画を投げるようにすると `draw()` の中が `try` で埋まり、上の層の存在意義である手軽さが失われる。逆に資源の生成は「失敗したら別の道を選ぶ」判断が要るので、黙って既定へ倒してはいけない。読み取りが落ちないのは、走っていない時点 (初期化子の中・後片付けの後) から呼ばれうるためである。

### 6. 面に出てよいのは、自前の型と Swift 標準ライブラリだけ

公開シンボルの署名 (引数・戻り値・プロパティの型) に現れてよいのは、**このパッケージが定義する型**と **Swift 標準ライブラリの型**に限る。Foundation・AppKit・Metal など外部フレームワークの型を面に出すのは例外で、**シンボルごとに理由を書く**。

モジュール単位で丸ごと許す形は採らない。「Foundation を許す」と決めた瞬間、その先 Foundation の型が何本面に出ても検査は黙る — 判断が入るのは最初の 1 回だけになり、規範として効かなくなる。シンボル単位なら**新しく外の型を面に出すたびに判断が入る**。摩擦がここでの狙いである。

理由は決定 4 とまったく同じ経路にある。面に出た外の語彙は、**版ごとに配る API 一覧を通してエージェントの書くコードに届く**。届いた語彙は 2 つの形で害になる:

- **呼べないものが「呼んでよい」顔で並ぶ。** 本 ADR を書いた時点で、AppKit の delegate 3 本が一覧に載っていた ([#324](https://github.com/mokume-metal/mokume/issues/324))。呼ぶのは OS であって利用者ではない。誰かが意図して公開したのでもなく、public な型が public なプロトコルへ準拠すると Swift が要件を public に要求するため、**黙って面に出た**ものである
- **外の版に縛られた機能が、落ちたまま残る。** 汎用エンジンの上に載せた先行実装では、エンジンの語彙が面へ漏れた結果、エンジンの更新に追随できない機能が無効のまま置かれていた ([#319](https://github.com/mokume-metal/mokume/issues/319) の 3-1)

例外を認めるときは、**その型でなければ表せない理由**を書く。`URL` はファイルの場所の正典が標準ライブラリの外にあるため、`MTLDevice` は既存の Metal 資源を持ち込む入口を意図して開けているため — どちらも「置き換えられる自前の型が無い」ことが理由になっている。「便利だから」は理由にならない。

## 影響

- 新しい API を足すときの手順に 1 段増える — **手本を引く**。引いた結果 (同名の API があったか) は PR の本文に書く。引く手間は 1 分だが、書いておくと後から規範との照合ができる
- 決定 3 により、3D を足すフェーズで変換の作用先を議論し直す必要が無くなる。代わりに、**3D の実装はこの宣言を満たす責任を負う**
- 決定 4 により、現状の重複した説明文 12 本は是正の対象になる。本 ADR は決定だけを置き、適用は 2D の各実装 PR に随伴させる
- 規範に反する公開シンボルは `make api` (`scripts/api-surface.py`) が落とす。材料はコンパイラの出すシンボルグラフで、決定 1 (転送の対称性)・決定 2 (オンオフの系統)・決定 4 (説明文の正本)・決定 6 (面に出てよい語彙) を見る。**見つけられないなら、規範は守られないものとして扱う** — 文書だけの規約は守られないという前提 ([ADR-0001](0001-founding-principles.md) 原則 6) は、この ADR 自身にも適用される。裏返せば、**機械で見つけられない決定は、書いても効かない**: 決定 3 (状態が 2D と 3D に等しく効く) と決定 5 (失敗の伝え方) はシグネチャからは判定できないので、いまも人が守る側にある
- 決定 6 により、外の型を面に出す API を足すたびに例外表へ 1 行と理由を書く手間が乗る。**これは狙った摩擦**だが、コストであることは変えられない。採用時点で例外は 10 件 (`URL` 9 / `MTLDevice` 1) で、手で読める規模に収まっている
- 手本のリファレンス自体が変わる可能性はある。追随はしない — 参照するのは「その名前が広く使われているか」であって、手本の版ではない
