# ADR-0036: 着手を人の打鍵から外す — 無人レーンと、在庫の作り方

## 状態

採用 (2026-09-07) / 改訂 (2026-09-23): 決定 2 の承認を省く範囲を、トリアージ済みの Issue に紐づく着手へ広げる / 改訂 (2026-09-27): 決定 6 で同じ根の兄弟を同じ PR に置き、判定が根を待つ Design を出す / 改訂 (2026-09-28): 決定 2 の現行範囲を先に置き、決定 7 で人が方向を返すための報告を具体化し、決定 8 で委任と事前判断の境界を定める / 改訂 (2026-09-28): 決定 1 の描画レーンと決定 4 のレーンの確保を、専用機が描画を見るようになったので畳む

## 文脈

PR の流れは、もう人を待っていない。直近 60 件の merge 済み PR は作成 → merge の中央値が 27 分で、47 件はレビュー 0 件で入っている ([ADR-0031](0031-triage-as-the-single-gate.md) が `verify: human` を畳んだ結果、PR 側に人が要るのは重要パスだけになった)。[#961](https://github.com/mokume-metal/mokume/issues/961) は止まった PR に時計を与え、詰まりを機械が動かすようにした。

**それでも、列の先頭は人が引かないと動かない** ([#975](https://github.com/mokume-metal/mokume/issues/975))。直近のセッションでメンテナが打っている入力の大半は `#886 に着手して` の 1 行と、そのあとのプラン承認である。選定も実装も PR も merge も機械が回しているのに、**着手の起動だけが人の打鍵に律速している**。#961 と同型の事象で、詰まりは*何かが起きること*ではなく***何も起きないこと***なので、`issues` や `pull_request` を契機に走る機構では原理的に捕まえられない。

### プラン承認は「押させているが止めていない」のか — 測り直した

#975 の起票時の実測は「却下 13 件・**却下に言葉が添えられたもの 0 件**」であり、[ADR-0031](0031-triage-as-the-single-gate.md) が `verify: human` を畳んだときと同じ形 (押させているが止めていない) に見えた。**同じ transcript を数え直したら、逆だった。**

08-31 以降の `ExitPlanMode` 108 回:

| セッションの入口 | 承認 | 却下 (言葉つき) | 却下 (無言) | `not in plan mode` の誤呼び出し |
| --- | --- | --- | --- | --- |
| **着手** (`#N に着手して` 等) | 63 | **2** | 0 | 3 |
| その他 (質問・起票・議論) | 35 | **4** | 0 | 1 |

**人の却下は 6 件で、すべてに言葉が添えられている** (無言の却下は 0 件)。13 件と見えたのは `is_error` だけで数えたためで、うち 4 件は `<tool_use_error>You are not in plan mode` という**エージェント自身の誤呼び出し**である。却下の言葉は別のフィールドではなく `tool_result` の中身に `To tell you how to proceed, the user said:` として入っており、そこを読まないと見えない。

添えられた言葉は 2 種類に割れる。

- **(a) リポジトリのどこにも書かれていない、将来の意図** — 「将来的にはネットワークで接続された複数の端末のコンテンツを可能な限り同期して表示させるような場合があります」「works のリポジトリ以外で、brew で入れたユーザも同じように使えるようにできるか？」
- **(b)「その観点で見たか」という問い** — 「センサー入力などの影響でインタラクティブな作品だとしてもこのプランで問題ないだろうか」

いずれも「立て直し」ではない。(b) はエージェントが調べ直して結論を変えており、(a) は**メンテナの頭の中にしかない情報**である。ADR-0031 が畳めたのは変更要求が **0 件**だったからで、ここは 0 ではない (着手セッションに限っても 65 回中 2 回 = 3.1%)。**同じ形では畳めない。**

### 在庫が尽きかけている

| | 09-06 | 09-07 01:22 |
| --- | --- | --- |
| open な Issue | 77 | **81** |
| `verify: triaged` (着手可能) | 14 | **8** (うち 2 件は着手中) |
| 未トリアージ | 63 | **73** |

直近 2 日で 40 件マージした速度に対して、着手可能な在庫は実質 6 件である。しかも [ADR-0002](0002-issue-lifecycle-and-merge-approval.md) 決定 1 の追補は「他人が書いた Issue には印を付けない」と定めているので、エージェントが自力で在庫を作れる余地は原理的に無い。

### その未トリアージの半分は、エージェント自身が作っている

未トリアージ 69 件を起票元で割ると:

| 起票元 | 件数 | 型の内訳 |
| --- | --- | --- |
| **エージェント** | **34** | Bug 12 / Task 7 / Design 6 / Feature 6 / Docs 2 / 型なし 1 |
| 人 | 35 | Task 12 / Design 10 / Bug 10 / Feature 2 / Docs 1 |

**作業中に踏んで起票した障害が、印を持たないまま積まれている。** 判断を要さない型 (Bug / Task / Docs) だけで 21 件ある。ADR-0031 決定 3 は既に「起票した Issue をその場で解決してよい」と書いているので、規律は足りていて**実践されていない**。原因は AGENTS.md の文面が「気付いたら起票する」で止まっており、**起票した後どうするかを書いていない**ことにある。

### 追補の「自分が起票した Issue」は、実質判定できない

[ADR-0002](0002-issue-lifecycle-and-merge-approval.md) 決定 1 の追補は、エージェントが自分で `verify:` を付けてよい条件を「自分が起票した Issue であること」と「本文に完了条件が書けていること」の両方とした。**前者は後から判定できない** — [ADR-0003](0003-agent-identity-separation.md) が identity を分離したのは **PR の作成だけ**で、エージェントが起票した Issue も GitHub 上の author はメンテナになる。#975 自身がその例で、本文には 🤖 の署名があるのに author は人である。

つまり追補が許した経路は、**起票したその瞬間のセッションにしか開いていない**。次のセッションから見ると、自分が書いた Issue も他人の Issue も区別が付かない。

## 決定

### 1. 3 層に分け、選ぶ側は実装しない

| 層 | 役割 | 置き場 |
| --- | --- | --- |
| 1. ディスパッチャ | 定期起床し、着手可能な Issue を選んで**子セッションを起こす**。自分では 1 行も実装しない | 判定はこのリポジトリの `scripts/` / 起床と起動は**外** (下記) |
| 2. レーン | 並行度の上限。全体で N 本 (描画と非描画を分けない。当初は描画レーンを 1 本に絞っていた — 決定 4) | `scripts/` |
| 3. 子セッション | 完了条件の再チェック → プラン投稿 → 実装 → PR → `--auto`。**今までどおりで、変えるのは起動する主体だけ** | 変更なし |

判定と実行をスクリプトごと分けるのは `scripts/stall-watch.sh` と `scripts/stall-act.sh` を分けたのと同じ理由で、**判定する側が実行して文脈を汚さないため**である。判定は読み取りしかしないので、手元でいつ打っても安全である。

**起床と子セッションの起動は、このリポジトリの外に残る。** [ADR-0017](0017-agent-support-locality.md) 決定 1 の改訂が外に残すと認めた 2 類型のうち、「守る場面がこのリポジトリの外にあるもの」に当たる — どのリポジトリにも属さない場所で走るからである。**手元の Mac である理由は選択ではなく制約で**、描画 PR は Gyazo の証跡を要し、それは Metal と窓を要求する ([#180](https://github.com/mokume-metal/mokume/issues/180))。当初は `local-render` の commit status も手元で打つ必要があったが、専用機が merge queue で描画を見るようになって畳んだ ([ADR-0019](0019-drawing-verification.md) 決定 7・[#879](https://github.com/mokume-metal/mokume/issues/879))。

### 2. トリアージ済みの Issue への着手は、プランを投稿して進む

| セッション | プラン |
| --- | --- |
| トリアージ済みの Issue 1 つに確定する着手 (入口を問わない) | Issue へ投稿して**待たずに進む** |
| それ以外 (質問・議論・起票など、Issue が確定しないもの) | **従来どおり承認を経る** |

#### 改訂 (2026-09-23) — 省く範囲は、セッションの入口ではなく「トリアージ済みの着手か」で決める

**当初の決定**は、人が手で起こしたセッションを承認に残した。文脈で数え直した 3.1% — 着手のプラン承認 65 回のうち 2 回に、リポジトリのどこにも書かれていない意図が却下の言葉として入っていた — を、最も安い注入口として潰さないためである。

実際の運用はこの決定より先へ進んでいた。repo-standards プラグインの `plan-pass.sh` (shinyaoguri/claude-plugins#155) は、同じ日から**手で起こしたセッションでも**、プランが open かつ `verify: triaged` の Issue 1 つに確定するなら承認を待たずに通している ([#1363](https://github.com/mokume-metal/mokume/issues/1363))。メンテナはこれを追認した。

**決定 2 の理由がそのまま当てはまる。** 効いているのは人が見ることであって、同期であることではない。トリアージの 1 クリックは完了条件を固めた人が押す実質のプラン承認で、手で起こした着手ではそこへもう 1 回同じ判断を重ねていた。記録は 1 文字も減らない (plan-record の投稿はそのまま)。失う 3.1% への対処は影響節が既に書いているとおり、意図を文書へ移すことである。数え直した却下 6 件のうち 4 件の入口 (「その他」) は、Issue が確定しないので承認に残る。

**`plan-pass.sh` の冒頭が根拠に挙げる集計 (却下に言葉が添えられたもの 0 件) は、この ADR の文脈が数え直して覆したものである。** この改訂はその数字に依らず、「トリアージが実質の承認である」という理由の上に立つ。待たせたいときは `RS_PLAN_PASS=0` で止まる。

無人の名乗りを起動側から渡す責務は残る。名乗りの扱いはリポジトリ側が持つ。

#### 2. 無人レーンにだけ、プラン承認を外す

**畳むのではなく、「同期であること」だけを外す。** 文脈で測ったとおり、効いているのは「人が見ること」であって「その瞬間に端末の前に居ること」ではない。

| セッション | プラン |
| --- | --- |
| 人が手で起こしたもの | **従来どおり承認を経る** — 最も安い注入口をわざわざ潰さない |
| ディスパッチャが起こしたもの | Issue へ投稿して**待たずに進む** |

投稿は `scripts/plan-record.sh` が既に行うので、**記録は 1 文字も減らない** (ADR-0031 決定 2 が承認を記録へ置き換えたのと同じ形)。

**無人であることの名乗りは起動側が環境変数で渡し、リポジトリ側がそれを読んで分岐する。** 「このセッションが無人か」を知っているのは起こした側だけなので、名乗りは外から来る。それをどう扱うかの判定はこのリポジトリが持つ ([ADR-0017](0017-agent-support-locality.md) 決定 3 — 判定の根拠を持っている側が判定する)。

</details>

### 3. 在庫は「材料はエージェント・印はメンテナ」で作る

エージェントは未トリアージの 1 件を調べ、完了条件を Issue 本文へ書く。**`verify: triaged` は付けない** — 押すのはメンテナである。

**基準を「調査して本文を固めた者」まで広げない。** トリアージが担っているのは完了条件だけではなく、**「やると決める」こと**でもある。[ADR-0002](0002-issue-lifecycle-and-merge-approval.md) は起票を「雑でよい・思いつき・不確かな報告を歓迎」と定めているので、**起票は着手の意思ではない**。未トリアージの山は「意思がまだ表明されていない思いつき」の山でもあり、基準を広げると意図の側の唯一の口が閉じる — 文脈の (a) は実際にその口から入っていた。

変わるのは押す回数ではなく、**押す場所と時刻**である:

| | いま | この決定の後 |
| --- | --- | --- |
| 人がする操作 | プラン承認 (端末の前・そのセッションが生きている間) | `verify: triaged` を 1 クリック (GitHub・溜めて後からでも) |
| 材料 | セッションが立ち上がってから作られる | **人が居ない間に溜まる** |

### 4. レーンは描画と非描画に分けない (2026-09-28 改訂)

レーンは全体で N 本とし、描画に触れる着手も触れない着手も同じレーンを取る。描画に触れるかの見込みも自己申告も持たない。

**当初の決定**は、描画レーンを 1 本に絞り、その確保をプランの確定時に行うものだった (下の履歴)。描画 PR が 2 本並ぶと、手元の実行を merge queue へ運ぶ覆いの機構が片方を待たせ、`make catch-up` を空費したためである ([#497](https://github.com/mokume-metal/mokume/issues/497))。

**守ろうとしたもの (並行した着手が互いを待たせて空費しないこと) は動いていない。** 動いたのは空費の原因である。覆いの機構は、専用機の `render` が merge queue の合流後の木を直接描くようになって畳んだ ([ADR-0019](0019-drawing-verification.md) 決定 7・[#879](https://github.com/mokume-metal/mokume/issues/879))。描画 PR も他の PR と同じく並んで入るので、レーンを分けても避けられる待ちが無く、並行度だけが下がっていた ([#1769](https://github.com/mokume-metal/mokume/issues/1769))。

代償は、描画 PR が並ぶと専用機のジョブ (1 本あたり約 4 分) が直列に並ぶことである。人手は要らない。

<details>
<summary>当初の決定 (2026-09-07): レーンの確保は、着手時ではなくプラン確定時</summary>

`scripts/drawing-paths.txt` が持つのは**ファイルの一覧**で、Issue はどのファイルを触るか宣言していない。着手時のレーン判定は必ず見込みになり、外すと「描画 PR が 2 本並走 → `#N の merge を待つ` で赤 → `make catch-up` の空費」という、レーンで避けたかった事象がそのまま起きる ([#497](https://github.com/mokume-metal/mokume/issues/497))。

子セッションはプランの「変更点」を出す時点で触るファイルが分かるので、そこで `scripts/drawing-paths.sh` に照らして自己申告し、**描画レーンが埋まっていたら実装前に降りる** (`status: in progress` を外して終了する)。降りるのは実装前なので、捨てるものが少ない。

判定 (`scripts/ready-queue.sh`) は、Issue のタイトルと本文に現れるパス片を `scripts/drawing-paths.sh` に照らし、ready の行に描画の見込み (`drawing?` / `plain?`) を付けていた。自己申告はスクリプトとしては実装されなかった。

</details>

### 5. 落ちた着手は出力に含めるが、拾わない

`status: in progress` が付いたまま、対応する worktree もセッションも open PR も無い Issue は、いま誰も見ていない。ただし本 ADR を書いた時点で該当は **0 件**であり ([#994](https://github.com/mokume-metal/mokume/issues/994) / [#927](https://github.com/mokume-metal/mokume/issues/927) はどちらも生きていた)、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) が要求する実害がまだ無い。

一方で判定側は**衝突回避のためにどのみち in progress を列挙する**ので、「落ちて見える着手」を出力に含めるのは 0 円である。**出すのは足し、拾う動作は実害が出てから足す** (判定と実行を分けた決定 1 と、向きが揃っている)。

### 6. 作業中に踏んだ問題は、起票の時点で行き先を決める

**無印のまま置かない。** 分けるのは **完了条件を自分で書けるかどうか**だけで、新しい基準は作らない — [ADR-0002](0002-issue-lifecycle-and-merge-approval.md) 決定 1 追補が既に持っている基準をそのまま当てる:

| 踏んだもの | 行き先 |
| --- | --- |
| その PR の説明で筋が通る大きさ | **起票して、その PR で閉じる** ([ADR-0031](0031-triage-as-the-single-gate.md) 決定 3 が既に許している。**既定はこちら**) |
| 筋が通らないが、完了条件は書ける | 起票し、**完了条件を本文へ書いて `verify: triaged` まで自分で付ける** |
| 完了条件を自分で書けない (設計・判断が要る) | **無印で置く** — メンテナの判断を待つ |

3 行目が「設計に関わる・判断が要るものは無理に片付けなくてよい」の判定である。**書けないことが、判断が要ることの印**なので、別の物差しを持ち込まない。

**`verify: triaged` は起票の瞬間に付ける。** 文脈で示したとおり、「自分が起票した」ことを知っているのはその瞬間のセッションだけで、次のセッションからは判定できない。後回しにすると、その Issue は誰にも着手されない状態で残る。

**1 PR の上限は動かない** — 「1 つの説明で筋が通る範囲」(ADR-0031 決定 3) が既定の歯止めであり、筋が通らなくなったら 2 行目・3 行目へ落とす。

#### 改訂 (2026-09-27) — 同じ根の兄弟は 1 行目に入り、根の直しは判定の先頭へ出る

**当初の決定**は、表の行を「筋が通るか」と「完了条件を書けるか」だけで分けていた。実際には、修正の途中で気付いた別の Bug 51 件のうち、元と同じ PR で閉じたのは 4 件 (8%) だけだった。兄弟の多くは 2 行目 (別に起票して自分で印を付ける) へ落ち、在庫として 1 件ずつ直された ([#1659](https://github.com/mokume-metal/mokume/issues/1659))。この ADR が在庫切れを問題として立てたので、**分けるほうが在庫を増やし、報われる形**になっていた。根の直しは設計に見えやすく、3 行目 (無印で置く) へ落ちて人を待った。症状の直しだけが流れ続けた。

[ADR-0040](0040-bugs-as-broken-promises.md) に合わせて、次の 3 つを変える。

1. **同じ根の兄弟は、常に 1 行目に入る。** 根の説明が「1 つの説明」である (ADR-0031 決定 3 の改訂)。2 行目へ落とすのは、根が違うと見立てたときだけである
2. **根を持つ子は、単独の着手先にしない。** 判定 (決定 1 の層 1) は、開いた `Bug` を親に持つ Issue を ready に出さず、根の着手に寄せる
3. **根の直しのうち、約束を変えないものは 3 行目へ落とさない。** 完了条件は約束と範囲で書ける (ADR-0040 決定 1・3)。3 行目に残るのは、約束そのものを決める・変える Design だけである。判定は、開いた `Bug` を子に持つ Design を子の数の多い順に出し、人の判断が最も効く所から見せる

在庫の数は目的ではない。着手できる Issue が減っても、それが根ごと閉じた結果なら後退ではない。

### 7. 変更を実物と具体例でまとめ、人が方向を返せるようにする (2026-09-28 改訂)

**当初の決定**は、Issue へのプラン記録で、人が後から意図を注入できるとした (決定 2)。理由は変わらないが、変更が速く積み上がると、個別の記録だけでは全体の方向を追いにくい。[#1717](https://github.com/mokume-metal/mokume/issues/1717) で実物・設計・判断待ちをまとめ、[#1720](https://github.com/mokume-metal/mokume/issues/1720) で2回試した。メンテナは第1回の実物を再生でき、約5分で読めたが、各 Issue にも実物と具体例が必要だと指摘した。

そこで各 Issue の調査と完了条件の具体化に、具体的な入力・操作、前後の結果、対処または代償を添える。可能な範囲でその Issue にも実物を置く。報告では対象の変更を全件辿れるようにし、意図・実物・設計の代償・判断待ちをまとめる。欠けた証跡、検証の失敗、未確認、報告の滞留も残す。撮影・公開は既存の視覚証跡の手順、記録は GitHub の Issue / PR を使い、別の正典や承認操作は作らない ([#1721](https://github.com/mokume-metal/mokume/issues/1721))。

**報告した版と、人が理解したと明示した版を分ける。** 未返答なら前の理解の基準版からの差を残し、未設定なら未設定と書く。返答が部分的なら、その対象だけを記録する。リンクの表示や再生の確認を、設計の採用や全件の理解に読み替えない。誤りや意図の相違が分かったら、元の Issue / PR を訂正し、判断が要るものを Issue へ戻す。合意した設計は ADR へ反映し、次の報告でその修正の実物または具体例まで示す。

**承認・委任の範囲は広げない。** トリアージ、重要パスの native Approve、App identity、merge queue は引き続き各 ADR と AGENTS.md に従う。沈黙を同意にせず、報告が読まれたことを PR の Approve に代えない。当初は制度自体の変更を [#1716](https://github.com/mokume-metal/mokume/issues/1716) で別に判断するとした。その後の採択を決定 8 に記録する。

代償は報告を作る手間と、返答まで理解の基準版が進まないことである。今は既存の記録を束ねる手順に留め、定期実行や新ゲートを足さない。報告の有無だけでは人の理解を保証しないので、読めた実物・分かりにくい具体例・所要時間の本人の評価を記録する。

### 8. 合意済みの約束の内側を委任し、新しい選択は人が先に判断する (2026-09-28 改訂)

**当初の決定**は、トリアージとプランの記録で人の意図を受け取り (決定 2・3)、報告で後から方向を返す形を加えた (決定 7)。人の意図を文書へ移す理由は変わらない。ただしファイルの場所や「バグ修正」という名前だけでは、利用者が引き受ける新しい代償や移行の判断を読み分けられない。[#1716](https://github.com/mokume-metal/mokume/issues/1716) の再検証では、重要パス外の PR #1694 が不正な frameRate を拒否し、公開 enum の case も増やしていた。仕様へ戻す修正であっても、使う側の対処は変わりうる。

メンテナは、次の分担と **現行の PR 承認を当面維持すること**を採択した ([#1739](https://github.com/mokume-metal/mokume/issues/1739))。

| 変更 | 進め方 |
| --- | --- |
| 合意済みの仕様へ戻す修正・事実訂正・既存方針内の保守 | トリアージ済み Issue の条件を再確認し、実装・検証・証跡・PR・queue へ進む。結果を報告する |
| 公開 API の意味・互換性方針・原則・重要な代償を新たに選ぶ | Issue に入力/操作と以前/以後、選択肢・推奨・移行方法や提供時期を示し、人が先に選ぶ |
| 検査の保証範囲・権限・エージェントの委任範囲を変える | ファイル名によらず、何を確かめなくなるか/誰が何をできるようになるかを示し、人が先に判断する |

**既存の採択を根拠にできる範囲は、その参照を示して続行する。** 同じ判断を毎回取り直さない。内部の実装方法や、同じ保証を保つ検査の修正を、重要パスに触れるだけで新たな設計判断にはしない。逆に、完了条件を書けたことを、新しい意味や代償の採択に代えてはならない。仕様へ戻す修正でも、既存作品への移行方法・提供時期が未合意なら、そこを確定する。変更の有無が判断できなければ、その不明点を Issue へ戻す。

具体例: 保存画像の破損を約束どおりに直す仕事は進める。API を廃止する仕事は、代替の書き方と提供時期を先に選ぶ。`make ci-check` から検査を外す仕事は `scripts/` だけの差分でも保証範囲の判断を要する。一方、既に合意した検査を同じ対象のまま速くする実装は、採択済みの範囲ならそのまま進められる。パスの承認の有無と、この読み分けは別である。

**判断待ちでも、調査・選択肢・試作・受け入れ条件は作れる。** 待つのは未採択の意味変更に依存する部分だけで、既存の約束を保つ独立した修正まで一律に止めない ([ADR-0040](0040-bugs-as-broken-promises.md) 決定 3)。報告の欠落・未確認を前提とする採択も同じ扱いにし、決定 7 の基準版・滞留・失敗・訂正の記録へつなぐ。

外部の貢献にも仕様と検証を求めるが、信頼して委任したエージェントと同じ権限を作者名だけで与えない。人が先に決めた方針、Issue のトリアージ、PR の native Approve はそれぞれの役割を保つ。承認の要求源は [ADR-0031](0031-triage-as-the-single-gate.md) 決定 1、identity は [ADR-0003](0003-agent-identity-separation.md)、報告は決定 7 に従う。

採らなかった案は、報告を導入した時点でパス承認を縮小・撤去すること。2回の試行は実物を届けられることを示したが、長期の見落としや判断負担が減る証拠には足りない。人の事前判断と PR の Approve の両方の手間、意味を読み違える可能性は残る。継続評価で実際の負担・見落とし・訂正を示してから別の変更として見直し、AI が委任範囲を自分で広げない。新しい分類器・ゲート・ラベルは足さず、既存 Issue/PR と報告の責務を広げる。

## 影響

- [ADR-0002](0002-issue-lifecycle-and-merge-approval.md) 決定 1 の追補「**在庫は着手のたびに 1 件ずつ固める**」を改訂する。決定 3 が先取りの在庫を作る以上、着手を待つ理由が無い。禁じ続けるのは**中身を見ずに印を付けること**だけである
- AGENTS.md の「してはならないこと」にある「気付いたら起票する」を決定 6 へ接続する。**起票で止めない**ことがこの ADR の実務上の主要な変更点である
- **人が一度も見ないまま main に入る経路ができる。** ADR-0031 が承認の代わりに置いたのは PR 本文の対応表 = 読む人間と AI の目であり、無人運転では前者が居ない。承認が減るぶん merge 後に問題が見つかる割合は上がりうる
- **そのとき戻すべきは「同期の承認」ではない。** 失われる 3.1% が運んでいたのは (a) リポジトリのどこにも書かれていない将来の意図であり、根治は**それを文書へ移すこと**である ([ADR-0001](0001-founding-principles.md) 原則 9)。実際、却下の言葉が挙げた「複数端末のコンテンツ同期」は、ADR にも Roadmap にも無いために毎回プランで注入されていた。承認を戻すのは、何が見落とされたかを名指しできなかったときの最後の手段である (ADR-0031 末尾と同じ向き)
- 判定スクリプト・在庫を作る側の作法・無人の名乗りを読む機構は、[#975](https://github.com/mokume-metal/mokume/issues/975) の sub-issue で個別に足す。本 ADR は形だけを決める
- 決定 6 は既に積まれた 34 件を消さない。それらは決定 3 の対象として拾い、判定スクリプトは「**エージェントが起票したのに無印で、型が Bug / Task / Docs のもの**」を先頭に出す
- [ADR-0003](0003-agent-identity-separation.md) の identity 分離を Issue の起票まで広げることは、本 ADR では決めない。追補の判定不能はここで回避しており (決定 6 が起票の瞬間に印を付ける)、広げる必要が実害として示されていない (ADR-0008 の順序)
