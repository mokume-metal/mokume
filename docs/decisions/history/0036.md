## 決定ごとの経緯

### 2. トリアージ済みの Issue への着手は、プランを投稿して進む

#### 改訂 (2026-09-23) — 省く範囲は、セッションの入口ではなく「トリアージ済みの着手か」で決める

**当初の決定**は、人が手で起こしたセッションを承認に残した。文脈で数え直した 3.1% — 着手のプラン承認 65 回のうち 2 回に、リポジトリのどこにも書かれていない意図が却下の言葉として入っていた — を、最も安い注入口として潰さないためである。

実際の運用はこの決定より先へ進んでいた。repo-standards プラグインの `plan-pass.sh` (shinyaoguri/claude-plugins#155) は、同じ日から**手で起こしたセッションでも**、プランが open かつ `verify: triaged` の Issue 1 つに確定するなら承認を待たずに通している ([#1363](https://github.com/mokume-metal/mokume/issues/1363))。メンテナはこれを追認した。

**決定 2 の理由がそのまま当てはまる。** 効いているのは人が見ることであって、同期であることではない。トリアージの 1 クリックは完了条件を固めた人が押す実質のプラン承認で、手で起こした着手ではそこへもう 1 回同じ判断を重ねていた。記録は 1 文字も減らない (plan-record の投稿はそのまま)。失う 3.1% への対処は影響節が既に書いているとおり、意図を文書へ移すことである。数え直した却下 6 件のうち 4 件の入口 (「その他」) は、Issue が確定しないので承認に残る。

**`plan-pass.sh` の冒頭が根拠に挙げる集計 (却下に言葉が添えられたもの 0 件) は、この ADR の文脈が数え直して覆したものである。** この改訂はその数字に依らず、「トリアージが実質の承認である」という理由の上に立つ。待たせたいときは `RS_PLAN_PASS=0` で止まる。

無人の名乗りを起動側から渡す責務は残る。名乗りの扱いはリポジトリ側が持つ。

#### 当初の決定 (2026-09-07): 無人レーンにだけ、プラン承認を外す

**畳むのではなく、「同期であること」だけを外す。** 文脈で測ったとおり、効いているのは「人が見ること」であって「その瞬間に端末の前に居ること」ではない。

| セッション | プラン |
| --- | --- |
| 人が手で起こしたもの | **従来どおり承認を経る** — 最も安い注入口をわざわざ潰さない |
| ディスパッチャが起こしたもの | Issue へ投稿して**待たずに進む** |

投稿は `scripts/plan-record.sh` が既に行うので、**記録は 1 文字も減らない** (ADR-0031 決定 2 が承認を記録へ置き換えたのと同じ形)。

**無人であることの名乗りは起動側が環境変数で渡し、リポジトリ側がそれを読んで分岐する。** 「このセッションが無人か」を知っているのは起こした側だけなので、名乗りは外から来る。それをどう扱うかの判定はこのリポジトリが持つ ([ADR-0017](../0017-agent-support-locality.md) 決定 3 — 判定の根拠を持っている側が判定する)。

### 4. レーンは描画と非描画に分けない (2026-09-28 改訂)

本文の決定 4 の見出しに併記した 2026-09-28 改訂の、当初の決定と理由をここに移した。現行の決定は本文にある。

**当初の決定**は、描画レーンを 1 本に絞り、その確保をプランの確定時に行うものだった (下の当初の決定)。描画 PR が 2 本並ぶと、手元の実行を merge queue へ運ぶ覆いの機構が片方を待たせ、`make catch-up` を空費したためである ([#497](https://github.com/mokume-metal/mokume/issues/497))。

**守ろうとしたもの (並行した着手が互いを待たせて空費しないこと) は動いていない。** 動いたのは空費の原因である。覆いの機構は、専用機の `render` が merge queue の合流後の木を直接描くようになって畳んだ ([ADR-0019](../0019-drawing-verification.md) 決定 7・[#879](https://github.com/mokume-metal/mokume/issues/879))。描画 PR も他の PR と同じく並んで入るので、レーンを分けても避けられる待ちが無く、並行度だけが下がっていた ([#1769](https://github.com/mokume-metal/mokume/issues/1769))。

#### 当初の決定 (2026-09-07): レーンの確保は、着手時ではなくプラン確定時

`scripts/drawing-paths.txt` が持つのは**ファイルの一覧**で、Issue はどのファイルを触るか宣言していない。着手時のレーン判定は必ず見込みになり、外すと「描画 PR が 2 本並走 → `#N の merge を待つ` で赤 → `make catch-up` の空費」という、レーンで避けたかった事象がそのまま起きる ([#497](https://github.com/mokume-metal/mokume/issues/497))。

子セッションはプランの「変更点」を出す時点で触るファイルが分かるので、そこで `scripts/drawing-paths.sh` に照らして自己申告し、**描画レーンが埋まっていたら実装前に降りる** (`status: in progress` を外して終了する)。降りるのは実装前なので、捨てるものが少ない。

判定 (`scripts/ready-queue.sh`) は、Issue のタイトルと本文に現れるパス片を `scripts/drawing-paths.sh` に照らし、ready の行に描画の見込み (`drawing?` / `plain?`) を付けていた。自己申告はスクリプトとしては実装されなかった。

### 6. 作業中に踏んだ問題は、起票の時点で行き先を決める

#### 改訂 (2026-09-27) — 同じ根の兄弟は 1 行目に入り、根の直しは判定の先頭へ出る

本文の決定 6 の後半 (同じ根の兄弟・根を持つ子・根の直し) が、この改訂の現行の決定である。ここには理由を残す。

**当初の決定**は、表の行を「筋が通るか」と「完了条件を書けるか」だけで分けていた。実際には、修正の途中で気付いた別の Bug 51 件のうち、元と同じ PR で閉じたのは 4 件 (8%) だけだった。兄弟の多くは 2 行目 (別に起票して自分で印を付ける) へ落ち、在庫として 1 件ずつ直された ([#1659](https://github.com/mokume-metal/mokume/issues/1659))。この ADR が在庫切れを問題として立てたので、**分けるほうが在庫を増やし、報われる形**になっていた。根の直しは設計に見えやすく、3 行目 (無印で置く) へ落ちて人を待った。症状の直しだけが流れ続けた。

### 7. 変更を実物と具体例でまとめ、人が方向を返せるようにする (2026-09-28 改訂)

本文の決定 7 の見出しに併記した 2026-09-28 改訂の、当初の決定と理由をここに移した。現行の決定は本文にある。

**当初の決定**は、Issue へのプラン記録で、人が後から意図を注入できるとした (決定 2)。理由は変わらないが、変更が速く積み上がると、個別の記録だけでは全体の方向を追いにくい。[#1717](https://github.com/mokume-metal/mokume/issues/1717) で実物・設計・判断待ちをまとめ、[#1720](https://github.com/mokume-metal/mokume/issues/1720) で2回試した。メンテナは第1回の実物を再生でき、約5分で読めたが、各 Issue にも実物と具体例が必要だと指摘した。

2026-10-06 の改訂 (本文の決定 7 の末尾) までは、次の段落が承認・委任の範囲を書いていた。重要パスの native Approve と App identity は [ADR-0044](../0044-maintainer-authored-prs-without-approval-gate.md) が外した。

**承認・委任の範囲は広げない。** トリアージ、重要パスの native Approve、App identity、merge queue は引き続き各 ADR と AGENTS.md に従う。沈黙を同意にせず、報告が読まれたことを PR の Approve に代えない。当初は制度自体の変更を [#1716](https://github.com/mokume-metal/mokume/issues/1716) で別に判断するとした。その後の採択を決定 8 に記録する。

### 8. 合意済みの約束の内側を委任し、新しい選択は人が先に判断する (2026-09-28 改訂)

本文の決定 8 の見出しに併記した 2026-09-28 改訂の、当初の決定と理由をここに移した。現行の決定は本文にある。

**当初の決定**は、トリアージとプランの記録で人の意図を受け取り (決定 2・3)、報告で後から方向を返す形を加えた (決定 7)。人の意図を文書へ移す理由は変わらない。ただしファイルの場所や「バグ修正」という名前だけでは、利用者が引き受ける新しい代償や移行の判断を読み分けられない。

メンテナは、分担の表と **現行の PR 承認を当面維持すること**を採択した ([#1739](https://github.com/mokume-metal/mokume/issues/1739))。承認の範囲は、その後の継続評価で ADR を外し ([ADR-0031](../0031-triage-as-the-single-gate.md) 決定 1 の 2026-10-03 改訂)、最後に承認のゲートそのものを外した (ADR-0044)。

次の 2 つの段落は、承認のゲートがあった頃の決定 8 の文面である。ADR-0044 が前提を外した。

外部の貢献にも仕様と検証を求めるが、信頼して委任したエージェントと同じ権限を作者名だけで与えない。人が先に決めた方針、Issue のトリアージ、PR の native Approve はそれぞれの役割を保つ。承認の要求源は ADR-0031 決定 1、identity は [ADR-0003](../0003-agent-identity-separation.md)、報告は決定 7 に従う。

採らなかった案は、報告を導入した時点でパス承認を縮小・撤去すること。2回の試行は実物を届けられることを示したが、長期の見落としや判断負担が減る証拠には足りない。人の事前判断と PR の Approve の両方の手間、意味を読み違える可能性は残る。継続評価で実際の負担・見落とし・訂正を示してから別の変更として見直し、AI が委任範囲を自分で広げない。新しい分類器・ゲート・ラベルは足さず、既存 Issue/PR と報告の責務を広げる。

その継続評価の結果が、ADR-0044 の文脈にある実測 (PR の Approve 62 回で変更 0) である。
