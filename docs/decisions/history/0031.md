## 決定ごとの経緯

### 1. `verify:` ラベルを 1 種類に畳み、承認の要求源をルールセット一本にする

本文に残したのは `verify: triaged` への畳み込みだけである。承認の要求源の部分は [ADR-0044](../0044-maintainer-authored-prs-without-approval-gate.md) 決定 2 が置き換えたので、置き換わる前の決定と、その 4 つの改訂をここに移した。

承認を要求するのは**ルールセットの `required_reviewers` だけ**である。対象パスの正本は [main-protection.json](../../../.github/rulesets/main-protection.json) に置き、team `maintainers` の 1 承認を求める。対象は、エージェントが自分の柵 (CI 設定・フックや権限のエージェント設定) を動かせるパスである。ADR は 2026-10-03 の改訂で対象から外した (次の節)。

#### 改訂 (2026-10-04) — 判定の中身を、名前の glob で上限の内側に畳む

**直前の決定** (下の改訂) は、判定の中身を**ファイル単位で**足した。ところがルールセットの `required_reviewers` は、レビュアー 1 つにつき `file_patterns` を **15 個まで**しか受け取らない。この上限は REST の文書にも OpenAPI の定義にも無く、適用の PUT が 422 (`Exceeded limit of 15 file patterns per required reviewer`) で初めて知らせた。18 個になった定義は merge されたまま適用できず、稼働中の保護は配線の 4 パターンに留まって、判定の中身は承認の外に残った ([#2075](https://github.com/mokume-metal/mokume/issues/2075))。

**同じ場所に並ぶ中身は、名前の glob で 1 つに畳む** (`scripts/*guard*.sh`・`scripts/drawing-paths.*`)。何を承認の対象にするかを閉包で決めることは変わらない。閉包のすべてが当たることは引き続き `scripts/tests/rulesets_test.py` が見る。上限を越える定義は、形の検査 (`scripts/rulesets_lib.py` の `check_shape`) が merge の前に赤にする。

**代償**: glob は閉包の外のファイルにも当たりうる。`scripts/*guard*.sh` は、これから足す柵 (名前に `guard` を持つスクリプト) を足した時点で承認の対象に入れる。柵を足す変更は承認を通すのが望ましい側なので、受け入れる。2026-10-04 の main では、畳んだ 2 つの glob が当たるのは畳む前に名指ししていた 6 本だけで、上の「承認の重さ」は変わらない。

**当初の決定** (下の改訂) は「ファイル単位で足す」だった。理由 (判定を緩める 2 段の経路を塞ぐ) は動いていない。変えたのは足し方だけである。

#### 改訂 (2026-10-03) — 承認の対象に、判定の中身を足す

**直前の決定** (下の改訂) は、承認の対象を柵の**配線** — ワークフロー・フック・権限の定義 (`.github/**` `.claude/**` `.agents/**` `.codex/**`) — に絞った。ところが配線が呼ぶ判定の**中身**は `scripts/` にあり、承認の外だった。配線を守っても、判定の本体や、それが読む部品と定義を書き換えれば判定は緩む。実際に、承認なしでゲート本体を変えた PR が 6 本あった ([#1716](https://github.com/mokume-metal/mokume/issues/1716))。決定 2 の 2026-10-03 の改訂で、PR は既定ブランチの版の判定で裁かれるようになり、同じ PR の中で自分の判定を緩めることはできなくなった。それでも、「判定を緩める PR を誰も見ないまま merge し、次の PR から緩い判定で通る」という 2 段の経路は残っていた ([#2003](https://github.com/mokume-metal/mokume/issues/2003))。

**判定の結果を変えうるファイルを、ファイル単位で承認の対象に足す。** 何を足すかは手で選ばず、根から辿って決める。根は、フックの配線 (`.claude/settings.json`・`.codex/config.toml` の command) と、判定のジョブ (`ci.yml` の `review-gate`・`drawing-evidence`、`parent-guard.yml`) が呼ぶスクリプトである。そこから、`dirname "${BASH_SOURCE[0]}"` で読む部品と定義を辿った閉包を判定の中身とする。閉包のすべてが `file_patterns` に当たることは `scripts/tests/rulesets_test.py` の検査が見るので、判定が新しい部品を読み始めたら、足し忘れはその場で赤になる。

**承認の重さ**: 直近 200 本 (#1496〜#1996) に当てはめると、新たに承認待ちになるのは 8 本 (4%) である。`scripts/` 全体を足す案 (22.5%・[#876](https://github.com/mokume-metal/mokume/issues/876)) は採らない。コードの実行の境界は「誰のコードが走るか」で、パスでは引けない (#876 の結論)。ここで守るのは「何を合格とみなすか」の基準だけである。

**台帳 (`Tests/MokumeCoreTests/scene-ledger.txt`) は足さない。** 描画が変わる PR の 1 割が触れる。台帳の更新は「目で見て絵が正しいと確かめた」という宣言で、その証跡は既に `drawing-evidence` が要求している。決定論が壊れたら台帳に触らない、という規範は [ADR-0019](../0019-drawing-verification.md) 決定 3 が持つ。承認を足しても、人の判断は増えない。

**確かめないこと**: `make ci-check` の構成 (`Makefile`) と、検査そのもの (`Tests/`・`scripts/tests/`) は対象の外のまま残る。検査を外す・緩める変更は、[ADR-0036](../0036-unattended-issue-processing.md) 決定 8 の事前判断 (保証範囲の変更は人が先に選ぶ) に委ねる。

#### 改訂 (2026-10-03) — ADR を承認の対象から外し、柵を動かすパスに絞る

**当初の決定**は、ADR・CI 設定・エージェント設定を触る変更がすべて人の目を通るとし、`docs/decisions/**` も承認の対象に置いた。下の 2026-09-28 の改訂は、その承認を「当面維持」して継続評価するとした。その評価の結果がこの改訂である ([#1952](https://github.com/mokume-metal/mokume/issues/1952))。承認の要求源をルールセット一本にする理由は変わらない。

**実測 — ADR の承認は、承認要求の 7 割を占めて何も差し戻していなかった。** 2026-09-03 以降に merge された 510 本のうち、重要パスに触れて承認を求められたのは 121 本である。

- 変更要求は 0 件だった
- 121 本のうち 85 本は、重要パスのうち ADR にしか触れていなかった
- ADR の差分が 10 行以下のコード修正 PR が 27 本あった。例: [#1938](https://github.com/mokume-metal/mokume/pull/1938) は全体 994 行のうち ADR が 4 行
- push で承認が落ちて取り直したのは 16 本で、最長 9 時間止まった

押すだけの承認が増えると、本当に見るべき柵の変更まで反射で押すようになる。

**ADR の意味は、承認ではなく事前の判断が守る。** 新しい約束・代償・保証範囲・委任範囲は、[ADR-0036](../0036-unattended-issue-processing.md) 決定 8 により Issue の段階で人が先に選ぶ。merge 前の承認が ADR に足していたのは、採択と文面の食い違いを止めることだけだった。規約の正典である root の `AGENTS.md` は元から承認の対象外で、ADR だけを守る非対称もこれで解ける。

**確かめなくなること**: ADR の文面の変更を、人が merge 前に見なくなる。採択と食い違う文面は、merge 後の報告 (ADR-0036 決定 7) と履歴で見つけて直す側に倒れる。

**戻す条件**: 採択と食い違う ADR の変更が merge 後に見つかったら、その Issue を根拠に、ADR を承認の対象へ戻すかどうかを見直す。

`.github/**` `.claude/**` `.agents/**` `.codex/**` の承認は変えない。そこはワークフロー・フック・権限の定義で、エージェントが自分を縛る仕組みそのものを書き換えられる場所である。

#### 改訂 (2026-09-28) — 意味の事前判断と、PR の承認を分ける

**当初の決定**は対象を `docs/decisions/`・`.github/`・`.claude/` の3パスと本文にも列挙した。
[ADR-0017](../0017-agent-support-locality.md) の接続追加で正本の対象が広がった後も列挙が残ったため、
一覧はルールセットの正本へ委ねる。承認の要求源を一つにする理由は変わらない。

[#1716](https://github.com/mokume-metal/mokume/issues/1716) で承認の縮小・撤去も検討したが、
報告による長期の判断負担・見落としの改善はまだ測れていないため、**現行の PR 承認を当面維持する** (継続評価の結果、2026-10-03 に ADR を対象から外した。上の改訂)。
未合意の意味・代償を人が先に選ぶ範囲は [ADR-0036](../0036-unattended-issue-processing.md) 決定 8 が持つ。
Issue での方針合意を native Approve に代えず、重要パス外であることも方針合意の不要を意味しない。
App identity と merge queue は維持する。パスによる承認が意味の変更をすべて拾う保証はなく、
判断と PR の承認の両方に手間が残る。この代償を引き受けて継続評価する。

### 2. 承認の代わりに、PR 本文へ「完了条件 × 検証」の対応表を要求する

本文は、対応表の要求・判定を既定ブランチの版で走らせること・Bug の PR で反証役が AI の目を担うことを、現行の決定として書く。ここには 2 つの改訂の全文を移した。脱出口の承認の部分は [ADR-0044](../0044-maintainer-authored-prs-without-approval-gate.md) が置き換えた。

#### 改訂 (2026-10-03) — 判定は既定ブランチの版で走る

**当初の決定**は判定の担い手を `review-gate` と定めたが、どの版の `review-gate` が判定するかを定めなかった。実際には CI が PR のマージコミットを取って走らせていたので、**PR は、自分が書き換えた版の判定で裁かれていた**。判定の本体は `scripts/` にあって承認の外なので、同じ PR の中で自分を裁く検査を緩め、そのまま通ることができた。承認なしでゲート本体を変えた PR は 6 本ある ([#1716](https://github.com/mokume-metal/mokume/issues/1716) の集計)。悪意のあったものではないが、「この PR では検査が邪魔だから直した」という形は、どの PR にも開いていた ([#2000](https://github.com/mokume-metal/mokume/issues/2000) の原則 2「裁く側は、裁かれる PR の外で走る」)。

**`review-gate` と `drawing-evidence` は、既定ブランチ (main) の版のスクリプトで PR を判定する** ([#2001](https://github.com/mokume-metal/mokume/issues/2001))。2 本とも PR の中身を API から読み、PR の木を使わないので、checkout する版を替えるだけで足りる。PR の base ではなく既定ブランチを取るのは、base は PR の側が選べるからである。

**捨てたもの**: 判定を変える PR が、その変更をその PR 自身で試せること。判定の変更は merge の後の PR から効く。

**脱出口**: ゲートが壊れていて、それを直す PR も同じゲートで赤になるときは、その PR の中で `ci.yml` の該当ジョブから `ref` の行を外す。`.github/**` に触れるので承認が要り、人が一度通る。外した行は後続の PR で戻す。

**→ [ADR-0044](../0044-maintainer-authored-prs-without-approval-gate.md) で承認が無くなり、この脱出口は人を一度通さなくなった (同 ADR の影響)。**

#### 改訂 (2026-09-27) — 「AI の目」を実在させる

**当初の決定**は、正しさの担い手を「読む人間と AI の目」とだけ書き、AI の目が何であるかを定めなかった。実際には何も置かれず、直近に merge された fix PR 23 件にレビューコメントは 0 件だった ([#1659](https://github.com/mokume-metal/mokume/issues/1659))。棚卸し・プラン・実装・検証を同じエージェントが担うので、**完了条件の範囲が、そのまま調べる範囲の上限になっていた**。直しが直しを呼んだ Bug 11 件と、取りこぼしから出た同じ根の後発 15 件がその帰結である。

Bug を閉じる PR については、[ADR-0040](../0040-bugs-as-broken-promises.md) 決定 4 の反証役がこの目を担う。完了条件を渡されないレビュアーの指摘と応えを PR 本文の `反証` の節に載せ、`review-gate` はその節の有無だけを見る。**見るのが構造の有無だけであることは変わらない。**

### 3. 1 PR の粒度を「1 つの説明で筋が通る範囲」とする

本文は、同じ根の兄弟を 1 つの説明に入れることを現行の決定として書く。ここには、その改訂の全文を移した。

#### 改訂 (2026-09-27) — 同じ根の兄弟は、1 つの説明に入る

**当初の決定**は「まとめて閉じてよい」と許すだけで、何が 1 つの説明に入るかを決めていなかった。実際には、修正の途中で気付いた別の Bug 51 件のうち、元と同じ PR で閉じたのは 4 件 (8%) だけだった ([#1659](https://github.com/mokume-metal/mokume/issues/1659))。兄弟は別に起票され、1 件ずつ直されている。

**同じ根から出た兄弟は、根の説明という 1 つの説明に入る。** 既定で同じ PR で閉じ、別の PR へ分けるには理由を書く。束ね方は [ADR-0040](../0040-bugs-as-broken-promises.md) 決定 2 (同じ根の群は sub-issue で束ね、根を直す PR がまとめて閉じる) に従う。
