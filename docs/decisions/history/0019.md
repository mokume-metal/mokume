## 決定ごとの経緯

### 2. 見た目に固有の承認は置換済み (→ ADR-0031)

本文に残したのは、[ADR-0031](../0031-triage-as-the-single-gate.md) 決定 1 に置き換わったことと、絵の正しさの担い手だけである。置換前の決定と置換した理由 (本文の `<details>` にあったもの) をここに移した。

#### 2. 見た目を伴う Issue は `verify: human` でトリアージする

**当初の決定**は「[ADR-0002](../0002-issue-lifecycle-and-merge-approval.md) の既定の機構がそのまま働き、新しい仕掛けは要らない — `review-gate` が『人間の Approve なしに merge できない』を強制する」で、続きに「自己判定テスト (下記 4) が厚くなった領域は `verify: machine` へ戻してよい」を置いていた。ラベルの二分がそのまま承認の有無を決める前提に立った書き方である。**その前提のほうが畳まれた** — 分類が実測で機能していなかったため ([#618](https://github.com/mokume-metal/mokume/issues/618)・ADR-0031)。**決定 1 の「目で判定する」は動いていない**ので、番号は増やさず、担い手が承認という操作ではないことをここに書き足す (2026-09-09・[#733](https://github.com/mokume-metal/mokume/issues/733))。

### 3. 触っていない絵の退行は、代表シーンのハッシュ照合で PR の差分に浮かび上がらせる

本文は、参照スケッチの採り方と字形の扱いを、現行の決定として小見出しに書く。ここには 2 つの改訂の全文 (当初の決定・改訂の理由を含む) を移した。2026-09-25 の改訂の「`local-render` を報告できなかった」「`local-render` の報告の条件も広げない」は、その機構を畳んだ ([#879](https://github.com/mokume-metal/mokume/issues/879)) ので本文に書いていない。

#### 改訂 (2026-09-23) — 代表シーンに参照スケッチの書き出しを加える

**当初の決定**では、「代表シーン」は検査の中で組んだシーンだけだった。検査が入力を完全に握れ、シーンごとに経路を 1 つずつ狙って組めるので、動いた行がそのまま動いた経路を名指しする。参照スケッチ (`Sketches/`) は目で見る側に置かれていた — PR の証跡として 1 度見られるもので、検査からその型を import する道も無く、`make ci-check` はビルドするだけだった。同じ前提から、参照スケッチの場所は「台帳が描く絵を動かせない」として手元の実行の覆いから外されていた ([#497](https://github.com/mokume-metal/mokume/issues/497))。

**理由 (触っていない絵は誰も見ない) は動いていない。** 動いたのは、その理由が参照スケッチにも当たるようになったことである。

- 参照スケッチは作者向けの API をほぼすべて、作者が書く形のまま呼ぶようになった ([#1350](https://github.com/mokume-metal/mokume/issues/1350))。それでも絵は PR の時点で 1 度見られるだけで、merge した後に共通部分を触った変更が絵を変えても、誰も見ない
- 走らせる検査も無かった。スケッチから呼ぶと必ず落ちる口が、窓を開いて走らせるまで見つからなかった ([#1367](https://github.com/mokume-metal/mokume/issues/1367))

そこで台帳の検査は、参照スケッチを 1 本 1 行 (`sketch:<名前>@45`) で載せる。描くのは書き出し (`--render`) と同じ 45 フレーム目で、経路も同じ `SketchRuntime` の `advance()` である。これは既存の機構の責務を広げる段 ([ADR-0008](../0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) であって、新しい部品ではない。**描く途中で落ちれば、検査ごと赤になる。**

- **標本に新しく入るのは、`Sketch` 層の中継と `SketchRuntime` の経路である** (setup / draw / 時計)。検査の中で組んだシーンは `Canvas` を直に叩くので、この経路を通る行はそれまで無かった
- **外から入る口は閉じて描く。** 観測・入力・つまみの区画と、つまみの保存を読まない。手元に残った保存で絵が動くと、「絵が変わった」の文面が台帳の書き換えを勧めてしまう
- **非同期で読む口は「届く前」の絵が載る。** `requestImage` / `requestModel` の続きは main actor で走り、検査は描き終えるまで main actor を手放さないので、45 フレーム目には必ず届いていない
- **複数フレームは持たない。** 動きのあるスケッチも 45 フレーム目には 45 フレーム分の状態が積み上がっている。取りこぼした実例が出てから足す

変えないこと:

- **役割は可視化のままである。** 動いた行が差分に現れれば足り、`drawing-evidence` の要求は広げない。失敗の文面が before / after の撮り方を示す
- **[ADR-0022](../0022-production-track.md) 決定 2 の追補の限界は残る。** 参照スケッチも面の作者が書くので、標本に現れるのは「面の作者が書く綴り」である。この改訂は [#1027](https://github.com/mokume-metal/mokume/issues/1027) の穴を塞がない ([#1377](https://github.com/mokume-metal/mokume/issues/1377))

#### 改訂 (2026-09-25) — 字形を写す行は、採った OS の版でだけ比べる

**当初の決定**は、台帳のすべての行をどの機械でも完全一致で比べていた。前提は決定論 (ADR-0001 原則 2) で、同じ入力からは同じ絵が出るので、手元の機械が違っても行は一致するはずだった。

**理由 (触っていない絵の退行を差分に浮かび上がらせる) は動いていない。** 動いたのは、字形については前提が OS の版の内側でしか成り立たないと分かったことである ([#1559](https://github.com/mokume-metal/mokume/issues/1559))。

- mokume は字形を 1 つずつ CoreGraphics で焼き、四角として置く。**字形を画素にするのは OS である**
- 同じ書体で輪郭と送り幅が同じでも、焼いた画素は macOS 26 と 27 で 1〜3 階調ずれた。既定の書体は字形そのものが変わっていた。書体の引き当ては原因ではなかった
- そのため、文字を含む 16 行は OS を上げるたびに 2 つの値を行き来していた。**OS の下限の内側にある機械なのに、素の `main` で `make ci-check` が通らず、`local-render` を報告できなかった**
- 巻き込まれていた行の多くは、文字が主題ではない。名札や数字を描く参照スケッチで、光・線・粒子を直した PR が、文字と無関係にその行を書き換えていた

そこで台帳の行を 2 つに分ける。これは既存の機構の責務を広げる段 ([ADR-0008](../0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) である。

- **文字が主題でない行は、字形の四角を置かずに採る。** 字を引き、送り幅を進める組版は通し、置く手前で止める。名札や数字は人が見るための表示で、突き合わせる絵に混ぜない ([ADR-0025](../0025-determinism-levels.md) 決定 5 と同じ向き)。字を測って決める置き場所は、そのまま写る
- **文字が主題の行は、台帳に採った OS の版 (`os=<macOS の major>`) を書く。** その版の機械でだけ比べ、版が違う機械では飛ばす。飛ばした理由 (行名・基準の版・その機械の版) は検査の記録に残す。字形を置いて採るのはこの行だけで、どちらで採るかは台帳の行が決める
- **`os=` の版はすべての行でそろえる。** OS を上げたら、文字が主題の行をまとめて新しい版の機械で採り直す。版が混ざると、どの機械でも比べられない行が残る

失うもの:

- **字と他の絵が重なる所の退行を、参照スケッチの行では見なくなる** (たとえば置き換えの混ぜ方で字の余白が下地を抜く、の種類)。文字が主題の行と、個別の検査で見る
- **文字が主題の行は、基準の版でない機械では誰も見ない。** その行を書き換える変更は、基準の版の機械で採る必要がある。1 台の機械で完結しないのは、この数行に限る

変えないこと:

- **役割は可視化のままである。** 飛ばした行は赤にしない。`local-render` の報告の条件も広げない — 台帳の検査の一部が飛んでも、残りが通れば報告する
- **字形を画素にする所を mokume 自身へ移す手は、ここでは取らない。** 輪郭から塗れば OS の版に依らなくなるが、文字の見た目がすべて 1 度動く工事になり、書体データそのものが変わる場合と絵文字には効かない。字の OS 依存が、この改訂で外した行の外で実害を出したときの次の段とする

### 4. API の仕様は自己判定テストで守る

本文は、期待値を変換を経て導く道筋を現行の決定として書く。ここには改訂の全文 (当初の文面と、字面を変えた理由) を移した。

#### 改訂 (2026-09-15) — 期待値は、打った数そのものではなく変換を経て導く

**当初の文面**は「図形の中心は指定色を量子化した値と完全一致」だった。当時は数値の入口が転送関数しか外していなかったので、打った数がそのまま書き出しの 8 bit に戻り、この文面のままで成り立っていた。[ADR-0011](../0011-color-model.md) 決定 3 の改訂 (2026-09-15) で、入口は原色も作業空間へ移すことになった。そのため彩度のある色は打った数に戻らない — `fill(204, 153, 0)` で塗った中心は `196, 155, 51` になる。

変えたのは字面だけである。**期待値を保存された画像ではなく仕様から導く**という決定の趣旨は動いていない。導く道筋が「入口の変換 (sRGB から Display P3 へ) → 出力段のエンコード → 量子化」になった。灰色 (3 成分が等しい色) は原色の取り方に依らないので、打った数と一致したままである。

### 7. CI は、隔離した専用機でだけ描画を見る (2026-09-28 改訂)

決定の見出しは本文と同じに残している (「ADR-0019 決定 7」の参照と、見出しへのリンクがそのまま効くように)。本文は、専用機の 3 つの起動・前提・定期の検査 (D)・門番を現行の決定として書く。ここには、置き換わった当初の決定と差し替えた理由 (本文の `<details>` にあったもの) と、2026-10-04 の改訂の全文を移した。2026-10-04 の改訂のうち「当初の歯止め」の段落は、本文には書いていない。

当初の決定 (2026-08-28) と、2026-09-28 に差し替えた理由:

#### 7. CI は今後も描画を見ない

これを恒久の決定として記録し、[#180](https://github.com/mokume-metal/mokume/issues/180) を閉じる。自前の機械をランナーにする案・台帳の承認をゲートにする機構・環境ごとの許容差は、**実害が出たときに** #180 の記録から読み直す (ADR-0008)。

**当初の決定**は、文脈の 2 つの理由 (他人のコードが実機で走る・得が釣り合わない) から、自前の機械をランナーにする道を閉じていた。

**守ろうとしたもの (新しい絵の正しさは目が判定し、触っていない絵の退行は機械が見る) は動いていない。** 差し替えたのは、機械が見る検査を走らせる場所だけである。2 つの理由はどちらも、当てはまる範囲が変わった。1 つ目は、専用機に届くコードを write 権限を持つ人のものに限れば当たらない。2 つ目は、手元でしか走らないことの代償が実害として測られた (上の 3 点)。#180 は閉じずに、実装の親として残した。

#### 専用機へ積む順番は、GitHub ホストの門番が決める (2026-10-04 改訂・[#2062](https://github.com/mokume-metal/mokume/issues/2062))

**専用機の runner は、queued の job を先着順に拾わない。** 2026-10-04 の実測では、queue の先頭の `render` が待つ間に、専用機は後から積まれた job を 6 本 (`render-pr` 4・後ろの group の `render` 2) と 7 本 (`render-pr` 2・後ろの group の `render` 5) 拾った。先頭の `render` は一度も拾われないまま queue の期限 (60 分) を越えて弾かれ、後ろの group がまとめて組み直しになった ([#2038](https://github.com/mokume-metal/mokume/issues/2038)・[#2040](https://github.com/mokume-metal/mokume/issues/2040))。

拾う順は GitHub が決めるので変えられない。そこで**専用機に同時に積む job を絞る**。専用機の各ジョブの前に GitHub ホストの門番ジョブ (`render-turn`・判断は `scripts/render-turn.sh`) を置く:

- `render` は、1 つ前の group の run が終わるまで積まない。group は queue の順に 1 本ずつ専用機に載る。**queue の期限の直前 (55 分) まで放さない** — 早く放すと後ろの group がそろって積まれ、期限に近い前の group と取り合って元の症状に戻る。上限は門番が自分で終わって守り、job の timeout には任せない
- `render-pr` は、merge_group の run が 1 本でも残っていれば見送る。必須ではないので merge の可否は変わらない (代償: queue が混んでいる間は、PR の時点で早く気付く情報が出ない。**例の絵の前後の比較 (#1986) を持つのは `render-pr` だけ**なので、実装だけが変わって絵が古くなったことの名指しもその間は出ない。見送りは run の要約に名乗る)
- 定期の検査 (D) は、merge_group の run が残っている間は待つ

**門番が判断するのは、専用機へ積む前の 1 回だけである。** merge queue が空いている間に門番を通って専用機の queue に入った job は、後から group ができても引き下がらない。2026-10-04 には 08:38 と 08:50 に積まれた `render-pr` 2 本が、08:53 に積まれた先頭の `render` より先に拾われた。先頭は 37 分待ち、queue の期限の 22 分前に人の手の cancel で解けた ([#2064](https://github.com/mokume-metal/mokume/issues/2064))。そこで、group ができる瞬間と PR が外れる瞬間に走る `queue-sweep` (GitHub ホスト・`actions: write` を既に持つ) が、**専用機でまだ拾われていない `render-pr` の run を cancel する** (判断は `scripts/queue-sweep.sh`)。既に走っている `render-pr` は止めない。cancel するのは `render.yml` の今の group の run が残っているときだけで (門番が見送りに使うのと同じ範囲)、待たせる相手が居なければ触らない。`queue-sweep` の `actions: write` が cancel する相手は、捨てられた group の run から、生きている PR の `render-pr` の run へ広がった。失う情報は、上の「見送る」で既に受け入れたものと同じである。ただし見送りと違い、cancel された PR の run には理由が残らない (`cancelled` とだけ出る)。理由は、その時刻の `queue-sweep` の run の出力に出る。

**見直すのは、group ができた瞬間と外れた瞬間だけである。** その後に門番を通らずに専用機へ積まれた `render-pr` は、次の契機まで残る。門番が API を読めずに通した回や、人が job 単位で rerun した回である。「先頭の `render` が待つ間、専用機の queue に他の job を置かない」を常に守るには、拾われる直前に専用機の job の中で判定し直すしかない。だがそれには専用機の job に token を渡すか、token なしで外の API を引く必要があり、上の「専用機のジョブは権限も秘密も持たない」とネットワークの隔離にぶつかる (#2064 の案 A)。そこで、取り合いの大半を占める「queue が空いている間に積まれた分」を、GitHub ホストの側で group ができる瞬間に退かせるところで止めた。

**定期の検査 (D) は退かせない。** 1 つの run の中では `needs` の鎖で 1 本ずつ積まれ (debug → 門番 → release)、どれも `wait` の門番の後ろにいるので、先頭の `render` と並ぶ定期の job は 1 本までである (`scripts/tests/render_workflow_test.py` が形を固定する)。`wait` は 60 分で通すので、queue が 60 分以上埋まり続ける間は、group がある最中にも 1 本積まれうる。それでも 1 本までである。run をまたいで重なるのは、専用機が 6 時間 (cron の間隔) 以上止まって前の回が queue に残ったときだけである。退かせると、その回の debug・release・起票がまとめて消え、赤が見えるまでの最大が約 6 時間から約 12 時間に延びる。2026-10-04 に先頭を待たせた分の多くは、既に走っていた release (30 分で切れた) で、queued の job を外す手では減らない。release の所要と頻度は [#1983](https://github.com/mokume-metal/mokume/issues/1983) の測り直しで選び直す。

門番は `actions: read` だけを持ち、GitHub ホストで走る。**専用機のジョブは権限も秘密も持たないまま**で、上の前提は動かない。門番が赤でも専用機のジョブは走らせる。`render` が skipped になると、skipped は必須チェックを満たしてしまうので、順番が乱れるほうを軽く取る。門番で待っている間に run を cancel すると `render` は cancelled で終わり、必須を満たさない (skipped にはならない・[#2063](https://github.com/mokume-metal/mokume/issues/2063) の実測)。

**当初の歯止め**は、debug と release を分け、release を debug の後に queue へ入れれば、その間に待っている `render` が割り込めるとしていた。runner が先着順に拾うことを前提にしていたが、上の実測でその前提は成り立たなかった。分けること自体は門番の前提でもあるので残し、割り込みを当てにする部分を門番に差し替えた。

2026-10-18 に、本文の日付入りの改訂・追補の見出しが 6 つになったので ([#2248](https://github.com/mokume-metal/mokume/issues/2248) の改訂)、2026-10-10・2026-10-14 の 3 つの改訂と 2026-10-14 の追補の見出しを、ここに全文で足した。本文は、同じ題 (見出しの「—」より後ろ) の小見出しの下に、現行の決定・退けた案・代償を書く。本文から外したのは、改訂の理由と当初の決定の段落 (2026-10-10 の「当初は」と、置き換わった代償・2026-10-14 の 2 つの「上の改訂の代償は」「当初は」) だけである。移した全文には、2026-10-18 に直す前の書き方がそのまま残っている (例: 2026-10-04 の改訂の「ネットワークの隔離にぶつかる」)。

#### 改訂 (2026-10-10) — 切れた (cancelled) 回も赤に数えて起票する

**当初は、起票を落ちた (`failure`) 回に限っていた** (`scheduled-report` の `if:` が `needs.*.result == 'failure'` だけを見た)。cancelled を外す理由は書かれていなかった。2026-10-08 までの定期の run 14 回のうち 7 回は release が 30 分の timeout で cancelled になり、debug が緑だった 6 回は何も起票されずに黙って抜けた ([#2084](https://github.com/mokume-metal/mokume/issues/2084))。起票された残る 1 回 ([#2211](https://github.com/mokume-metal/mokume/issues/2211)・debug が別の理由で落ちた) も、release の節は「記録が無い」とだけ名乗り、「ビルドかジョブの開始で落ちている」と案内した。実際には検査が約 26 分走ってから切れていた。上の理由 (赤は Actions に出るだけでは誰にも読まれない) は動いていないので、赤に数える範囲だけを広げる。

**起票の本文は、job ごとの結論を名乗る** (`scripts/report-scheduled-render.sh`)。記録が無い理由の候補が、落ちた回 (ビルドかジョブの開始で落ちたか、検査のプロセスが記録を残さずに消えた) と切れた回 (走っている途中か、始まる前に止められた) で違うためである。本文は test-log の有無など、材料から分かることだけを名乗り、原因を 1 つに決めつけない。定期の job が cancelled で終わる経路は 3 つある。job の timeout、人の cancel、run をまたぐ重なりである。重なりは、前の回の job が concurrency の group に残っている間に次の回の job が来ると、待っていた job を GitHub が置き換えて cancel する形で起きる (下の「定期の検査 (D) は退かせない」の、run をまたいで重なる場合)。`queue-sweep` は定期の検査を退かせない。

**代償**: release が慢性的に timeout する間は、固定タイトルの Issue が開いたままになり、その間に起きた別の赤 (検査が落ちた回) は重複抑止で起票されず、`scheduled-report` の run のログに残るだけになる。開いている Issue の本文は、立てた回の job ごとの結論を名乗るので、timeout だけで立った Issue かどうかは読めば分かる。この状態が解けるのは、release の所要を [#1983](https://github.com/mokume-metal/mokume/issues/1983) / [#2074](https://github.com/mokume-metal/mokume/issues/2074) が直した後である。**この代償は、下の改訂 (2026-10-14) で、開いた Issue への追記に置き換えた。**

退けた案:

- **timeout だけを起票し、ほかの cancel と見分ける** — 起票の job が job の annotation (`exceeded the maximum execution time`) を読むには `checks: read` が要り、`issues: write` だけだった権限が広がる。見分けて救える実害も無い (上の 14 回の cancelled 7 回は、どれも timeout だった)。timeout でない cancel の起票が実害になったときに改めて決める
- **cancelled は起票せず、起票しないことをここに書く** — 上の「赤を誰が読むか」で却下した形 (赤は Actions に出るだけ) に戻る。切れた job は落ちた job より見えにくいので、却下した案よりさらに見えない

#### 改訂 (2026-10-14) — 固定タイトルの Issue が開いていれば、黙らずにそこへ追記する

**上の改訂 (2026-10-10) の代償は、release の timeout が直るまでの一時的なものとしていた。** 実際には、timeout ではない理由でも同じ形になった。#2251 (定期の赤の自動起票・着手中) が開いている間、専用機の定期の赤 2 回 (10-12) が重複抑止で起票されず、`scheduled-report` の run のログに 1 行残るだけだった ([#2658](https://github.com/mokume-metal/mokume/issues/2658))。着手中の Issue は、直す PR が merge されるまで開いている。その間に起きた別の赤 (release でだけ出る赤を含む) は、上の「赤を誰が読むか」で却下した形 (赤は Actions に出るだけ) に戻っていた。

**`scripts/report-check-failure.sh` は、同じタイトルの Issue が開いていれば、二重には立てず、その Issue へコメントで追記する。** 追記には新規起票と同じ本文 (job ごとの結論・落ちた検査・run の URL) を載せる。後から出た赤は前の赤と別物でありうるからである。追記に失敗したら、起票のジョブは赤になる。共通部品の変更なので、定期の検査以外の呼び手 (ルールセットのドリフト・外に置いた証跡の死活・専用機の前検査) にも効く。

**代償**: 赤が続く間、回ごとに 1 コメント増える。専用機の定期は最大 1 日 4 回で、merge_group で走る前検査の起票 (`render-environment-report`) は、前検査が落ちた group ごとに 1 回である (2026-10-12 に 14 回続けて落ちた事象なら 14 コメント。以前は Issue 1 本で、2 回目以降は黙っていた)。また、追記された赤は前の赤と同じ Issue に載るので、閉じる人は追記された分も同じ直しで解けたかを確かめる (呼び手の本文がそう言う)。

退けた案:

- **開いている Issue を閉じて済ませる** — いまの 1 件は解けるが、次に着手中の Issue が開いたままになれば同じ形が再び起きる
- **専用機の定期の検査だけ追記する** — 他の呼び手も同じ重複抑止を通り、同じ形で黙る。呼び手ごとに選ばせる口を足すほどの違いが無い

#### 改訂 (2026-10-14) — release の赤は merge の前ではなく、版を出す前と定期で止める

**当初は、ホストの release の検査 (`make test-release`・GPU なし・下限 OS の `macos-26`) を merge queue の必須にしていた** (`ci.yml` の `test-release`・`ci-gate` の `needs`)。GPU を要する release は上の定期 (D) が見て、GPU を要さない release は merge の前に止める分担だった。この検査は group ごとに約 12 分のホストの macOS を使い、queue の律速の 63% を占めていた ([#2610](https://github.com/mokume-metal/mokume/issues/2610) の判断 2)。

**ホストの release の検査は `release.yml` の `release-check` に移し、版にする SHA そのものを検査して、緑のときだけタグを打つ** ([#2662](https://github.com/mokume-metal/mokume/issues/2662))。出すものが無い日も走るので、ホストの日次の検査を兼ねる。落ちた・切れた回は、`release-check-report` が `scripts/report-check-failure.sh` で起票する (開いていれば追記する)。権限の分け方は上の D と同じで、検査を走らせるジョブは `issues: write` を持たない。GPU を要する release は、これまでどおり専用機の定期 (`scheduled-release`) が見て、版の関門にはしない。GPU の停止という環境の故障で版が止まり、6 時間おきの SHA も版の SHA と一致しないためである。

あわせて、**GPU の待ちが期限を越えた回は、報告が「環境で成り立たなかった」と先に名乗る** (`scripts/read-test-record.py --failure-messages`)。期限を越えるとプロセスの関所が閉じ、以後の GPU の検査はすべて `gpuNotResponding` で落ちる。2026-10-13 09:20Z の定期の release では 2,108 件がそうなり、要約の先頭 80 件が巻き込みで埋まって、引き金の期限切れも release 固有の赤も載らなかった。関所の分は件数と 1 例に畳み、本物の赤を先に並べ、その周期の保証が欠けていることを言う。

**代償**: release でだけ出る赤は main に入りうる。気付くのは、次の日次の `release-check` (版を出す時) か、専用機の 6 時間おきの定期である。日次の 1 回には前の版からの PR が並ぶので、原因の PR を絞る手間が増える。赤の間は版が出ない (`release:now` の出し直しも関門を通る)。版が出ないと、メンテナが新しい絵を見るリリースノートの「この版の絵」(ADR-0036) も止まる (絵は次の版にまとめて載るので、欠けずに遅れる)。merge queue の中で、合流後の木の検査のターゲットを下限 OS で組むものも無くなる (`ci-check` は merge_group で build と test を外している)。下限 OS でだけ合流後に壊れる形は、日次の `release-check` で気付く。版が出るのは約 15 分遅れる。ホストの macOS の消費は 1 日に約 15 分増え、merge_group ごとの約 12 分が減る。

退けた案 (2026-10-14 にメンテナが比べた):

- **merge queue の必須に残す** — main にも版にも赤が入らないが、queue の律速が残る。いまの形でも GPU を要する release は merge の前に走っておらず、[#1086](https://github.com/mokume-metal/mokume/issues/1086) はこの経路で入った
- **release に効かない変更の group だけ飛ばす** — 2026-09-30 以降の main の 251 コミットのうち、Sources・Tests・Makefile 等に触れるのは 183 で、飛ばせるのは約 27% だけだった。分け方を誤ると穴になる
- **release のビルドを速くする** ([#2596](https://github.com/mokume-metal/mokume/issues/2596)) — 効果は実測まで分からず、キャッシュの誤りは偽の緑になる
- **専用機の merge queue の検査で release も走らせる** — GPU の分も含めて merge の前に止まるが、1 台の専用機の所要が group ごとに約 8 分延びる。下限 OS の分は別に要る
- **`ci.yml` の `test-release` に日次の schedule を足す** (当初の #2662) — 日次の検査の後から版を出すまでに merge された分が、下限 OS の release を通らないまま版に入る

#### 追補 (2026-10-14) — 外のリポジトリから専用機に届くのは、render-pr が組む mokume-syphon の main だけ

**塞ぐ実害**: [mokume-syphon#26](https://github.com/mokume-metal/mokume-syphon/issues/26) では、本体の振る舞いの変化 (出口へ渡す絵が 1 フレーム遅れた) で mokume-syphon の GPU の検査が 4 件落ちた。気付いたのは mokume-syphon の追随の PR で、本体は壊した版をもう出していた。mokume-syphon の GPU の検査は GitHub ホストでは Suite ごと飛ぶので、専用機の外では誰も見ない。

**決定** ([#1971](https://github.com/mokume-metal/mokume/issues/1971)・[#1973](https://github.com/mokume-metal/mokume/issues/1973)): `render-pr` の最後の段 (`scripts/syphon-check-pr.sh`) が、mokume-syphon の `main` を clone し、依存の mokume を PR の木へ差し替えて組み、GPU の検査まで走らせる。警告だけで merge は止めない (`continue-on-error`)。**mokume-syphon には runner を登録しない。**

届く範囲を延ばしてよい理由は、B (同じリポジトリの PR) の水準を外れないことである。

- mokume-syphon の `main` も PR 必須・bypass なしの ruleset で守られ、書ける人は本体と同じである (2026-10-14 の実測で collaborator は admin 1 人)。「専用機に届くコードは write 権限を持つ人のもの」が保たれる
- 専用機のジョブは token も秘密も持たないままである。clone は公開リポジトリを匿名で引き、Syphon.xcframework は mokume-syphon の Release の資産 (同じ org の成果物) を引く
- 走るのは `render-pr` の中だけで、`render` (A) と定期の検査 (D) には入れない。必須の所要を延ばさず、外のリポジトリの赤が merge や起票を動かさないためである (`scripts/tests/render_workflow_test.py` が形を固定する)
- 届く範囲は `render.yml` 1 枚で言えるまま残る。外の clone 元は `scripts/syphon-check.sh` の既定の 1 つだけである

**却下した案**:
- (a) org 単位の runner に直して、mokume-syphon の PR も専用機で受ける — 別のリポジトリのジョブは門番 (`render-turn.sh`) に見えず、必須の `render` が待たされる
- (b) 同じ機械に 2 つ目の runner を立てる — 1 台に 1 ジョブずつの前提が崩れ、描画の検査と GPU を取り合う

**代償**: mokume-syphon の PR 自身 (Dependabot の pin の張り替えを含む) は、PR の時点では GPU の検査を受けない。(a) へ移るのは、その穴のために壊れた版が出たときである。
