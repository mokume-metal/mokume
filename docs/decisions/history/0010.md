## 決定ごとの経緯

### 1. スケッチは main actor 既定とする

決定 1 の 2 つの改訂は、どちらも現行の決定に足したもので、置き換わった決定は無い。中身は本文の小見出し「新しい値型は main actor の外に置く」と「値だけを扱う数と色の関数も main actor の外に置く」に残した。

#### 改訂 (2026-10-23) — 値だけを扱う数と色の関数も main actor の外に置く ([#2389](https://github.com/mokume-metal/mokume/issues/2389))

下の改訂は、既存の関数 (`map`・`lerp`・`color` など) を main actor の外へ出すかを範囲の外に置いていた。この改訂でそれを決めた。

#### 改訂 (2026-10-14) — 新しい値型は main actor の外に置く

採択時の決定 1 は「ライブラリの公開 API も、既定では main actor 隔離として提供する」だけで、値型を外に置く道を持たなかった。外部サービスの結果を `ExternalQueue` で送ることと、リプレイで `Codable` な値を記録すること ([ADR-0045](../0045-game-direction.md) 決定 10・12) が決まり、この改訂を足した。

### 4. 並列は actor と structured concurrency で明示分離する

本文の決定 4 の見出しは、2026-10-21 の改訂で「並列は actor と Task で明示分離する」に直した。**当初の見出しと文言は、`Task` / `TaskGroup` を structured concurrency (構造化された並行処理) の例に挙げていた。** `Task { … }` と `Task.detached { … }` は非構造化タスクなので、言葉を直した (決定の中身は変えていない。理由は本文の決定 4)。

本文には、2026-10-03 の改訂 (例外は条件で認める) の現行の扱いが、日付なしの小見出しで残っている (本文の改訂の見出しが 5 つを超えるため、日付入りの見出しは 2026-10-23 にここへ移した・[#2389](https://github.com/mokume-metal/mokume/issues/2389))。下の追補 (2026-09-09) は、その改訂が「現行の扱い」を引き継いだ前の、ファイルの見張りだけを例外とした時点の理由である。

#### 改訂 (2026-10-21) — 見出しと文言を、`Task {}` が非構造化だと分かる言葉に直す

**当初の見出しと文言は、`Task` / `TaskGroup` を structured concurrency の例に挙げていた。** 決定の中身 (分離する・境界を越える値は `Sendable`・`DispatchQueue` を新たに導入しない) は変えず、`Task {}` が非構造化だと分かる言葉に直しただけである。本文では見出しに「(2026-10-21 改訂)」と併記していたが、2026-11-08 に本文を軽くしたとき、この節へ移した。

#### 改訂 (2026-10-03) — 例外は 1 本ではなくなった。条件で認める

現行の扱い (ADR-0042 決定 7 の条件で認める) は、本文の決定 4 の小見出し「例外は 1 本ではなくなった。条件で認める」にある。ここには、その改訂の理由だけを残す。

**追補 (2026-09-09。[history/0010.md](0010.md)) は、ファイルの見張りを「この決定に対する唯一の例外」と数えていた。** カメラと音を標準の機能に入れると ([ADR-0041](../0041-standard-scope-map.md))、その数え方が成り立たなくなった。カメラの受け取り (`AVCaptureVideoDataOutput`) は待ち行列を引数に取り、音の入力と出力は OS の realtime スレッドで呼ばれる。どちらも、ファイルの見張りと同じく**並列の設計ではなく OS の受け口の形**で、「渡さない」「呼ばれない」は選べない。

**理由は動いていない。** 禁じているのは自前の並列を待ち行列で組むことで、その追補が挙げた守り (受ける点でしかない・値を渡さない・callback を漏らさない) は ADR-0042 決定 7 の条件にそのまま入っている。変わったのは、例外を 1 本ずつ数える形から、条件で認める形にしたことだけである。

#### 追補 (2026-09-09) — 見張りの待ち行列だけは例外である

`Sources/MokumeCore/Drawing/FileWatcher.swift` が `DispatchQueue` を 1 本持っている ([#733](https://github.com/mokume-metal/mokume/issues/733))。**この決定に対する唯一の例外**だった (2026-10-03 の改訂で、条件で認める形へ移った)。ほかの並列は宣言どおり分けてある — `FrameWriter` と `MovieWriter` は待ち方を semaphore に寄せ、コードのコメントで本決定を引いて「`DispatchQueue` は足さない」と名乗っている。

**例外が要るのは、ここが並列の設計ではなく OS の受け口だからである。** ファイルの保存を拾う口は `DispatchSource.makeFileSystemObjectSource(fileDescriptor:eventMask:queue:)` で、**待ち行列を引数に取ることが API の形そのもの**である。actor で包んでも `AsyncSequence` に包んでも、その内側でこの引数を埋めることは避けられない — 選べるのは「どの待ち行列を渡すか」だけで、「渡さない」は選べない。**この決定が禁じた「新たに導入する」— 自前の並列を待ち行列で組む — には当たらない。**

**主キューを渡す形は成立しない。** 主キューが捌かれるのは窓のある実行だけで、検査の実行では捌かれず、**実装が正しくても保存が届かない**ことを実測している (同ファイルの「主キューへ直に載せない」節)。逃げ道が塞がっているという意味でも、ここは選択ではない。

**そして決定 4 が守ろうとしたものは、例外の下でも守られている。** 待ち行列は出来事を受ける点でしかなく、拾った先は `Task { @MainActor in … }` で main actor へ渡る。境界を越えるのは「変化があった」という合図だけで (`@Sendable () -> Void`)、値は渡らないので `Sendable` の要求も自明に満たされる。決定 5 に触れないのも、この口が internal で、callback が利用者へ漏れないためである。

**何が示されたら畳むか**: ファイルの変化を待ち行列なしに待てる口 (`AsyncSequence` を直に返すもの) が使えるようになったとき。そのときはこの例外を消し、決定 4 を例外なしに戻す。

### 5. 継続的な値の流れは AsyncSequence を一級 API とする

本文の見出しの `AsyncSequence` は採択時の選択で、いまは退けている。現行の形 (フレームで読む値) と退けた理由は、本文の小見出し「フレームで標本化する値は、フレームで読む値として持つ」と「取りこぼしたくない出来事の列も、フレームで読む値として持つ」に残した。

#### 改訂 (2026-10-08) — 取りこぼしたくない出来事の列も、フレームで読む値として持つ

**下の改訂 (2026-10-06) は、表の 2 行目 (1 つでも取りこぼすと意味が変わる出来事の列) を `AsyncSequence` で出すとしていた。** 例は「OSC・MIDI のメッセージ、ネットワーク経由の制御、入力イベント」で、当初の決定の冒頭も同じものを挙げ、`for await message in osc.messages { … }` を例にしていた。OSC の実装 ([#1962](https://github.com/mokume-metal/mokume/issues/1962)) で、これを落とさない列 ([ADR-0028](../0028-external-inputs.md) 決定 2) に溜めてフレームごとに全部渡す形に変えた。

#### 改訂 (2026-10-06) — フレームで標本化する値は、フレームで読む値として持つ

届き続ける値を、本文の表の 2 つの性質に分けた。この改訂で決めたのは 1 行目 (フレームで標本化する値) で、2 行目 (出来事の列) は `AsyncSequence` のまま残していた (上の改訂 (2026-10-08) で変えた)。

当初の決定は「オーディオ解析の結果」を `AsyncSequence` の例に挙げていた。音の入力の実装 ([#1978](https://github.com/mokume-metal/mokume/issues/1978)) で、この例を外した。カメラ ([#1977](https://github.com/mokume-metal/mokume/issues/1977)) は、この使い分けを書く前に、既にフレームで読む値として入っていた。
