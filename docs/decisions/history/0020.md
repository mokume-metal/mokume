## 決定ごとの経緯

### 1. 名前は、手本があればそれに従い、無ければ Swift の慣行に従う (2026-09-03 改訂)

本文に残したのは、2 つの改訂のうち現行の決定として読まれる段落 (手本に倣う射程・方式の違う兄弟の型の名前と、その退けた案) である。改訂した理由と、3 件の観測の経緯をここに移した。

#### 改訂 (2026-09-09): 手本に倣う射程は、名前と引数の順序まで

**手本に倣うのは名前と引数の順序までで、同じ引数から同じ画素が出ることは約束しない。** 決定 1 はもともとそれしか採ると言っていないし、上の段 (手本を引く意味は綴りが広く使われているかを見ること) と影響節の最後の行 (手本の版には追随しない) も同じ向きを向いている。決定論のはしご ([ADR-0025](../0025-determinism-levels.md) 決定 1) も水準 3「同じ機械の画素」で止まっていて、外の実装と画素が揃う段は無い。それでも、手本と同じコードを書いたら同じ絵が出ると期待するのは自然である。「画素」という言葉で射程を名乗った行が無かったので、手本と絵が違うという観測が来るたびに同じ導出をやり直していた。実際に 3 件来ている — 半透明の合成が 214 ではなく 232 になる ([#669 のコメント](https://github.com/mokume-metal/mokume/issues/669#issuecomment-5549141573))、同じ光の指定で陰影が明るく出る ([#913](https://github.com/mokume-metal/mokume/issues/913))、太さ 1 の線が p5 と違う画素に載る ([#912](https://github.com/mokume-metal/mokume/issues/912))。

- **画素が手本と違うという観測は、[ADR-0022](../0022-production-track.md) 決定 6 の物差しで判定する。** 既にある規範・ADR が求める一貫性の欠けを示せるなら `Bug` として直す。示せるのが「手本と違う」だけなら追わない (同じ表の 3 行目「一般にそういう API があるから」に当たる)。3 件はどれも後者だった。合成と、光に渡す数の掛け方は、色の計算を線形の値で行う規範 ([ADR-0011](../0011-color-model.md) 決定 1) から来ている。線の載り方は、画素の格子の規範 ([ADR-0039](../0039-pixel-grid-and-edge-antialiasing.md) 決定 2) から来ている。`lights()` の既定の光組が違うことは、引数を 1 つも取らない口の中身の話なので、そもそも名前と引数の面に無い
- **追わないと決めたものは、その口の説明文で「手本とは違う」と名乗る。** 正本はこの段で、説明文は名乗るだけにする。置き場は決定 4 のとおり、利用者が最初に触る層の説明文である。[ADR-0033](../0033-color-specification-surface.md) 決定 7 の `lerpColor` の行 (「手本と中間色の数値が違うことは説明文で名乗る」) と同じ扱いになる
- **綴りだけ手本に合わせて値の体系が違う形は、この段の外にある。** [ADR-0034](../0034-input-surface-units.md) は、`keyCode` が手本と同じ名前で別の体系の数を運んでいたことを「名前が合っているぶんより悪い」として直した。引数や戻り値が何の体系の数かは名前と引数の面に属するので、射程の内側にある。画素が違うことは、値の体系が違うことと同じではない

> 破れたとき: 手本と絵が違うという観測が来るたびに、Bug かどうかの導出を最初からやり直すことになる。逆に、画素まで追うと決めた口が 1 つでもあると、残りの口がなぜ追わないのかを説明できなくなる。

#### 改訂 (2026-10-09): 方式の違う兄弟が並ぶときは、型の名前に方式を名乗らせる

**手本に同名の API があっても、同じ領域に方式の違う兄弟が並び、手本の名前だけでは方式が読めなくなるときは、型の名前に方式を名乗らせ、手本の名前はその型の説明文で名乗る。** メンバの名前と引数の順序は、これまでどおり手本に倣う。決定 1 が手本を引く理由は、利用者が覚えている綴りで探せることだった。兄弟の 1 つだけが手本の総称を取ると、総称がどの方式を指すのかを覚えることになる。その総称は、他の兄弟から見れば「方式を名乗らない名前」になってしまう。

最初の適用は TCP・WebSocket・UDP の文字列の受け送り ([#2018](https://github.com/mokume-metal/mokume/issues/2018)・[#2250](https://github.com/mokume-metal/mokume/issues/2250)) である。

- TCP には Processing 本体の `Server` (`processing.net`) がある。WebSocket と UDP は本体に無い
- 手本どおり `Server` を採ると、`OSCPort`・`UDPPort` と並んだときに方式が読めない
- そこで型は `TCPServer`・`WebSocketServer`・`UDPPort` とし、`TCPServer` の説明文に「Processing の `Server` に当たる」と書いた
- `write`・`clientCount`・`stop` は手本どおり
- 送る動詞は区切りを誰が持つかで分けた。TCP は流れに書くので手本の `write` を採り、1 通を送る WebSocket と UDP は `send` (ブラウザの `WebSocket.send` と同じ)

退けた案:

- **手本の名前をそのまま型にする (`Server`)。** 方式を作る口の名前 (`createServer`・`createWebSocketServer`) だけで言うことになり、並べたときに見分けにくい
- **WebSocket にも同じ型を返す。** 区切りと送る動詞が違うものが 1 つの型に入る。TCP の `write("hit\n")` は流れに書き、WebSocket の `write("hit")` は 1 通を送る、と同じ名前が 2 つの意味を持つ
- **手本の名前を別名で置く (`typealias Server = TCPServer`)。** 正本が 2 つになる (決定 4 の向きに反する)。別名は後から足せるが、外すと利用者のコードを壊す。手本の名前で探して困った実例が出たら、そのときに足す

> 破れたとき: 手本の総称を取った兄弟だけが方式を名乗らない形になり、並んだ口のどれが何の方式かを、名前ではなく説明文で覚えることになる。

### 7. アンブレラは、外のモジュールを丸ごと再輸出しない

本文に残したのは、mokume 自身が書く純粋な計算の置き場と、`map`・`lerp`・`constrain` の口の形である。保留していた理由と、足す日の条件 (2026-09-22 に満たされて役目を終えた) をここに移した。

#### 改訂 (2026-09-05): 保留していた語彙は、名指しではなく自前で書く

**当初の決定**は「角度の単位変換・補間・写像は通していない — 『毎回書いている』ものが作品トラック ([ADR-0022](../0022-production-track.md)) から見えてから決める」だった。その条件が満たされたので、ここで決める ([#883](https://github.com/mokume-metal/mokume/issues/883))。

実需は 2 つの強さで来た。制作トラックの `Solids` と `Ring` が**同じ度→ラジアンの 1 行を 2 度書き**、`Ring` は `map` 相当も手で展開している。さらに Processing Examples 254 本の全数計測では、測る対象 203 例のうち `map` が 33 例 (1 位)・`radians` が 23 例 (3 位) を止めていた。

**決めるのは、本決定が禁じている範囲の外である。** `radians` / `degrees` / `map` に対応する関数は Darwin に無いので、名指しで通せる先が最初から無い。だから禁止 (モジュールを丸ごと再輸出しない) には触れず、**mokume 自身が書く**。書いたものは描画コアに置き、アンブレラが `MokumeCore` を丸ごと再エクスポートする経路でそのまま通る。

口の形は決定 1 と [ADR-0033](../0033-color-specification-surface.md) の先例に従う:

- **`Sketch` のメソッドにしない。** 実害が起きたのはスケッチの外 (`Ring` の `private static func`) で、メソッドではそこから呼べない。状態を持たない純粋な計算なので、乱数列という状態を持つ `random()` が `Sketch` にあるのとは事情が違う。**色の値を作る口 (`color()` / `red()`) が既にグローバル関数**で、置き場もその隣に倣う
- 名前と引数の順序は手本のまま (決定 1)。p5 の 6 引数目 `withinBounds` は採らない — 締めは `constrain` の仕事である
- **`angleMode()` は持たない。** [ADR-0033](../0033-color-specification-surface.md) 決定 4 (`colorMode()` を持たない) と同じ理由で、単位は呼んだ 1 行から読めるべきである。`rotate(_ radians: Float)` は既に引数名で単位を名乗っている
- `map` は、元の幅が 0 のとき・数でない値や無限が混じったときに**写した先の下端を返す**。手本は ±∞ / NaN を返すが、毎フレーム呼ばれる口が数でない値を返すと**絵が黙って消える** (決定 5)。範囲の外は丸めない (手本どおり外挿する)

##### `lerp` / `constrain` を足す日

同じ計測に `constrain` は 9 例・`lerp` は 3 例で出てくるが、**作品トラックではまだ踏んでいない** ([ADR-0001](../0001-founding-principles.md) 原則 4)。いまは作らない。足す日にやることだけ決めておく:

| 論点 | 足す日の答え |
| --- | --- |
| 置き場 | `map` と同じ場所。新しい判断は要らない |
| 名前と引数 | 手本のまま `lerp(start, stop, amount)` / `constrain(value, low, high)` (決定 1) |
| `lerp` が 0…1 の外を受けたら | 締めない。外へ伸びる (手本と同じで、`map` の外挿と揃う) |
| `constrain` の上下が逆なら | 入れ替えて締める。`map` が逆向きの範囲を受けるのと揃う |
| 異常な入力 | `map` と同じ控えへ事情を 1 つ足す (口ごとに数える) |
| 色の補間 | ここには入れない。作業空間で混ぜる規範 ([ADR-0011](../0011-color-model.md)) が先に効く、色の面の話である |

**何が示されたら足すか** — 作品トラックの作品が、これらを手で書いたことを 2 作品で踏んだとき。そのときは [#883](https://github.com/mokume-metal/mokume/issues/883) を開き直さず、新しい `Feature` を立てる。

#### 改訂 (2026-09-22): 足す日が来たので、補間と締めを足した

**当初の決定**は「`constrain` は 9 例・`lerp` は 3 例で手本に出てくるが、作品トラックではまだ踏んでいないので、いまは作らない」だった ([ADR-0001](../0001-founding-principles.md) 原則 4)。上の段が定めた条件が満たされたので、ここで足す ([#1281](https://github.com/mokume-metal/mokume/issues/1281))。

**条件どおり 2 作品が手で書いた。** `Tempo` ([works#65](https://github.com/mokume-metal/works/pull/65)) は `Ease.swift` に `mix` と `clamp` を、`Cast` ([works#67](https://github.com/mokume-metal/works/pull/67)) は `Stage.swift` に `mix`・`Score.swift` ほか 4 ファイルに `min(max(x, 0), 1)` を書いている。

**踏まれ方が、保留のあいだに 1 つ増えていた。** 2 作品の `mix` は**引数の順番が違う** — `Tempo` が `(t, a, b)`、`Cast` が `(a, b, t)` である。毎回その場で書くと順番が揃わないので、実害は「同じ 1 行を 2 度書いた」だけではなく「**同じ名前が 2 通りの意味を持った**」でもある。上の表が名前と引数の順序を手本のまま (`lerp(start, stop, amount)`) と決めてあったことが、そのまま答えになっている。

表の各行がどう実装に落ちたかは次のとおりで、**表を離れた判断はしていない**:

| 表の行 | 実装 (`Sources/MokumeCore/Math/NumberSurface.swift`) |
| --- | --- |
| 置き場は `map` と同じ | 同じファイルのグローバル関数。`Sketch` のメソッドにしない — 実害はどちらの作品でも `enum` の `static func` の中で起きた |
| 名前と引数は手本のまま | `lerp(_ start:, _ stop:, _ amount:)` / `constrain(_ value:, _ low:, _ high:)` |
| `lerp` は 0…1 の外で締めない | 外挿する (`lerp(0, 10, 2)` は 20)。締めたい呼び手は `constrain` を通す |
| `constrain` の上下が逆なら入れ替える | 両端を `min` / `max` で正規化してから締める |
| 異常な入力は `map` と同じ控えへ事情を 1 つ足す (口ごとに数える) | `NumberValues.Warning.notANumber` に**口を連想値として持たせた**。綴りを並べる (`lerpNotANumber` …) 形にすると、足す人が既存の綴りを使い回せてしまい、先に鳴った口が残りを永久に黙らせる — 連想値なら鍵の共有が起こりようがない |
| 色の補間はここに入れない | 入れていない ([ADR-0011](../0011-color-model.md) が先に効く色の面の話である) |

**この改訂で「足す日」の段は役目を終えた。** 上に残してあるのは、何を待っていたかと、待つと決めた理由の記録である。
