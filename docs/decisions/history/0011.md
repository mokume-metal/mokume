# ADR-0011 の経緯

[ADR-0011](../0011-color-model.md) の本文から移した、改訂の経緯。本文は現行の決定を書き、ここには当初の決定と各改訂の理由・改訂の見出しの本文を残す。決定の番号 (1〜6) は本文と同じで、決定 1・2・6 には移した節が無い (決定 6 の「sRGB は転送関数のこと」という改訂の断りは見出しではなく本文の段落なので、動かしていない)。

- この文書は ADR ではなく、番号付きの ADR として数えられない
- 採択時 (2026-08-27) の全文は `git show 89549099:docs/decisions/0011-color-model.md` で引ける
- 各節は本文にあった順のまま、元の綴りの見出しで移した。決定の見出しに併記していた改訂の日付 (`(2026-09-30 改訂)`) は、本文の見出しから外して、ここの節の題に元の綴りのまま残した ([#3016](https://github.com/mokume-metal/mokume/issues/3016))
- 移したのは、当初の決定・改訂の理由・改訂の見出しである。**現行の決定になっている段落 (入口の表・退けた案・代償・足す日の表) は本文に残した**ので、本文の同じ題の小見出しを合わせて読む。コードや文書にある「ADR-0011 決定 3 の改訂 (2026-09-15)」のような呼び名は、ここの同じ見出しに解決する
- 改訂の一覧は見出しから引ける: `grep -nE '^#{2,4} .*(改訂|追補).*20[0-9]{2}-' docs/decisions/history/0011.md`
- 本文に立てた日付入りの見出しは、この経緯を軽くした後の改訂だけである (2026-10-23 以後)

## 決定ごとの経緯

### 3. 転送関数の適用は出力段の 1 箇所に集約する

#### 改訂 (2026-09-28) — 画像入力は CPU で読むか GPU で使う時点までに変換する

本文の同じ題の小見出しに現行の決定を残した。ここには、当初の決定との関係を述べた 1 文を移した。

当初の決定は入力の変換時点を「作業空間へ入る時点」とだけ定め、実装は `write` のたびに CPU で全画素を変換していた。

#### 改訂 (2026-09-15) — 入口は原色も作業空間へ移す。利用者が書いた数は sRGB の原色の値である

本文の同じ題の小見出し (「入口は原色も作業空間へ移す。…」) に、現行の入口の表・退けた案・代償・足す日の表を残した。ここには、当初の決定と、改訂の動機になった食い違い、改訂の理由を移した。

**当初の決定**は、入口の変換を「線形へ変換する」の 1 語で書き、読み込んだ画像と利用者が指定した色を同じ 1 文に束ねていた。この 1 語は、転送関数だけを外すとも、作業空間へ移す (原色も変換する) とも読める。実装は 2 つの入口で別々の読み方をしていた ([#1081](https://github.com/mokume-metal/mokume/issues/1081))。

| 入口 | 当初の実装 | 同じ `204, 153, 0` の行き先 (書き出した 8 bit) |
| --- | --- | --- |
| 利用者が書いた数 (`fill(204, 153, 0)`) | 転送関数だけを外す (数は暗に P3 の原色の値) | `204, 153, 0` |
| 読み込んだ sRGB の画像 | CoreGraphics が原色ごと作業空間へ移す | `196, 155, 51` |

**同じ 3 つの数が、同じ作業空間で 2 つの違う色になる。** これは手本 (Processing / p5) を持ち出さなくても起きる食い違いである。手本から移した例では、157 本のうち 32 本が「形も位置も合うが色が違う」になった ([#911](https://github.com/mokume-metal/mokume/issues/911))。

理由は当初の決定から動いていない。境界は入口と出口の 2 箇所しかなく、入口はどこから入っても同じ規範に従う。変えたのは「線形へ変換する」の中身を名乗ったことだけなので、番号を増やさずこの ADR を改訂する。

### 4. アルファは、数の口を straight、`LinearRGBA` の口と内部合成を premultiplied とする (2026-09-30 改訂)

本文の決定 4 の見出しからは、併記していた「(2026-09-30 改訂)」を外した。決定の中身 (2 段の表・変換点) は本文に残している。ここには、当初の決定と、改訂の理由を移した。

#### 当初の決定と、改訂の理由

**当初の決定は「利用者が指定する色・取得する色は straight」だった。** 変換点を「色が作業空間へ入る時点で premultiplied にし、利用者へ返す時点で straight に戻す」の境界 1 箇所に固定し、途中で掛け戻さないためである。

実装はこの文面と違っていた ([#736](https://github.com/mokume-metal/mokume/issues/736))。作業空間の型 `LinearRGBA` を公開しており、その成分は型として乗算済みである。`Pixels` / `PixelBuffer` / `Image.get` はそれを乗算済みのまま返し、`fill(_:)` もそのまま受けていた。数で読む口 ([ADR-0033](../0033-color-specification-surface.md) 決定 6) は、乗算を戻してから数へ移していた。**つまり実装は、境界を「数と `LinearRGBA` の境目」に置いていた。** 当初の文面の「利用者へ返す時点」は、この境目を名指ししていなかった。

理由 (境界を 1 箇所に固定し、途中で掛け戻さない) は動いていない。変えたのは、境界がどこにあるかを口の段で名乗ったことだけなので、番号を増やさずこの ADR を改訂する。実装の値は変えない。

### 5. EDR / HDR 出力は情報を捨てない設計を既定とし、有効化は opt-in

#### 改訂 (2026-09-30) — opt-in の口は、作品が踏むまで足さない。足す日の答えを表にする

本文の同じ題の小見出しに、足す日の答えの表と、口を足さないという現行の決定を残した。ここには、当初の決定と、改訂の理由を移した。

**当初の決定**は「有効化は opt-in」と決めただけで、opt-in の口の形は決めていなかった。実装も口を持たず、画面へ差し出す層は `wantsExtendedDynamicRangeContent = false` を明示したままである。情報は出口まで来ているのに、出す口が無い ([#906](https://github.com/mokume-metal/mokume/issues/906))。

> 本文の次の段落は、改訂時には、末尾にこう続いていた: 「理由 (既定は標準レンジ・有効化は opt-in) は動かないので、番号を増やさずこの ADR を改訂する。」
