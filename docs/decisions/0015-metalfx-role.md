# ADR-0015: MetalFX の位置づけ — 空間方向だけを解像度戦略に組み込み、時間方向は決定論の代償を明示して opt-in にする

## 状態

採用 (2026-08-27)

## 文脈

[ADR-0009](0009-platform-floor-and-toolchain.md) が Metal 4 世代を前提に置いたことで、MetalFX の 3 つの機能が選択肢に入る。

- **アップスケール** — 低い解像度で描いた絵を高品位に拡大する
- **フレーム補間** — 描かれたフレームの間に、新しいフレームを生成する
- **デノイズ** — ノイズを含む描画結果を平滑化する (レイトレーシングの前提部品)

このうちアップスケールは実用上の価値が大きい。**重いスケッチを低解像度で描いて拡大すれば、フレーム時間に収まらなかった表現が動くようになる。** 後処理の 1 つとして opt-in で置くより、解像度の決め方そのものに組み込むほうが届く範囲は広い。

### しかし 3 つを一括りにはできない

[ADR-0001](0001-founding-principles.md) 原則 2 は、決定論を設計目標に置いている。

> 同じコード・同じシード・**同じフレーム番号**からは、バイト単位で同じ画像が得られることを設計目標にする。(中略) これを壊す機能は導入時に**代償を明示する**。

ここで 3 つの機能は決定論に対して**まったく違う性質**を持つ。

- **空間方向だけで完結するアップスケール**は、そのフレームの画素だけから出力を作る。フレーム番号 N の絵は N の入力だけで決まり、決定論を壊さない
- **時間方向の情報を使うアップスケール**は、前のフレームの結果と動きの情報を蓄積して品質を上げる。**フレーム N の絵は、そこへ至る経路に依存する。** 単独でフレーム 100 を描いた結果と、0 から 100 まで進めて得たフレーム 100 は一致しない。決定論の検証 ([ADR-0011](0011-color-model.md) 決定 6) と、単一フレームのヘッドレス描画 ([ADR-0012](0012-view-layer.md) 決定 1) の両方に直接効く
- **フレーム補間**は、スケッチが計算していないフレームを作る。「同じ入力から同じ絵」以前に、**そのフレームには対応する入力が無い**

一括りに「MetalFX を採るか」と問うと、この違いが消える。**機能ごとに別々に位置づける。**

### 置き場はパイプラインであってビューではない

[ADR-0012](0012-view-layer.md) 決定 1 により、描画の成果物はテクスチャであり、画面はそれを受け取る出口の 1 つにすぎない。アップスケールはテクスチャからテクスチャへの変換なので、**パイプラインの段として置く**のが正しい。ビュー層に置くと、画面に出すときだけ効いて書き出しには効かない、という不整合が生まれる。

## 決定

### 1. 空間方向のアップスケールを解像度戦略に組み込む

描画解像度と出力解像度を別々に持てるようにし、その間を空間方向のアップスケールで埋める。後処理エフェクトの 1 つとしてではなく、**解像度の決め方の一部**として提供する。

決定論は保たれるため、既定で使えてよい。

### 2. 時間方向の情報を使うアップスケールは opt-in とし、代償を明示する

有効にできるが既定では無効とする。有効にした場合、**単一フレームの再現性が失われる** — フレーム N の絵はそこへ至る経路に依存し、単独描画と連続描画で結果が一致しない。

これは [ADR-0001](0001-founding-principles.md) 原則 2 が要求する「代償の明示」に当たる。API のドキュメントと、決定論に依存する経路 (検証・ヘッドレスの単一フレーム描画) での挙動を、有効化の時点で示す。

### 3. フレーム補間は採らない

スケッチが計算していないフレームを生成する機構は、このライブラリの契約の外側にある。フレームはスケッチが描くものであり、**描かれなかったフレームは存在しない**。

書き出し経路 (映像として出力するとき) での利用は別の問題だが、**それも実需が現れてから判断する** ([ADR-0001](0001-founding-principles.md) 原則 4)。

### 4. デノイズは設計が閉じないことだけ確認し、実装しない

デノイズはレイトレーシングと組で意味を持つ。どちらも 1.0 に必須ではない。**将来採れる余地を残す** — パイプラインの段として後から差し込める構造にしておく — ことだけを確認し、今は実装しない。

### 5. 置き場はパイプラインの段とする

アップスケールはテクスチャからテクスチャへの変換としてパイプラインに置く。画面表示・書き出し・観測のいずれの出口からも同じ結果が得られる ([ADR-0012](0012-view-layer.md) 決定 1)。

## 影響

- 決定 1 により、「描画解像度」と「出力解像度」が別の概念として API に現れる。重いスケッチの救済がエフェクトの追加ではなく設定で済む
- 決定 1・5 により、アップスケールは [ADR-0011](0011-color-model.md) の作業空間 (linear 16F) の上で動く段になる。出力段のエンコードより前に位置する
- 決定 2 により、決定論に依存する機構 (画像比較・単一フレームのヘッドレス描画) は「時間方向の機能が有効か」を知る必要がある。この状態はランタイムから見えるようにする
- 決定 3 により、フレームレートを機構で水増しする道を持たない。フレームレートはスケッチの計算量とアップスケールの設定で決まる
- 決定 4 により、パイプラインの段は**後から差し込める形**である必要がある。この制約は GPU 応用の設計に引き継ぐ
- mesh shaders・レイトレーシングも同じ扱いとする — 設計が閉じないことだけ確認し、採用は実需から ([ADR-0001](0001-founding-principles.md) 原則 4)
