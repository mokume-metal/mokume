# ADR-0021: 立体を絵に載せる規範 — 空間・重ね順・フレームの組み立て・設定の寿命

## 状態

## 文脈

いま描けるのは平面だけである。立体を足すと、平面には無かった決めごとが 4 つ現れる — **空間の取り方・奥行きを持つ描画と持たない描画の重ね方・影を含むフレームの組み立て・設定の寿命**。どれも 1 本の API の話ではなく、**後から変えると既に描かれた絵が全部動く**種類の決定なので、道具を足す前に置く。

### いまの描画は 1 本の経路になっている

図形は溜められ、`draw { }` を抜けるときにまとめて描かれる。溜まった頂点は**呼び出し順**に並び、混ぜ方・読む面・切り抜き・利用者が書いた断片が変わるところで列が閉じる。閉じた列は閉じた時点の設定を持ち歩くので、**記録した列だけで絵が決まる** — 描く時点で「いまの状態」を読み直さない。

この形は立体にとって都合がよい。**影を作るには、描く前にそのフレームで何をどこに置くかが分かっている必要がある**が、溜めてから描く形は既にその条件を満たしている。影を「後から足す機能」として扱うと、影のあるフレームだけ別の組み立て方 (一度記録してから描き直す) になり、経路が 2 本に割れる。割れると、**片方でしか呼び出し順どおりの重なりが出ない・片方では同じフレームの画素を読み戻せない**という非対称が生まれ、利用者から見れば「影を入れたら別の絵になった」になる。doc で説明しても解消しない種類の非対称である。

### 奥行きの面はまだ無い

描画先は色の面だけを持つ。平面の図形は重なりを列の順で解決しており、奥行きの比較は要らなかった。立体はそうはいかない。

### 立体は「シーンの記述」を持ち込む

平面の設定は大半が**描き方** (色・太さ・端点・モード) である。立体はそこへ**シーンの記述** (視点・投影・光・材質) を持ち込む。どちらがフレームを越えるかを API ごとの都合で決めると、規則は必ず割れる — 重い下ごしらえを伴うもの (影・周囲の光) だけ越える、という例外が生まれ、利用者は表を暗記することになる。しかも破れ方が静かで、初期化のときに書いた設定は**警告も出さずに捨てられ**、既定値で描かれるだけである。

### 形を作る道具は 1 つに保てる

保持した形 ([`Shape`](../../Sources/MokumeCore/Drawing/Shape.swift)) は、穴・輪郭・頂点ごとの色を**形の種類ではなく頂点の性質**として持つ設計になっている。立体へ広げるときに増えるのは頂点の中身であって、形の種類ごとの対応表ではない。この性質を保てば、「平面では効くが立体では黙って無視される」機能が生まれる場所が無い。

## 決定

### 1. 空間は平面の約束をそのまま延長する

- **1 単位は 1 画素、原点は左上、縦軸は下向き。** 奥行きの軸は**見ている側が正**とする (手本のある向きに従う — 正の値を渡すと手前へ出る)
- **既定の視点は、面がちょうど収まる位置**に置く。何も指定せずに立体を置いたら、画素の大きさで見える
- 要件として: **奥行き 0 に置いた立体は、同じ座標に描いた平面の図形と一致する**

縦軸の向きを平面と揃えるのは [ADR-0020](0020-api-naming-and-surface.md) 決定 3 (状態は 2D と 3D に等しく効く) の帰結でもある。同じ `translate(x, y)` が平面と立体で逆向きに動くなら、「等しく効く」は成り立たない。立体の慣行 (縦軸が上向き) とは逆になるが、**1 つの絵の中で 2 つの約束が同居するほうが害が大きい**。

投影の範囲を決める引数のように、行列の規約と画面の上下が食い違いうる箇所は、**画面の側を正とする** (画面の上端を指す引数が `top` である)。

> 破れたとき: 平面と立体を重ねた絵だけが、ずれる・上下反転する。片方しか使わないスケッチでは一生現れない。

#### 改訂 (2026-09-14) — 「一致」は幾何の一致である

**当初の決定**は「一致する」とだけ書き、何が一致するのかを書いていなかった。検査 (`planeAtZeroDepthMatchesRect`) がバイト一致で比べていたため、縁の AA の掛け方まで揃うことを要求していると読まれた ([#905](https://github.com/mokume-metal/mokume/issues/905))。

この決定が守るのは空間の約束であり、上の「破れたとき」が挙げる害も「平面と立体を重ねた絵が**ずれる・上下反転する**」である。だから、**一致とは位置・大きさ・向きの一致を指し、縁の AA の掛け方は射程の外にある。** 理由は動かないので、決定の本文は書き換えない。

回した形では、この意味での一致も破れていた。平面の `rect` の塗りだけが半画素ずれていたためである。どの座標をどの画素に落とすか (画素の格子) と、一致を検査でどう見るかは、[ADR-0039](0039-pixel-grid-and-edge-antialiasing.md) 決定 1・2 が決める。

### 2. 重ね順は呼び出し順で決まり、奥行きの面は 1 枚を共有する

- 描画先は**奥行きの面を 1 枚持つ** (立体を使わないスケッチでも持つ。経路を分けないため)
- **立体は奥行きを読み書きし、平面は常に通して書かない。** 平面は奥行きを持たない挿入レイヤーであり、2 つの立体の間に挟んだ平面は、後の立体の奥行き比較に参加しない
- 列は既に呼び出し順に並んでいるので、**順に投入するだけで呼び出し順の重なりが出る**。追加の描画パスは作らない
- **半透明の立体は並べ替えない。** 奥から順に描く責任は作品側にある

平面を先に置けば立体がその上に重なり、後に置けば最前面に出る。「背景 → 立体 → 前景」も「平面の絵の中に立体を差し込む」も、書いた順そのままで成立する。

> 破れたとき: 平面と立体を混ぜた絵の前後が入れ替わる。決定的に起きるが、混ぜないスケッチでは現れない。

#### 改訂 (2026-09-28) — 呼び出し順を保ち、頂点の所有を分ける

**列は呼び出し順を持ち、形の頂点は列をまたいで共有してよい。** 同じ形を指す列が離れていても、同じ頂点の範囲を指せる。塗りと線を別々にまとめ直すことはしない。描画回数の少なさより、半透明・同じ奥行き・平面を挟んだときの重なりを保つことを優先する。

組み込み立体の不透明な既定の線は、形の稜線を共有し、帯・角・視線への寄せを頂点段で作ってよい。**世界へ置いた後の視点から画面での太さを決める**ので、非一様な拡大でも線幅は伸ばさない。線の半画素の寄せは ADR-0039 に従う。影も同じ帯を光の行列へ落とし、画面とは違う骨や幅を焼かない。描画先や設定によって別のフレーム組み立てを作らない (決定 3)。

最初の適用では、半透明の線・既定以外の折れ目・利用者の断片・保持した形・モデル・自由な輪郭を従来の CPU の組み立てに残す。**経路の違いは既存の線の意味を変える許可ではない。** 利用者の断片が読む形自身の座標・色・面の向きは変えず、公開の切り替え API は足さない。半透明の局所的な重なりを引く判断 ([#1561](https://github.com/mokume-metal/mokume/issues/1561)) と、保持した線を置く視点で組み直す判断は維持する。適用範囲の拡張は、既存の絵と費用を同じ方法で確認してから決める ([#1604](https://github.com/mokume-metal/mokume/issues/1604))。

**当初の決定**は、溜まった頂点を呼び出し順に並べる構成を前提にしていた。線が塗りの列を切るたび塗りの頂点を積み直し、線の帯と角も配置ごとに CPU で作ると、同じ球100個でも約193MBを GPU 側へ確保した (#1596 / #1606 の実測)。呼び出し順を守る理由は変わらず、頂点を個数分持つ必要だけが無いため、この部分を改訂する。

使い回す骨の控えには ADR-0023 の予算を適用する。控えからの追い出しと、描画列が読み終える寿命は別に持つ。列ごとの配置・視点・太さは描いた時点で記録し、後の設定で先の描画を変えない。実装と費用の確認は [#1738](https://github.com/mokume-metal/mokume/issues/1738) が持つ。

> 破れたとき: 高速化のために塗りを先にまとめると、半透明の前後や平面を挟んだ重なりが変わる。骨だけを共有して視点を記録しないと、先に置いた線まで最後の視点に向き直る。

#### 改訂 (2026-09-30) — 保持した形の中の組み込み立体の線も GPU で組む

**保持した形 (`createShape`) の中で組み込み立体に引いた線も、置くときに同じ骨で組んでよい。** 条件はその場で描くときと同じ (不透明・既定の折れ目・通常の混ぜ方・絵も利用者の断片も無し・閉じた稜線) で、**記録した時点のスタイル**で判じる。置いた線の太さ・色・焼き場の白い区画は記録したものを使い、変換は置き場所に記録時の変換を重ね、視点は置く時点のものを使う (保持した線を置く視点で組み直す判断は変えない)。置き場所の色は、焼いた頂点に掛かるのと同じ式で線にも掛かり、それで透けた線は CPU の帯へ戻る。

**記録の中身と重ね順は変えない。** 記録の間は今までどおり CPU の帯を頂点に焼き、GPU で組めるかと、その帯の区間を別に覚える。置くときは置き場所ごとに、区間を記録した順に「焼いた頂点 → GPU の線の列 → …」と割るので、塗りと線の重ね順は CPU で置いたときと同じで、全部の塗りを先にまとめない。形の頂点の数・区間の数・組 (`group`) の意味も変わらない。記録の中で置き直す (入れ子)・添字を持つ区間・通常以外の混ぜ方の区間は、CPU の帯のまま置く。描く回数は、その場で描くときと同じく置き場所の数に応じて増える。

**当初の改訂 (2026-09-28)** は、最初の適用で保持した形を CPU の組み立てに残し、広げるなら既存の絵と費用を同じ方法で確かめてから決めるとしていた。保持した線は置くたびに CPU で帯を組み直していて、線だけの球 30 個で 1 フレーム約 9.8 ms、200 個で約 61 ms かかっていた。7 形状 × 11 の置き方 × 塗りの有無で GPU で組んだ絵が CPU の帯と全バイトで一致し、費用が 30 個で約 0.47 ms・200 個で約 1.75 ms に下がることを確かめたので、この範囲へ広げる ([#1756](https://github.com/mokume-metal/mokume/issues/1756))。モデル・自由な輪郭・半透明の線・既定以外の折れ目は、引き続き CPU の組み立てに残す。

> 破れたとき: 置く時点のスタイル (太さ・`noStroke`) で記録した線を描くと、組み立てた形と違う線が出る。区間を割らずに GPU の線を後へ回すと、塗りと線の重ね順が変わる。

#### 改訂 (2026-09-30) — 奥行きは、前の描き切りが書き出したものだけを引き継ぐ

**奥行きの面は、前の描き切りが書き出した奥行きを持っているときだけ引き継ぎ、持っていなければ消してから描く。** 持っているのは、直前の描き切りが奥行きを残す描き切り (フレームの最後でないもの) で、何かを描いたか、さらに前の奥行きを引き継いだときである。塗り直し (`background()`) は、持っていても消す。フレームの最後の描き切りは奥行きを捨てるので、その後の面は持っていない。この規則は、フレームを分けた描き切り・止まっている間のコールバック・`setup()` のどれにも同じに効く。

持ち越しを約束する区間 (決定 4 の追補 (2026-09-27)) で描き切らせた立体は、これで描き切らせずに持ち越した立体と同じに扱われる。

- 止まっている間の最初の描き切りは、前のフレームの最後が捨てた奥行きを読まず、消してから描く
- 止まっている間や `setup()` で描き切らせた立体の奥行きは、次のフレームの最初の描き切りが引き継ぐ。そのフレームで置く立体と前後を比べられるので、描き切らせたかどうかで絵は変わらない。効果の有無にも依らない

費用は変えない。走るフレームは、最初の描き切りが消し、途中の描き切りだけが書き出し、最後の描き切りが捨てる (面も増えない)。止まっている間に読むだけのコールバックは、これまでどおり空の描き切りが奥行きを書き出すが、捨てた奥行きを読み込まなくなる。描き切らせた区間の次のフレームだけ、最初の描き切りが奥行きを読み込む。

**背景で置き換えるときと失敗したときの線引き。**

- **塗り 1 色の背景** (`background(色)`) は、色と奥行きを消して塗り直すので、引き継いだ奥行きも消える。
- **周囲の背景** (`background(.sky)`) は、色を塗り直さず、いちばん奥の板を奥行きの比較つきで置く (当時。いまは比べずに置き換える — 下の改訂 (2026-10-02))。区間の中と、そのフレームがまだ何も描き切っていない間に呼ばれたときは、引き継いだ奥行きだけを手放す (色は消さない)。手放さないと、板が区間で描き切らせた立体の画素で落ち、その立体だけが背景の手前に残る。溜めたまま持ち越した立体は、背景を置くときに捨てられるので出ない — 描き切らせたかどうかで絵が変わる。
- **フレームの中で描き切らせた後の周囲の背景は、この改訂の射程の外**だった (下の改訂 (2026-10-02) で扱った)。自分が描いた立体の奥行きは手放さず、背景の板が立体を覆わないのは、この改訂の前からの挙動で変えない (別の根: [#1685](https://github.com/mokume-metal/mokume/issues/1685)・[#1657](https://github.com/mokume-metal/mokume/issues/1657))。
- **最後の描き切りが失敗したフレームも、フレームの終わりで引き継ぎを切る。** 奥行きはフレームごとに作り直す約束を、失敗した回も成功した回と同じにするためである。失敗した回だけ奥行きを残すと、その次のフレームで置いた立体が、成功したときと違い、区間で描き切らせた立体の奥行きと比べられる。

**当初の決定**は、引き継ぐかを「このフレームで既に描き切ったか」で決めていた (数はフレームの頭で 0 に戻る)。フレームの最後は奥行きを捨て、数は次のフレームの頭でしか戻らないので、その間 (止まっている間) の最初の描き切りは、捨てた奥行きを読み込んだ (中身は機械による)。さらに、その間や `setup()` で描き切った立体の奥行きは、次のフレームの最初の描き切りが消してから描くので失われた ([#1888](https://github.com/mokume-metal/mokume/issues/1888))。

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| フレームの最後の描き切りでも奥行きを残す | 分けて描き切らないスケッチまで、毎フレーム奥行きの書き出しを払う。奥行きを残すのは途中の描き切りだけ、という費用の約束に反する |
| 止まっている間の描き切りが、前のフレームの奥行きを読まないだけにする | 中身の決まっていない奥行きを読むのは直るが、区間で描き切らせた立体の奥行きが次のフレームの頭で消えるのは残り、描き切らせたかどうかで前後が変わる |
| 最後の描き切りが失敗したフレームでは、引き継ぎを残す | 次のフレームの奥行きが、成功したフレームの後と違う始まりになる。奥行きはフレームごとに作り直す約束が、失敗した回で崩れる |

> 破れたとき: 区間で描き切らせた立体が、次のフレームで置く立体の手前へ出る (奥にあるはずなのに)。効果を使わなくても起きる。捨てた奥行きを読んでいるときは、機械によって区間の立体が描かれないか、前後が入れ替わる。次のフレームの `background(.sky)` が、区間で描き切らせた立体だけを残すのは、引き継いだ奥行きを手放していないとき (いまは、置き換える列が奥行きを比べているとき — 下の改訂 (2026-10-02))。

#### 改訂 (2026-10-02) — 背景は、色でも周囲でも 1 つの関所で面を置き換える

**`background()` は、色でも周囲でも、面をその時点から置き換える。** 違うのは置く中身 (1 色か、視点から見た周囲か) だけで、規則は口によらず 1 つである ([#1685](https://github.com/mokume-metal/mokume/issues/1685))。

- **呼んだ時点の図形のスタイルを読まない。** 混ぜ方・断片・貼る絵・影を落とすか・光と材質のどれも、置き換えには効かない
- **同じフレームの途中の描き切りに左右されない。** 描き切って載った絵も奥行きも置き換える
- **切り抜きがあれば、その中だけを置き換える** (中は色も奥行きも置き換わり、外に先に置いたものは残る)
- 置き換えた後の奥行きは、どちらの口でも**いちばん奥 (1)** である。後から置く立体は、どちらの背景でも同じ前後で出る

手段は 2 つあり、どちらも同じ絵になる。切り抜きが無く中身が 1 色なら、溜めたものを捨てて塗り直しを予定し、描き切りの load 動作が色と奥行きを消す (安い道)。それ以外 (切り抜きの中・周囲) は、**置き換える列**を 1 本積む。列は視点が写す範囲いっぱいの板で、混ぜ方は置き換え・断片は組み込み・影は落とさず、奥行きは比べずに 1 を書く。板は手前と奥の面の真ん中に置く — 書く奥行きは位置によらず 1 なので、位置に求めるのは切り取られないことだけで、真ん中ならどの投影でも間に入る (奥の面の近くに置くと、手前と奥が近い透視や、奥行きの範囲が負の側にある平行で板が消え、何も置き換えない)。呼び出し順に並ぶ列なので、それより前に置いたものの上を、切り抜きの中だけ置き換える。

**当初は**、周囲の背景を図形の 1 つとして描いていた。列を閉じる経路を通るので、呼んだ時点の混ぜ方・断片・切り抜き・影を落とすかを拾い ([#1658](https://github.com/mokume-metal/mokume/issues/1658))、板は奥の面の手前の奥行きで比較を受けたので、フレームの中で描き切らせた立体の手前へ出られなかった ([#1657](https://github.com/mokume-metal/mokume/issues/1657))。上の改訂 (2026-09-30) は、引き継いだ奥行きだけを手放してこの片方を埋めていたが、比べずに書けば手放す必要は無い。塗り 1 色の背景は load 動作に乗っていたので、切り抜きを表せず、切り抜きの外まで塗っていた ([#1648](https://github.com/mokume-metal/mokume/issues/1648))。周囲の背景が書く奥行きも、板の位置 (奥の面の 98%) から 1 に変わったので、その間に置いた立体は空の手前に出るようになった (塗り 1 色の背景と同じ)。

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| 切り抜きを見ず、面全体を置き換える | `clip` の説明 (描くものをこの矩形の中だけに収める) に例外ができる。手本 (Processing の P2D は scissor に従って消し、p5 は 2D の切り抜きの中を塗る) とも食い違う |
| 周囲の背景だけを直す (スタイルを外し、奥行きを手放す) | 色の口は load 動作に乗ったままで、切り抜きを表せない。2 つの口が別々の仕組みで「置き換え」を作る形が残り、口を足すたびに同じ食い違いが起きうる |
| いつも置き換える列を描く (load 動作の clear を使わない) | 毎フレーム `background(色)` を呼ぶスケッチが、面全体の板 1 枚ぶんを払う。絵は変わらない |

> 破れたとき: `blendMode(.add)` のまま `background(.sky)` を呼ぶと空がフレームごとに明るくなる。立体を置いて `loadPixels()` を読んでから `background(.sky)` を呼ぶと立体が空の手前に残る。`clip` の中の `background()` が切り抜きの外まで塗り、先に置いた図形を消す。検査は `BackgroundReplacementTests` が口を並べて回す。

#### 追補 (2026-10-02) — 1 つの形の中の裏 → 表は、形どうしの並べ替えではない

**裏面が絵に出うる立体は、形 1 つ (置き場所 1 つ × 記録した形 1 つ) の中だけ、裏を向いた面 → 表を向いた面の順に描く。** 裏面が絵に出うるのは、半透明の塗り・貼る絵・重ねる以外の混ぜ方・利用者の断片のどれかで置いた組み込みの形と読み込んだモデル、それらを記録した保持した形 (半透明の色で置いたものを含む) である。奥行きは読み書きのままで、1 回で描くと先に積まれた手前の面が後の奥の面を捨て、奥の面が出るかが形の向き (三角形を積んだ順) で変わっていた ([#1549](https://github.com/mokume-metal/mokume/issues/1549)・[#1565](https://github.com/mokume-metal/mokume/issues/1565))。

この追補は上の決定の文言を変えない。

- **「立体は奥行きを読み書きし」は保つ。** 奥行きを書かない案は、光を当てた形で向きの差が残り (混ぜる順が積んだ順のまま)、半透明の形が後から奥に置いた形を隠さなくなるので採らない。
- **「並べ替えない」は形どうしの話で、これも保つ。** 置き場所どうしも、1 つの `createShape` に記録した形どうしも、呼び出し順 (記録した順) のままで、奥から順に描く責任は引き続き作品側にある。列ごと・保持した形ごとにまとめて裏 → 表で描く案は、作品側が奥から並べた 2 つの半透明の形で奥の形の手前の面を手前の形の裏面に捨てさせ、作品側が責任を果たしても報われないので採らない。
- **「追加の描画パスは作らない」にも当たらない。** 増えるのは同じパスの中の描く呼び出しで、裏面が絵に出うる形 1 つにつき 2 回になる。同じ列に居ても、裏面が絵に出ない置き場所の描き方と費用は変えない (続けて並んだものは 1 回の呼び出しにまとめる)。

**どちらが裏かは巻き方で決まる。** 組み込みの形は外向きに巻いてある。読み込んだモデルは巻き方が逆のことがあるので、初めて裏 → 表が要る置き方をされたときに形から向きを求めて控え (閉じていて巻き方が揃っていれば、繋がった成分ごとの符号付きの体積の符号で決まる)、内向きなら表 → 裏の順に入れ替える。向きの求まらないモデル (閉じていない・巻き方が揃っていない・成分どうしで向きが食い違う) は裏 → 表に分けず、1 回で描く — 向きを取り違えて裏 → 表で描くと、奥の面がどの向きでも捨てられ、1 回で描くより悪くなるためである。

凸でない形 (`torus` など) で、同じ側を向いた面どうしが重なる所は、積んだ順が残りうる。粒と自分で並べた頂点 (`beginShape`) は裏 → 表に分けない — 粒は板 1 枚で自分の面が自分を隠さない。自分で並べた頂点は巻き方の向きを利用者が決め、塗りと線を原始形ごとに交互に積むので、形の塗りが 1 つの区間にまとまらない。立体の線の帯は形の外として呼び出し順のまま描き、半透明の線どうしの重なりは別に扱う ([#1561](https://github.com/mokume-metal/mokume/issues/1561))。

> 破れたとき: 半透明の球を回しただけで中心の明るさが 1 層ぶんと 2 層ぶんに分かれ、球の中に横縞のような境目が出る。列ごと・保持した形ごとにまとめると、奥から並べた半透明の形の重なりが崩れる。巻き方の逆なモデルを外向きと取り違えると、奥の面がまったく透けない。

### 3. フレームの組み立ては 1 本で、機能の有無で分岐しない

- 影の下ごしらえは、**同じフレームの中で、本描画の前**に行う。溜まった列がそのまま材料になる
- **影を有効にしても、絵の重なり方は変わらない**
- **影を有効にしても、画素の読み戻しは同じ意味で使える** (読めるのは常に、いま描き終えたフレームである)
- 環境変数や設定で「別の組み立て方」へ切り替える口を作らない

> 破れたとき: 影を入れた瞬間に前後が入れ替わる / 画素が 1 つ前のフレームを指す。どちらも利用者には「影を入れたら壊れた」としか見えない。

#### 改訂 (2026-10-03) — 途中で描き切っても、影はそのフレームのそこまでの落とす側から焼く。前に描いた面へは後から効かせない

**フレームの途中で画素を読む (描き切る) と、そこが区切りになる。区切りより後に描く面は、区切らずに描いたときと同じ影を受ける。区切りより前に描いた面は、区切りの後に置いた立体の影を受けない。** 読み戻しが「いま描き終えた絵」を返す約束は保ったまま、影の受け方だけを次のように決める。

- 焼き付けは描き切るときに走り、そのフレームでそこまでに置いた落とす立体の全部を、そのときの光から焼く。途中の描き切りが描いた落とす立体は、フレームの終わりまで落とす側に残す (塗り直しでは捨てる — 区切らなくても、塗り直しは前の立体を捨てるので一致する)
- 区切りより前に描いた面は既に描画先に載っている。後から置いた立体の影・後から置いた光と影の設定は、その面へは効かせない (描き直すしかない)
- 置いた描き場所を同じフレームで描き換えるのは、区切りにしない。置いた側は描き換わる直前の絵を写しに取って読む。ただし置いた側が形を組み立てている途中のとき・写しの上限 (置いた側 1 つにつき 4 枚) に達したとき・写しを用意できないときは、これまでどおり置いた側を描き切る (区切りになる)
- 落とす側を区切りで控えるのは、影を 1 度でも有効にした面のフレームの中だけである。影を初めて有効にしたフレームで、区切りの後に影を有効にすると、そのフレームだけ区切りより前の立体は影を落とさない

利用者の説明 (`shadows(_:)`・`loadPixels()`・`pixels`・`createGraphics(_:_:)`) は、区切りが入る口とこの線引きを書く。決めたのは [#1656](https://github.com/mokume-metal/mokume/issues/1656) で、メンテナが 2026-09-27 に案 A (取り返せる向きを直し、取り返せない向きは説明で引き受ける) と案 A2 (描き場所の描き換えは写しで区切らない) を選んだ。

**当初の決定**は「影を有効にしても、画素の読み戻しは同じ意味で使える」だけを書き、途中で描き切った後の影を決めていなかった。実装は描き切るたびにその回の列だけから落とす立体を選んでいたので、区切りより前に置いた立体の影が、後に置いた面へ落ちなかった。読み戻しが同じ意味で使えるという約束は成り立っていたが、読み戻しを入れるだけで絵が変わり、利用者には「影を入れて画素を読んだら壊れた」としか見えなかった。

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| フレームの頭の絵とそのフレームの列を全部控え、フレームの終わりに描き直す (案 B) | 約束は変わらないが、区切るスケッチが毎フレーム控えと描き直しを払う。画素の書き込み (`set`) を描き直しのどこへ差し戻すかの設計も要る |
| 描き場所の描き換えで入る区切りを、説明に書いて残す (案 A1) | 利用者が呼んでいない区切りで、前の面が後の立体の影を受けなくなる。`image(pg)` の後に `pg` を描き換える形は毎フレーム入る |
| 区切りのたびに、控えた落とす側を全部焼き直して全部を上げ直す | 1 フレームの区切りの数の 2 乗で重くなる。控えた分は区切りごとに 1 度だけ上げ、面が既に持つ分へ足して焼く |

### 4. 描き方は越え、シーンの記述は越えない。例外を作らない

| 種類 | 寿命 | 例 |
|---|---|---|
| **描き方** (どう描くか) | フレームを越える。一度書けば残る | 塗り・線・太さ・端点・混ぜ方・各種モード・文字の設定 |
| **シーンの記述** (何を描くか) | 越えない。毎フレーム書く | 視点・投影・光・材質・変換・影・周囲の光 |

重い下ごしらえを伴うもの (影の焼き付け先・周囲の光) も**シーンの記述として扱う**。毎フレーム宣言してよい形にし、**同じ宣言なら実体を作り直さない** — 同一性は宣言の内容で見る。これにより「重いから越える」という例外が要らなくなる。

**シーンの記述を初期化のときに呼んだら、警告して無視する。** 黙って捨てない ([ADR-0020](0020-api-naming-and-surface.md) 決定 5 の「警告を出して安全な既定へ倒す」の適用)。初期化はフレームが始まる前なので、そこで書いた視点や光は**どのフレームにも属さない**。

> 破れたとき: 初期化のときに書いた設定が黙って捨てられ、既定値で描かれる。利用者からは「効かない」としか見えず、自分のコードを疑うしかない。

#### 追補 (2026-09-06) — 積んだ履歴もフレームに属する

上の表が定めるのは**状態そのもの**の寿命である。`push` が積む履歴 (`pushMatrix` / `pushStyle` が積むスタック) は、**どちらの種類の状態を積んだかによらず、フレームを越えない**。

**越える状態の履歴も越えない。** `pushStyle` が積むのは「描き方」= 越える側の状態だが、**積んだという事実そのものはフレームに属する**。積む・降ろすは 1 つのフレームの中で釣り合う操作で、フレームをまたいで釣り合わせるものではないからである。フレームの外で積んだものも、どのフレームにも属さないので警告して無視する (決定 4 本体と同じ扱い)。

**この 1 段が書かれていなかったので、実装は割れていた** ([#925](https://github.com/mokume-metal/mokume/issues/925)) — `transformStack` は毎フレーム空になるのに `styleStack` は残り続け、釣り合わない `pushStyle` が 60 fps で積み上がっていた。`push()` は変換とスタイルの両方を積むので、`pop()` を書き忘れると**次のフレームで変換だけが戻る**という片肺の状態も生んでいた。

> 破れたとき: 釣り合わない `push` がフレームをまたいで積み上がり、長く走らせるほど記憶を食う。`push()` / `pop()` の対応がフレームの境目で崩れ、同じ 1 つの呼び出しの結果が半分だけ効かなくなる。

#### 追補 (2026-09-15) — 形の組み立ての中は、フレームの外でも変換とスタイルが意味を持つ

**当初の決定**は「シーンの記述をフレームの外で書いたら、例外なく警告して無視する」だった。変換は上の表でシーンの記述に属し、2026-09-06 の追補が積んだ履歴まで同じ扱いに揃えている。

**保持した形の組み立て (`createShape`) の中だけは、フレームの外でも変換とスタイルの積み降ろしが効く。** 組み立ての中は**形自身の座標で記録する文脈**であり、そこで書いた変換は絵ではなく**形に焼き付く** — 属する先がフレームではなく形なので、どのフレームにも属さないまま意味を持つ。決定 4 本体の理由 (どのフレームにも属さないものを黙って捨てない) とは衝突しない。

**シーンの記述の側は変えない。** 視点・光・囲み・影・材質・粒・計算は、記録の間もフレームの外のままで警告して無視する。形に焼き付かないので、記録の中に属する先が無いためである。

**フレームの中で組み立てるときも同じ扱いである** (2026-10-02 に足した・[#1529](https://github.com/mokume-metal/mokume/issues/1529))。形に焼き付かないもの — 上の列挙に切り抜き・効果と、面全体の明るさを決める露出・明るさの丸め方を加えたもの — は、`draw()` の中で組み立てても警告して無視する。当初の追補は `setup()` で組み立てる場合しか書いておらず、実装は `draw()` の中の組み立てで守りを素通りしていた。`Style` に入っている切り抜き・材質・影の落とし方は形にも入らず出口で黙って消え、光・視点・効果はそのフレームにそのまま効いていた — 組み立てる場所で扱いが割れ、下の「破れたとき」と同じ形の破れになっていた。そのフレームに効かせる案は、`setup()` の組み立てと割れたまま残るので採らなかった。

**積んだ履歴も、記録の中で閉じる。** 組み立ては入口で積み履歴を切り離し、出口で戻す。記録の中の `pop()` は記録より前に積んだ段を取らず、記録の中で積んだまま抜けた段も外の `pop()` に拾われない。積む・降ろすが釣り合う単位は、フレームか**形の組み立て**のどちらかである。

**この 1 段が書かれていなかったので、実装は破れていた** ([#1172](https://github.com/mokume-metal/mokume/issues/1172)) — `setup()` で組み立てた形の中の `push()` / `translate()` が落ち、参照スケッチの 9 枚の葉が 1 か所へ重なったまま main に入っていた。

> 破れたとき: `setup()` で組み立てた形だけが、`draw()` で組み立てたのと違う形になる。コードは同じなので、利用者からは「組み立てる場所で形が変わる」としか見えない。

#### 追補 (2026-09-27) — 置いたものは、持ち越しを約束する区間でだけフレームの外に置ける

上の表と 2 つの追補が定めていたのは**状態**の寿命である。**置いたもの** (図形・絵・背景・画素の書き込み) は表に無く、フレームの外で置いたときの扱いは、実装の既定「次の描き切りまで溜めて持ち越す」に任されていた。面によって帰結が違った ([#1603](https://github.com/mokume-metal/mokume/issues/1603))。

| 置いた場所 | 当時の帰結 |
| --- | --- |
| 本体の `setup()` | 最初のフレームに出る |
| 本体の止まっている間のコールバック | 次に描くフレームに出る |
| 描き場所の `beginDraw()` の外 | 次の描き切りが来ないので、永遠に溜まる ([#1592](https://github.com/mokume-metal/mokume/issues/1592))。書いた画素は、`get()` と `image()` で違う絵に見える ([#1654](https://github.com/mokume-metal/mokume/issues/1654))。効果が 2 回掛かる ([#1655](https://github.com/mokume-metal/mokume/issues/1655)) |
| `Canvas` を直に使って、`draw {}` の外 | 次の `draw {}` に出る |

**置いたものをフレームの外に置いてよいのは、持ち越しを約束する区間だけである。** 区間を決めるのは、次のフレームを約束する主体である。

| 面 | 持ち越しを約束する区間 | 約束する主体 |
| --- | --- | --- |
| 本体 | `setup()` と、止まっている間のコールバック。置いたものは次に描くフレームへ持ち越す (止まっている間のコールバックで書いた画素だけは、配った直後に面へ戻す — 下の追補 (2026-10-02)) | ランタイム |
| 描き場所 | `beginDraw()`〜`endDraw()` | 作者 |

区間の外 (描き場所の `beginDraw()` の外、`Canvas` を直に使う `draw {}` の外、`Task` の続きなど) で置いたものは、**警告して無視する**。黙って溜めない・黙って捨てない (決定 4 本体と同じ理由)。画素の書き込み (`set()`・`pixels` への代入・`fill`) も「置くこと」に含む。書いた画素は、置いた図形と同じく区間が約束する先 (次の描き切り。止まっている間のコールバックでは配った直後 — 下の追補 (2026-10-02)) で面に載るので、属する先の規則が同じでなければならない。

**止まっている間に `redraw()` を呼ばずに置き続けたものは、上限を付けずに持ち越す。** 区間の中の話であり、上限の数に根拠が無い。溜まるのは、作者が置き続けているからである。

`setup()` だけで 1 枚を描く書き方は、区間の中なので壊れない。**フレームの外をすべて断る案は採らなかった。** Processing の Examples を移した 157 本のうち 40 本が、`setup()` で描く (16 本は `draw()` を持たず、`setup()` だけで 1 枚を描く)。この書き方は Processing の基本であり、断ると 40 本が壊れる (#1603 の実測)。

**開いたまま境目を越える操作も、同じ理由で越えさせない。** 2026-09-06 の追補の「積む・降ろすは 1 つのフレームの中で釣り合う」は、積み履歴だけでなく、対で開いて閉じる操作すべてに当たる。

- **組み立て中の形** (`beginShape`〜`endShape`) はフレームに属する。境目で開いていれば、フレームの頭と終わりの両方で形ごと捨て、1 度注意する ([#1591](https://github.com/mokume-metal/mokume/issues/1591))。頭だけだと `draw()` で開いた形が止まっている間のコールバックへ漏れ、終わりだけだと `setup()` で開いた形に 1 枚目の点が積まれる
- **描き場所の閉じ忘れたフレーム**は、本体の次のフレームの頭で描かずに捨て、1 度注意する ([#1622](https://github.com/mokume-metal/mokume/issues/1622)・[#1834](https://github.com/mokume-metal/mokume/issues/1834))。前のフレームで書いた変換を、次のフレームへ持ち込まない。捨てる時点は下の 2026-10-02 の改訂が決めた (当初は次の `beginDraw()`)

**口ごとに守ると、書き落としが黙る。** この追補の前にも、フレームの外を断る規則は口ごとの `guard` で守られていた。書き落とした口 (#941・#1505・#1605) と、境目で戻し落とした状態 (#925・#1472・#1504・#1591) が、1 件ずつ見つかっては直された ([ADR-0040](0040-bugs-as-broken-promises.md) の文脈の「同じ根の群」)。したがって、守り方も範囲で持つ。

| 守るもの | 検査 |
| --- | --- |
| シーンの記述の口 | 公開の口を種類で分類した表に無い口と、フレームの外で注意が出ることを回す検査に無いシーンの記述の口を、`make api` が赤にする ([#1670](https://github.com/mokume-metal/mokume/issues/1670)) |
| 境目で戻す状態 | `Canvas` の格納プロパティを、「フレームに属する」「持ち越す」の 2 つの表のどちらかに載せる。どちらにも無ければ赤。フレームに属する状態は、全部汚して境目を越えると既定へ戻る ([#1671](https://github.com/mokume-metal/mokume/issues/1671)) |
| 置いたものの寿命 | フレームの頭で、区間の外で置いたものが溜め場に残っていれば、捨てて 1 度注意する。**止まるのは mokume の検査の中だけ**で、口を足し忘れると検査が赤になる。漏れは mokume の中の不具合でしか起きないので、利用者の作品 (debug 組みを含む) は止めずに名乗る ([#1672](https://github.com/mokume-metal/mokume/issues/1672)・[#1682](https://github.com/mokume-metal/mokume/issues/1682)) |

**本体の止まっている間のコールバックで書いた画素は、この追補では決めなかった。** 区間の中なので断らないが、効果を掛けた面では控えの絵との順序で食い違いが残りうる。それは [#1524](https://github.com/mokume-metal/mokume/issues/1524) の判断に残した。下の 2026-09-30 の追補が決めた。

> 破れたとき: 描き場所で `beginDraw()` を書き忘れると、何も出ないまま記憶だけが増える。書いた画素が、読む口によって違って見える。`Canvas` を直に使う道具では、フレームの外で置いたものが、いつの絵に出るかを呼び手が知らない。

#### 追補 (2026-09-30) — 止まっている間に変えたものは、効果を掛けた面でも次のフレームへそのまま持ち越す

**効果 (`effects()`) を掛けたフレームの後でも、本体の止まっている間のコールバックで描く先に加えた変更は、次に描くフレームで効果を通す前の絵の上に載る。** 当たるのは、書いた画素・置いた図形・絵・背景のすべてである。上の追補の「次に描くフレームへ持ち越す」を、効果の控え ([#1469](https://github.com/mokume-metal/mokume/issues/1469)) と食い違わせずに通す。例外の追補は書かない (決定 4 の見出し「例外を作らない」)。決めたのは [#1524](https://github.com/mokume-metal/mokume/issues/1524) の甲-1 である。

効果を掛けた面の描く先は、フレームの合間に「効果を通した絵 (出口と同じ 1 枚)」を持つ。次のフレームの入りは「効果を通す前の絵 (控え)」である。止まっている間は、この 2 枚に**変えるたびに同じ変更を加える**。

| | 描く先 | 控え |
| --- | --- | --- |
| 持つ絵 | 効果を通した絵に、変えた分が載ったもの | 効果を通す前の絵に、同じ変えた分が載ったもの |
| 見る口 | 画面・書き出し・観測・止まっている間に読む画素 (コールバックを配った直後に、書いた画素を描く先へ戻し、描く細かさを下げた面では描く先を出す先へ広げ直すので、どの口も同じ 1 枚を受け取る。細かさ 1 の窓と共有の面は効果と関係の無い別の根で遅れていて、[#1906](https://github.com/mokume-metal/mokume/issues/1906) が直した) | 次のフレームの入り |

- **図形・絵・背景は、控えにも同じ列で描く。** 縁のなめらかさ・半透明・足す混ぜ方のように下地と混ざるものも、置いた面の上で混ざる。描き切らせたかどうかで、次のフレームの絵は変わらない。**立体の奥行きも同じである** — 描き切らせた立体の奥行きは次のフレームの最初の描き切りが引き継ぎ、次のフレームで置いた立体と前後を比べられる。効果と関係の無い別の根で、決定 2 の改訂 (2026-09-30) が決めた ([#1888](https://github.com/mokume-metal/mokume/issues/1888))
- **書いた画素は、値で見分けて控えへ写す。** 書き込みは値そのものを置く (下地と混ぜない) ので、書き戻す前の描く先と値が違う画素が、書いた画素である。比べるのはビットである (数でない値は自分とも等しくないので、値で比べると数でない値を出す効果の画素がすべて書いた画素になる)。**描く先と同じ値を書いた画素は、書かなかった扱いになる。** 止まっている間に読む画素は効果を通した絵なので、読んだ値をそのまま書き戻すのと見分けられないためである (`pixels[x, y] = pixels[x, y]` は絵を変えない)。読んだ値を元に書いた値には、効果が入る

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| 止まっている間に変えたら、効果を通した絵ごと次のフレームへ持ち越す | 効果が 1 回焼き込まれる。決定 4 に例外の追補が要る |
| 次のフレームの頭で、描く先と「変える前の描く先」の値の差を控えへ写す (図形も含めて) | 混ざる画素では、効果を通した絵と混ざった値が控えへ写り、効果がもう 1 回掛かる (#1524 の反証 1)。値で見分けるのは、書き込みのように値そのものを置く変更でしか正しくない |
| 止まっている間の最初の変更の前に、控えを描く先へ戻す | 止まっている間に読む画素と画面が、効果を通さない絵へ変わる。効果を通した絵を見せ続けるには、フレームの外で効果を掛け直すことになる。どちらも、ここで決めていない公開の振る舞いを選ぶことになる |

#### 追補 (2026-10-02) — 止まっている間のコールバックで書いた画素は、配った直後に面へ戻す

**本体の止まっている間のコールバックが書いた画素 (`set()`・`pixels` への代入・`fill`) は、そのコールバックが `redraw()` / `loop()` を呼ばなければ、配った直後に面へ戻す。** 窓・共有の面・書き出し・観測が、書いた絵をその場で同じ 1 枚として受け取る (ADR-0023 決定 2) ためである。窓と共有の面は面のテクスチャを直に読むので、書いた画素を CPU の写しに溜めたままでは、次に描くフレームまで書く前の絵が出る ([#1906](https://github.com/mokume-metal/mokume/issues/1906))。効果を掛けた面では、戻すときに上の追補 (2026-09-30) のとおり控えへも写す。描く細かさを下げた面は、同じ 1 点で戻してから出す先へ広げ直す ([#1882](https://github.com/mokume-metal/mokume/issues/1882) で先に採った形を、すべての細かさへ広げた)。

戻した画素は、もう溜めたものではない。**後で描くフレームの描き切りが失敗しても消えない。** そのフレームと一緒に捨てるのは、そのフレームへ持ち越した図形・絵・背景と、そのフレームで置いたものだけである。同じコールバックで `redraw()` を呼んだときは、配った直後には戻さず、描くフレームの頭で戻す (そのフレームの一部として載るので、描き切りが失敗すれば図形と一緒に捨てる)。戻すのは書いたときだけで、書かなければ何も積まない (ADR-0023 決定 5)。外から止めている間 (道具の一時停止) も、戻し損ねた書き込みが残っていればリフレッシュごとに戻し直す。

当初の決定 (2026-09-27 の追補) は、止まっている間のコールバックで書いた画素も「次に描くフレームへ持ち越す」と読める書き方だった。細かさ 1 の面ではそのとおり次の描き切りか出力段まで溜まり、窓に出る絵と `save()` が食い違った。描き切りの失敗で消えるかどうかは、窓に一度出した絵が後から消えることになるので、窓に出た絵と揃える側を採った。

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| 書いた画素は溜めたまま、窓と共有の面が読む前に書き戻す | 窓は毎リフレッシュ読むので、読む口ごとに門を置くことになる。口を足すたびに書き落としうる (上の追補 (2026-09-27) の「口ごとに守ると、書き落としが黙る」) |
| 配った直後に戻すが、後のフレームの描き切りが失敗したら戻した画素も捨てる | 窓に一度出した絵が、描けなかったフレームの後で消える。戻す前の絵を控える置き場も要る |

#### 改訂 (2026-10-02) — 描き場所の閉じ忘れたフレームは、本体の次のフレームの頭で捨てる

**描き場所で `beginDraw()` を開いたまま閉じ忘れたフレームは、本体の次のフレームの頭で描かずに捨てる。** 本体が自分のフレームの番号を進める所で、同じ時刻の置き場を使う描き場所のうち、`beginDraw()` で開いたままのものを捨てる。捨てた後の描き場所はフレームの外に居る。越えた後に描き場所へ触れる口は、どれも今ある「フレームの外」の扱いに落ちる。読めば捨てる前の絵が返り、置けば注意して置かない。遅れて呼んだ `endDraw()` は、既に捨てたことを言って何もしない。本体・`Canvas` を直に使う面は変わらず、自分の次のフレームの頭で捨てる。`draw {}` で開いたフレームは閉包が閉じるので、捨てる相手に入らない。

捨てる規則は 1 つである。**描き場所が `beginDraw()` で開いたフレームは、属する本体のフレームを持つ。本体のフレーム F が始まる所で、F より前のフレームに属したまま開いているものを捨てる。** 属するフレームは開いたときに決まる。本体のフレームの中で開けばそのフレームで、`setup()`・止まっている間のコールバック・本体のフレームの合間で開けば、次に描くフレームである。持ち越しの区間は次に描くフレームに属する (上の 2026-09-27 の追補) からである。本体のフレームが始まる所は、本体の頭と、`noLoop()` で止まっている間のコールバック (次に描くフレームに属する区間) に入る所の 2 つである。止まっている間は頭が来ないので、止まる前のフレームに属したものを区間に入る前に捨てる。帰結として、`setup()` やコールバックで開いて次の `draw()` で閉じる対、ある回のコールバックで開いて別の回で閉じる対は捨てない。境目は頭なので、本体のフレームが終わってから次の頭までの間 (`Task` の続き・外から止めている間) は、まだ同じフレームである。そこで読んで描き切った分は、同じ本体のフレームの中の途中の描き切りと同じく取り消せない。

例: 本体のフレーム 2 で描き場所に赤い画素を書き、白い四角を溜めて、`endDraw()` を忘れる。フレーム 3 の頭で捨てるので、フレーム 3 で描き場所を `get()` で読むと捨てる前の黒が返り、後で本体へ置いた絵にも赤と白は出ない。

**当初の決定**は、上の 2026-09-27 の追補の「次の `beginDraw()` で描かずに捨てる」だった。その間 (本体のフレームを越えてから、次に開き直すまで) に読まれたときの扱いが書かれていなかった。越えたフレームは置く口だけが見分けて断っていたので、読む口 (`get()`・`pixels`・`loadPixels()`)・この描き場所を置いた面が描き換わるときの描き切り・数の並びの読み・遅れた `endDraw()` が、捨てるはずの中身を描いた。図形は面に残り、後で捨てても消えなかった ([#1834](https://github.com/mokume-metal/mokume/issues/1834))。捨てる約束 (変換・図形・画素を次へ持ち込まない) の理由は動かず、時点だけを差し替える。

境目 (本体のフレームが始まる所) を越えた状態そのものを作らないので、越えたフレームを口ごとに見分ける印は要らない。上の追補の「口ごとに守ると、書き落としが黙る」の形である。

採らなかった形:

| 形 | 採らなかった理由 |
| --- | --- |
| 越えた後に最初に触れた口が、その場で捨てる | 捨てる口を列挙して守ることになる。起票時に挙げた口は 4 つで、調べ直すと 6 つになり、`emit` のように `guard isDrawing` だけを見る口も加わった。口を 1 つ書き落とした日に、そこだけ捨てる前の中身が描かれる |
| 読む口は捨てずに、描き切らずに読ませる | 書き込み待ちを残したまま面の絵を読ませる仕掛け (写しを 2 系統にする等) が要り、読む口ごとに分岐が増える。遅れた `endDraw()` で描くか捨てるかを別に決める必要が残る |
| 仕様として説明に例外を書く | 「描かずに捨てる」と食い違ったままになる。捨てた後も図形が面に残るのは約束にできない |

代償: 本体のフレームの頭が、ほかの面 (描き場所) の状態を変える。時刻の置き場が、描き場所を弱く持つ一覧を持つ。揺らぎの置き場が書き換える前に描き切らせる相手を持つのと同じ形で、載せるのは描き場所を作る口の 1 つである。本体のフレームの中で開いて閉じ忘れたフレームを、本体のフレームが終わった後〜次の頭の前に読むと、それまでどおり描き切って読み、その分は後で捨てても面に残る (境目の前の途中の描き切り)。

### 5. 形を作る道具は 1 つ。広がるのは頂点の性質だけ

- 頂点を並べて形を作る記述は 1 つに保つ。**その場で描くか、保持して繰り返すかは使い道の違い**であって、別の実装にしない
- 立体で増えるのは**頂点の中身** (位置の奥行き・面の向き) であって、形の種類ごとの対応表ではない
- **穴・輪郭・頂点ごとの色は、平面と立体の両方に効く**

> 破れたとき: 同じ形を書いても、通した道具によって面の向きや色が変わる。あるいは「平面では効くが立体では黙って無視される」機能が生まれ、利用者は書いたのに効かない指定を自分の座標のせいだと考える。

## 影響

- **描画先が奥行きの面を持つ。** 立体を使わないスケッチでも確保される (面と同じ大きさ)。使うときだけ確保する案は、確保の有無で経路が分かれるため採らない — 決定 3 と同じ理由である
- **影と周囲の光の API は「毎フレーム呼ぶ」形になる** (決定 4)。呼ぶたびに焼き直さないことは、実装側の完了条件になる
- **決定 2 の「並べ替えない」を後から変えるのは、絵が変わる変更である。** 変えるなら本 ADR を改訂する。散文の但し書きで運用しない
- 決定 1 により、立体の実装は [ADR-0020](0020-api-naming-and-surface.md) 決定 3 の宣言を満たす責任を負う。変換とスタイルの作用先を実装ごとに議論し直さない
- **各決定に添えた「破れたとき」は、実装の検査の入口である。** どの決定も、破れても例外が出ず絵が少し変わるだけなので、[ADR-0019](0019-drawing-verification.md) 決定 4 の自己判定テスト (画素の意味・数え上げ) で守る。どの Issue がどの決定を守るかは、立体のフェーズの sub-issue が持つ
- 本 ADR は**規範だけを置き、適用は各実装 PR に随伴させる**
