# ADR-0033: 色を指定する面 — 素の数値は 0–255、ラベルが尺度を名乗る

## 状態

採用 (2026-09-03)

## 文脈

[ADR-0011](0011-color-model.md) は色の**規範**を決めたが、影響節の最後の行で**面**を先送りした。

> 利用者が色を指定する API の形 (0–255 か 0–1 か、色空間を明示できるか) は本 ADR の範囲外とし、2D 描画 API の設計で決める。**そのとき本 ADR の決定 1・4 が制約として効く**

2D の面はその後ひととおり揃ったが、この決定は書かれないままだった。結果としていま利用者の面に出ているのは、設計された色指定 API ではなく、**作業空間の型の境界コンストラクタがそのまま露出したもの**である。

```swift
background(.display(red: 0.06, green: 0.07, blue: 0.09))
fill(.display(red: 0.95, green: 0.85, blue: 0.35, alpha: 0.9))
```

これは [ADR-0020](0020-api-naming-and-surface.md) 決定 1 (手本があれば名前と引数の順序をそのまま採る) から見ると、**足りていない**。`fill(v1, v2, v3)` は Processing と p5.js の両方が持つ形で、手本が無いから採らなかったのではなく、誰も決めなかったから無い。

### 決めるべきこと

1. 素の数値を受けるとして、その目盛りは何か
2. 目盛りが複数あることを、読む人がどう見分けるか
3. `colorMode()` のようなモード状態を持つか
4. HSB をどう表すか — **手本が割れている** (Processing は 3 成分とも 0–255、p5 は 360 / 100 / 100)
5. 書いた尺度で読み出せるか (`red(c)` 相当を持つか)
6. どの口まで数値形を広げるか

### 決めないと何が起きるか

**尺度が行から読めない状態が固定される。** `fill(1, 0.4, 0.2)` と書いたとき、それが線形の光の量なのか、ディスプレイのエンコード値なのか、0–255 の値なのかは、型からもコードからも判定できない。ADR-0011 決定 1・4 により作業空間の値は「表示できる色」ではないので、**素の 3 数値は必ずどこかで意味を宣言しなければならない**。

**書く側だけ手本に寄せると、読み出しで破綻する。** `fill(255, 204, 0)` と書けるのに `get(x, y)` が返す値が線形・アルファ乗算済みでは、往復が成立しない。手本の `red(c)` は 0–255 のエンコード値・straight を返す。

経緯と実測は [#669](https://github.com/mokume-metal/mokume/issues/669) にある。

## 決定

### 1. 上の層の素の数値は、0–255 のディスプレイのエンコード値

```swift
fill(255, 204, 0)
fill(255, 204, 0, 128)   // 4 つ目は不透明度
fill(128)                // 1 つなら灰色
fill(128, 64)            // 2 つなら灰色と不透明度
```

手本 (Processing / p5) の既定の目盛りをそのまま採る。値は**エンコード値の 255 倍**として読み、入口で `/255` してから線形へ戻す — 変換点は ADR-0011 決定 3 の言う入口の 1 箇所のままである。

引数の型は `Float` 1 本にする。`Int` と `Float` の overload を並べると、`fill(1, 0, 0)` が 0–255 側・`fill(1.0, 0, 0)` が 0–1 側に落ちる、**リテラルの書き方で意味が変わる罠**が入る。

### 2. 読む規則は 1 本 — ラベルの無い素の数値は 0–255、ラベル付きは名前が尺度を名乗る

| 形 | 尺度 |
| --- | --- |
| `fill(255, 204, 0)` / `color(255, 204, 0)` | 0–255 のエンコード値 |
| `.display(red: 1, green: 0.8, blue: 0)` | 0–1 のエンコード値 |
| `color(hex: 0xFF6600)` | 24bit RGB |
| `color(hue: 200, saturation: 80, brightness: 90)` | 度 / % / % |

**尺度は 1 行を読めば決まる。** モード状態を見に行く必要が無いことが、この規則の要点である。

目盛りが 2 つ以上あること自体は避けられない — 作業空間の型の口 (`.display`) は 0–1 のまま残す必要があり (パラメータ・補間・Swift 側のコードが使う)、そこへ 0–255 を足すのだから、同居は前提である。ADR-0020 決定 1 が `noFill()` と `loadImage(from:)` の同居を**二層の設計**として説明したのと同じ構造で、上の層は手本に、下の層は Swift の慣行に従う。

### 3. alpha は、どの形でも 0–255

`color(hue: 200, saturation: 80, brightness: 90, alpha: 128)` のように、HSB の中でも alpha だけは 0–255 とする。1 回の呼び出しの中で単位が揃わないことは承知の上で採る。

理由は読み出し側にある。**`alpha(_:)` が返せる目盛りは 1 つしかない。** 形ごとに書く目盛りを変えると、`alpha(color(hue: 0, saturation: 0, brightness: 100, alpha: 50))` が 127.5 を返す — 書いた値と読んだ値が違う面になる。手本も一貫して 0–255 である。

### 4. `colorMode()` は持たない

決定 2 により尺度は行ごとに確定するので、モードを持つ理由が無い。0–1 で書きたいときは `.display(red:...)` がある。

**この決定で失うものを 1 つ名乗っておく。** p5 の HSB のコードをそのまま貼ると、`fill(200, 80, 90)` は 0–255 の RGB として読まれ、**黙って違う色になる**。どちらの解釈も正当な数値なので検知もできない。`colorMode()` の唯一の実利はここだったが、モード状態が持ち込む「値だけ見ても色が読めない」状態のほうが高くつくと判断した。

### 5. HSB は、量ごとの慣習に従う

hue は 0–360 の**度**、saturation と brightness は 0–100 の**百分率**とする (alpha は決定 3 により 0–255)。

手本が割れている (Processing 255/255/255・p5 360/100/100) ので、どちらかを写すのではなく、**その量について世の中が使っている単位**を採る — CSS・Figma・Photoshop・Illustrator・p5 が同じ組である。これはこのパッケージの既存の実践でもある: `rotate(_ radians: Float)` は引数名で単位を名乗っており、角度の回転はラジアン、色相は度という**量ごとの慣習**に従っている。

範囲外の扱いは、量ごとに違う。

| 量 | 範囲外 | なぜ |
| --- | --- | --- |
| hue | **巻き戻す** (`-40` → `320`、`380` → `20`) | 色相は円環なので、丸めても情報が増えない。`color(hue: Float(frameCount), …)` が剰余なしで書ける |
| saturation / brightness の上側 | **通す** | `brightness: 150` は表示範囲を超えた明るさ、`saturation: 120` は色域外の色として意味を持つ。ADR-0011 決定 1 が保っている情報を、入口で捨てない |
| saturation / brightness の下側 (負) | **0 へ丸める** | 負にすると最大成分が入れ替わり、**hue が 180° 反転する**。`hue: 200, brightness: -50` は画面では橙に見える。これは「値を保持する」ではなく「引数の意味が変わる」ので、決定 1 の対象ではない |

**非有限の値 (NaN・無限) は受け口で弾く。** 巻き戻しと区画の割り出しは、非有限の入力で trap する (`Int(h / 60)` が変換できない)。ADR-0020 決定 5 は「フレームごとに呼ばれるものは投げない」と言っており、trap は投げるより悪い。`color(hue: 360 * part / total, …)` の `total == 0` は実際に起きる。

### 6. 読み出しも面に置く。置き場はトップレベル

`red(_:)` `green(_:)` `blue(_:)` `alpha(_:)` `hue(_:)` `saturation(_:)` `brightness(_:)` を、**書いたのと同じ尺度**で返す口として置く。書く側だけを手本に寄せると、`get(x, y)` で読んだ色を人が読める値にする手立てが面に無い。

**`Sketch` のメソッドにしない。** `Sketch` は protocol で、描画の口はその extension にある。Swift では具象型の stored property が同名の protocol extension メンバを覆うので、`@Param var red: Float` を持つスケッチでは `red(c)` が呼べなくなる — **しかも `self.` を付けても property を指すので逃げられない**。同じ形は既にリポジトリにあり、`Sketches/KnobsAndValues.swift` の `@Param var tint` により、その型では `tint(_:)` が呼べない。トップレベル関数なら `mokume.red(c)` で逃げられる。色を作る `color(...)` も同じ層に置いて揃える。

返す値の契約を 3 つ決める。

- **アルファが 0 の色は、成分 0 を返す。** 乗算済みの表現からは元の色を復元できない (ADR-0011 決定 4 の代償)。0 で割らない
- **範囲外は丸めない。** `red(color(510, 0, 0))` は 510 を返す。「0–255」は目盛りであって上限ではない (決定 1・ADR-0011 決定 1)
- **NaN は 0 へ倒す。** 出口の `clampToStandardRange` が既に持っている規律に揃える

### 7. 射程は、手本が持つ形だけ

| 口 | 足す形 |
| --- | --- |
| `background` / `fill` / `stroke` / `tint` | 1・2・3・4 引数 |
| `ambient` / `emissive` / `ambientLight` | 1・3 引数 |
| `directionalLight` / `pointLight` / `spotLight` | 3 成分のみ |

**光に alpha 形と gray 形は足さない。** 手本に無く、`directionalLight(128, 64, 0, -1, 0)` の `64` が何を指すのかを説明できない。`set(x, y, color)` は手本も色の値を取るので、数値形を持たない。

決定 1 が言うのは「手本があれば従う」であって「手本を超えて揃える」ではない。**機械的に全部へ 4 形を配ると、手本に無い口が生える。**

### 8. 数値形は、上下の層の両方に置く

理由は検査ではなく、食い違いを作らないためである。`scripts/api-surface.py` の `check_forwarding` が見るのは名前と引数ラベルだけで型を持たないため、1 引数の gray 形は下の層に無くても**黙って通る**。それでも置くのは、**上で書けて下で書けない状態**を作らないためで、ADR-0020 決定 1 が「下の層が上の層の転送先である場合に限り、同じ名前・同じ引数ラベルを許す」と開けてある枠に収まる。

下の層には説明文を書かない (決定 4 のとおり、正本は上の層)。

### 9. 誤りの検知は、非有限の値だけにする

0–1 のつもりで書かれた値 (`fill(0.5, 0.5, 0.5)`) を推測で検知する仕組みは**持たない**。

検討した条件 (全成分が 0…1 で 1 つ以上が非整数) を実際の呼び出しに当てると、最も多い誤りである `fill(1, 0, 0)` (全部整数) と `fill(255, 204, 0, 0.5)` (成分が 0…1 でない) を**両方取り逃す**一方、正当なフェードイン (`fill(t * 255)` の t が小さいフレーム) を誤検知する。警告は 1 度しか鳴らさない約束なので、**誤検知が本当の誤りを黙らせる**。

代わりに非有限の値だけを受け口で弾き、警告して安全側へ倒す (ADR-0020 決定 5)。判定が曖昧にならず、`Surroundings` が既に同じ規律を持っている。

## 影響

- ADR-0011 が先送りした「利用者が色を指定する API の形」は、本 ADR で決着する。ADR-0011 の影響節はここを指すよう更新する
- 決定 5 は ADR-0020 決定 1 が想定していない状況 (手本が割れている) に踏み込む。**判定の規則を持たない決定は裁量に戻る**ので、ADR-0020 側に「割れている場合は、その量について広く使われている単位を採り、理由を ADR に書く」の段を足す改訂を随伴させる
- 決定 7 の射程で、公開の面はおよそ 30 宣言増える。決定 4 (説明文の正本は上の層) により、上の層の分には説明文が要る。例を書けば `scripts/check-examples.py` が全部を型検査する
- 決定 1 の `Float` 1 本という選択の帰結として、**`Int` の変数はそのまま渡せない** (`for i in 0..<255 { fill(i, 0, 0) }` は書けない)。既存の `circle(x, y, d)` 等も `Float` なので、ライブラリ全体では一貫している
- 決定 1・2 により、説明文の例と参照スケッチの綴りを 0–255 へ寄せる仕事が生じる ([#743](https://github.com/mokume-metal/mokume/issues/743))。説明文は生成される API 一覧を通してエージェントの書くコードに届くので、**入門経路がどちらの綴りかは面の設計の一部である**
- `LinearRGBA` で色を作る口が増え、同じ `red` という語で 3 つの目盛りが並ぶ。**降ろすのではなく、名前が目盛りを名乗る形に改めた** — `opaque` は不透明であることしか言っておらず、読み手が知りたい「どの目盛りか」を名乗っていなかった ([#744](https://github.com/mokume-metal/mokume/issues/744))。線形の値を直に置く用途は光の強さに実在する (`ambientLight(.linear(red: 0.35, green: 0.35, blue: 0.35))`・1 を超える明るさ) ので、口そのものは要る

  | 口 | `red` の意味 |
  | --- | --- |
  | `linear(red:green:blue:)` | 線形の 0–1 (1 を超えてよい) |
  | `display(red:green:blue:)` | エンコード値の 0–1 |
  | `color(_:_:_:)` | エンコード値の 0–255 |
- 決定 6 の読み出しが入ると、つまみの窓が出す 16 進 (線形の値をそのまま 255 倍している) との食い違いが表に出る ([#746](https://github.com/mokume-metal/mokume/issues/746))
- **機械で見られるのは決定 8 の一部だけである。** `make api` が見るのは名前と引数ラベルの対称性で、目盛り (決定 1〜3)・範囲外の扱い (決定 5)・置き場の理由 (決定 6)・射程 (決定 7) はシグネチャから判定できない。ADR-0020 影響節の言う「機械で見つけられない決定は、書いても効かない」がここにも当たるので、**守るのは書く人とレビューである**
