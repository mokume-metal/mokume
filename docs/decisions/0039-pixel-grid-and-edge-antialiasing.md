# ADR-0039: 画素の格子は「塗りは角、線は中心」。縁の AA は足す日の形だけを置く

## 文脈

### 整数の座標をどの画素に落とすかは、どの ADR にも無い

いまの約束は `Canvas` の型の説明 (「座標の約束」) にあり、**整数の座標は画素の中心に落ちる**と書いている。平面は `Canvas.makeProjection`、立体は `Camera.clipAdjustment` が、投影に半画素のずらしを掛けてこれを実装している。理由は線にある。`x = 10` に引いた太さ 1 の線は 10 から 11 までを覆い、中心 10.5 の画素 1 列だけがはっきり塗られる。

この約束のままだと、整数に置いた四角の縁が画素の中心を通って滲む。そこで**一部だけ半画素戻している**。

- 字形と画像は「画素の境目に合わせた四角」として戻している (`appendPixelAlignedQuad`)
- 基本図形を距離関数で描く経路では、`rect` の塗りだけを戻している ([#772](https://github.com/mokume-metal/mokume/issues/772) の `fillShift`)
- 三角形で描く経路 (立体・`beginShape`・絵や断片を持つ `rect`) は戻していない

戻す場所が経路ごとに散っているので、**同じ図形が経路によって半画素ずれる**。回すか小数の座標に置くまでは現れない。軸に沿って整数に置いた形では、三角形の側でもラスタライザの境界の規則が同じ画素を選ぶからである。既存の検査 (`planeAtZeroDepthMatchesRect`) はその場合だけを見ていた。

### ADR-0021 決定 1 の「一致」が、何の一致かを書いていなかった

[ADR-0021](0021-solid-space-and-frame-assembly.md) 決定 1 は、要件として「奥行き 0 に置いた立体は、同じ座標に描いた平面の図形と一致する」と書いている。回した形でこれが破れていた ([#905](https://github.com/mokume-metal/mokume/issues/905))。

#905 ははじめ、これを**バイト一致**と読んだ。そのうえで、立体に縁の AA が無いことを原因と見て、描画先を多標本 (MSAA) にする方式を決めかけた。ところが決定 1 が「破れたとき」に挙げる害は「平面と立体を重ねた絵が**ずれる・上下反転する**」で、縁の濃さの話ではない。**ずれは実際にあった**。面積だけを見て重心を見ていなかったので、見落としていた。

### 測ったこと (2026-09-14・Apple M3 Max)

**格子。** #905 の再現 (64×64 の面に、回した `plane(30, 20)` と `rect(-15, -10, 30, 20)`) と、決定 2 の約束を試作に組んだものを比べた。重心は線形の被覆で重みを付けて出した。

| | 違う画素 / 最大差 | 縁を 50% で白黒にしたときの不一致 | 重心 |
| --- | --- | ---: | --- |
| いまの約束 | 107 / 255 | 45 | `plane` (32.5, 32.5) / `rect` (32.0, 32.0) |
| 決定 2 の約束 | 102 / 184 | **0** | 両方 (32.0, 32.0) |

- 回した `rect` と、同じ `rect` に `texture()` を足したもの (三角形の経路) は、いまの約束で白黒の不一致が 31、決定 2 の約束で 0 だった
- 決定 2 の約束で、次のものはいまの約束と**バイト一致**した: `rect` (整数・小数・回転・輪郭つき)、絵を貼った `rect`、画像、文字、線 (水平・斜め・縦の太さ 3)、点、輪郭だけの形。例外は太さ 2 の斜めの線など 2 例で、3 画素に 1 階調の丸めの差が出た
- 動いたのは円・多角形・`triangle`・立体の**塗り**だけで、重心が (−0.5, −0.5) 動いた。AA の無い三角形は、動きが画素に量子化される
- 台帳 (`scene-ledger.txt`) は 43 行のうち 32 行が動いた。動かなかった 11 行は、線・端点・角・画像・文字・`rect` だけの絵である

**縁の AA。** 描画先を 4x MSAA にする試作で測った。

- **MSAA の下でも、距離関数の経路の解析的な被覆率は変わらない。** 1 標本と 4 標本の絵がバイト一致した。断片は画素に 1 回しか走らず、覆う四角は形の外に余白を持つので、被覆率が標本の数と掛け合わさらない
- **MSAA だけでは、形と三角形の縁は揃わない。** 回した組で 94 画素が違い、最大差は 107 だった (`rect` の半画素戻しを外した組)。揃えるには、形の側も被覆率を捨てて標本マスクを出す必要がある。そうすると揃うが、円と線の縁は、8 倍の面で描いた正解に対する誤差が RMSE 0.013 → 0.083・最大 0.11 → 0.28 に増え、中間値は 249 段 → 3 段になる
- GPU 時間の中央値 (1920×1080・release・240 フレーム):

| 絵 | 1 標本 | 4x・形は解析的 | 4x・形は標本ごとに断片 | 4x・形は標本マスクで塗りと輪郭を 2 回 |
| --- | ---: | ---: | ---: | ---: |
| 寸法違いの円 4000 個・輪郭あり | 0.121 ms | 0.158 ms | 0.309 ms | 0.436 ms |
| 画面を覆う円と矩形 200 個 | 0.61 ms | 0.77 ms | 1.60 ms | 2.03 ms |
| 葉 2000 個 (三角形の経路) | 0.714 ms | 0.927 ms | 0.927 ms | 0.927 ms |

- **MSAA の面の置き方** (1920×1080・rgba16Float・小さな三角形 40000 枚と画面を覆う半透明 40 枚の使い捨てのスクリプト):

| 置き方 | GPU 時間の中央値 | 面の確保 |
| --- | ---: | ---: |
| 1 標本・描き足し | 0.18 ms | 16.1 MiB |
| 4x を常駐させて描き足す | 0.57 ms | 80.3 MiB |
| 4x を memoryless の一時面にし、毎回塗り直す | 0.53 ms | 16.1 MiB |
| 4x を一時面にし、正本を描き戻してから描き足す | 0.54〜0.57 ms | 32.1 MiB |

- この世代の GPU は 8x を持たない (`supportsTextureSampleCount(8) == false`)

計測の詳細と試作の差分は [#1137](https://github.com/mokume-metal/mokume/issues/1137) と [#905](https://github.com/mokume-metal/mokume/issues/905) のコメントにある。

### 先例

公式ドキュメントとソースで確かめた。

| 観点 | 先例 |
| --- | --- |
| 整数の座標 | **角が主流。** Metal・Direct3D 10 以降・OpenGL・HTML Canvas・Skia・Java2D・Godot・Processing P2D がそうである。整数を中心にしたのは Direct3D 9 で、Direct3D 10 は「テクセルの座標系と揃い、1:1 の描画が単純になる」ことを理由に角へ移した |
| くっきりさせる手当て | **線の側だけを寄せる。** Java2D (Processing の既定の描画) は、AA が有効で `STROKE_PURE` でないとき、ストロークだけを `floor + 0.5` に寄せ、塗りは寄せない。Godot は、奇数幅の線に 0.5 足すよう利用者に案内している |
| 縁の AA の混成 | **Skia Graphite** は rect・rrect・線・円弧を解析的に描き、それ以外のパスをアトラスか MSAA に回す。解析的に描く狙いを「MSAA を起こさずに済ませる」とコードに書いている。**Flutter Impeller** は全体を 4x MSAA にしたうえで、基本図形を SDF で描く |
| MSAA と描き足し | **新しい実装ほど「正本は 1 標本、MSAA の面は使い捨て」。** Skia Graphite はパスの頭で resolve 済みを描き戻す。Flutter Impeller は MSAA の面を memoryless にし、大きな MSAA の面を store / load するより速く省メモリだとコメントに書いている。Bevy (Nannou 0.20) と Processing の FBO 層も、前の絵を毎回描き戻す |
| 2D と 3D の一致 | Processing・p5.js・openFrameworks・Nannou は、2D と 3D を同じ機構で描き、z = 0 の面が 1:1 になるカメラを持つ。一致を明文の要件にしている資料は見つからなかった |

## 決定

### 1. ADR-0021 決定 1 の「一致」は、幾何の一致である

- **一致するのは位置・大きさ・向きである。** 検査では、縁を 50% の被覆で白黒にした形と、線形の被覆で重みを付けた重心を比べる
- **縁の AA の掛け方は射程の外に置く。** 解析的な被覆率・標本・AA 無しのどれで縁を塗るかによって、縁の中間値は違ってよい
- 軸に沿って整数に置いた形は、縁が画素の境目に乗る (決定 2)。AA が働かないので、**バイトで一致する**

> 破れたとき: 2D と 3D を重ねた絵、あるいは経路の違う同じ図形が、画素の数分の 1 だけずれる。縁の濃さの違いと区別がつかないので、バイト比較の検査では見分けられない。

### 2. 画素の格子は「塗りは角、線は中心」

- **塗りの縁は、整数の座標で画素の境目に乗る** (整数の座標 = 画素の角)。`rect(10, 20, 4, 8)` は、ちょうど 4×8 画素を塗る。円・楕円・多角形・立体の塗り・字形・画像も、同じ約束に従う
- **線・輪郭・点の中心は、整数の座標で画素の中心に乗る。** `x = 10` に引いた太さ 1 の線は、1 列の画素をちょうど塗る
- **投影は Metal の約束 (整数 = 画素の角) のままにする。** 線・輪郭・点の側を画面で +0.5 画素寄せる。丸めずに寄せるので、小数の座標の精度は落ちない
- **形の経路・三角形の経路・畳み込み・保持した形・立体のどれで描いても、同じ約束に従う。** 経路ごとの半画素の戻しは持たない。寄せる理由は「線である」ことだけにする

> 破れたとき: 経路によって同じ図形が半画素ずれる。回すか小数の座標に置くまでは現れず、`texture()` を 1 行足しただけで図形が動く。

### 3. 縁の AA はいまは足さない。足す日の形だけを置く

三角形の経路 (立体・任意形状・絵や断片を持つ基本図形) の縁に AA を足すことは、[ADR-0022](0022-production-track.md) 決定 6 の実需を待つ。決定 1 を幾何と読むと、経路をまたいで縁の AA を揃えることを要求する規範は無い。

足す日の形:

| 項目 | 形 | 理由 |
| --- | --- | --- |
| 方式 | **基本図形は解析的な被覆率のまま。三角形を含む描き切りだけ 4x MSAA** | 形の側も標本にすると、円と線の縁の誤差が 6.6 倍、形の多い絵の GPU 時間が 2.6 倍になる。Skia Graphite・Flutter Impeller と同じ混成である |
| MSAA の面 | **memoryless の一時面。正本は 1 標本の面**のまま。描き足す描き切りは、パスの頭で正本を描き戻す | 常駐させる形と速さが変わらず、確保は 80 MiB → 16 MiB (描き足すときは 32 MiB) に減る。描き足し・`pixels` への書き込み・効果の書き戻しは正本を読み書きするので、今の形のまま動く |
| MSAA を起こす条件 | **描き切りの列に三角形の経路があるときだけ** | 形の画素は MSAA でも変わらない (測ったこと) ので、起こすかどうかで絵が割れない。数式の図形だけの絵は費用ゼロのまま |
| 標本数 | 4 | この世代の GPU は 8 を持たない |
| 決定論 | [ADR-0025](0025-determinism-levels.md) 決定 1 の水準 3 を保つ | 同じ機械の resolve は決定的である。描き戻しも、同じ値を全標本に置くので決定的である |
| 代償 | 三角形の経路の多い絵で GPU 時間 1.3 倍。描き足すときは 1 標本の写しを 1 枚持つ | 測ったこと |
| 残る論点 | 1 フレームを分けて描き切るとき、奥行きをどう引き継ぐか (多標本の奥行きを常駐させるか、resolve した奥行きを描き戻すか)。下地を読む混ぜ方は標本ごとに走る | 未測 |

足すときは、この ADR を改訂して、表を決定の本文へ移す。

> 破れたとき (足す日にこの形から外れたとき): 常駐させればメモリを払う。形も標本にすれば、縁の質と速さを払う。起こす条件を持たなければ、数式の図形だけの絵の速さを払う。

### 4. 決定論の水準は変わらない

- 決定 2 の約束の変更は、水準 3 (同じ機械の画素でバイト一致) を保つ。台帳は一度だけ一斉に動く
- 決定 3 の形で縁の AA を足す日も、水準 3 を保つ

### 5. 塗りと輪郭を両方持つ形の 1 画素は、4 つの面積の和で読む

距離関数の経路は、塗りと輪郭を両方持つ基本図形 (`rect` / `square` / `ellipse` / `circle` / `arc`) を 1 つの断片で描く。その 1 画素を、**混ぜ方によらず次の読みで約束する** ([#1867](https://github.com/mokume-metal/mokume/issues/1867) 決定 1)。

- 画素の中の塗りの被覆を `f`・輪郭の帯の被覆を `s`・その重なりを `o` とし、画素を 4 つの面積に分ける: 塗りだけ `f − o`・重なり `o`・帯だけ `s − o`・どちらでもない `1 − (f + s − o)`
- それぞれの面積を被覆 1 で混ぜた色 (重なりは塗りの上に輪郭を置いた色) を、面積で足し合わせる。どちらでもない面積に入るのは、形の掛からない所に残る色で、**どの混ぜ方でも下地 `D`** である (置き換える混ぜ方も、当初は透明 (0) だった。下の改訂 2026-10-29・[#3111](https://github.com/mokume-metal/mokume/issues/3111))
- 丸ごと塗りだけ・重なり・帯だけのどれかに入る画素では、塗りだけの形の上に輪郭だけの形を重ねた絵と同じになる。違ってよいのは縁と継ぎ目の画素だけで、そこは継ぎ目で下地を漏らさない (下の「継ぎ目の重なり」)

混ぜ方ごとの解き方 (S・F は乗算済みの輪郭と塗りの色・α は輪郭の不透明度):

| 混ぜ方 | 置く色 | 状態 |
| --- | --- | --- |
| 重ねる (`.blend`) | `S·s + F·(f − α·o)` (これに固定機能のブレンドが下地 `D` を、透けた割合だけ足す) | 継ぎ目の割り戻し (下の「継ぎ目の重なり」) が、この読みを over で解いた式と項ごとに一致する。絵は動かない |
| 置き換える (`.replace`) | `S·s + F·(f − o) + D·(1 − (f + s − o))` | 重なりには後に置いた輪郭だけが入る。どちらでもない面積には下地 `D` を残す (縁の画素は、形が掛かる面積だけが置き換わり、残りに下地が残る。当初は透明 0 で、縁の画素が下地ごと置き換わった。下の改訂 2026-10-29)。形が丸ごと掛かる画素 (どちらでもない面積 0) は下地に触れず置き換わる。**部品ごとに置き換わり、帯では輪郭だけが残る** — 三角形の経路と、塗りだけ → 輪郭だけの順に分けて描いた絵と同じ ([#1819](https://github.com/mokume-metal/mokume/issues/1819)・下の「置き換える列の代償」) |
| 下地を読む 8 つ | 塗りだけ・重なり・帯だけを、それぞれ被覆 1 で下地と混ぜた色 (`mokume_composite`・重なりは塗りを混ぜた結果の上に輪郭を混ぜる) の面積の和に、どちらでもない面積の下地 `D` を足す | 塗りの縁が帯に掛かる画素だけを 4 つに分け、ほかの画素は被覆率を掛けて塗り → 輪郭の順に混ぜる (同じ色になる)。`.add` / `.subtract` は、不透明な地の上では分けて重ねた絵と同じ色になる (下の改訂 2026-10-06・[#1818](https://github.com/mokume-metal/mokume/issues/1818)) |

面積の元になる輪郭の被覆率 `s` は、**塗りの有無・混ぜ方によらず、輪郭だけの形と 1/255 以内で同じに取る** ([#1867](https://github.com/mokume-metal/mokume/issues/1867) 決定 2)。楕円の輪郭を塗りの距離場から 1 次の近似でずらすのは、その誤差が 1/255 に収まる楕円だけにする ([#1820](https://github.com/mokume-metal/mokume/issues/1820)・下の「楕円の輪郭の近似」)。

採らなかった読み:

- **分けて重ねた絵と同じ** ([#1643](https://github.com/mokume-metal/mokume/issues/1643) の直しのまま): 線形でない混ぜ方で継ぎ目の漏れが残る (太さ 1 で最悪 24%)
- **置き換えは「形の単位」で置く** (塗りと輪郭を先に重ねてから置き、三角形の経路もそれに揃える): 三角形の経路は塗りと輪郭が別々の三角形なので、別の描き場所か順序の仕掛けが要り、費用が大きい。利用者が分けて描いた絵とも揃わない
- **経路の間の食い違いを約束の内にする**: 決定 1 は縁の中間値だけを射程の外に置く。帯の内側の色は縁の中間値ではない

> 破れたとき: 同じ形が、混ぜ方や `shader()` の有無で、帯や重なりの画素に違う色を置く。`.replace` では、半透明の輪郭の帯に塗りが透け、透明な描き場所では帯の不透明度が輪郭の不透明度を越える。

#### 継ぎ目の重なり

形の経路は、塗りと輪郭の被覆率を 1 つの断片で出す。2 つを互いに無関係な重なりとして掛けると、帯が塗りの縁に接する側の画素で下地が透ける。決定 2 で輪郭を画面で半画素寄せるので、塗りと帯の中心が半画素違い、片側に必ず現れる。そこで、画素の中で塗りと帯が重なる面積 `o` を、縁が画素の幅では平行とみなして `min(f, 外縁) − min(f, 内縁)` と見積もる (平行な半平面どうしの共通部分の被覆率は、小さいほうになる)。

塗りと輪郭を先に重ねてから 1 回置く列 (重ねる・置き換える) は、塗りの被覆率を割り戻して 4 つの面積の和を解く。重ねる列で塗りが見える重みは「帯の外の塗りは全部、帯の下の塗りは輪郭が透ける分だけ」(`f − α·o`) で、それを輪郭 over 塗りの式で割り戻した `(f − α·o) / (1 − α·s)` を塗りの被覆率とする。置き換える列の重みは `f − o` である (`mokume_formPaint` の `replacing`)。

**割り戻すのは、先に重ねる列だけである。** 割り戻しは「輪郭を塗りの上に重ねる」前提の式で、下地を読む列に持ち込むと、不透明な輪郭の帯の内側半分で分母 (帯が透ける割合) が 0 になって塗りが消え、加算で塗りが足されなかった ([#1643](https://github.com/mokume-metal/mokume/issues/1643))。下地を読む列は割り戻す前の被覆率と `o` を受け取り、4 つの面積をそれぞれ下地と混ぜて足す (下の改訂 2026-10-06)。楕円の輪郭も常に輪郭の位置で式を解き直す。

三角形の経路は縁に AA を持たないので、継ぎ目のこの漏れは起きない (下の改訂 2026-10-06 で測った。立体は測っていない)。漏れるのは、距離関数の経路で塗りだけの形と輪郭だけの形を 2 回に分けて描いた絵である。

#### 置き換える列の代償

- 不透明な輪郭 (α = 1) では、重ねる列と置き換える列の重みが同じになり、絵は 1 ビットも動かない
- 帯に丸ごと入る画素は、`rect` / `circle` / `ellipse` / `arc`・輪郭の不透明度 255 / 128 / 0・黒と透明の地で、三角形の経路とも分けて描いた絵とも 1/255 以内になる (`FormShapeTests.replaceModeKeepsOnlyTheStrokeInTheBand`)
- **`.replace` で塗りと半透明の輪郭を重ねていた絵は、帯の下の塗りが見えなくなる。** 帯の画素の不透明度は輪郭の不透明度になり、輪郭の不透明度 0 では帯が透明に抜ける。三角形の経路と、利用者が分けて描いた絵はもとからそう描いていた

#### 楕円の輪郭の近似は、誤差が 1/255 に収まる楕円だけに使う

塗りと輪郭を両方持つ楕円では、輪郭の距離場を塗りの距離場から 1 次の近似でずらして作ると、式を 1 回で済ませられる (面を覆う大きな円 200 個の絵で、式を 2 回解くと GPU 時間が 21% 増えた)。**扇形には使えない** — 近似は勾配が形の内でも外でも外向きであることに頼るが、扇形の直線の辺は内側で勾配が扇の中を向く。扇形は式を 2 回解く。

**誤差を決めるのは形の比ではなく、輪郭の内縁の曲率半径 `R = 短半径² / 長半径 − 太さの半分` (画素) である。** 距離場を `s` (画面で半画素・長さ 0.71 画素) だけずらす 1 次の近似が落とすのは 2 次の項で、円では被覆率の誤差が `0.25 / R` ほどになる。1/255 (0.0039) に収めるには `R` が 64 画素ほど要る。円でない楕円は、距離場が真の距離ではないので、長さ 1 の向きではなく距離場そのものの勾配で足す (測った値と理由は経緯にある)。

**決定。** 近似は、誤差の見積もりが `1/512` (表示の 1 段の半分) に収まる楕円だけに使い、ほかは式を輪郭の位置で解き直す。

- 見積もりは `|s| / (2R) · (|s| / σmin + (σmax / σmin − σmin / σmax) / 2)`。σmin・σmax は「描く画素 → 形自身の座標」の行列の特異値で、回す・一様に拡大するだけなら σmin = σmax になり、見積もりは `0.25 / R` (画素) に戻る。縦横で違う拡大・剪断では、向きによって描く画素の大きさが違うので、小さいほうで割って保守側に倒し、ずらしで法線が回る項を足す。描く細かさを下げた面は描く画素が粗いので、近似を使える範囲が広がる。**この見積もりは 1 次の項までで、厳密な上限ではない。** CPU の float64 のモデルで置き方を約 15,000 組探すと、実測は見積もりの最大 1.04〜1.06 倍だった (半径 153.8・太さの半分 1.12 の円を、回して一様に 0.21 倍・細かさ 0.25 で置くと、見積もり 0.00195 に対して実測 0.00206)。1/255 の半分を余裕に取ってあるので、見積もりが最大で 6% ほど甘くても 1/255 の内側に収まる (その最悪の例で 1/255 の 0.53 倍)
- 回す・一様に拡大するだけなら、内縁の曲率半径が 128 画素ほど要る。半径 29・太さ 7 の円 (25.5) や、84×26 (0.52) は解き直す。直径 700 の円 (346) や、1060×530・太さ 7 (129) は近似のまま残る。内縁が無い (`R ≤ 0`) 楕円・大きさ 0 の楕円は常に解き直す
- 近似を使う楕円は、円は法線でずらし (距離場が真の距離)、円でない楕円は距離場そのものの勾配でずらす。縁から遠い所 (輪郭の帯が届かない) では勾配が膨らむので、足す量は、法線で足した量からずらしの 2 成分の絶対値の和の 2 倍 (長さの 2〜2√2 倍) までしか離さない
- 判定は頂点関数で楕円ごとに 1 度だけ出し、断片へ `[[flat]]` で渡す。判定を断片で出す案は、寸法違いの円 4000 個 (塗り + 輪郭) の GPU 時間が頂点で出す案の +14% に対して +31% になった (下の費用の表とは別の、フレームの間を空けて投入した計測。release・1920×1080)
- 近似を使う楕円の誤差は、実測で最大 0.5/255 (内縁の曲率半径 128〜500 画素の円・楕円を、軸の向き・斜め・縦横で違う拡大・細かさ 0.5 で置いた)。解き直す楕円は、塗りを外した絵と 1 ビットも違わない。許す範囲を 1/255 の半分に取ったのは、半精度の 1 ulp (0.0005) の差が両側に出るぶん実測が見積もりより大きくなるためで、見積もりと実測はほぼ等しい (最悪で実測が 1.06 倍)

**費用。** release・1920×1080・Apple M3 Max (macOS 27.0.1) で、1 フレームの GPU 時間 (`MTL4CommitFeedback` の `gpuStartTime` / `gpuEndTime`) の中央値を、近似をすべての楕円に使っていた版と並べた。塗り + 輪郭の円・楕円で、`.blend` と `.replace` はほぼ同じ:

| 場面 | すべての楕円に近似 | 近似を絞った後 | 差 |
| --- | ---: | ---: | ---: |
| 大きな円 200 個 (直径 700・太さ 7) | 2.54 ms | 2.78 ms | +9.5% (別の 4 巡の計測では +6%) |
| 細長い楕円 200 個 (長さ 300〜600・太さ 7) | 0.099 ms | 0.118 ms | +19% |
| 寸法違いの円 4000 個 (直径 1〜30・太さ 1) | 0.070 ms | 0.082 ms | +17% |

大きな円は近似のまま残るが、塗りと輪郭を先に重ねる断片が解き直す側の式も抱えるので、わずかに増える。小さな円と細長い楕円は式を 2 回解くので、増えるのは 2 回目の費用である。**費用を払うのは小さい・細長い楕円で、面を覆う大きな円には払わない** — 式を 2 回解くと大きな円 200 個で +21% になる費用は払わない。

採らなかった案:

- **すべて解き直す**: 大きな円 200 個で GPU 時間が 21% 増える。近似を残して誤差を許す範囲に収めれば、払わずに済む
- **近似を残し、誤差の上限を説明に書くだけ**: 同じ楕円の輪郭が入口によって動くことを約束の内に置くことになり、決定 5 の「10 の混ぜ方で 1 画素の読みが 1 つ」を満たさない
- **列の旗 (function constant) で近似の有無を分ける**: 小さな楕円が 1 個混ざった列が全部解き直す側に倒れ、大きな円の費用が戻る。列は旗で切らない約束 (細い塗りの `kFormHasThinFill` と同じ) とも合わない。**計測していない**

> 破れたとき: 同じ楕円の輪郭の被覆率が、塗りの有無・混ぜ方で 1/255 を越えて動く。重ねる列と置き換える列で、内縁の曲率半径が小さい楕円の内縁が塗りを足すと動く。

#### 改訂 (2026-10-06) — 下地を読む 8 つも、4 つの面積に分けて混ぜる

決定 5 の読みを、下地を読む混ぜ方の列 (`mokume_formFragment`) で解いた ([#1818](https://github.com/mokume-metal/mokume/issues/1818)・[#1867](https://github.com/mokume-metal/mokume/issues/1867) 決定 1)。

**当初は**、下地を読む列は被覆率を掛けた塗りと輪郭を順に下地と混ぜ、塗りだけの形の上に輪郭だけの形を重ねたのと同じ絵を出していた (経緯の改訂 2026-09-29)。被覆率について線形でない 6 つ (`.lightest` / `.screen` / `.darkest` / `.multiply` / `.difference` / `.exclusion`) では、塗りと帯が接する継ぎ目で下地が透けた。

**決定。**

- 塗りだけ `f − o`・重なり `o`・帯だけ `s − o` を、それぞれ被覆 1 で下地と混ぜ (重なりは塗りを混ぜた結果の上に輪郭を混ぜる)、どちらでもない `1 − (f + s − o)` の下地と面積で足す
- 4 つに分けるのは、`0 < f < 1` かつ `s > 0` の画素 (継ぎ目と、帯の下の塗りの縁) だけである。`mokume_composite` は上の色の被覆率について線形 (`mix(下地, 被覆 1 で混ぜた色, 被覆率)`) なので、片方しか掛からない画素と、塗りに丸ごと覆われた画素 (`o = s`) では、4 つの面積の和が被覆率を掛けて順に混ぜる式と同じになる。そこは順に混ぜる式のまま出すので、塗りだけ・輪郭だけの形と丸ごと覆われた画素の絵は 1 ビットも動かない (直す前後の作業空間の値で確かめた)
- 分ける画素で `mokume_composite` を最大 3 回呼ぶ (直す前は 2 回)。どちらでもない面積は下地そのままなので呼ばない
- `.add` / `.subtract` も同じ式で描く。不透明な地の上では、順に混ぜる式と丸めの差 (最大 1e-3) しか違わない。**透けた地では違う** — 順に混ぜる式は塗りと帯を画素の中で無関係に散らばったものとして不透明度を重ねる (`1 − (1 − α·s)(1 − a_F·f)`) ので、継ぎ目の不透明度が面積と違っていた (透明な地の太さ 1 で最大 0.22)。`.add` は色が足し算のままなので不透明度だけが変わるが、`.subtract` の色は途中の下地の不透明度に依る (`d + X·(1 − 2·α_d)`) ので、色と不透明度の両方が変わる。透明な地に不透明な塗りと輪郭が半分ずつ掛かる継ぎ目 (`f = s = 0.5`・`o = 0`) は、順に混ぜると色 `0.5·F`・不透明度 0.75、4 つの面積では色 `0.5·F + 0.5·S`・不透明度 1 になる。**当初の決定 5 の表は「`.add` / `.subtract` は被覆率について線形なので、いまの別々に混ぜる式で既にこの読みと同じ絵になる」と書いていた** — 不透明な地に限れば正しかった
- `.difference` / `.exclusion` で同じ色の塗りと輪郭を重ねた所は、打ち消し合って地に近い色になる (黒地に白なら、重なりは塗りの白の上で輪郭の白と差を取って黒)。重なりの色は塗りを混ぜた上に輪郭を混ぜる色で、分けて重ねた絵と同じ — 約束どおりで、この改訂が直したのは継ぎ目の漏れだけである。継ぎ目の漏れを数えるときは、塗りだけ・重なり・帯だけの 3 色の範囲の外に地が来る組を選ぶ (下の「測ったこと」)
- `.blend` と `.replace` の式と絵は動かない

**測ったこと。** `PixelGridTests.fillAndStrokeLeaveNoSeam` の置き方 (同じ色の塗りと輪郭の円を、6 通りの小数の位置に置く) で、塗り ∪ 帯に丸ごと入る画素に地が混ざる割合の最悪 (平均) を数えた。地と色は、塗りだけ・重なり・帯だけに丸ごと入る画素の 3 色の範囲の外に地が来るように、混ぜ方ごとに選んだ (黒地に白では、加算の重なりは 2・差と除外の重なりは 0 になり、地との差が読めない):

| 混ぜ方 | 太さ 1 (直す前) | 太さ 1 (直した後) | 太さ 2 (直す前) | 太さ 2 (直した後) |
| --- | --- | --- | --- | --- |
| `.blend` | 3.6% | 3.6% | 0.05% | 0.05% |
| `.lightest` / `.screen` / `.darkest` / `.multiply` / `.exclusion` | 24.4% (平均 0.45%) | 3.6% (平均 0.008%) | 12.2% (平均 0.21%) | 0.05% |
| `.difference` | 14.0% | 3.5% | 2.0% | 0 |
| `.add` / `.subtract` | 3.5% | 3.5% | 0 | 0 |
| 三角形の経路 (`shader()` を付ける・9 つとも) | 0 | 0 | 0 | 0 |

検査 (`PixelGridTests.fillAndStrokeLeaveNoSeam`) の上限は、太さ 1 で最悪 8%・太さ 2 以上で 1%・平均 0.1% に取る。太さ 2 以上を 2% にすると、`.difference` の直す前 (1.98%) が緑のまま通る。

**三角形の経路は、継ぎ目で漏れない。** 縁に AA を持たない (決定 3) ので、画素は中心が塗りか帯に入るかで丸ごと塗られる。太さ 3 も 9 つとも 0 だった。経緯の改訂 2026-09-14 の「三角形の経路と立体は AA を持たないので、この漏れは起きない」が三角形の経路について正しく、改訂 2026-09-29 の前置きの「分けて重ねた絵 (三角形の経路も同じ) が持つ継ぎ目の漏れ」は誤りだった。漏れるのは、距離関数の経路で塗りだけの形と輪郭だけの形を 2 回に分けて描いた絵で、`.blend` でも太さ 1 で 24.4%・太さ 2 で 12.2% 漏れる。立体は測っていない。

**残る漏れは形による。** 重なり `o` は縁を平行な半平面とみなす見積もりなので、円以外の形・角・細い塗りでは外れうる。検査が数えるのは円の継ぎ目 (`fillAndStrokeLeaveNoSeam`) と `rect` の縁の重み (`FormShapeTests.compositeModesWeighEdgePixelsByArea`) だけなので、ほかの形を 1 度測った。8 倍の面に塗りだけと (画面で半画素寄せた) 輪郭だけを描いた和集合で丸ごと覆われる画素の、地が混ざる割合の最悪 (4 通りの位置と回転。`.blend` と `.lightest` の差は 0.05% 以内):

| 楕円 30×6 | 3.0% | 6.4% | 0.6% |
| 扇 (直径 30・0.4〜4.1 rad、要と弧と半径の角を含む) | 0.15% | 3.3% | 0.05% |

**費用を払うのは、塗りの縁が帯に掛かる画素の多い、小さい・細い形である。** 面を覆う大きな形は、ほとんどの画素が片方しか掛からないので 1 回で返り、ほぼ払わない。分ける画素だけの枝に `mokume_composite` を 3 つ置く形は、分ける画素と分けない画素が同じ SIMD の組に混ざると別々の口が順に走り、小さな円 4000 個で +32% になった。呼ぶ口を共有し、片方しか掛からない画素を先に 1 回で返す形にした (口を共有しても先に返さないと、直径 700 の円 200 個が +10% になった)。

台帳は動かない (下地を読む混ぜ方で、塗りと輪郭を両方持つ形を描く行が無い)。

採らなかった案:

- **`.add` / `.subtract` だけ、順に混ぜる式のまま残す**: 不透明な地では同じ色で、呼ぶ回数も増えない。しかし透けた地の継ぎ目で不透明度が漏れ、決定 5 の「混ぜ方によらず」を満たさない

> 破れたとき: 下地を読む線形でない混ぜ方で、塗りと輪郭が接する継ぎ目に下地が透け、輪郭の内側に細い筋が出る。

#### 改訂 (2026-10-16) — 帯の穴が 1 画素より細い・潰れた形は、内縁を両縁で数える

1 画素より細い塗りに輪郭を付けた形の継ぎ目の漏れ (上の改訂 2026-10-06 の「残る漏れ」) を直した ([#2186](https://github.com/mokume-metal/mokume/issues/2186))。

**当初は**、輪郭の帯の被覆を「外縁の被覆 − 内縁の被覆」とし、内縁 (帯の穴) を縁 1 本の距離場で数えていた。縁 1 本では穴の向こう側の縁を見られないので、穴が潰れている (線幅が形より太い) か 1 画素より細いと、内縁の被覆が実際の穴より大きく出て、帯が欠ける。`rect` は負の半幅が縁の渡し (1 画素) の内に残って内縁の被覆が 0 にならず、楕円は近似の距離場 (`mokume_ellipseField`) が長軸の上で先端までの距離を返すので、内縁が長軸の近くを丸ごと覆った。

**測ったこと。** `mokume_formPaint` の `rect` と楕円を float64 で写した CPU の模型と GPU の検査で、内縁だけを直す・`o` だけを直す・両方を、直す前と比べた。**漏れは全部が内縁の口で、`o` の見積もりの分は 0 だった** — 内縁だけを直すと 0 になり、`o` だけを直しても減らない。模型で幅 0.2〜0.9 の細い `rect` と楕円に太さ 0.5〜3 の輪郭を付け、置き方を 30 通りずつ取っても、内縁を直した後に残る漏れは 0 だった。和集合は真の幾何で取る (楕円は真の距離。画素の四角を 1/8 画素広げた所を 9×9 の標本と、4 辺の 201 点ずつで見る。9×9 だけでは尖った細い穴の端が標本の間をすり抜け、穴の掛かる画素を丸ごと覆われると数えて 3.6%・6.6% の残りに見えた)。改訂 2026-10-06 の測り方 (8 倍の面に輪郭だけを描いた絵から和集合を取る) は、輪郭だけの絵そのものが同じ口で欠けるので、欠けた所を数えられなかった。直す前後の最悪 (本件の 4 通りの置き方。塗り + 輪郭は 9 つの混ぜ方で 0.1% 以内の同じ値、輪郭だけは `.blend`):

| 形 | 太さ | 直す前 | 直した後 |
| --- | ---: | ---: | ---: |
| 塗り + 輪郭 `rect(-0.3, -10, 0.6, 20)` | 1 / 2 | 1.3% / 0 | 0 / 0 |
| 塗り + 輪郭 `ellipse(0, 0, 0.7, 20)` | 1 / 2 | 21.6% / **83.6%** | 0 / 0 |
| 輪郭だけ `rect(-0.3, -10, 0.6, 20)` | 1 / 2 | 14.7% / 0 | 0 / 0 |
| 輪郭だけ `ellipse(0, 0, 0.7, 20)` | 1 / 2 | 20.1% / **100%** | 0 / 0 |
| 輪郭だけ `rect(x, y, 1.5, 20)` | 2 | 23.5% | 0 |
| 輪郭だけ `ellipse(80, 80, 100, 6)` | 20 | **100%** (長軸に沿って帯が抜ける) | 0 |
| 輪郭だけ `ellipse(0, 0, 40, 2.4)` (穴の幅 0.4) | 2 | 100% | 0 |

**決定。**

- 帯の穴が描く画素で 1 画素より細いか潰れている `rect` と楕円は、内縁の被覆を**両縁を見る積**で数える (`mokume_thinHole`)。境目は細い塗り・細い線と同じ 256/258 画素で、それより太い穴は縁 1 本の式のまま (絵は 1 ビットも動かない)
- `rect` の穴は `半幅 − 太さの半分` の箱で、`max(穴の半幅, 0)` の 1 次元の被覆の積。楕円は、短い向きの穴の半幅 `短半径 − 太さの半分` (厳密。楕円に内接するいちばん大きい円の半径は短半径なので、太さの半分がそれ以上なら穴は無い) と、長い向きの穴の端 (太さの半分が長い軸の端の曲率半径 `短半径² / 長半径` までなら `長半径 − 太さの半分`、越えると長い軸の上の点から縁までの距離 `短半径 · √(1 − x² / (長半径² − 短半径²))` が太さの半分になる所) を出し、画素の中で中心にいちばん近い長い軸の上の点での穴の半幅を長さに掛ける (`mokume_thinEllipseHoleCoverage`)。穴を楕円とみなすと、尖った穴の端で 16% の欠けが残った (CPU の模型)
- 穴が細いかは図形ごとに頂点関数が 1 度だけ決め (`FormFragmentIn.thinHole`)、枝は列の旗 `kFormHasThinFill` (細い塗りの旗) に乗せて、含まない列の原稿から外す。旗は「1 画素より細い塗りか、帯の細い穴を含みうる」に広げ、CPU の判定 (`FormInstance.mayHaveThinHole`) も迷ったら含む側に倒す。輪郭だけの列にも旗が立つので、組むパイプラインは 1 組 (旗 6) 増える
- `o` の見積もり (`min(f, 外縁) − min(f, 内縁)`) は変えない
- 扇は当初は範囲の外で、扇の帯の内縁も縁 1 本の式のため潰れた穴で帯が欠けた (`strokeWeight(20)` の `arc(0, 0, 100, 6, −π/2, π/2)` で 100%)。[#2747](https://github.com/mokume-metal/mokume/issues/2747) で直した (下の「扇の帯の穴」。[#2181](https://github.com/mokume-metal/mokume/issues/2181) は扇の細い塗りの件で not planned)

**費用。** release・1920×1080・Apple M3 Max (macOS 27.0.1) で、1 フレームの GPU 時間 (`MTL4CommitFeedback` の `gpuStartTime` / `gpuEndTime`・一時の仕掛けで測り、コミットしていない) の中央値。60 フレームの中央値を 1 回とし、直す前と直した後のシェーダを入れ替えながら 10 回ずつ走らせて、その中央値を並べた。塗りと輪郭は不透明:

| 場面 | 直す前 | 直した後 | 差 |
| --- | ---: | ---: | ---: |
| 直径 700 の円 200 個 (太さ 7)・`.blend` | 1.654 ms | 1.657 ms | +0.2% |
| 同・`.lightest` | 2.112 ms | 2.105 ms | −0.3% |
| 寸法違いの円 4000 個 (直径 1〜30・太さ 1)・`.blend` | 0.136 ms | 0.158 ms | +16% |

CPU では、図形を置くたびに列の旗の判定 (`FormInstance.mayHaveThinPart`) が帯の穴も見るので、release で判定だけが図形 1 つあたり 5.8 ns から 13.4 ns に、寸法違いの円 20 万個を置く本体が 1 つあたり 51.7 ns から 56.8 ns (+10%) になった (4 回の計測)。塗りと穴の判定で行列式と行ノルムを共有しても、2 つを順に呼ぶのと変わらなかった。

**GPU で費用を払うのは、帯の細い穴を含む列だけである。** 寸法違いの円 4000 個は、直径 2 より小さい円 (太さ 1 で穴が 1 画素より細い) を含むので旗が立ち、細い枝を残した組で描く。それらの円は塗りがあっても漏れていた (直径 1.4・太さ 1.2 の円で最悪 7.5%・CPU の模型) ので、払う費用である。旗の立たない列は動かない。

採らなかった案:

- **`o` を積の形に合わせて見積もる** (起票時の案): 測ると漏れは内縁の口で、`o` を直しても減らない
- **穴が細いかを断片で画素ごとに出す**: 楕円の穴の端 (平方根 2 つ) を画素ごとに解き、直径 700 の円 200 個が +22% になった (1 回の計測)
- **図形ごとの判定だけで分け、列の旗に乗せない**: 枝が原稿に在るだけで、直径 700 の円 200 個が +11% になった (3 回の計測)
- **帯の細い穴だけの旗を別に立てる**: 細い塗りを含まない列で細い塗りの枝を外せるが、起動時に組むパイプラインが 9 本増える (細い塗りの旗に乗せると 3 本)。細い枝を図形ごとに分ける判定は残るので、旗を分けても列ごとの絵は変わらない。**計測していない**

**残る外れ → 直した ([#2742](https://github.com/mokume-metal/mokume/issues/2742))。** 楕円の近似の距離場 (`mokume_ellipseField`) は縁の上でだけ真の距離と一致し、縁から離れるとずれる。輪郭の内縁・外縁は縁から太さの半分だけ離れた所なので、そのずれが帯の位置のずれになる。長い軸の端 (曲率半径 `短半径² / 長半径`) の近くで最も大きく、太さの半分がそれを越えると、近似は長軸の上で先端までの距離を返すので、穴が 1 画素以上ある楕円でも内縁が実際の穴の端より先まで伸び、外縁は先端の外へはみ出して、帯が丸ごと抜けた。この改訂の直しの入口は「穴が潰れているか 1 画素より細い」なので、境目で絵が跳んだ — `noFill()` の `ellipse(0, 0, 100, 6)` は太さ 5.0 で長軸に沿って 100% 欠け、5.02 (穴が 1 画素より細くなる) で 0 になった。ほかにも太さ 14 の `ellipse(0, 0, 84, 26)`・太さ 6 の `ellipse(0, 0, 40, 10)`・太さ 4 の `ellipse(0, 0, 30, 6)` が 100% 欠け (CPU の模型)、帯の欠けない太さでも `ellipse(0, 0, 84, 26)`・太さ 7 で内縁が最大 0.8 画素ずれた。塗りがあれば、穴の端の先に塗りの色が出た。

直し方は、近似のずれが許容を越える楕円だけ、輪郭を**真の距離**で解くこと:

- ずれの見積もり `0.35 · (長半径 − 短半径) · 太さの半分² / 短半径²` が描く画素の 1/200 (上限 1% の半分) を越える楕円を、頂点関数が楕円ごとに決める (`mokume_needsExactRing`)。見積もりは、縁から太さの半分だけ離れた平行曲線の上で近似の距離場と目標の差を CPU の 64 bit の模型で測った最大 (内縁側で `0.31 · (1 − 短半径 / 長半径) ·` 太さの半分 · 太さの半分 / 曲率半径。太さの半分 / 曲率半径が 1 までで、短半径 / 長半径が 0.03〜0.5) の 1 割増しで、`FormShapeTests` が実測を下回らないことを見る。円は距離場が真の距離なので対象外で、越えない楕円は近似のままなので絵は 1 ビットも変わらない (台帳は動かない)
- 真の距離は D. Eberly の方程式の根を、凸で単調に減る形にして左からニュートン法で解く (`mokume_ellipseExactField`・32 bit・1 回の動きが 1e-4 に収まるまで、多くても 16 回。長軸の近くの点で根が −1 のすぐ上に来て表せなくなるので、`t + 1` を変数にする。出発点は `zy` と `n0 − m` (`g` が正になる 2 つの下限) の大きいほうで、ほぼ円の楕円も根の近くから始まる。`m` は 1e30 で押さえ、長半径 / 短半径が約 1.8e19 を越えても NaN にならない)。短半径 / 長半径が 0.001〜0.99999 の楕円で縁の近くの点を走査し (ほぼ円の楕円は太さの半分が短半径の 0.4 倍までの太い輪郭も)、64 bit の二分法との差が 2.3e-5 以内に収まった。出発点を `zy` だけにすると、短半径 / 長半径が 0.997 より 1 に近い楕円で収まらず、長軸の上の行の距離が大きく外れた (`a = 100, b = 99.9, h = 37.8` で誤差 9.8・`nearCircleEllipseKeepsTheBandOnItsLongAxis`)
- 太さの半分が長い軸の端の曲率半径を越える楕円は、穴の端が尖る。真の距離でも縁 1 本の式は、尖りの先の画素で穴を挟む 2 本の縁の片方しか見ず、穴の面積より大きく数える (`ellipse(0, 0, 100, 6)`・太さ 4 で帯に丸ごと入る画素に最大 35% の欠け)。両縁を見る積 (`mokume_thinEllipseHoleCoverage`) を内縁の被覆の上限に置いて、丸ごと入る画素の欠けを消した。**積は穴を長方形で数えるので、穴を含む画素の部分被覆はまだ過大で、帯が 0.15〜0.22 薄く出た** (`ellipse(0, 0, 40, 10)`・太さ 6 で 0.22)。そこで穴の端から長軸の向きに 6 画素以内の画素は、穴の面積を画素の中の 8×8 の標本で数える (`mokume_ellipseHoleSampled`・標本は真の距離で決める)。部分被覆の外れは、真の幾何の面積 (16×16 の標本) に対して最悪 6.6% になった (`ellipseHoleTipKeepsItsPartialCoverage`。1 標本 = 1.6% の粗さが残る。16×16 なら 2.3% だが、細長い楕円 200 個の GPU 時間が 3.5 倍になるので採らなかった)。下の表の「1% 未満」は帯に丸ごと入る画素と丸ごと外の画素に限った主張で、部分被覆は尖りの先で 6.6% 以内
- 穴が 1 画素より細い枝 (`mokume_thinHole`) はそのままで、境目の両側で同じ帯が出る (`ellipse(0, 0, 100, 6)` を太さ 4.5〜5.5 で掃いて、欠けも滲みも 1% 未満)

直す前後の最悪 (`noFill()`・`.blend`・4 通りの置き方。欠けは帯に丸ごと入る画素の、滲みは帯の外に丸ごと入る画素の被覆。どちらも画素の四角を 1/8 画素広げて数える。`PixelGridTests.elongatedEllipseRingFollowsTheTrueGeometry`):

**払うのは、見積もりが許容を越えた楕円を含む列だけである。** 円と、ずれが許容に収まる楕円 (ほぼ円・細い輪郭) の列は絵が動かない。細長い楕円は、輪郭が縁から離れた所でも真の距離を画素ごとに解くので 1.9 倍になった (200 個で +0.8 ms)。内訳は、真の距離の解き方 (反復を固定の 14 回にすると 2.0 倍で、1 回の動きが十分小さくなったら止める形に縮めた) と、穴の尖りの先の標本 (8×8 で +0.4 倍、16×16 だと全体で 3.5 倍になるので 8×8 にした)。寸法違いの円と直径 700 の円は旗の立つ列で、断片の枝が増えたぶんをわずかに払う (1.05 前後)。

**CPU の費用。** 図形を置くたびに走る列の旗の判定 (`FormInstance.mayHaveThinPart`) に、3 つ目の判定 (`mayNeedExactRing`) を足した。release で図形 1 つあたり (20 万個ずつ・9 回の中央値): 円 4.7 ns → 5.6 ns、矩形 3.3 ns → 4.0 ns、非円の楕円 (長さ 100〜200・厚み 0.6 倍・太さ 2) 4.2 ns → 16.6 ns (最初は 19.8 ns で、特異値の端を 2 乗で比べて縮めた)。

採らなかった案:

- **全楕円を真の距離で解く**: ほぼ円・細い輪郭の楕円まで絵が動き (見積もりがごく小さい楕円でも 1/200 未満のずれは出る)、台帳が動く範囲が広がる。ずれが許容に収まる楕円は近似のままにして、絵と費用が動く範囲を外れの大きい楕円に絞った
- **穴の端の被覆を、2 本の縁それぞれの距離から `c1 + c2 − 1` で出す** (2 本目の縁は、長軸の向こう側の足を長軸の鏡像で近似): CPU の模型で、帯に丸ごと入る画素の欠けが両縁を見る積の上限と同じ 1.2% で改善せず、`ellipse(0, 0, 60, 40)`・太さ 30 では最大の外れが 0.10 から 0.22 に増えた。向こう側の足を解く反復も要る

**扇の帯の穴 ([#2747](https://github.com/mokume-metal/mokume/issues/2747))。** 扇 (`arc`) の内縁も、穴が潰れているか細いと縁 1 本の式 (`ring − 太さの半分`) のまま数えて帯が欠けた。同じ 2 つの口で、#2742 の根も 1 つ踏む。

- 穴が潰れている (扇の内接円の半径が太さの半分以下) と、内縁は「どこにも無い」はずなのに、被覆が縁の渡し (1 画素) の内に残る (`arc(0, 0, 20, 20, 0, π)`・太さ 10.4 で 20%)
- 穴が 1 画素より細いと、穴の両端が鋭く尖り、尖りの先で距離が小さいまま長く残って、穴から離れた画素まで被覆が残る (半円 `arc(0, 0, 40, 40, 0, π)`・太さ 19.5 で 30%)
- 細長い楕円の扇は、弧の距離場が #2742 と同じ外れ方をして帯が丸ごと抜ける (`arc(0, 0, 100, 6, −π/2, π/2)`・太さ 20 で欠け 100%・滲み 100%)

直し方:

- 扇の内接円の半径 (輪郭までの最大の深さ) の上限 (`mokume_sectorDepthBound`) と下限 (`mokume_sectorDepthLower`) を出す。円の扇は一致して厳密 (`半径 · sin(θ/2) / (1 + sin(θ/2))`・θ が π 以上は半径の半分)。楕円の扇は、扇が短半径の円板に収まるので上限は短半径と `長半径 ·` 円の扇の比の小さいほう、媒介変数の空間 (半径で割った空間) で単位円の扇の内接円の像の中に円が入るので下限は `短半径 ·` 円の扇の比 (`arc(0, 0, 100, 60, 0, π)` で 15〜25・実際は 15 ほど)。`FormShapeTests` が実測の最大の深さを 2 つの間に挟むことを見る
- **穴が細いかは下限から測る** (反証: 上限だけだと、楕円の扇は上限が実際の 1.7〜2 倍に緩く、細い穴を太いと外して太さ 30.1 で帯が最悪 45% 欠けた)。下限から太さの半分を引いた半径が潰れている (0 以下) か、描く画素の 3 つ分より小さい扇は、頂点関数が決め (`thinHole = 1`)、内縁の被覆を**画素の中の 8×8 の標本**で数える (`mokume_sectorHoleCoverage`)。潰れていれば 0。穴から画素の半対角より離れた画素は標本を取らずに 0 か 1。3 画素は、半円 `arc(0, 0, 40, 40, 0, π)` の穴の半径を 1.0〜4.0 に振った欠け (4 通りの置き方の最悪) が、1.0 で 12.5%・2.5 で 7%・1.5・2.0・3.0・4.0 で 0 だったことから、欠けの出た半径を覆う値に取った (rect と楕円の細い穴の境目 (幅 1 画素) より広いのは、扇の穴は両端が尖って、穴の幅の上限だけでは足りないため。欠けは置き方に依るので、3 以上でも出ないとは言えない)
- **中心の角が尖った扇** (掃引が π 未満で、角の半分の正弦が 0.5 未満・角が 60° 未満。楕円の扇は弧の端の位置ベクトルの向きで測る) は、穴が細くなくても (`thinHole = 2`)、尖りの先の画素だけ標本で数える (`mokume_sectorApex`)。中心の角は、内側へ太さの半分縮めても同じ角度の尖りになり、尖りまでの距離 t で縁 1 本の被覆の余りが `0.5 − t · sin(θ/2)` になって、θ が小さいほど遠くまで残る (反証: `arc(0, 0, 400, 400, …, 0.1)`・太さ 10 で、穴は太い (半径 4.5) のに尖りの先の画素が 52% 欠けた)。標本を取る範囲は尖りから `2 / sin(θ/2) + 2` 画素
- 近似の距離場がずれすぎる細長い楕円の扇 (#2742 の見積もり) は、弧を真の距離で解く
- 穴が太く中心の角が 60° 以上の円の扇の絵は **1 ビットも変わらない**。中心の角が 60° 未満の扇は、穴が太くても尖りの先の画素だけが変わる (上)。直前と直後のシェーダを同じ処理で読み込み、直径 100 の扇 91 本 (掃引 0.3〜6.0 の 13 通り × 太さ 3〜10 の 7 行・塗りと輪郭) を並べた 1820×980 の絵を画素ごとに照合した: 掃引 1.05 以上の 63 本は 0 画素、掃引 0.3〜1.0 の 28 本は 1 本あたり 11〜54 画素 (合計 585 / 1,783,600 画素)。変わった画素は扇の中心から 8〜47 画素以内で、成分の差は最大 0.34 (直す前に欠けていた尖りの先の画素)。台帳も動かない。楕円の扇は、見積もりが許容を越える形だけ動く (楕円と同じ)
直す前後の最悪 (`noFill()`・`.blend`・4 通りの置き方。欠けは帯に丸ごと入る画素の、滲みは帯の外に丸ごと入る画素の被覆。`PixelGridTests.collapsedArcHoleLeavesNoGapInTheBand`・`thinArcHoleLeavesNoGapInTheBand`):

**CPU の費用。** 扇は以前は列の旗の判定 (`FormInstance.mayHaveThinPart`) が常に偽で、置くたびの費用は無視できた。中心の角の判定 (`mayNeedApexSampling`) は三角関数を解くので、release で図形 1 つあたり、円の扇 21.7 ns・楕円の扇 30.6 ns になった (20 万個ずつ・9 回の中央値)。

**残る外れ。** 穴が画素の 3 つ分以上ある扇の穴の端、掃引 60° 以上の中心の角 (尖りの先の画素に残る被覆の余りは、尖りまでの距離 0.6 画素の画素で `0.5 − 0.6 · sin(θ/2)` と見積もって、角 90° で 6%・60° で 19% 前後。計算で、GPU では測っていない) と弧の端の角には、縁 1 本の被覆の余りが残り、穴の端の画素で数 % から 2 割の欠けが出ることがある。尖りの先を標本で数える範囲を広げると、穴の太い扇の絵が動く範囲も広がるので、広げなかった。標本は 8×8 なので、標本を取る画素の部分被覆は 1 標本 = 1.6% の粗さを持つ。

**楕円の扇の弧の最近点 ([#2914](https://github.com/mokume-metal/mokume/issues/2914))。** 扇の距離場は、楕円の弧を輪郭の候補に入れるかを扇の内外 (中心から弧の端への 2 本の半直線・媒介変数の空間) で決めていた。楕円では最近点の向き (法線) が中心から見た向きとずれるので、扇の内でも楕円全体への最近点が弧の角の範囲の外にあり、範囲の外の弧まで距離を測って帯が外へ滲んだ (`arc(0, 0, 80, 20, 0.3, 2.9)`・太さ 22 で、帯の外に丸ごと入る画素に最大 67%)。逆に扇の外でも最近点が範囲の内にあり、弧が最も近いのに線分への距離を返して帯が欠けた。円は法線の向きが中心から見た向きと一致するので起きない。
- **近似の距離場 (`exact` でない枝) にも同じずれが残る。** 近似の勾配は中心から見た向き (`p / 半径²`) で、扇の内外と同じ向きになる。塗りの縁 (弧の上) では最近点と一致するが、輪郭の帯の縁 (弧から太さの半分離れた所) は弧の端の近くで取り違える。`mokume_needsExactRing` の見積もりは距離の値のずれしか見ず、弧を数えるかの取り違えを入れていないので、既定の太さ 1 の扇も半径比 2:1 程度の楕円ならこの枝で描かれ、帯の縁の被覆が最大約 25% 外れた (CPU の模型で距離が最大 0.25 画素。GPU で、弧の端から 8 画素以内の画素を 24 通りの置き方で見て、半径 50×25 の扇に 15%)
- 直し方: 弧を候補に入れる条件を、楕円への最近点の媒介変数が弧の角の範囲にあるかに変える。媒介変数は、`p` から縁の足 `p − 距離 · 勾配` を引いて半径で割った向き `(cos t, sin t)` で測る。**真の距離の枝でも近似の枝でも同じ式**で、距離の値そのものは近似のまま (真の距離の反復は払わない)。近似の距離は縁の近くで 1 次の精度があるので、足の向きは 1 画素の内で 2 次の誤差になる。符号 (内外) は扇の内外のまま。範囲の外の最近点は、弧の端 (2 本の辺の端) が受け持つ。CPU の模型で、半径 50×25・25×12.5・30×20・20×15 の楕円 × 開始角・掃引で、帯の縁 (|距離 − 太さの半分| が 1 以内) の誤差が、いまの式は最大 0.248 (`arc(0, 0, 100, 50, 5.4, …)`・太さ 1)、足で測る式は 0.017 (距離の近似そのものの誤差) になった。縦横比 4:1・1.7:1・3:1・10:1 の楕円 × 開始角 6 通り × 掃引 5 通り × 太さ 2 通り (300 通り) を掃くと、扇の内外の式は多くの組で帯の内外が最大 13 画素食い違い、直した式は 0 になった
- 円の扇の絵は **1 ビットも変わらない**。動くのは楕円の扇で、直前 (#2747) と直後のシェーダを同じ処理で読み込み、縦横比 1〜10:1 の扇 210 本 (開始角 3 通り × 掃引 5 通り × 輪郭だけ太さ 8 と塗りありの太さ 3) を 1950×1820 に並べた絵を画素ごとに照合した: 縦横比 1:1 は 0 画素、1.1:1 は 12 画素・成分の差 0.005、1.3:1 は 22 画素・0.06、2:1 は 56 画素・0.34、3:1 は 120 画素・0.8、5:1 は 255 画素・0.8、10:1 は 527 画素・0.8 (直す前に滲んでいたか欠けていた画素)。合計 992 / 3,549,000 画素。台帳は動かない
- 採らなかった案: 扇の内外の判定を最近点の媒介変数で置き換える (塗りの内外も変わり、#1448 で決めた「辺は中心から弧の端への半直線」を動かすので、輪郭の弧の候補だけを直した)。見積もりに取り違えを足して、既定の太さの扇も真の距離の枝へ送る (真の距離の反復が細長い楕円で 1.9 倍の GPU 時間を払わせるので、足で測る補正で済ませた)
- 費用: 足の計算 (積和 1 回と半径で割る 2 回) だけ。release で、細長い楕円の扇 200 個・半径比 2:1 の細い輪郭の扇 200 個・円 4000 個の場面とも、直す前後で 1.0〜1.05 (交互 8〜10 巡の比の中央値。ほかのプロセスの GPU の使い方で巡ごとに 0.5〜1.8 に散る場面もあり、±5% 以内の差は読めない)

> 破れたとき: 線幅が形より太い `rect` / `ellipse` / `circle`、輪郭の内側の穴が 1 画素より細い形で、帯に下地が点や筋になって透ける。細い塗りに輪郭を付けると、継ぎ目に下地が透ける。

#### 改訂 (2026-10-29) — 置き換える列も、どちらでもない面積に下地を残す

置き換える列のどちらでもない面積 `1 − (f + s − o)` を、透明 (0) から下地 `D` に改める ([#3111](https://github.com/mokume-metal/mokume/issues/3111))。縁の画素は、形が掛かる面積 (被覆 `c`) だけを置き換え、残りに下地が残る: `c·S + (1 − c)·D`。決定 5 の「混ぜ方によらず、どちらでもない面積は形の掛からない所に残る色」を、置き換える列にも適用する。

**当初は**、置き換える列のどちらでもない面積を透明 0 とした (改訂 2026-10-02・[#1867](https://github.com/mokume-metal/mokume/issues/1867) 決定 1)。理由は「下地を読まず固定機能のブレンドも掛けないので `D` ではなく 0」で、書く経路の都合から導いた形だった。縁を下地と混ぜる案を意味として比べた記録は無い。測ると、被覆 0.5 の縁の画素が色の半分の濃さ・半分の不透明度で下地を**消し**、下地とも色とも違う 1 画素の半透明の輪が残った (`Sketches/ShapesAndStyle.swift` の `.replace` の円で、縁の画素の不透明度は 0.5 × 217/255 ≈ 0.43。#2991 で縁の被覆を画素の面積にしたとき 45° の縁で ±0.2 画素広がり、輪が少し太くなった)。同じ `.replace` の中でも、細い線の帯 ([#1637](https://github.com/mokume-metal/mokume/issues/1637)) は `S·c + D·(1 − c)` で下地を残していたので、経路で読みが割れていた。

**決定。**

- 距離関数の経路 (`mokume_formFragmentReplace`) は、断片が下地を読み、`S·s + F·(f − o)` に `D·(1 − (f + s − o))` を足す。塗りと輪郭を両方持つ形は 4 つの面積の和、塗りだけ・輪郭だけ・線は `c·S + (1 − c)·D`
- 三角形の経路 (`mokume_fragmentReplace`) の縁は被覆 1 (AA を持たない) なので変わらず、下地も読まない。被覆が 1 未満になるのは字形の縁 (焼き場の α) だけで、**置き換えで字を置いた列は、細い線の帯と同じ印 (`Batch.thinCoverage`) で下地を読む列 (`composite`) に回し**、`mokume_fragmentMain` の置き換えの枝が字形の被覆の残りに `D·(1 − α)` を残す。利用者の断片の置き換えも同じ 2 つの入口を通る
- 細い線の帯 (`mokume_fragmentMain` の置き換えの枝) は、すでにこの読みである。変えない
- どちらでもない面積が 0 の画素 (形が丸ごと掛かる画素) は、下地に触れず、前と同じ色で置き換わる。**α 0 の色で描き場所に穴を抜く使い方 ([#1542](https://github.com/mokume-metal/mokume/issues/1542)) は、形の中が透明に抜けるまま**で、縁が `(1 − c)·D` になり、穴の縁がなめらかになる
- 下地を読むのは、基本図形の置き換える断片 (`mokume_formFragmentReplace`) と、字・細い線の帯の列だけである。基本図形の断片は `[[color(0)]]` で下地を受け取る (パイプラインの組みはブレンドなしのまま。下地を読む列の断片と同じ口)。**三角形の経路の被覆 1 の図形と、面を置き換える `background()` は、下地を読まない断片のまま** — 下地を読む口を足すと、被覆 1 の図形まで費用を払う
- **費用** (1920×1080・面を覆う `.replace` 200 枚・GPU 時間の中央値・交互 5 巡。ほかのセッションが GPU を使う機械で測った Metal の検証層なしの debug 構成で、同じ巡で比べた `.blend` は動かない): 全面の `rect` 17.7〜18.1 → 20.2 ms (+12〜14%)・全面を覆う大きな円 24.4〜24.9 → 26.0 ms (+5〜6%)・縁が画面の中にある円 9.5〜9.8 → 9.9 ms (+2〜4%)・三角形の経路の全面の四角 12.7 → 12.3 ms (変わらない)。下地を読む口を三角形の経路の断片にも足すと、全面の四角が +22% だったので、足さなかった
- 帯では輪郭だけが残る ([#1819](https://github.com/mokume-metal/mokume/issues/1819)) は変えない。重なりには後に置いた輪郭だけが入る
- 絵が動くのは、置き換える列の縁の画素だけである。重ねる列と下地を読む 8 つの列、置き換える列の形が丸ごと掛かる画素は、1 ビットも動かない

採らなかった案:

- **現状 (縁は下地ごと置き換わる)**: 縁の輪は残り、細い線の帯との読みの割れも残る。置き換える (`.replace`) が「下地を消す」のは、形が掛かる面積だけにする
- **被覆 1 未満の画素を置き換えない・被覆 0.5 で切る** (案 C): 輪は消えるが、ADR が縁のなめらかさを約束している経路で、置き換えだけが AA を失う
- **経路ごとに 1 つずつ直す**: 同じ `.replace` の読みが経路で割れたのが、この改訂の動機である

> 破れたとき: `.replace` で描いた図形の縁に、下地とも色とも違う半透明の輪が残る。不透明な色を不透明な地へ置き換えで描くと、同じ色を重ねる混ぜ方で描いた絵と同じになるはずが、縁の画素が違う。

## 影響

- **ADR-0021 決定 1 を改訂する。** 理由 (空間は平面の約束をそのまま延長する) は動かさず、「一致」を幾何の一致と読むことを明記する
- **決定 2 の実装は [#1138](https://github.com/mokume-metal/mokume/issues/1138)、決定 1 を検査に載せるのは [#1139](https://github.com/mokume-metal/mokume/issues/1139) が担う。** 台帳が動くので 1 PR にする。`Canvas` の型の説明「座標の約束」はそこで書き換え、字形・画像・`rect` の塗りの半画素戻しはコードから消える
- **台帳は、塗りを持つ行が一度動く** (実装で 43 行のうち 31 行。動かなかったのは線・端点・角・画像・文字・`rect` だけの絵と、立体の輪郭の行)
- **塗りと輪郭を両方持つ形では、塗りが輪郭に対して半画素ずれる。** 形の経路では、そのまま重ねると継ぎ目で下地が漏れるので、重ね方を直す (決定 5 の「継ぎ目の重なり」)
- **線の寄せは、描く経路ごとに持つ必要がある。** 立体の輪郭は切り取り座標で、畳み込みの雛形は頂点関数が置き場所の変換を掛けた後・投影の前に、保持した形は置く側で寄せる。畳み込みの雛形は、雛形の中の輪郭の区切りの番号 (色の塗り分けに既に使っているもの) で輪郭を見分けるので、逆行列も頂点の印も要らない
- [#928](https://github.com/mokume-metal/mokume/issues/928) (b) のうち、半画素の跳びは決定 2 で閉じる。縁の質の違いは、決定 3 の足す日を待つ
