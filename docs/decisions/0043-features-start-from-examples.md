# ADR-0043: 機能は先に置いた作例から作る

## 状態

採用 (2026-10-04)

## 文脈

### 機能を入れる根拠が、3 本の ADR に分かれている

機能 (公開の口) を本体に入れてよい根拠は、次の 4 か所に積み重なっていた。

| 置き場 | 言っていること |
| --- | --- |
| [ADR-0001](0001-founding-principles.md) 原則 4 | 機能の追加は、実際の作品制作で踏まれた必要によって正当化する。想定だけの API を先回りで作らない |
| [ADR-0022](0022-production-track.md) 決定 6 | 実需の物差しは 3 行 (書けなかった・規範の一貫性の欠け・「一般にそういう API があるから」は認めない)。`Sketches/` で踏んだものは数えない |
| [ADR-0041](0041-standard-scope-map.md) 決定 3 | 地図の標準に載った領域は、作品の実需を待たずに入れる。口の形は作例と作品で詰める |
| ADR-0001 の 2026-10-03 の改訂 | 領域の範囲は地図が決め、口の形は引き続き実需が駆動する |

ある機能を入れてよいかを知るには、それが地図の領域か、作品で踏んだものか、規範の欠けかを先に見分け、それぞれ別の ADR の別の線を引き当てる必要があった。

### 機能の不足には、踏まれる機会自体が来ない

ADR-0022 決定 6 は「足りなければ次の作品で踏み、そのとき起票される」とした。バグにはこれが当たる。約束と違う結果が出るからである。

機能の不足には当たらない。**無い機能は作品が使わないので、作品の側には「無いので作らなかった」しか残らず、Issue にならない。** 外部入力が、作品の側からの戻りが 0 件のまま保留され続けたのはこのためである ([#1734](https://github.com/mokume-metal/mokume/issues/1734))。地図 (ADR-0041) は領域の単位でこれを解いた。しかし地図に無い機能は、同じ構造に残っている。メンテナが「こうしたい」と方針を持っていても、待つ以外の道が無い ([#2058](https://github.com/mokume-metal/mokume/issues/2058))。

### 地図の領域では、すでに作例が口を決めている

ADR-0041 決定 3 は、地図に載った領域を作品を待たずに入れた。代わりに、口は最小の作例が書けるところまでにした。シリアルなら「Arduino から届いた値で円を動かす」までである。「使う先の無い口まで一度に面へ出る」を防いでいるのは、作品を待つことではない。**作例が要る分だけ作ることである。**

### `Sketches/` を数えなかった理由は、書いた順序にある

ADR-0022 が `Sketches/` で踏んだものを実需に数えなかったのは、面から逆算して書かれたもので面の穴を測ると循環するからである (同 ADR の文脈)。循環を生むのは**書いた順序** (口が先、使う側が後) であって、書いた場所 (このリポジトリの中) ではない。作りたいものを口より先に書けば、循環は起きない。

## 決定

### 1. 入れるかは、トリアージで決める

機能は `Feature` の Issue で入り、着手は `verify: triaged` が付いてからである ([ADR-0031](0031-triage-as-the-single-gate.md))。

**`Feature` の印はメンテナが押す。** 公開の面に口を足すことは、公開 API の意味を新たに選ぶことであり、[ADR-0036](0036-unattended-issue-processing.md) 決定 8 により人が先に判断する。作業中に踏んだものの行き先 (ADR-0036 決定 6 の表) では、新しい口は「その PR で閉じる」(1 行目) にも「自分で印を付ける」(2 行目) にも入らず、3 行目 (無印で置き、判断を待つ) に落ちる。

**出どころは問わない。** 作品で止まった記録 (ADR-0022 決定 3)・地図の領域 (ADR-0041)・メンテナの方針は、どれも判断の材料である。どれか 1 つが無ければ入れない、という門ではない。

> 破れたとき: エージェントが自分で起票した `Feature` に自分で印を付け、誰も決めていない口が公開の面に入る。

### 2. 口は、Issue に先に置いた作例が要る分だけ作る

**作例は、作りたい絵・動きを示す最小のものである。** 主語は絵・動きで、コードはいまの API で書いても、擬似コードでも、参考の絵でもよい。口の綴りを先に決め、それを呼ぶだけのコードは作例と呼ばない — 面から逆算すると循環する (文脈)。

- 着手の前に、Issue に作例がある。起票の時点では要求しない (起票は雑でよい — [ADR-0002](0002-issue-lifecycle-and-merge-approval.md))
- `Feature` の完了条件に「作例が書け、`Sketches/` の参照スケッチか公開の説明の例として残る」を入れる。PR の対応表 (ADR-0031 決定 2) で確かめる
- 作例に要らない口・引数・設定は作らない。足すのは、次の作例か作品がそれを要ったときである ([ADR-0024](0024-extension-seams.md) 決定 9 はそのまま効く)

これは ADR-0041 決定 3 の形から、「地図に載っていること」という前提を外したものである。ADR-0022 決定 6 の「一般にそういう API があるから」を認めない線は、**「作例の無い口は作らない」**の形で残る。

たとえば線の破線は、いまの本体に無く、地図にも無い。

- **これまで:** `Feature` を起票しても、作品で踏んだ記録が無いので待つ。無いので作品も破線を使わず、踏まれる機会が来ない
- **この決定の後:** メンテナが Issue に作例「格子の補助線を、実線と破線で描き分ける」を置き、印を押す。口は破線の長さと間隔の指定までにする。破線の位相を動かす口や段階のある模様は、次の作例か作品が要ったときに足す。作例は参照スケッチか説明の例として残る

> 破れたとき: 作例に要らない口まで一度に面へ出て、使われないまま消せなくなる (ADR-0041 決定 3 が挙げた害)。

### 3. 削る提案は、実害なしで起票できる

入れた口が要らないと思えば、誰でも削る提案を起票してよい。削るほうに実害は求めない ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 4 と同じ向き)。決めるのはトリアージである。0.x の間は破壊的変更を許容している (ADR-0001 原則 6)。

**「作品で使われているか」を削る基準にしない。** 作例を使用に数えれば永久に削る候補にならず、数えなければ入れた直後から全部が候補になる。どちらでも判断に使えない。しかも作品での使用は、このリポジトリからは観測できない (ADR-0022 決定 5)。領域の単位の棚卸し (ADR-0041 決定 5) はそのまま残る。

### 4. 境界

| 当たるもの | 扱い |
| --- | --- |
| 地図の区分・地図に無い新しい領域 | ADR-0041 決定 4 の手続き (地図の表の改訂) で扱う |
| 足す条件を個別の ADR が書いている口 (例: [ADR-0011](0011-color-model.md) の EDR・ADR-0024 決定 2 の追補) | その ADR を改訂して入れる。改訂は実装の PR と同じでよい |
| 既にある約束と違う | [ADR-0040](0040-bugs-as-broken-promises.md) 決定 1 のとおり、約束を名指せるなら `Bug`、約束を決める必要があるなら `Design` |
| 運用の機構 (ゲート・検査・hook・ラベル・ワークフロー) | ADR-0008 のまま。この ADR は機構の基準を変えない |

## 影響

- **機能を入れる根拠の正本は、この ADR 1 か所になる。** ルートの `AGENTS.md` の「してはならないこと」の 1 行目は、その要約である
- 既存の ADR との関係:

| ADR | 扱い |
| --- | --- |
| ADR-0001 原則 4 | 改訂する。原則 4 の適用は本 ADR が持つ。理由 (使われない口を公開面に残さない) は決定 2 が引き継ぐ |
| ADR-0022 決定 4 の着手条件・決定 6・影響の「削る候補」 | 一部置換する。フェーズの着手も、トリアージの門だけで決まる。削る基準は決定 3 に置き換わる。決定 1〜3・5 (作品との境界と、作品からの逆流の口) と、決定 4 の「作品の完成を出口にしない」は変えない |
| ADR-0041 | 変えない。決定 3 は本 ADR 決定 2 の先例で、決定 5 は地図の棚卸しとして残る |
| ADR-0008 | 変えない |
| 個別の ADR の写し (`Sketches/` を数えない・作品で踏んだら足す) | 全面移行しない。その ADR を改訂するときに本 ADR に揃える (決定 4 の 2 行目) |

- **ラベル・検査・ワークフローを 1 つも足さない。** 作例があるか、口が要る分だけかは実質の判断である。機械にできるのは Issue に何か書いてあるかの確認までで、それは書く動機だけを増やす (ADR-0008 決定 3・ADR-0022 影響と同じ理由)
- 作品の制作トラック (ADR-0022) は、入口の 1 つとして残る。作品で止まった記録は、最も純度の高い作例である
