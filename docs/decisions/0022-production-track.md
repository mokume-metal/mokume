# ADR-0022: 実需を生む制作トラックの体制

## 状態

採用 (2026-08-29)

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 4 は、機能の出どころを定めている。

> **実需が機能を駆動する** — 機能の追加は、実際の作品制作で踏まれた必要によって正当化する。想定だけの API を先回りで作らない。リファレンス作品の制作をライブラリ開発と並走させ、そこで困ったことがロードマップの源泉になる。

そして影響節はこう予約した — 「原則 4 により、リファレンス作品の制作トラックをライブラリ開発と並走させる (**体制は別途 Issue で設計する**)」。**この予約は回収されないまま、2D の面が完成した。**

### 原則として書いてあるだけでは効かなかった

[#231](https://github.com/mokume-metal/mokume/issues/231) は図形・線・文字・画像・画素・シェーダまでを揃えて閉じたが、**外の実需を 1 つも通していない**。何を作るかは面の側から決まった。

`Sketches/` の 4 本は実需ではない。あれは #231 の出口条件「参照スケッチ数本が動き、その絵が証跡として残っている」を満たすもので、[`Sketches/main.swift`](../../Sketches/main.swift) 自身が「面が実際に成立していることを、使って示す」と名乗っている。**面から逆算して書かれたもので面の穴を測ると、循環する** — 書けることしか書かないのだから、書けないものは現れない。

同じことが次に起きようとしていた。[#287](https://github.com/mokume-metal/mokume/issues/287) 配下の 13 本も、決めたのは面の側である。原則 4 が禁じている「一般にそういう API があるから」との差は、**作りながら踏んだかどうか**にしかない。

### 機構の側には、既に同じ物差しがある

[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) は原則 4 を機構へ適用し、決定 1 で「足すときは、それが塞ぐ実害を名指しする」を置いた。実害とは実際に起きた事故か、成立していることを示せる穴を指す。

**機能の側には、これに対応する物差しが無い。** 原則 4 の本文は「実際の作品制作で踏まれた必要」と言うが、その作品制作をどう回すかが決まっていないので、踏む場所自体が存在しない。

### 体制を作ること自体に、固有の失敗がある

作品はこのリポジトリの外で作られる (決定 1)。**外にあるものの運用をここに書くと、必ず古くなる。** 書いた側からは観測できず、向こうが変えても誰も気づかず、この文書を読み直す理由も生まれない。原則 9 の「同じ内容の二重管理を作らない」は、リポジトリの境界をまたぐときに最も破られやすい。

ずれを検知する機構を足すのは筋が悪い。実害はまだ 1 件も出ておらず (ADR-0008 決定 1)、しかも境界の向こうを見張る機構はこのリポジトリの外に手を伸ばすことになる。**代わりに、ずれようのない書き方をする** — 向こう側の事実を主張しなければ、向こうが何をしても古くならない。

同じ姿勢は既に [ADR-0018](0018-observation-and-control-surface.md) が採っている。プロセスの外とやりとりする JSON は**境界の形だけを正典にし、実装は従う側**に置いた。本 ADR はそれを、プロセス間ではなくリポジトリ間の運用で行う。

### いま決める理由

#287 は sub-issue が [#300](https://github.com/mokume-metal/mokume/issues/300) を残して全て閉じており、次のフェーズの**着手前**が開いている。実需がロードマップへ逆流できる余地は、フェーズの中身が決まる前がいちばん大きい。面を広げてから体制を作っても、既に決まった一覧を後追いで正当化するだけになる。

## 決定

### 1. 作品はこのリポジトリの中に置かない

中に置くと、作品に次の 4 つが自動でかかるためである。

| かかるもの | 出どころ |
| --- | --- |
| MIT ライセンス | リポジトリの `LICENSE` |
| 帰属の機械検査 (帰属不明のファイルは存在した時点で CI が落ちる) | 原則 8 |
| 生成物・バイナリの禁止 (画像・動画・モデル) | 原則 7 |
| `make ci-check` を緑に保つ義務 | 「コミット・PR の規約」 |

**作品が持つ資材は、その全部に当たる。** フォント・画像・モデル・音は帰属の宣言を要求され、バイナリは置けず、作品が壊れれば CI が赤くなる。ここで起きるのは「制約に合う作品しか作らなくなる」ことで、それは**実需の側が道具に合わせて歪む**という、原則 4 が防ごうとしているものそのものである。

置き場は役割の線引きでもある。`Sketches/` は面の成立を示すために面から逆算して書かれ、このリポジトリの中にあることに意味がある。作品をその隣に置けば、作品まで「ライブラリのための作品」になり、2 つの役割が混ざる。

原則 6 (単一リポジトリ・単一バージョン) には触れない。あれが 1 つに束ねるのは**出荷物** (ライブラリ・CLI・テンプレート) で、作品は出荷物ではないからである。

**決めるのはここまで。** 作品が何本のリポジトリに分かれるか、どう構成されるかは作品の側が決める (決定 5)。最初の置き場として org 配下にリポジトリを 1 本立てる — その実体は [#354](https://github.com/mokume-metal/mokume/issues/354) が持つ。

### 2. 依存は一方向にする。このリポジトリは作品を参照しない

**作品が mokume に依存する。逆は無い。** 作品リポジトリは `Package.swift` にも CI にもワークフローにも現れず、このリポジトリのどのファイルからも参照されない。

こうすると次が成り立つ。

- **作品が壊れても mokume は赤くならない。** 作品は道具の検証物ではないので、壊れていることは情報であって故障ではない
- **mokume が壊れたら作品の側で気づく。** 気づいた結果は決定 3 の口を通って戻る
- **どちらの版がどちらを縛るかを決めなくてよい。** 作品が mokume のどの版を指すか (タグか `main` か・いつ追随するか) は、作品の側だけで完結する

作品側で本体の未マージの変更を試す方法も、作品の側の都合である。ここには書かない (決定 5)。

### 3. 実需がこのリポジトリへ入る口は、`Feature` 型の Issue 1 本だけ

疎結合であるためには、逆流にも口が 1 つだけ要る。**それが `Feature` 型の Issue である。**

本文に実需の出どころを書く。

- どの作品で
- 何を作ろうとして
- 何ができなかったか (書けなかったか、書けたが歪んだか)

そして作品の側へリンクを 1 本張る。**リンク先が Issue か PR か commit か、どれでもよい** — 形を決めると向こうの運用を縛ることになり、縛れば必ずずれる。GitHub がリンクの相互参照を両側に描くので、**実需由来かどうかは印を別に持たなくても後から読める**。

新しいラベルは足さない。[ADR-0005](0005-pr-labels-as-machine-input.md) 決定 2 の「読み手のいないラベルは足さない」に当たる — 実需由来を表すラベルを読む機械はいない。

出どころを書けないなら、それは `Feature` ではない。保守・整備は `Task`、期待と違う挙動は `Bug` で、実需を要求されるのは機能の追加だけである。

### 4. フェーズは、実需の Issue が 1 本以上立ってから着手する

同期点はこの 1 つだけとし、**このリポジトリの側に置く** — フェーズ親 Issue に着手する前に、決定 3 の Issue が 1 本以上立っていること。止まった場所がフェーズの sub-issue 群の核になる。

作品の完成をフェーズの出口条件にはしない。出口に置くと作品がノルマになり、**フェーズを閉じるために作品の側が妥協する** — 実需のふりをした逆流が起きる。「作ろうとして止まる」が最も純度の高い実需であり、完成した作品から後で振り返るより、止まった瞬間のほうが「何が無かったか」を正確に指せる。

**作品をいつ立てるか・どこまで作るか・完成させるかは、作品の側が決める。** このリポジトリが待ち合わせるのは実需の Issue であって、作品の進み具合ではない。

### 5. この ADR は、作品の側のことを決めない

**ライセンス・CI・ブランチの切り方・Issue や PR の書式・コメントの作法・依存の指し方・題材・締切・公開範囲。どれもここには書かない。**

書けば必ずドリフトする (文脈節)。このリポジトリからは観測できず、向こうが変えても気づかず、本 ADR を読み直す理由も無い。**ずれを見張る機構は足さない** — 代わりに、ずれようのない範囲だけを書く。

本 ADR が決めてよいのは、決定 1〜4 が示す**境界の形**だけである。

- 作品がこのリポジトリの中に「無い」こと (決定 1)
- 依存の向き (決定 2)
- 逆流の口の形 (決定 3)
- 待ち合わせの点 (決定 4)

このどれもが**このリポジトリの側で観測できる**。作品リポジトリを 1 度も開かずに、守られているかを確かめられる。

### 6. 実需の物差しは、ADR-0008 決定 1 を機能側へ写したものとする

| | 機構 (ADR-0008 決定 1) | 機能 (本決定) |
| --- | --- | --- |
| 認める | 実際に起きた事故 | 作品制作で**書けなかった / 書けたが歪んだ** |
| 認める | 現に成立している穴で、成立を示せるもの | 既にある規範・ADR が**要求する一貫性の欠け**で、欠けを示せるもの |
| 認めない | 「業界の標準だから」 | 「一般にそういう API があるから」 |

2 行目の例が [ADR-0020](0020-api-naming-and-surface.md) 決定 3 (状態は 2D と 3D に等しく効く) である。3D で効いていないなら、それは既にある規範が要求する一貫性の欠けであり、作品を待たずに起票できる。**規範は既に合意されたものなので、そこから導ける欠けは先回りではない。**

ここに 1 行足す — **`Sketches/` で踏んだものは実需に数えない**。参照スケッチは面から逆算して書かれるので、面の穴をそれで測ると循環する (文脈節)。参照スケッチが書けないことに気づくのは有用だが、それは面の実装が規範に届いていないという 2 行目の話であって、実需ではない。

判断に迷ったら、足さない側へ倒す (ADR-0008 決定 1 と同じ)。足りなければ次の作品で踏み、そのとき起票される。

## 影響

- ADR-0001 影響節の「体制は別途 Issue で設計する」の予約を、本 ADR が回収する。**ADR-0001 は改訂しない** — 原則の本文を書き換えると採用時点の記録が変質するため、適用の詳細は本 ADR が持つ (ADR-0008 と同じ姿勢)
- **新しいラベル・検査・ワークフロー・スクリプトを 1 つも足さない。** 決定 3 は既にある Issue Type の責務を広げ (ADR-0008 決定 5 の第 1 段)、実需由来の印は GitHub が native に描く相互参照で足りる (第 2 段)。実需由来かどうかを機械で検査する仕組みも、境界のずれを見張る仕組みも持たない — 「作品で踏んだか」の判定には実質的な判断が要り、機械にできるのはリンクの存在確認までで、リンクを書けば通る検査は書く動機だけを増やす (ADR-0008 決定 3 と同じ理由)
- **外の締切 (展示・SNS 投稿) は要求しない。** 締切があると「最後まで描かざるを得ない」ので実需の純度は上がるが、これは作品の側のことであり (決定 5)、作品ごとに作者が決める
- **最初の 1 本は、次のフェーズ (GPU 応用) の着手前に立てる。** そこで止まった場所が、そのフェーズの sub-issue 群の核になる。リポジトリの実体と最初の 1 本は [#354](https://github.com/mokume-metal/mokume/issues/354) が持つ
- 既に閉じたフェーズ (#231・#287) の機能を遡って正当化しない。実需を通していないことは記録として残し、**次の作品で踏まれなかった機能は、そのとき削る候補になる**
- `Sketches/` は役割を変えずに残る。面の成立を示す参照スケッチであり続け、フェーズの出口条件としては引き続き働く
- **決定 5 が窮屈になる日は来うる。** 作品の側の運用をここに書きたくなったら、それは境界の切り方が間違っている合図なので、書き足すのではなく本 ADR を改訂して境界を引き直す
