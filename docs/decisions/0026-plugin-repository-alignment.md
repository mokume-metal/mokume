# ADR-0026: 外のパッケージのリポジトリを、本体のどこまでに揃えるか

## 状態

採用 (2026-08-30)

## 文脈

[ADR-0024](0024-extension-seams.md) が外から機能を足せる形を決め、その最初の実装として [mokume-syphon](https://github.com/mokume-metal/mokume-syphon) が別リポジトリに立った。**設定と規約は、そのとき毎回その場で決めた。** 決めたものは概ね妥当だったが、決め方に拠りどころが無かった。

### 割れは既に 3 件起きている

| 何 | どう割れたか |
| --- | --- |
| 帰属の宣言 (REUSE) | `.license` の添えファイルを 3 つ作り、後から本体の形に揃え直した ([mokume-syphon#6](https://github.com/mokume-metal/mokume-syphon/issues/6))。Issue と PR を 1 往復 |
| コメントの署名 | 本体の作法が「あちらの署名の作法は別に決まっている」と言うだけで、**あちらでは決まっていない** |
| Issue のラベル | 既定の GitHub ラベル (`bug`・`enhancement`・`documentation` ほか) が残っている。本体は削除済みで、ラベルは Issue Type と直交する属性だけを表す ([ADR-0005](0005-pr-labels-as-machine-input.md)) |

1 件目が最も明確な実害である。**同じ機構の使い方が 2 つのリポジトリで割れ、直すのに 1 往復した。**

2 件目は形が違う。壊れているのは子リポではなく**本体の記述**で、「あちらで決まっている」と書いてある「あちら」が存在しない。実際には個人環境のフックが差し戻して署名を足させたが、それは個人環境を持つ人にしか効かない — [ADR-0017](0017-agent-support-locality.md) が本体で避けている形そのものである。

3 件目は本 ADR を書くために子リポを読んで見つけた。**誰も気づいていなかった**ことが、割れが黙って起きる性質を示している。

### 本体が固い理由は、外のパッケージには当てはまらない

本体は承認の分立 ([ADR-0003](0003-agent-identity-separation.md) / [ADR-0007](0007-approvability-invariant.md))・設計判断の正典 (ADR)・描画の証跡 ([ADR-0019](0019-drawing-verification.md)) を抱えている。機構はどれもそのために立っている。**外のパッケージはそのどれも抱えていない。**

だから「本体と同じにする」は答えにならない。かといって「その都度決める」は今の状態で、割れが 3 件出ている。**決めるべきは線をどこに引くかである。**

### 正本の持ち方が問題の本体である

[ADR-0001](0001-founding-principles.md) 原則 9 は「どれが正かを常に 1 つに保ち、同じ内容の二重管理を作らない」と言う。ところが揃え方を配ろうとすると、**配る仕掛け自体が本体の規約の写しになりうる**。

候補は 3 つあった。

| 候補 | 何が起きるか |
| --- | --- |
| **文書だけ** — 判断の線を 1 本の ADR に置き、雛形は持たない | 新しい部品が 0 個。ただし文書の書き方を誤ると、そこが写しになる |
| 雛形リポジトリ (GitHub の template repository) | 生成は楽。しかし**生成した瞬間から本体と独立に古びる** — 写しが 1 リポジトリぶんずつ増える |
| 跨りリポの検査 — 本体の `scripts/` から外のリポジトリを見て、ずれたら赤くする | 写しは作らないが、跨りリポの読み取り・token・CI ジョブという新しい部品が要る |

[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の順序 (既存の責務を広げる → native → 置き換える → 新設) をここに当てる。**実害は 3 件で、うち 2 件は 1 往復で直っている。** それに見合うのは一番小さい手である。

**いま 2 本目のパッケージの予定は無い。** 急いで機構を作る理由も無い。

## 決定

### 1. 揃えるのは「本体と割れると害が出るもの」だけ。3 段に分ける

#### 第 1 段 — 必ず揃える

**この表は在処を指すだけで、規約そのものを持たない。** 中身を書けばその瞬間に写しになる ([ADR-0001](0001-founding-principles.md) 原則 9)。

| 揃えるもの | 正典 |
| --- | --- |
| 帰属の宣言の形 (SPDX ヘッダが原則・添えファイルを使わない) | 本体の `REUSE.toml` の冒頭 |
| コミットと PR の書式 (Conventional Commits・1 関心・squash 前提) | 本体の AGENTS.md「コミット・PR の規約」 |
| Issue → ブランチ → PR の流れ、`Closes #N` の置き場 | 本体の AGENTS.md「進め方」 |
| 検査の入口が `make ci-check` 1 つで、CI はそれを呼ぶだけ | 本体の AGENTS.md・[ADR-0001](0001-founding-principles.md) 原則 8 |
| Issue の分類 (Issue Type + 直交する属性ラベルだけ・既定ラベルは消す) | [ADR-0004](0004-issue-classification-by-issue-type.md) / [ADR-0005](0005-pr-labels-as-machine-input.md) |
| コメントの署名 | 決定 4 |
| 生成物・バイナリをコミットしない。視覚的な証跡は外部ホスティング | 本体の AGENTS.md「してはならないこと」 |
| 機構を足す順序 (実害 → Issue → 機構) | [ADR-0008](0008-mechanism-needs-demonstrated-harm.md) |
| AGENTS.md が本体を正典として指し、写しを置かない | 決定 3 |

**基準は「割れたときに害が出るか」の 1 つである。** 帰属の宣言は割れて 1 往復した。コミットの書式が割れれば版の上げ幅が壊れる。ラベルが割れれば分類の正典が二重になる。

#### 第 2 段 — 育ってから。ただし 3 つ同時

- ブランチ保護のルールセット
- `mokume-agent` App のインストール

**引き金は「そのリポジトリに、承認が要る変更が育ったとき」である。** 具体的には、設計判断の正典を自分で持ち始める・機構の定義ファイル (ワークフロー・ルールセット) を抱える、のどちらかが起きたとき。

**2 つは必ず同じ PR で入れる。** ルールセットだけを入れると、その瞬間から**誰も承認できない PR** が作れてしまう — App がインストールされていなければ App identity の token が出せず、メンテナ名義の PR は自己承認になって詰む ([ADR-0007](0007-approvability-invariant.md) 決定 1)。逆に App だけ入れても何も守らない。

(当初はここに `.github/CODEOWNERS` を含む 3 点だった。本体が [#530](https://github.com/mokume-metal/mokume/issues/530) で CODEOWNERS を畳んだので 2 点になっている — 承認を課すのはルールセットの `required_reviewers` だけで、CODEOWNERS は要求を二重に飛ばすだけの写しだった。)

> 破れたとき: 承認を要求する機構だけが先に入り、詰んだ PR を close して作り直すことになる。しかも詰みは PR 作成時には何も言わず、承認を求める段階で初めて分かる (ADR-0007 文脈の 2)。

#### 第 3 段 — 要らない

| 揃えないもの | 理由 |
| --- | --- |
| 描画の証跡 (`drawing-evidence`・`local-render`・描画 PR の順番待ち) | 絵を描くのは本体だけ ([ADR-0019](0019-drawing-verification.md)) |
| merge queue | 合流後の姿を再検証する必要が、並走する PR の量から生じていない |
| ルールセットのドリフト検査 | 見張る対象 (ルールセット) が第 2 段にある |
| `changelog.d` と週次リリースの機構 | 版の出し方はパッケージごとに事情が違う (mokume-syphon は焼く・pin を張る・tag を打つを 1 回でやる必要がある) |
| ADR (設計判断の正典) | 判断は本体の ADR に従う。従えない事情ができたら本体へ Issue を立てる |
| `scripts/` のフック群 (`comment.sh`・`plan-record.sh`・各 guard) | 決定 4 と同じ理由 — スクリプトとテストの写しになる |

**足りなければ実害が出て、そのとき Issue が立つ** ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 1)。第 3 段は「永久に要らない」ではなく「いま要らない」である。

> 破れたとき: 本体の機構が理由なく子リポへ写り、どちらを直せばよいか誰も言えなくなる。

### 2. 正本は本体の文書 1 か所。雛形も検査も作らない

**採るのは文書だけの案である。** 本 ADR が線を持ち、外のパッケージの AGENTS.md がそれを指す。新しい部品は 0 個で、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の**第 1 段 (既存の機構の責務を広げる)** に当たる — 「AGENTS.md が本体を指す」形は既に成立しており、それを規範にするだけである。

**雛形リポジトリは採らない。** 生成した瞬間から本体と独立に古びる。写しが 1 リポジトリぶんずつ増え、しかも古びたことは誰にも見えない。

**跨りリポの検査も、いまは作らない。** 実害 3 件のうち 2 件は 1 往復で直っており、新しい部品 (跨りリポの読み取り・token・CI ジョブ) と釣り合わない。**足すときの形と引き金だけ書き残す** — 同じ割れが 2 本目のパッケージでも起きたとき、本体の CI から第 1 段の表の項目を見に行く検査を 1 本足す。それ以前には足さない。

> 破れたとき: 3 段の表が古びる。**第 1 段に足すときは、本体側の正典を直してから表の行を足す** — 表は在処を指すだけなので、正典の無い行は書けない。書けてしまったらそれは写しである。

### 3. 外のパッケージの AGENTS.md は「違うこと」だけを持つ

先頭で本体の AGENTS.md を正典として名指しし、**このリポジトリだけで違うこと**を表 1 つで持つ。規約の写しは 1 行も置かない。

mokume-syphon が既にこの形になっている ([AGENTS.md](https://github.com/mokume-metal/mokume-syphon/blob/main/AGENTS.md))。本 ADR はそれを追認して規範にする。

**「違うこと」に書けるのは第 2 段と第 3 段の項目である。** 第 1 段の項目がそこに現れたら、それは割れである。

> 破れたとき: 子リポの AGENTS.md が本体の縮小版になる。縮小版は正典を名乗らないまま読まれ、本体が改訂されても追随しない。

### 4. コメントの署名は形だけ揃え、ラッパーは持ち込まない

本体の AGENTS.md は「他のリポジトリの Issue / PR へは素の `gh` で書く (あちらの署名の作法は別に決まっている)」と言う。**mokume-metal の外のパッケージについては、その「あちら」をここで決める。**

- **署名は本体と同じ 1 行を付ける。** 同じ場所に人間も複数のエージェントも書き込む事情は、リポジトリが変わっても変わらない
- **`scripts/comment.sh` は複製しない。** ラッパーとフックとテストの 3 点セットが写しになり、片方だけ直す事故が起きる。素の `gh` で書き、署名を足す
- **もう一度破れたときの一手だけ決めておく** — `comment.sh` に `-R` を足して責務を広げる ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第 1 段)。[#188](https://github.com/mokume-metal/mokume/issues/188) が `-R` を却下した理由の 1 つ (「あちらの署名の作法は別に決まっている」) は、本決定によって前提を失う。ただし**いまは足さない** — 実害は 1 件で、しかも手で足して直っている

> 破れたとき: 署名の無いコメントが積み上がり、後から発言の出どころを辿れなくなる。本体側と違い、機械で止める仕掛けはここには無い。

### 5. [mokume-syphon#3](https://github.com/mokume-metal/mokume-syphon/issues/3) は第 2 段の項目である

あちらが挙げる 2 つの選択肢のうち、**選択肢 2 (当面入れないと決め、AGENTS.md を実態どおりに直す) を採る。** 第 2 段の引き金がまだ引かれていない — mokume-syphon は設計判断の正典を持たず (決定 1 第 3 段)、抱えている機構の定義ファイルは CI とリリースのワークフロー 2 本だけである。

**あちらの AGENTS.md の改訂は #3 が持つ。** 本 ADR は位置づけだけを置く。

> 破れたとき: 実態より強い記述が残り続ける。「App identity で作る」と書いてあるのに App がインストールされていないので、読んだ者は鍵の探し方を疑って時間を使う ([ADR-0007](0007-approvability-invariant.md) 文脈が指す #88 と同じ入口)。

## 影響

- **本体の `REUSE.toml` の冒頭に、添えファイル (`.license`) を使わないことを明文で書き足す。** いまこの規則を明文で持っているのは **mokume-syphon 側だけ**で、正典が子リポにしかない状態になっている。本 ADR には書かない — 書けば写しになる (決定 1 の「表は在処を指すだけ」の自己適用)
- 本体の AGENTS.md に接続の行を足す。「してはならないこと」に線引きの在処を 1 行、「コメント」節の「あちらの署名の作法は別に決まっている」に決定 4 への接続を 1 行
- **2 本目のパッケージは、決定 1 の 3 つの表と決定 3 のひな型を読むだけで立てられる。** 判断を作り直さずに済むことが、本 ADR が効いているかの検査である
- **第 2 段の引き金が引かれた日には、ルールセットと App のインストールを 1 つの PR で入れる。** 分けて入れられないことは決定 1 が持つ
- **既定ラベルの割れ (文脈の 3 件目) は、あちらの Issue が持つ。** 本 ADR は第 1 段に「既定ラベルは消す」を置くだけで、mokume-syphon 側の掃除は行わない (1 PR 1 関心)
- 本 ADR は検査・hook・ワークフロー・ラベルを 1 つも追加しない (決定 2 の自己適用)。**追加したのは判断の置き場だけである**
- 各決定に添えた「破れたとき」は、2 本目のパッケージが立ったときの検査の入口である
