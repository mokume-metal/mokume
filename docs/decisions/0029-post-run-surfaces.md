# ADR-0029: 走らせた後に持つ面 (切り分け・数字・束ね)

## 状態

採用 (2026-08-30)

## 文脈

道具はいま **作る (`new`)・走らせる (`run`)・見張る (`watch`)・窓口 (`mcp`)** の 4 つで、作って走らせるところまでは通る。無いのは**走らせた後に起きること**への口である。

[#484](https://github.com/mokume-metal/mokume/issues/484) は候補を 5 つ並べた — 動かないときの**切り分け**、新しい版が出たことの**知らせ**、いま何が起きているかの**数字**、作品を作者以外の環境で動く形にする**束ね**、見張りをまたいで**状態を保つ**再読込。

**5 つを順に作る、では始めない。** [ADR-0001](0001-founding-principles.md) 原則 4 は機能の出どころを実需に置き、[ADR-0022](0022-production-track.md) 決定 6 はその物差しを [ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 1 から写した。並べた 5 つは候補であって、採るかどうかは踏まれたことで決まる。だからこのフェーズは**面の範囲を決めること**から始まる。

### 判断材料 1 — 作品トラックが戻したもの

[works#1](https://github.com/mokume-metal/works/issues/1) (Grain) は描き切り、絵も残っている。そこから戻された 3 本は次のとおりで、**すべて描画の面**である。

| 戻ったもの | Issue |
| --- | --- |
| シードから同じ値が出る乱数とノイズが無い | [#366](https://github.com/mokume-metal/mokume/issues/366) |
| 利用者が書いた断片が、立体の表面の位置も向きも受け取れない | [#367](https://github.com/mokume-metal/mokume/issues/367) |
| 焼いた画像を立体の面に貼る口が無い | [#368](https://github.com/mokume-metal/mokume/issues/368) |

**走らせた後の面は 1 つも戻っていない。** これを額面どおりに読めば、5 つとも採らないことになる。

例外が 1 つある。[#383](https://github.com/mokume-metal/mokume/issues/383) (道具を入れる手段が無い) は同じ制作から戻ったもので、こちらは走らせる前の話 — [#398](https://github.com/mokume-metal/mokume/issues/398) の Homebrew tap で片付いている。**走らせた後の面のうち、実需を通って実装まで届いた前例はまだ無い。**

### 判断材料 2 — 名指しできる沈黙は 1 件

走らせた後に「設定したのに効かない」が沈黙として出た実例として記録があるのは [#464](https://github.com/mokume-metal/mokume/issues/464) の 1 件である。作ったばかりのスケッチでは窓口の `observe` も `input` も 1 回目が必ず空振りし、案内に従って起動し直すまで通らない。

**この 1 件は、それ自体としては個別に塞げる** (`new` が区画を空で置くか、`watch` が起動前に既知の区画を作る)。一般の切り分けの口が要るかどうかは、この 1 件だけからは決まらない。

### 判断材料 3 — 作者が名指ししたもの

本 ADR の着手時に、works#1 を作った当人へ「実際に踏んだのはどれか」を確かめた。**名指しされたのは 3 面**である。

- 作ったものを人に渡せない
- 動かないとき切り分けられない
- 速さ・重さが分からない

残る 2 面 (更新の知らせ・状態を保つ再読込) は名指しされなかった。

**証言は Issue と同じ重みでは扱わない。** ADR-0022 決定 3 は実需の口を `Feature` 型の Issue 1 本と定め、本文に「どの作品で・何を作ろうとして・何ができなかったか」を書くことを求めている。証言はその Issue を**書く根拠**にはなるが、証言そのものが Issue の代わりにはならない。だから本 ADR は採否だけを決め、**採ると決めた面はそれぞれの sub-issue が実需を書く**。

### 判断材料 4 — 既に在るもの

足す前に、いま何があるかを実測した ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5)。

| 既にあるもの | いま何をしているか | 届いていないところ |
| --- | --- | --- |
| `StartupReads` / `StartupReadsReport` | 起動の瞬間に決まるもの (区画の基準・区画の有無) を報告する。`watch` は起動時に基準を 1 行名乗り、全文は窓口の `reference` が返す | **端末から打てない。** 沈黙に当たった人が最初に読むべきものが、窓口を立てないと読めない。環境の前提 (OS・ツールチェーン) も含まない |
| `ResourceDeclaration` | 宣言されていない資材の置き場を見つけ、`run` が走らせる前に止める | `watch` は通らない。束ねるときに何を入れるかは、まだ誰も読んでいない |
| `scripts/orphan-processes.sh` ([#454](https://github.com/mokume-metal/mokume/issues/454)) | 手元に残ったプロセスを出所つきで一覧する | 開発者の手元向けで、配布物には入らない |
| `scripts/measure-frame-rate.sh` | フレームレートを条件ごとに測る | **1 プロセスで 1 条件**を測る検証手順。走っているスケッチを見ながら読むものではなく、配布物にも入らない |
| Homebrew tap ([#398](https://github.com/mokume-metal/mokume/issues/398)) | 版が出るたび formula が人手を介さず追随する | — |

[#484](https://github.com/mokume-metal/mokume/issues/484) が「ここで作り直さない」とした 3 本のうち、[#454](https://github.com/mokume-metal/mokume/issues/454) (孤児の一覧) と [#473](https://github.com/mokume-metal/mokume/issues/473) (走っているスケッチが名乗る) は解決済みで、残るのは #464 である。**「走っているものの見え方」は既に扱われている**ので、本 ADR はそこへ手を出さない。

## 決定

### 1. 採る 3 面と、採らない 2 面

| 候補 | 採否 | 根拠 |
| --- | --- | --- |
| 動かないときの切り分けの口 | **採る** | 沈黙の実例 (#464) と作者の名指しが揃う。決定 2 |
| いま何が起きているかの数字 | **採る** | 作者の名指し。決定 3 |
| 作品を、作者以外の環境で動く形に束ねる | **採る** | 作者の名指し。works#1 は描き切っており、渡す先が次に来る。決定 4 |
| 新しい版が出たことの知らせ | **採らない** | 下記 |
| 見張りをまたいで状態を保つ | **採らない** | 下記 |

**採らないものには「何が示されたら作るか」を書く。** これが無いと、次に話題が出たときに同じ議論を最初からやり直す。

#### 採らない① — 新しい版が出たことの知らせ

道具は Homebrew で入り、`brew outdated` と `brew upgrade` が既にこの役目を持つ。README も更新の打ち方を案内している。ADR-0008 決定 5 の第 2 段 (既存ツールが native に持つもので済ませる) がそのまま当たる。

**作る条件**: Release の tarball を直に展開して入れた利用者が、古い版のまま使い続けて事故った実例が 1 件出たとき。tarball の経路だけはパッケージ管理の外にあり、そこには知らせの持ち主がいない。

#### 採らない② — 見張りをまたいで状態を保つ再読込

作り直しのたびに子プロセスが入れ替わるので、積み上げた状態と時計はゼロに戻る。これが痛むのは**時間で育つ作品**を作っているときだが、works#1 はそうではなく、実際に戻ってきてもいない。

**作る条件**: 時間で育つ作品を作っていて、1 行直すたびに積み上げが消えることで制作が止まったとき。

**先に決めておくことが 1 つある** — 作るとしても、**道具は状態を運ぶだけで中身を解釈しない**。状態の形はスケッチ作者のものであって道具の関心ではなく、道具が型として知った瞬間、スケッチ側で構造を変えるたびに道具が追随することになる。契約にしてよいのは置き場だけである。

### 2. 切り分けの口は、既にある報告器を人が打てる形へ広げる

**新しい判定機構を作らない。** `StartupReadsReport` は既に「起動の瞬間に決まるもの」を文にしており、足りないのは**読める場所**である (いまは窓口の `reference` からしか読めない)。ADR-0008 決定 5 の第 1 段 (既存の機構の責務を広げる) を採る。

広げる先は 2 つ。

- **端末から打てるようにする。** 沈黙に当たった人は窓口を立てられるとは限らない。窓口が応えないこと自体が症状の 1 つである
- **環境の前提と手元の状態を同じ出力に並べる。** 区画の話だけでは「そもそも前提を満たしていない」と「前提は満たしているが区画が割れている」を切り分けられない

**規律は 3 つ。** いずれも #454 が孤児の一覧で採ったものと同型である。

1. **何も殺さず、何も直さない。** 出すのは状態と、読み方だけ。直すのは人間が行う。自動で直す口を持つと、直った理由が残らず、次に同じことが起きたときに何が効いたのか分からなくなる
2. **断定できないときは断定しない。** 「判定できず」と名乗り、**壊れていない側へ倒す**。切り分けの口が誤って断定すると、正しい原因から人を遠ざける — 沈黙より悪い
3. **回避策は、不要になったことも言えなければならない。** 版に依存する助言は、版が分かるときだけ出す。前提が変わったのに助言だけが残ると、それ自体が次の失敗になる

### 3. 数字は、走らせる名乗りの 1 行に構成と一緒に出す

**新しいコマンドを足さない。** `run` と `watch` は既に名乗りを持っているので、そこへ 1 行を足す。

**数字と前提を同じ行に置く。** 速さは最適化の有無で数倍変わるので、fps だけを見せると「重い / 軽い」の判断が構成の違いに引きずられる。別の場所に書いてあっても読まれない。

**構成の判定は、渡した引数からだけ導く。** ビルドシステムへ問い合わせない — 渡す引数がすべてなので、外へ聞いても得られる情報は同じで、プロセスが 1 つ増え判定経路が二重化するだけである。

> この決定は後から「問い合わせたほうが確実では」と読まれて差し戻されやすい。**確実さの差は無く、コストと経路の数だけが違う。** 差し戻すなら、引数以外から構成が決まる経路ができたことを先に示す必要がある。

**窓口 (`mcp`) には出さない。** 決定 5 の 2 番目の規律に当たる。

**停止しているスケッチは数字を返さない。** 表示は欠測を許す形にし、欠測を 0 と書かない。

### 4. 束ねは、責務の線を先に引き、保証を段で名乗る

#### 責務の線

- **束ねた中で資材が見つかること = ライブラリ**
- **束ねること = 道具**

決め手は 2 つある。(a) 束ねた中での資源の解決はライブラリの実行時の振る舞いなので、束ねる側から後付けで直せない。(b) 署名できるレイアウトを選べるのは、解決の規則を自分で持っている側だけである。

#### 保証は段で名乗る

**1 段目は「自分の別の Mac で起動して絵が出るところまで」。** Developer ID による署名と公証は 2 段目とし、実需が立ってから着手する。

「配れます」ではなく「別の機械で起動するところまで」と言えると、期待と実装がずれない。**保証の範囲は、口の名前と一緒に決める** — 名前だけが先に決まると、名前が段を追い越す。

#### 束ねるものの正典

**`Package.swift` が宣言した資材が正典で、ソースを走査して推測しない。** 推測は当たっているうちは楽で、外したときに**黙って欠ける**。宣言の有無を見る目は `ResourceDeclaration` が既に持っているので、その責務を広げる。

**欠落は、配る前に分かる形にする。** 束ねた後で気づくのでは遅い。

#### 名乗り

`.app` の名乗り (表示名・識別子・版・用途文言) は、**作品の振る舞いとは変更の理由も頻度も違う**ので、実行時の設定と分けて独立に持つ。

**ひな形には同梱しない。** 「書かなくても動くが、書かないまま配ると事故になる」性質のもので、とくに識別子は**権限の許可がぶら下がる鍵**である。仮の値のまま配ると、許可の状態が別の作品と混ざる。同梱すると全員が同じ仮の値を持つことになるので、**同梱しないほうが安全側**になる。

代わりに、**名乗りが未設定のまま配られようとしたときに止める**。

#### 配る前に踏む経路

束ねた作品は、開発中に一度も踏まない経路を通る — 作業ディレクトリが端末からの起動時と違い、資源の解決が別の規則で走り、権限は識別子にぶら下がる。どれも開発中は「たまたま動く」。

したがって検証は、別の機械を用意する前に、**手元の成果物を退避してから起動する**。作者の環境に依存した解決は、その 1 手順で捕まる。

なお、区画の基準を環境変数で外から与えて起動時に一度だけ解決する形は [ADR-0018](0018-observation-and-control-surface.md) 決定 2 が既に決めており、**束ねる側でもこの前提を置き直さない**。

### 5. 付け足しの規律 3 本

[#484](https://github.com/mokume-metal/mokume/issues/484) が「全体に効く条件」として挙げた 3 本を、規範としてここで確定する。**採った 3 面の完了条件はこれを含む。**

1. **付け足しは本体を妨げない。** 知らせ・数字・切り分けのような付け足しは、コマンドを遅らせない・止めない・失敗しても飲む。**例外を投げる経路を持たない。** 3 つが揃って初めて「付け足し」になる
2. **機械が読む出力に、人向けの行を混ぜない。** 窓口のように機械が読む経路では、標準エラー出力も汚さない。出力の宛先で分ける
3. **数字を出すときは、前提を同じ行に置く** (決定 3)

### 6. 新しいラベル・検査・ワークフローを足さない

本 ADR は面の範囲を決めるだけで、機構を増やさない。採った 3 面の実装も、判定は既存の `make ci-check` に載る範囲で行う。

## 影響

- **sub-issue は 3 本になる** — [#486](https://github.com/mokume-metal/mokume/issues/486) (束ね。完了条件を決定 4 で確定する) と、切り分けの口・数字の新規 2 本。採らない 2 面は起票せず、本 ADR の「作る条件」が置き場になる
- **切り分けの口の実害は #464 が名指す。** ただし **#464 自身の直し (区画を先に作る) とは別物**である。前者は「沈黙に当たった人が原因へ辿れること」、後者は「その沈黙をひとつ消すこと」で、後者が済んでも前者の必要は消えない (逆も同じ)
- **works#1 が走らせた後の面を 1 つも戻していない**という記録は残す。3 面を採る根拠は作者の証言であり、Issue として書かれるのはこれからである。**次の作品で踏まれなかった面は、そのとき削る候補になる** (ADR-0022 影響節と同じ扱い)
- 決定 3 により、`run` / `watch` の出力に 1 行増える。**窓口の出力は変わらない**
- 決定 4 の 1 段目は署名を伴わないので、**受け取った側が初回に許可を与える必要がある**。これは保証の段としてそう名乗る (隠さない)
- **`Sketches/` は本 ADR の対象外。** 面の成立を示す参照スケッチであって、走らせた後の面の実需にはならない (ADR-0022 決定 6)
