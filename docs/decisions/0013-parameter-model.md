# ADR-0013: パラメータ機構 — Observation に載せ、値の正典を 1 つに保つ

## 状態

採用 (2026-08-27)

## 文脈

スケッチには「書いた後に動かしたい値」がある — 速度・しきい値・色・粒子の数。これらを実行中に操作できることは、作品を作る過程そのものである。値を変えて絵を見る往復が速いほど、作品は前に進む。

この往復を成立させるには 3 つの経路が要る。**GUI から触れること・保存して次回も同じ値から始められること・外部から制御できること** (ライブ演奏の卓や、別プロセスからの操作)。

決めるべきことは 3 つある。

1. 値の変更をどう追跡し、GUI へ伝えるか
2. スケッチ側でパラメータをどう宣言するか
3. エントリポイントのボイラープレートをどこまで畳むか

### 変更追跡を自作しない

素朴に作ると、値が変わったことを GUI へ伝えるための通知機構を自前で持つことになる。監視の登録・解除、通知の重複排除、値の同一性判定 — いずれも一度書くと保守が続く。

Swift には言語側の変更追跡機構 (Observation) がある。**自作の通知機構は、これで済むものを別の形で作り直すことになる** ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第 2 段 — native に持っているもので済ませる)。SwiftUI は Observation を直接理解するため、GUI 側の再描画は登録も通知も書かずに成立する。

### 宣言は macro になる

パラメータの宣言には、値そのものに加えてメタデータが要る — 表示名、取りうる範囲、刻み幅。GUI を組み立てるにはこれらが要り、外部制御の名前解決にも要る。

Observation 自体が macro として提供されている以上、その上に property wrapper を重ねる形は噛み合わない。**メタデータを添えた宣言を macro として提供するのが素直**である。

ただしこれは代償を伴う。macro を書くと `swift-syntax` への依存が生まれ、これは [ADR-0001](0001-founding-principles.md) 原則 5 と正面から緊張する。

> 依存は Apple 標準フレームワークを第一選択とし、外部パッケージは代替が無い場合に限る。

`swift-syntax` は Apple が Swift 本体と共に開発しているが、標準フレームワークではなく別パッケージである。**macro を使う以上これは避けられない** — 代替は「利用者にボイラープレートを書かせる」ことであり、それは原則 1 (気楽さを最優先) を降ろすことになる。**原則 5 の例外として、macro のための `swift-syntax` 依存を引き受ける**と明記する。

### 双方向同期を作らない

GUI・保存された値・外部からの制御という 3 つの入口があると、「どれが本当の値か」が曖昧になりやすい。それぞれが値を持ち、互いに同期しあう形にすると、同期のループ・競合・順序の問題が生まれる。

**値の正典は 1 つに定める。** 残りは投影であり、入口は正典を書き換える。読むときは常に正典を読む。

## 決定

### 1. 変更追跡は Observation に載せる

パラメータの変更追跡に自前の通知機構を持たない。SwiftUI の GUI は Observation の追跡によって更新され、登録・解除・通知のコードを書かない。

### 2. パラメータの宣言は macro で行う

値の宣言にメタデータ (表示名・範囲・刻み幅) を添えられる macro を提供する。macro は Observation が要求する形へ展開しつつ、GUI と外部制御が使うメタデータを保持する。

**この決定のために `swift-syntax` への依存を引き受ける。** [ADR-0001](0001-founding-principles.md) 原則 5 の明示的な例外とし、以後 macro を増やすときに依存の是非を再び議論しない。

### 3. 値の正典はスケッチが持ち、GUI・保存・外部制御はその投影とする

パラメータの値はスケッチのインスタンスが持つ。GUI・保存された値・外部からの制御は、正典を読み書きする入口であって、値の複製を持たない。**双方向同期の機構を作らない。**

### 4. エントリポイントのボイラープレートは macro で畳む

スケッチを 1 ファイルから始められるよう ([ADR-0001](0001-founding-principles.md) 原則 1)、アプリケーションの起動に要する定型コードは macro で畳む方向を採る。**具体の形は最初のテンプレートを書くときに決める** — 何が定型かは、実際に書いてみるまで確定しないためである。

### 5. 保存・外部制御・GUI の自動生成は、必要になってから足す

本 ADR が固定するのは決定 1〜4 だけである。値の保存形式、外部制御のプロトコル、メタデータから GUI を自動生成する範囲は、**実際の作品制作で必要になった時点で決める** ([ADR-0001](0001-founding-principles.md) 原則 4)。決定 3 (正典が 1 つ) を守る限り、後から足せる。

## 影響

- 決定 1 により、GUI の更新経路は SwiftUI と Observation の組み合わせに一本化される。パラメータのために独自の監視 API を公開しない
- 決定 1・3 は [ADR-0010](0010-concurrency-model.md) の main actor 既定と噛み合う。スケッチと GUI が同じ隔離にあるため、値の読み書きに境界越えが発生しない
- 決定 2 により、ビルドに macro の展開が加わる。ビルド時間への影響は実装後に測る
- 決定 2 の依存の引き受けは**この 1 件で完結する**。以後 macro を追加するとき、原則 5 との緊張を毎回議論し直さない
- 決定 3 により、「GUI で変えた値が保存されない」「外部から変えた値が GUI に出ない」というクラスの不具合が構造的に起きない。入口が増えても正典は 1 つのまま
- 決定 4 は方向だけを固定する。テンプレートの設計時に、この方向に沿った具体形を決める
- GUI は SwiftUI で作る ([#135](https://github.com/mokume-metal/mokume/issues/135) 決定 4)。本 ADR はその上に載る
