# ADR-0008: 機構の追加にも「実需が機能を駆動する」を適用する

## 状態

採用 (2026-08-27) / 改訂 (2026-09-05): 写しを畳む線 (決定 6) を足した

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 4 は**製品の原則**として書かれている。

> **実需が機能を駆動する** — 機能の追加は、実際の作品制作で踏まれた必要によって正当化する。想定だけの API を先回りで作らない。

対象は API である。しかしこのリポジトリが今まで作ってきたのは API ではなく、**機構そのもの**だった。

| | |
| --- | --- |
| ライブラリのコード | 0 行 (`Sources/` はまだ無い) |
| ADR | 7 本 |
| ワークフロー | 4 本 |
| スクリプト | 10 本 + テスト 106 件 |

設計フェーズなのだから当然ではある。問題は、**機構を足すかどうかを判断する基準が、機構に対しては明文化されていない**ことである。

現に判断待ちが溜まっている。2026-08-27 時点で `status: needs-triage` の機構追加提案が 4 件並ぶ — [#89](https://github.com/mokume-metal/mokume/issues/89) (ワークフロー検査を actionlint に替える)・[#90](https://github.com/mokume-metal/mokume/issues/90) (docs のリンク切れ検査)・[#91](https://github.com/mokume-metal/mokume/issues/91) (changelog.d の書式検査)・[#92](https://github.com/mokume-metal/mokume/issues/92) (SECURITY.md)。いずれも「あると良さそう」で、**いずれも実害から出たものではない**。

### 原則 8 は逆向きの圧力を持つ

> 問題が再発したら、文書ルールの追記ではなく機構 (CI・hook・lint) で塞ぐ。 — 原則 8

この二つは矛盾しない。原則 8 の起点は「**再発した**問題」であって、起きていない問題ではないからである。だが接続が明示されていないため、実務では原則 8 だけが読まれ、「機構で塞ぐのが正しい」が独り歩きしやすい。

### 判断は既に 2 回下されている

この ADR は新しい規則ではない。**同じ判断が既に二度、原則 4 を根拠に下されている。**

- [ADR-0004](0004-issue-classification-by-issue-type.md) 影響節 — 「型が org と ADR でずれる可能性は残る。型は 5 つで人の目が届くため、**今は突き合わせの検査を作らない** (実需が機能を駆動する — 原則 4)。ずれが実際に起きたら検査を入れる」
- [ADR-0005](0005-pr-labels-as-machine-input.md) 決定 2 — 「**読み手のいないラベルは足さない** (原則 4: 実需が機能を駆動する)」

明文化されていない基準が二度使われているなら、それは既に規範として働いている。本 ADR はそれを言語化するだけであり、**この ADR 自身も実需 (上記 4 件の判断) から出ている**。

### 機構を増やすこと自体は否定しない

対比として [ADR-0006](0006-github-settings-as-code.md) がある。ルールセットの定義ファイルと照合スクリプトという機構を新たに増やしたが、その根拠は「誰でも 1 項目変えられて誰も気づかない」という**実際に成立している穴**だった。これは正しい追加である。

否定するのは機構そのものではなく、**実害より先に機構が来る順序**である。

### 実害があっても、部品は重複しうる

順序を守っても防げない失敗が別にある。**実害はあったが、既存の機構で済んだ追加**である。

- [#19](https://github.com/mokume-metal/mokume/issues/19) で `scripts/review-gate.sh` に**重要パス判定**と **`review: approved` ラベル**を自作した。塞ぐ実害はあった — 承認を機械で強制しないと、誰も見ないまま main へ入る
- [#43](https://github.com/mokume-metal/mokume/issues/43) / [#59](https://github.com/mokume-metal/mokume/pull/59) で、重要パスの承認を **GitHub native** へ移した (CODEOWNERS → ルールセットの `required_reviewers`)
- [#44](https://github.com/mokume-metal/mokume/issues/44) / [#65](https://github.com/mokume-metal/mokume/pull/65) で自作分を縮小・廃止した。PR #65 は理由をこう書いている — 「重要パス判定と `review: approved` ラベルの fallback は**二重化・不要になった**」

しかも廃止だけでは終わらなかった。`scripts/tests/review_gate_test.py` を新規に書き、**廃止したものが戻らないこと**を固定する必要があった。

決定 1 の基準はこの追加を止めない。実害はあったからである。止めるには別の問いが要る — **その実害を、既にある機構で塞げないか**。「問題を塞ぐことに実需がある」と「**新しい部品**に実需がある」は同じではない。

## 決定

### 1. 機構を足すときは、それが塞ぐ実害を名指しする

新しいゲート・検査・hook・ラベル・ワークフロー・スクリプトを追加する PR は、**それが塞ぐ実害を Issue 番号で示す**。実害とは次のいずれかを指す。

- 実際に起きた事故 (壊れた main・取り逃したイベント・誤った判定・詰まった PR)
- 現に成立している穴で、成立していること自体を示せるもの (ADR-0006 の「誰も気づかない」がこれ)

「あると良さそう」「他のリポジトリにもある」「いつか困りそう」では足さない。**業界の標準であることは、このリポジトリでの実需の証明にならない。**

判断に迷ったら足さない側へ倒す。足りなければ実害が出て、そのとき Issue が立つ。逆に、要らない機構は自分では消えない。

### 2. 順序は「実害 → Issue → 機構」

原則 8 の「問題が再発したら機構で塞ぐ」は、この順序の後半だけを述べている。前半 — 問題が実際に起きること — を省略して機構から始めるのは、原則 8 の実践ではない。

機構の提案を思いついたときの置き場は Issue である。**起票は歓迎する** (雑でよい)。そこで待たせておけば、実害が出たときに「これだ」と拾える。思いつきを捨てる必要はない — 順番を守るだけでよい。

### 3. この基準は機構で強制しない

原則 8 は「文書ルールの追記ではなく機構で塞ぐ」と言うが、**本決定はその明示的な例外とする**。

機構の増殖を止める機構を作れば、それ自体が増殖の一例になる (自己言及の罠)。「実害を名指ししているか」の判定には実質的な判断が要り、機械にできるのは Issue 番号の存在確認までで、それは基準の形だけを検査して中身を検査しない — 番号を書けば通る検査は、書く動機だけを増やして判断を素通りさせる。

代わりに、判断が入る場所は既にある。機構は `.github/` `.claude/` `scripts/` `Makefile` のいずれかに現れ、前二者はルールセットの `required_reviewers` がメンテナの承認を要求する。**残る `scripts/` と `Makefile` は承認を経ずに入りうる** — ここは人とエージェントの目に委ねる。塞ぐ価値が出たら、そのとき決定 1 の基準で塞ぐ (この ADR 自身が自分の基準に従う)。

### 4. 機構を消すことには実害を要求しない

追加に実害を要求する以上、**削除は対称にしない**。役目を終えた機構・重複した検査・読み手のいないラベルは、実害を待たずに消してよい。

非対称にする理由は、誤りのコストが非対称だからである。消しすぎれば実害が出て気づき、Issue が立って戻せる。増やしすぎても何も起きず、ただ全員が少しずつ遅くなる。**気づける方向へ倒す。**

### 5. 新しい部品を作る前に、既存の機構で済まないかを確認する

実害が認められても、それは「その問題を塞ぐこと」に実需があるという意味であって、**新しい部品に実需があるという意味ではない**。既存の機構を広げれば済むなら、新しく作る部品の側には実需が無い — 決定 1 と同じ原則 4 が、部品の粒度でもう一度効く。

機構を作る前に次の順で検討し、**どの段を選んだかを PR 本文に書く**。

1. 既存の機構の**責務を広げて**済むか
2. GitHub や既に使っているツールが **native に持っている**もので済むか (自作は最後に置く)
3. 既存の機構を**置き換えて**、総量を増やさずに済むか
4. どれでも済まないときだけ、新しい部品を足す

**重ねるときは、なぜ重複が必要かを書く。** 正当な重複は既にある — `scripts/pr-identity-guard.sh` (Claude Code のフック) と `scripts/review-gate.sh` (CI) は同じ不変条件を二重に見張るが、これは**フックの効かないエージェントがいる**ためで、理由が AGENTS.md に書かれている ([#104](https://github.com/mokume-metal/mokume/issues/104))。理由を書けない重複は、どちらかが要らない。

**この基準も機構では強制しない** (決定 3 の射程に含める)。「既存で済まないか確認したか」の判定には実質的な判断が要り、機械にできるのは PR 本文に段が書かれているかの字面検査までである。段を書けば通る検査は、書く動機だけを増やして判断を素通りさせる。

### 6. 写しを畳むのも部品を足すことである (2026-09-05 追補)

写しを 1 箇所へ畳むと、**共有の置き場という新しい部品が増える** (`scripts/site_source.py`・
`scripts/pr-files.sh`・`scripts/repo-slug.sh`・`scripts/secret-scan.sh` …)。決定 5 が部品の
粒度で効くのと同じく、**畳む側にも実害が要る**。「同じものが 2 箇所にある」は、それだけでは
実害ではない。

**畳む実害は「割れたときに黙って壊れる」ことである。** 写しの片方だけが直ったときに、
失敗が「何も見つからなかった」と同じ見た目になるなら畳む。

**線を引く問いは 1 つ**である — 片方だけが直ったとき、誰かがそれに気付くか。気付かない
なら畳む。気付くなら、写しのままにして**割れても直せる形** (検査) を置くほうが、読み手に
とって近い。

**原則 9 と衝突しない。** [ADR-0001](0001-founding-principles.md) 原則 9 が禁じているのは
「どれが正か」が 2 つある状態、つまり**文書**の二重管理である。同じ振る舞いを実装した
コードの写しは、それだけでは正典が割れていない。割れたときに黙って壊れるものは
**実質的に正典が 2 つある**状態なので、そこでは原則 9 がそのまま効く。

**この決定も機構では強制しない** (決定 3 の射程に含める)。silent か visible かの判定には
実質的な判断が要り、機械にできるのは「同じ字面が 2 箇所にある」の検出までである — それは
畳むべきかについて何も言っていない。

## 影響

- AGENTS.md の「してはならないこと」で、原則 4 の適用範囲に機構を含める。決定 5 の要点 (足すと決めた後も、まず既存で済まないかを見る) も 1 行として足す
- `needs-triage` の機構提案 (#89・#90・#91・#92) は、本 ADR の基準で判断できる状態になる。**判断そのものは本 ADR では行わない** (それぞれの Issue で行う)。[#89](https://github.com/mokume-metal/mokume/issues/89) (自作の `check-workflows-yaml.sh` を actionlint + shellcheck に替える) は「足す」ではなく決定 5 の**第 3 段 (置き換え)** に当たる判断として扱える
- ADR-0001 は改訂しない。原則 4 の本文は製品の原則として書かれたままにし、適用範囲の拡張は本 ADR が持つ。原則そのものを書き換えると、採用時点の記録が変質する
- 本 ADR は検査・hook・ワークフローを 1 つも追加しない (決定 3 の自己適用)。決定 5 を新しい ADR ではなく本 ADR への追記としたのも同じ姿勢で、**この改訂自身が第 1 段 (既存の責務を広げる) を選んだ実例**である — ADR を 1 本立てれば、機構の判断のたびに 2 本読むことになる
- 決定 6 により、「写しがある」だけを理由にした畳み込みの PR は止まる。**畳む提案の置き場は Issue で、そこで「割れたら誰か気付くか」を先に決める** (決定 2 の順序が写しにも効く)。畳まないと決めた判断も本 ADR の表へ足す — 同じ導出を繰り返さないためである
- 「業界の標準だから」を根拠にできなくなる。他のリポジトリの実践は**着想の源泉としては歓迎する**が、採用の理由にはならない。原則 5 (対象を絞る) と同じ姿勢である
