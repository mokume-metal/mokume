# ADR-0047: ホットリロードは、作り直して子プロセスを入れ替える — 状態は運ぶ形で足す

## 状態

採用 (2026-11-07)

## 文脈

### 方式は、比べられないまま入った

[ADR-0001](0001-founding-principles.md) 原則 1 は、実行中のコード変更の反映 (ホットリロード) を一級機能にすると決めた。決めたのはそこまでで、どう反映するかは決めていない。

`mokume watch` は 2026-08-27 に入った ([#201](https://github.com/mokume-metal/mokume/issues/201)・[#216](https://github.com/mokume-metal/mokume/pull/216))。保存を見つけるたびに `swift build` で作り直し、新しい子プロセスを起こし、前の子を畳む。この方式は前提として入り、他の方式と比べた記録は残っていない ([#3825](https://github.com/mokume-metal/mokume/issues/3825) で確かめた)。

その上に、次の決定が載っている。

- [ADR-0029](0029-post-run-surfaces.md) 決定 1 の「採らない②」は、見張りをまたいで状態を保つ再読込を退けた。「作り直しのたびに子プロセスが入れ替わるので、積み上げた状態と時計はゼロに戻る」と書いている
- [ADR-0032](0032-window-ownership.md) は、窓を道具の側に置き、子が焼いた絵を共有できる面の番号で渡すと決めた。子が入れ替わっても窓が残るようにするためである。決定 6 は、作り直しの間も直前の絵を出したままにし、保存による入れ替えでは新旧の子を重ねて「子が居ない間」を無くした
- [ADR-0042](0042-camera-and-audio-standard.md) の影響は、走らせ直すたびにカメラ・マイクなどの機材を開き直すと書いている

見張りとプロセスをまたぐ絵の受け渡しのコードは、2026-11-07 に約 7,000 行ある。方式を変えれば、これらの決定とコードがまとめて動く。

### 反映の時間の内訳 (2026-11-07 の実測)

`mokume new` の雛形で `fill` の値を 6 回書き換えて保存し、作り直しの記録 (`.mokume/build/status.json` の `timings`) を読んだ。条件は M3 Max・macOS 27.0.1・Swift 6.4.2・debug で、計測中の機械の負荷は load average 3.6〜6.8 だった (他の作業のビルドが同時に走っていた可能性がある)。

| 段 | 値 |
| --- | --- |
| 作り直し (`buildMs`) | 2.73〜3.50 秒 |
| 入れ替え (`relaunchMs`。前の子を畳み、新しい子を起こすまで) | 約 2 ms |
| 新しい子の最初の 1 枚 (`firstFrameMs`。入れ替えを含む) | 約 450 ms (5 回)。入れ替えの 1 回目だけ 3.1 秒 |
| 保存から新しい絵まで (壁時計) | 3.3〜4.0 秒 |

時間の約 87% は作り直しが占める。プロセスを入れ替える部分 (起こして最初の 1 枚を出すまで) は約 450 ms である。

### 作り直しの間は、すでに状況を伝えている

- 端末に `Change spotted — rebuilding…` が出る
- プレビューに「変更を見つけた — 作り直している…」が重なる ([#695](https://github.com/mokume-metal/mokume/issues/695)・ADR-0032 決定 6)
- 作品の窓は、直前の絵を出したままにする (ADR-0032 決定 6)

## 決定

### 1. ホットリロードは、作り直して子プロセスを入れ替える。選ぶ基準は速さではない

方式を選ぶ基準は、次の 4 つである。

- 安定して確実に動くこと
- 拡張できること
- 保守できること
- 簡潔で、設計として筋が通っていること

反映の速さは基準に入れない。作り直しの待ちは、状況が伝わっていれば制作を止めない (決定 4)。

いまの方式は、4 つの基準を次のように満たす。

- **確実さ**: 毎回まっさらなプロセスで走る。古いコードの型・静的な状態・実行中のスケッチへの参照 (`runningSketch`)・`Task` は、前のプロセスと一緒に消える。「差し替えたつもりが、古いものが効いている」が起きない
- **安定**: 子が落ちても、道具と窓は残る (ADR-0032)
- **簡潔さと保守性**: 見張りが反映のために持つ仕組みは、作り直す・起こす・畳むの 3 つだけである。実行の形は `mokume run` と同じなので、見張りで見ている絵は、本番で走る絵と同じプロセスの形から出る。スケッチの API とライブラリの側には、差し替えの都合を何も持ち込まない
- **拡張性**: 作者の時計を運ぶ (`--keep-time`・[#2414](https://github.com/mokume-metal/mokume/issues/2414))・保存した版を試聴する ([#2071](https://github.com/mokume-metal/mokume/issues/2071)) などは、プロセスの外の値や面として足せる。どちらも子のコードに手を入れない

> 破れたとき: 反映を速くするための仕組みが、子の中とライブラリの側に入り込む。差し替えに失敗したときにだけ起きる不具合が増え、利用者は、見えている絵がいまのコードから出たものかを疑うことになる。

### 2. 状態を保ちたい要望には、プロセスを入れ替えたまま運ぶ形から検討する

状態を保つ再読込は、ADR-0029 の「採らない②」が作る条件つきで退けた。作る条件が満たされたときは、まず子プロセスを入れ替えたまま、運びたい状態だけを新しい世代へ渡す形を検討する。

- 渡す中身の形は、スケッチの作者が決める。道具は状態を運ぶだけで、中身を解釈しない (ADR-0029 の「先に決めておくこと」と同じ)
- 作者の時計 (秒と、止めているか) を運ぶ `--keep-time` が、この形の最初の例である

> 破れたとき: 状態を保つために、プロセスを残してコードだけを差し替える方式へ寄る。決定 1 の確実さを失う。

### 3. 退けた案

- **dylib の差し替え** (長く生きるホストに、作り直したスケッチを動的ライブラリとして載せ直す)
  - **確実さと簡潔さを失う。** 古い dylib の型のメタデータ・静的変数・main actor のグローバル (`runningSketch`)・走っている `Task` が、古いコードを指したまま残る。Swift では、載せた dylib を下ろす (`dlclose`) ことが実用上できないので、版を重ねるたびにメモリが積み上がる。**この 2 点は Swift の一般的な性質からの推論で、mokume では試していない**
  - ホストと dylib の ABI を合わせる仕組みが要る。[ADR-0024](0024-extension-seams.md) 決定 5 がプラグインの実行時ロードを退けた理由 (ABI の安定・署名・並行性の隔離) が、ほぼそのまま当たる
  - **得るものも小さい。** 省けるのは、プロセスを起こして最初の 1 枚を出すまでの約 450 ms で、反映の時間の約 12% である。時間の大半を占める作り直しは残る
- **関数の差し替え** (InjectionIII のように、走っているプロセスの関数を差し替える)
  - 差し替えられない変更 (格納プロパティを足すなど) が、黙って効かない。確実さを失う
  - 外の道具に依存する
- **インタプリタ** (スケッチを Swift 以外の言語で書き、解釈して走らせる)
  - Swift で書けることそのものを変える。ADR-0001 原則 5 (Swift・Metal への一本化) と食い違う

### 4. 作り直しの待ちには、状況を伝えて応える。方式は変えない

- いま何をしているかを、端末とプレビューの表示で伝える (#695・ADR-0032 決定 6)。端末の表示を豊かにする件は [#3423](https://github.com/mokume-metal/mokume/issues/3423) が扱う
- 反映を速くするために、確実さ・簡潔さを手放す方式 (決定 3 の dylib や関数の差し替え) へ寄せない
- それでも速さが要るときは、まず内訳を測る (作り直しの記録の `timings`)。手を付けるのは、この方式の内側にあって確実さを損なわない改善 (ビルドの構成など) に限る

> 破れたとき: 待ちを減らす名目で、決定 3 の案が繰り返し持ち込まれる。

### 5. 方式を見直すのは、決定 1 の基準そのものが破れたとき

見直す条件は、たとえば次のような実例が出たときである。

- 子プロセスの入れ替えが原因で、不安定になる・不確かになる
- その原因を、入れ替えの仕組み (ADR-0032 の重ね方・区画の権利など) の中で直せない

状態を運ぶ形で足りない実例が出たときも、方式を変える前に、決定 2 の形を広げることから検討する。

## 影響

**この方式の代償を、ここに 1 か所でまとめる。** 個別の決定が、それぞれの代償をどう減らしているかも並べる。

| 代償 | 扱い |
| --- | --- |
| 反映の下限は、作り直しと最初の 1 枚の和になる (2026-11-07 の実測で 3.3〜4.0 秒) | 状況を伝えて応える (決定 4) |
| 積み上げた状態が、保存のたびに 0 に戻る | 時計は `--keep-time` で運べる。それ以外は決定 2 の形で足す (ADR-0029 の作る条件) |
| カメラ・マイク・MIDI などの機材を、走らせ直すたびに開き直す | ADR-0042 の影響のとおり受け入れる |
| 窓をプロセスの外に置き、絵をプロセスの間で受け渡す仕組みが要る | ADR-0032。新旧の子を重ねて、絵が途切れないようにしている |

- ADR-0029 の「採らない②」と ADR-0032 が前提として書いていた「作り直しのたびに子プロセスが入れ替わる」の出どころは、この ADR になる
- [ADR-0013](0013-parameter-model.md) 決定 2 の改訂 (2026-09-07) の実測 (増分ビルド 1.35〜1.55 秒) から、作り直しの時間は 2026-11-07 にほぼ倍になっていた。決定 4 のとおり、それ自体は方式を見直す理由にならない
