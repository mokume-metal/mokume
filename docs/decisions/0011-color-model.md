# ADR-0011: 色規範 — linear Display P3 / 16F を作業空間とし、エンコードとアルファ変換の点を固定する

## 状態

採用 (2026-08-27) / 改訂 (2026-09-15): 決定 3 の入口で原色も作業空間へ移し、利用者が書いた数を sRGB の原色の値とする。決定 6 の「sRGB」は転送関数を指すと名乗る

## 文脈

色の扱いは、シェーダ・テクスチャ・合成・書き出し・表示のすべてに現れる。**後から変えると、絵に関わるコードの全域が書き換え対象になる。** 最初のシェーダを書く前に決めるべき決定であり、[ADR-0009](0009-platform-floor-and-toolchain.md) (プラットフォーム) と並んで土台に属する。

決めるべきことは 5 つある。

1. どの色空間で計算するか
2. どの精度 (ピクセルフォーマット) で保持するか
3. 転送関数 (ガンマ) をどこで適用するか
4. アルファを straight と premultiplied のどちらで扱い、変換をどこに置くか
5. 決定論 ([ADR-0001](0001-founding-principles.md) 原則 2) に基づく画像比較を、どの量子化点で行うか

### 決めないと何が起きるか

色空間と転送関数を宣言せずに書き始めると、実装は「そのとき手近だった形式」に従う。8 bit の非線形値をそのまま加算・乗算するコードが積み上がり、**ブレンドとフィルタの結果が数学的に誤ったまま「そういう見え方」として固定される**。後から線形合成へ移すと、既存のスケッチの絵がすべて変わる。

アルファも同じ構造を持つ。straight と premultiplied のどちらで持つかを決めずに書くと、変換が必要になった箇所ごとにその場で掛けたり割ったりが挿入され、**どの時点でどちらの表現なのかがコードから読めなくなる**。半透明の合成が絡む不具合は、この曖昧さの上でしか発生しない。

### 精度を上げると何ができるようになるか

8 bit / チャンネルは、表示の直前まで持ち回るには狭い。多段の合成・ブラー・トーン操作を重ねると量子化誤差が積もり、階調の段差 (バンディング) として現れる。また 8 bit は**表示できる範囲を超えた明るさを保持できない** — 1.0 を超える値が保持できなければ、露出・グロー・HDR 出力といった表現は入口で失われる。

浮動小数の作業空間はこれらを構造的に解消する。作品を作る道具として、明るさの情報を途中で捨てないことは表現の幅そのものになる。

### 検証との相互作用

原則 2 は「同じコード・同じシードからはバイト単位で同じ画像が得られる」ことを設計目標に置く。ここで比較対象を**作業空間の生の値**にすると、目に見えない下位ビットの違いで検証が赤くなりうる。**見えない差で落ちる検証は、やがて信用されなくなり無視される。** 比較する画像をどの時点のものにするかは、色規範の一部として決める必要がある。

## 決定

### 1. 作業空間は extended linear Display P3

合成・フィルタ・ライティングなど、色に対する計算はすべて**線形**の値で行う。色域は Display P3 とし、その範囲外の値 (負値および 1.0 超) を**切り捨てない** (extended)。

### 2. 中間バッファの精度は 16 bit 浮動小数 (`rgba16Float`)

オフスクリーンの描画先と中間バッファは半精度浮動小数で保持する。表示できる範囲を超えた明るさと、色域の外側の値を、出力段まで保持する。

### 3. 転送関数の適用は出力段の 1 箇所に集約する

線形からディスプレイのエンコードへの変換は、**画面への提示・ファイルへの書き出しの直前に 1 度だけ**行う。途中の段でエンコード・デコードを往復させない。入力側 (読み込んだ画像・利用者が指定した色) は、作業空間へ入る時点で線形へ変換する。

**規範は「線形で計算し、境界で変換する」であり、境界は入口と出口の 2 箇所しかない。**

#### 改訂 (2026-09-15) — 入口は原色も作業空間へ移す。利用者が書いた数は sRGB の原色の値である

**当初の決定**は、入口の変換を「線形へ変換する」の 1 語で書き、読み込んだ画像と利用者が指定した色を同じ 1 文に束ねていた。この 1 語は、転送関数だけを外すとも、作業空間へ移す (原色も変換する) とも読める。実装は 2 つの入口で別々の読み方をしていた ([#1081](https://github.com/mokume-metal/mokume/issues/1081))。

| 入口 | 当初の実装 | 同じ `204, 153, 0` の行き先 (書き出した 8 bit) |
| --- | --- | --- |
| 利用者が書いた数 (`fill(204, 153, 0)`) | 転送関数だけを外す (数は暗に P3 の原色の値) | `204, 153, 0` |
| 読み込んだ sRGB の画像 | CoreGraphics が原色ごと作業空間へ移す | `196, 155, 51` |

**同じ 3 つの数が、同じ作業空間で 2 つの違う色になる。** これは手本 (Processing / p5) を持ち出さなくても起きる食い違いである。手本から移した例では、157 本のうち 32 本が「形も位置も合うが色が違う」になった ([#911](https://github.com/mokume-metal/mokume/issues/911))。

**この改訂で、入口の変換は「作業空間へ移す」ことだと決める。** 転送関数を外すことと、原色を作業空間 (決定 1 の Display P3) へ移すことの両方を指す。入口が受ける値がどの原色の値かは、次のとおり入口ごとに決まっている。

| 入口 | 受ける値の原色 | 入口で行う変換 |
| --- | --- | --- |
| 利用者が書いた数 — 0–255 の数値形 ([ADR-0033](0033-color-specification-surface.md) 決定 1) と 0–1 のエンコード値 (`LinearRGBA.display`) | **sRGB** | 転送関数を外し、linear sRGB から linear Display P3 へ 3×3 の行列で移す |
| 読み込んだ画像・字形 | **絵が宣言した原色** | 同じく作業空間へ移す (CoreGraphics が行う) |
| 作業空間の線形値 (`LinearRGBA.linear`) | **作業空間の原色 (Display P3)** | 何もしない。境界の内側の値だからである |

**読み出し (`red()` などで数へ戻す口) は、入口の逆をたどる。** 作業空間から sRGB へ移してから転送関数を掛ける。こうすると [ADR-0033](0033-color-specification-surface.md) 決定 6 の往復 (`red(color(255, 204, 0)) == 255`) が保たれる。原色の行列は範囲外の値も切らない (決定 1 の extended)。sRGB の外にある作業空間の色は、負の成分や 255 を超える成分として読める。

理由は当初の決定から動いていない。境界は入口と出口の 2 箇所しかなく、入口はどこから入っても同じ規範に従う。変えたのは「線形へ変換する」の中身を名乗ったことだけなので、番号を増やさずこの ADR を改訂する。

退けた案とその理由:

- **P3 のまま扱い、出力段で sRGB へ落とす。** 決定 6 の「8 bit sRGB」を原色のことと読む案である。「同じ数から違う色が出る」が「同じ色から違う数が出る」に言い換わるだけで、食い違いは消えない。そのうえ決定 1 の広い色域を出口で捨てることになる
- **P3 のまま扱い、数は P3 の値だと名乗るだけにする。** 実装は 1 行も変わらない。しかし数値の入口と画像の入口が食い違ったままであることは、名乗っても解消しない

代償: 彩度のある色を数で書いた既存のスケッチは絵が変わる。`fill(204, 153, 0)` で塗った面を書き出すと `196, 155, 51` になり、打った数とは一致しなくなる (書き出しは作業空間の原色 Display P3 を刻むため)。灰色 (3 成分が等しい色) は、原色の取り方に依らないので変わらない。

**P3 の値を数で受ける口は残さない。** 残せば既存のスケッチを同じ絵に戻す移行手段になる。しかし、その口を必要とした実害はまだ無い ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md))。sRGB の外にある色は、`LinearRGBA.linear` で作業空間の線形値として書けば既に表せる。

| --- | --- |
| 何が示されたら足すか | 作品トラック ([ADR-0022](0022-production-track.md)) の作品が、P3 のエンコード値を手で線形へ戻す式を書く場面を 2 作品で踏んだとき |
| 形 | 数値形を増やさず、原色を名乗るラベル付きの口にする ([ADR-0033](0033-color-specification-surface.md) 決定 2 の「ラベルが尺度を名乗る」に従う)。名前はその日に決める |

### 4. アルファは公開 API を straight、内部合成を premultiplied とする

利用者が指定する色・取得する色は straight (色成分がアルファで乗算されていない) 表現とする。GPU 上での合成は premultiplied で行う。

**変換点は境界 1 箇所に固定する** — 色が作業空間へ入る時点で premultiplied にし、利用者へ返す時点で straight に戻す。中間の経路では「いま premultiplied である」ことを不変条件として扱い、その場限りの掛け戻しを書かない。

### 5. EDR / HDR 出力は情報を捨てない設計を既定とし、有効化は opt-in

決定 1・2 により、表示範囲を超える明るさは出力段まで保持される。EDR 対応ディスプレイでその範囲を実際に出すかどうかは**スケッチ側の opt-in** とし、既定は標準レンジへのトーンマップとする。

既定を標準レンジにするのは、**同じスケッチが環境によって違う明るさで表示される状態を既定にしない**ためである。opt-in で有効にしたときだけ、表示環境の能力に応じた出力になる。

### 6. 画像比較の量子化点は「出力段のエンコードを経た 8 bit sRGB」

決定論に基づく画像比較 (golden image) は、**出力段を通した後の 8 bit / チャンネル sRGB 画像**で行う。作業空間の 16F の生値では比較しない。

**改訂 (2026-09-15) — ここで言う「sRGB」は転送関数のことである。** 原色は作業空間の Display P3 のままで、書き出した PNG も Display P3 を刻む。当初の文面は原色まで sRGB に落とすとも読めた。その読みで出口を sRGB へ落としても入口の食い違いは消えないことを、決定 3 の改訂が退けた案として書いている ([#911](https://github.com/mokume-metal/mokume/issues/911))。

理由は 2 つある。

- 比較対象が人の見る絵と一致する。絵が変わっていないのに落ちる検証を作らない
- 量子化を経ることで、視覚的に等価な最下位ビットの揺れが差として現れない

EDR レンジで出力するスケッチの検証方法は本 ADR では決めない — 標準レンジの比較が動いてから、必要になった時点で決める ([ADR-0001](0001-founding-principles.md) 原則 4)。

**本 ADR は比較の機構を追加しない。** 視覚検証の自動化はレンダラ実装後の整備対象という ADR-0001 影響節の位置づけを変えず、その機構が従うべき量子化点だけを先に固定する ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md))。

## 影響

- すべてのシェーダは「入力は線形・出力も線形」を前提に書ける。エンコードの有無をシェーダごとに考える必要がない
- 決定 4 により、半透明の合成に関わる不具合の調査は「境界の 2 箇所」に絞り込める。中間経路のどこかで表現が入れ替わっている可能性を疑わなくてよい
- 決定 2 により、中間バッファのメモリ使用量は 8 bit 構成の 2 倍になる。これは表現の幅と引き換えに引き受ける
- ビュー層 ([#135](https://github.com/mokume-metal/mokume/issues/135)) は、決定 3・5 を満たせること — 出力段でのエンコードと EDR の有効化を制御できること — を選定条件に含める
- 後処理・フィルタ・書き出し ([#138](https://github.com/mokume-metal/mokume/issues/138) を含む GPU 応用の設計) は、線形 16F を入出力の前提にできる
- 決定 6 により、golden image の比較機構を作るときの仕様が先に定まっている。機構の追加自体は実装後の判断のまま
- 利用者が色を指定する API の形 (0–255 か 0–1 か、色空間を明示できるか) は本 ADR の範囲外とし、[ADR-0033](0033-color-specification-surface.md) が決めた — 上の層の素の数値は 0–255 のエンコード値、ラベル付きは名前が尺度を名乗る。**本 ADR の決定 1・4 はそこで制約として効いている**: 範囲外の値を丸めない扱い (あちらの決定 5・6) と、乗算済みの表現からは復元できないもの (アルファ 0 の色の成分) の契約が、それぞれ決定 1・決定 4 の帰結である
