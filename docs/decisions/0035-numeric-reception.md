# ADR-0035: 描画 API が数を受け取る形 — 受け口は広く、中は `Float`

## 状態

採用 (2026-09-06) / 改訂 (2026-09-07): 総称が持ち込む 2 つ目の経路 (リテラルが `Int` へ倒れる) を決定 6 へ足し、受け口を戻さない判断を決定 7 に置いた / 改訂 (2026-09-29): 決定 1 の費用の説明を、逆アセンブルで確かめた呼び先 (特殊化されない総称の入口) に合わせた / 改訂あり (本文の「改訂 (日付)」見出し)

改訂の経緯 (当初の決定・各改訂の理由・置き換わった決定) は [history/0035.md](history/0035.md) にある。本文は現行の決定を書く。

## 文脈

描画 API の受け口は `Float` 1 本である。`typealias` を置かず全箇所で `Float` と綴り、`map` / `noise` / `random` / `radians` も `Float` を返す。この一貫性は [ADR-0033](0033-color-specification-surface.md) 決定 1 が色の面で意図して選んだもので、`Int` と `Float` の口を並べると「`fill(1, 0, 0)` が 0–255 側・`fill(1.0, 0, 0)` が 0–1 側に落ちる、リテラルの書き方で意味が変わる罠」が入るためだった。

### 書き手が変換を書かされている

Swift の浮動小数リテラルは `Double` に推論され、`for i in 0..<n` は `Int` を返す。どちらも受け口が `Float` 1 本だと、呼ぶ側が変換を書くことになる:

```swift
let gap = 120.0          // Double に推論される
circle(gap, gap, 40)     // 通らない。Float(gap) と書かされる
```

**実害は測ってある** ([#969](https://github.com/mokume-metal/mokume/issues/969))。ローカルモデルにスケッチを書かせた実験で、**全モデルが `let gap = 120.0` を `Double` に推論して落ちた**。システムプロンプトに型の作法を 2 行書くと通るようになったので、**書けないのではなく、書き手が型を意識し続けなければならない**形である。同じ摩擦は人間の作者にも効き、参照スケッチ 16 ファイル 1777 行に明示変換が 78 個ある (約 23 行に 1 個)。

ADR-0033 の影響節も、これを代償として記録していた — 「決定 1 の `Float` 1 本という選択の帰結として、**`Int` の変数はそのまま渡せない** (`for i in 0..<255 { fill(i, 0, 0) }` は書けない)」。

### `Double` へ移す案は成立しない

**Metal のシェーダに `double` は無い。** 8 本のシェーダで `float` 150 / `float4` 140 / `float2` 124 / `float3` 94 に対し `double` は 0 件で、GPU へ渡る構造体もすべて `Float` と `UInt32` である。

面を `Double` にしても変換は消えず、**書き手のコードから GPU 境界へ移り、回数が「1 行 1 回」から「毎フレーム全頂点」に増える**。得るものは Swift のリテラル既定に乗ることと、`CGFloat` 境界 (macOS では `Double`) の変換 14 箇所・観測の 13 箇所が消えることだが、失うほうが大きい。

## 決定

### 1. 受け口は `ScalarConvertible`、中と GPU は `Float`

```swift
public protocol ScalarConvertible { var asFloat: Float { get } }
extension Float: ScalarConvertible { @inlinable public var asFloat: Float { self } }
extension Double: ScalarConvertible { @inlinable public var asFloat: Float { Float(self) } }
extension Int: ScalarConvertible { @inlinable public var asFloat: Float { Float(self) } }
```

**費用は測ってある** ([#976](https://github.com/mokume-metal/mokume/issues/976))。別のパッケージからこのライブラリを引いて release で呼び、20,000,000 回で 0.0151〜0.0168 秒 — **1 回あたり約 0.8 ns (2〜3 クロック)** である。`circle` 本体は 60〜70 ns なので、変換は **1% 台**である。

**呼ぶ側では特殊化されない (2026-09-29 改訂)。** 別のパッケージの release のバイナリを逆アセンブルすると、`circle(x, 10, 5)` は特殊化されていない総称の入口 (`Canvas.circle<A, B, C>`) を呼び、引数は番地で渡り、`asFloat` は証人表を通って引かれる ([#1797](https://github.com/mokume-metal/mokume/issues/1797))。それでも existential の箱化 (20〜50 ns) にはならず、引数 1 つあたり約 1 ns で収まるので、上の「1 行 1 回・1% 台」という結論は変わらない。`@inlinable` を付けて呼ぶ側で特殊化させる手は採らない — 本体を公開の約束に載せる割に、得が 1〜3 ns しかない。

> **当初この節は**「existential の箱化なら 20〜50 ns かかるので、ジェネリックは呼ぶ側で特殊化されている」と書いていた。測った速さから呼び先を推し量っただけで、呼び先そのものは確かめていなかった。速さの結論は正しかったが、理由の説明が事実と違った。

**オーバーロードではないが、罠は別の経路で起きる (2026-09-07 改訂)。** ADR-0033 決定 1 が避けたのは「`Int` と `Float` の口を並べると、どちらが呼ばれるかで目盛りが変わる」罠で、それはここでは起きない — どの型を渡しても同じ 1 本が呼ばれる。**しかし「リテラルの書き方で結果が変わる」ことそのものは起きる。**呼ばれる関数が 1 本でも、**渡る値**が変わるからである (決定 6)。

> **当初この節は**「その罠は起きない」とだけ書いていた。オーバーロード解決だけを見ていて、リテラルの既定型がどう決まるかを勘定に入れていなかった ([#1018](https://github.com/mokume-metal/mokume/issues/1018))。

> 破れたとき: 中を `Double` で持つと、GPU へ渡す直前で毎フレーム全頂点ぶんの変換が走る。作者からは見えない場所で費用が増える。

### 2. 広げるのは連続量だけ。数え上げは `Int` のまま

座標・寸法・長さ・角度・比率・色の成分は広げる。**個数・添字・分割数・種・世代・キーコードは `Int` のまま**にする。`sphere(_ radius:detail:)` は前半だけ広げ、`detail` は `Int` で受ける。

**同じ語が層によって違う型になることは受け入れる。** `shadowDetail(size: Int)` と `shadowRange(size: Float)` は同じファイルで引数ラベルまで同じだが、前者は焼き付け先の画素数、後者は世界の長さである。読んで区別できないという costs は、`Int` の場所を広げて「個数に 1.5 を渡せる」形にする costs より小さい。

> 破れたとき: 分割数や添字に小数が渡せるようになり、内部で丸める。渡した数と使われる数が違うのに、警告も出ない。

#### トップレベルの色と数の口にも広げる

広げる範囲を、Sketch 層と Canvas 層の描画の口から、**どの型にも属さないトップレベルの色と数の口**へ広げた ([#2255](https://github.com/mokume-metal/mokume/issues/2255))。対象は次の 11 の口の連続量で、受け方は決定 1 と同じ `some ScalarConvertible`、返り値は決定 3 のとおり `Float` (色は `LinearRGBA`) のままである。

- 数の口: `radians`・`degrees`・`map`・`lerp`・`constrain`・`norm`・`smoothstep`
- 色の口: `color(_:_:_:_:)`・`color(_ gray:_ alpha:)`・`color(hue:saturation:brightness:alpha:)`・`lerpColor` の `amount`

当初の採択は「描画 API」を題にしていて、トップレベルの口を広げるとも退けるとも書いていなかった。そのため docc の入口の「数の型」は「変数を渡すときは型を気にしなくて構いません」と言うのに、`map(i, …)`・`color(i, 0, 0)` は `Float(i)` と書かせていた。これは実装の取りこぼしではなく、決定の抜けだった。

選んだ形と、退けた 2 つの案:

- **採る: 総称だけにする。** 決定 7 と同じ天秤で、決定 6 の 2 つの代償を承知して受ける。このリポジトリの中で赤くなったのは参照スケッチ 1 行 (`degrees(2 * .pi)`) と検査 50 行で、どれも `Float.pi` などと綴り直した。黙って値が変わる呼び出し (11 の口の引数に、整数リテラルだけの割り算があるもの) は、このリポジトリの中には無かった。作品の側 ([works](https://github.com/mokume-metal/works)) は数えていない — 決定 6-a のとおり、手本を移す層ほど多く出る
- **退ける: `Float` 版を残し、総称を `@_disfavoredOverload` で併置する。** 既存の呼び出しは 1 つも変わらないが、`Int` の変数と整数リテラルの割り算を混ぜた呼び出し (`lerp(i, 10, 1 / 2)`) だけが総称へ行き、黙って 0 になる。決定 7 が描画の口で「どんな併置の仕方でも消せない崖」として退けた形を、別の層で採ることになる
- **退ける: `Float` のまま据え置き、決定 5 に「届かない」と足す。** 決定 5 の 3 か所は protocol では覆えないものだが、トップレベルの口は覆える。据え置くと、Sketch の口とトップレベルの口で書き味が割れたまま残る

決定 6 の 2 つの代償のほかに、このとき測った代償が 2 つある (#2255 の反証役が、単独の `swiftc` で口の形だけを写して測った。mokume の実物の組み立てではない):

- **型が決まらなくなる経路が、6-a のほかにもある。** 整数リテラルを渡した `atan(1)`・`sin(1)` の結果をこれらの口へ渡すと、`Float` 版と `Double` 版のどちらか決まらず赤くなる (`degrees(atan(1))`)。整数と小数を混ぜた数だけの式を引数ごとに連ねると、型検査が打ち切られて赤くなることがある (`color(255 * 0.8 + 1, 255 * 0.6 + 10 * 2, 255 * 0.2 - 5 * 3, 255 * 0.9 - 1)` は約 1.9 秒かけて打ち切られる。引数を 3 つにした形は通るが約 250 ms かかる)。どちらも描く口では採択の時点から同じで、赤くなるので黙っては変わらない。`.breaking.md` で名乗る
- **本体が数 ns の口では、総称の入口の上乗せが本体と同じ桁になる。** 決定 1 のとおり呼ぶ側では特殊化されないので、別のパッケージから `-O` で呼ぶと `map` は 1 回 2.5 ns から 6〜11 ns、`lerp` は 1.7 ns から 4.2 ns になった。決定 1 の「1% 台」は本体 60〜70 ns の `circle` で量ったもので、この口には当てはまらない。画素ごとに `map` を呼ぶ参照スケッチ (`PixelsAndPaint`・480×540) で、1 フレームあたり 1〜2 ms の見込みである。`@inlinable` で取り戻す手は決定 1 が退けた形なので、この改訂では採らず、実害 (作品のフレームが落ちる) が出たら決め直す

広げない口は決定 2 のとおりである。数え上げ (`color(hex:)` の `Int`) と、`LinearRGBA` を受けて `Float` を返す読む口 (`red`・`hue` など) は、連続量を受けないので対象に入らない。

#### 改訂 (2026-10-20) — `Transform` のメソッドと `jumpTime(_:)` を広げ、`LinearRGBA` の口の据え置きと音・カメラの射程の外を名乗る

2026-10-13 の改訂が残した 4 つの問いを、1 つの改訂で決めた ([#2525](https://github.com/mokume-metal/mokume/issues/2525))。当初の問いは #2255 の反証役が、同じ約束 (「変数を渡すときは型を気にしなくてよい」) を破る `Float` 固定の口が型のメンバと音・カメラに残っていると指摘したことで、#2644 が `jumpTime(_:)` などを「射程に入るかはこちらの問い」として寄せた。

| 口 | 決定 | 理由 |
| --- | --- | --- |
| `Transform` のメソッド (`translate`・`rotate(by:)`・`rotateX/Y/Z`・`scale`・`shearX/Y`) | **広げる** (`some ScalarConvertible`) | 同じ型の `apply` が総称で、積む口だけが `Float` だと、1 つの型の中で書き味が割れる。参照スケッチも使う口である。整数リテラルの割り算の罠 (決定 6-b) は、角度や倍率ではまず出ない |
| `Sketch.jumpTime(_:)` | **広げる** | Sketch の面の連続量 (秒) で、中は `Double` に直して使う。同じ動詞の `Movie.jump` と受け方が割れるのは、ターゲットが違うこととして受ける |
| `LinearRGBA.display(…)`・`.linear(…)` | **据え置く** | 下記 |
| 音とカメラの口 (`SynthSound`・`SoundEffect`・`SoundFile`・`Movie.jump` ほか) | **射程の外** | 下記 |

**`LinearRGBA.display`・`.linear` を据え置く理由は、0–1 の目盛りにある。** 0–255 の数を `n / 255` と直して渡す書き方が自然に出る口で、広げると整数リテラルの割り算が `Int` に決まり、黙って 0 (黒・透明) になる (決定 6-b)。このリポジトリの中だけで、`.display(red: 90 / 255, …)` の形が 7 行 (`LightColorTests` の 6 行と `ColorSurfaceTests` の `alpha: 128 / 255`) と ADR-0033 決定 3 の改訂 (2026-09-23) の説明にある。トップレベルの `color(…)` は 0–255 の目盛りで、割って渡す書き方がまず出ないので、2026-10-13 の改訂の天秤とは逆に倒れる。**決定 5 の「public init」の保留とは理由が違う** — あちらは protocol で覆えないこと、こちらは覆えるのに広げると黙って値が変わることである。同じ箱へは混ぜない。

**音とカメラの口は射程の外と決める。** この決定の射程は、スケッチが描く・数える面 (Sketch・Canvas とトップレベル、値を作る `Transform`・`LinearRGBA`) である。音とカメラは別ターゲット (`MokumeAudio`・`MokumeCamera`) の別の面で、変数を渡す作例で詰まった報告もまだ無い。作例で詰まったら、`Feature` として改めて起こす (ADR-0043)。

**検査を持つ。** 同じ取りこぼしが #2255 (11 の口) と #2524 (#2526 が自分の洗い出しで見落とした 3 の口) で、どちらも反証役が後から見つけた。足した本人には見えない — 組み立ては通り、`Double` の変数を渡した利用者だけが赤くなる。新しい検査を立てず、既存の `scripts/api-surface.py` (`make api`) の責務を広げた (`check_float_ports`)。見るのは MokumeCore の Sketch の面・`Canvas`・`Transform`・`LinearRGBA` とトップレベルの口で、連続量を `Float` で受ける引数があると名指しで落とす。通すのは次のとおり:

- 決定 2 の数え上げ (`Int` で受ける口なので、そもそも `Float` を取らない)
- 決定 5 の `ClosedRange<Float>`・public init (enum の case ペイロードも決定 5 だが、持ち主が見る対象に入っていない)
- 利用者が実装する口 (プロトコルの要件と既定の実装。`mouseMoved(deltaX:deltaY:)` の引数は mokume が渡す値で、利用者が渡す口ではない)
- 理由つきの表 (`FLOAT_ALLOWLIST`): 上の `LinearRGBA` の 2 本と、`Float`・`Double`・`Int`・`String` の口が並ぶ `expose(_:_:)`

`Table`・`Numbers`・`TextBounds`・`Orbit`・`Placement`・`Force`・`SketchSettings` のようなデータや設定の値を作る口と、音・カメラのモジュールが足した口は、見る対象の外である。

退けた案:

- **`LinearRGBA.display`・`.linear` も広げる** — 上のとおり、7 行と ADR-0033 の例が黙って 0 になる。広げたうえで検査を書き直す手もあるが、書き直す先が「割らずに 0–1 の数で渡す」になり、手本を移す書き方 (0–255 を割る) と逆を向く
- **`Transform` を据え置き、決定 5 に「届かない」と足す** — `apply` と積む口が 1 つの型の中で割れたまま残る。protocol で覆えるので、届かない理由にならない
- **検査を足さず、説明文だけで案内する** — #2255・#2524 のどちらも、説明文はあったのに口が取りこぼされた。文書だけの規約は守られない (ADR-0001 原則 6)

**代償**は決定 6 の 2 つと同じである。このリポジトリの中で赤くなったのは、`rotate(by: .pi / 2)` の形 (6-a) の検査 7 行と、`scale(x: .nan, …)`・`scale(x: .infinity, …)` の検査 4 行で、どれも `Float.pi`・`Float.nan` などと綴り直した。**黙って値が変わる呼び出し (6-b。`Transform` のメソッドと `jumpTime` の引数に、整数リテラルだけの割り算があるもの) は、このリポジトリの中には無い。** 作品の側 ([works](https://github.com/mokume-metal/works)) は数えていない。`Transform` の戻り値を `Vector2`・`Vector3` へ移す破壊 (#2617) と同じ版に出し、利用者の直しを 1 回にまとめる。呼び出しの費用は測っていない — モジュールの中では特殊化され、別のパッケージから呼ぶときは決定 1 の総称の入口の費用が付く。画素ごとに積む作品で実害が出たら、決め直す。

### 3. 返り値は `Float` のまま

`width` / `screenX` / `random` はすべて `Float` を返す。返り値まで広げると、受け取る側の型が呼び出しごとに変わって推論が壊れる。

### 4. 混在演算子は定義しない

`width / cols` (`Float ÷ Int`) は通らないままにする。`import mokume` した途端に標準の型どうしの演算が変わるのは、副作用が読みにくい。

**この決定により、#969 が実測した 2 つの失敗のうち片方しか消えない** — `let gap = 120.0` を渡す形は通るようになるが、`width / cols` は依然として `Float(cols)` と書く必要がある。要るとなったら別に決める。

### 5. 今回は届かない 3 か所がある

protocol では覆えないので、要るとなってから別に決める:

- **`ClosedRange<Float>` を取る口** — `emit` の `speed` / `angle` / `life` / `size` の 4 つ
- **enum の case ペイロード** — `Force` の 5 case・`Emitter` の 4 case
- **public init** — `Orbit.init` の Float 6 個・`Placement.init` の Float 4 個

#### `ClosedRange<Float>` の口は据え置く

1 つ目の `ClosedRange<Float>` を取る口は、保留ではなく**据え置き**と決めた ([#1707](https://github.com/mokume-metal/mokume/issues/1707))。幅の端に数でない値 (NaN) を書くと (`speed: Float.nan...1`)、Swift の `...` が `lowerBound <= upperBound` の前提違反で、幅を作る作者の行でプロセスごと止める。`emit` の受け口は値を検めて注意を言い 1 個も出さないが ([#1623](https://github.com/mokume-metal/mokume/issues/1623)・ADR-0020 決定 5)、この値はそこへ届かない。

それでも口の形は変えない:

- **止まるのは作者のコードで、mokume の受け口ではない。** 下端が上端を越える幅 (`speed: 60...20`) も同じ所で止まり、それを mokume の約束違反と読む人はいない。NaN の端はその特別な場合で、ADR-0020 決定 5 の「受け口で検める」は受け口に届かない値までは約束しない
- **形を変える作例が無い。** 2 つの数や自前の幅の型で受ければ受け口で検められるが、今ある `emit` の呼び出しをすべて書き換えさせる。それを正当化する作例も、作品で踏んだ報告も無い (#1623 の反証で見つかった)。作例が出たら `Feature` として起こす (ADR-0043)

代わりに `emit` の説明が、幅の端の NaN と逆順の幅は `emit` に届く前に Swift が止めることと、計算した値を端に使うときの書き方を名乗る。無限の端は止まらずに届き、受け口が断る。残りの 2 か所 (enum の case ペイロード・public init) の保留は動かない。

### 6. 総称の引数では、リテラルの型の決まり方が 2 通りに変わる

**これが受け口を広げることの代償である。** 引数の型が `Float` に固定されていたときは、渡す式の型がそこから逆算されていた。逆算が効かなくなると、**赤くなる経路と、黙る経路の 2 つ**が出る。

#### 6-a. 型が決まらず、赤くなる

```swift
rotate(.pi / 4)                        // 以前は Float に決まった。いまは決まらない
fill(.nan, 0, 0)                       // 同上
perspective(2 * atan(64 / 300), …)     // 64 / 300 の型が決まらない
```

`Float.pi` / `Float.nan` / `Float(64) / 300` と綴る。

**当初この節は「実測では影響は小さい」と書いていた** — 移行時に直したのは `.pi` が 6 箇所 (リポジトリ全体の `.pi` 47 箇所のうち)、`.nan` / `.infinity` が 15 箇所、逆算していた式が 1 箇所だったからである。

**その標本はこのリポジトリの内側で閉じていた。** 制作トラックを `v0.7.0` へ上げたら 23 箇所だった ([works#36](https://github.com/mokume-metal/works/pull/36)・[#1017](https://github.com/mokume-metal/mokume/issues/1017)) — Atlas 22・Solids 1 で、内訳は `rotate[XYZ]` / `perspective` / `arc` / `spotLight(angle:)` / `random`、**どれも手本 (Processing / p5.js) が `PI` と書いている場所**である。[ADR-0020](0020-api-naming-and-surface.md) 決定 1 が「利用者が最初に触る層は手本の綴りが正」と決めている以上、**手本を移す層ほど濃く出る**。参照スケッチだけを標本にすると必ず過小評価になる。

#### 6-b. 型が `Int` に決まり、黙る

```swift
fill(255, 255 * 50 / 100)   // v0.6.0: 127.5   v0.7.0: 127
circle(x, y, 1 / 2)         // v0.6.0: 0.5     v0.7.0: 0   ← 何も描かれない
```

**整数リテラルだけで書かれた式には、リテラルの既定型 (`Int`) が付く。** `Int` の割り算は整数除算なので、小数部が落ちたうえで `Float` に変わる。6-a と違って**コンパイルは通る**ので、絵だけが変わる。

実害は測ってある ([#1018](https://github.com/mokume-metal/mokume/issues/1018))。works の 6 作品・約 167 枚のうち動いたのは `additivewave-1.png` の 1 枚で、透かしが 1 階調ぶん濃い。**目には見えず、指紋の台帳を持っていたから見つかった。**

**案内では消せない。** `1 / 2` は渡る前に `Int` の `0` になっているので、受け取る側からは作者が意図して書いた `0` と区別が付かない。lint も利用者のコードには届かない。書く側が「割り算を含む式は片方を `Float` で書く」を知っているかどうかに懸かる。

> 破れたとき: 作者が `rotate(.pi / 2)` と書いて「曖昧」と言われ、なぜ通らないのか分からない (6-a)。あるいは `circle(x, y, 1 / 2)` と書いて、何も描かれない理由が分からない (6-b)。

#### 6-c. 型が `Int` に解かれ、誤りが `width` を指す

```swift
for i in 0..<count {
    circle(i * width / count, height / 2, 10)
    // error: cannot convert value of type 'Float' to expected argument type 'Int'   ← width を指す
}
```

6-a・6-b はリテラルの型の決まり方だが、これは**変数どうしを混ぜた式**で起きる。添字 (`Int`) と面が返した数 (`Float`) を混ぜた式は、決定 4 が混在の演算子を定義しないので、受け口の型にかかわらず通らない。**変わったのは誤りの向きである。** 受け口が具体の `Float` だったとき (v0.6.0 まで) は、コンパイラが `binary operator '*' cannot be applied to operands of type 'Int' and 'Float'` と混在のことを言った。受け口が総称になると渡す式の型が決まらず、コンパイラは式を `Int` で解こうとして、`width` のほうを「`Int` ではない」と名指しする (本体を `import mokume` した swiftc 6.4 で確かめた。トップレベルの `map(i * width / count, …)` も同じ文面で `width` を指す)。読んだ人も AI も、`width` を `Int` にする向きへ直しかねない。

**正しい直し方は添字の側である。** `Float(i) * width / Float(count)` と添字を揃えるか、`stride(from: Float(0), to: width, by: step)` で添字を経ずに `Float` のまま回す。

**これも総称の受け口の代償として、決定 7 が戻さないと決めた中に入る。** 6-a・6-b と同じく、案内で名乗る — `Documentation/mokume.docc/mokume.md` の「数の型」に、誤りの文面と直し方を置く。決定 7 の表には行を足さない。表は 6-a・6-b を案ごとに測ったもので、この形はどの案でも (混在演算子を定義しない限り) 通らず、案の選びを分けないためである。

退けたもの:

- **混在の演算子を定義する** — 誤りは消えるが、決定 4 が理由に挙げた「`import mokume` した途端に標準の型どうしの演算が変わる」は、いまも当たる
- **`Float` で回す補助の口** (例: 添字ごとに `Float` の位置を返す口) — 公開の口が増える。作例が出てから `Feature` として別に起こす (ADR-0043)。文書で足りるうちは足さない

> 破れたとき: 作者が `i * width / count` を書いて、コンパイラの言うとおりに `width` を `Int` へ直そうとし、`width` が使えなくなって行き詰まる。

### 7. 6-b を承知したうえで、受け口は戻さない

**戻す/併置する案は全部組んで測った。** `swiftc -O` で実際に実行した結果:

| 案 | 6-a (`.pi`) | 6-b (`1 / 2`) | `Int` 変数 | `let gap = 120.0` |
| --- | --- | --- | --- | --- |
| v0.6.0 (`Float` 1 本) | ✓ | ✓ 0.5 | ✗ 赤 | ✗ 赤 |
| **本 ADR (総称)** | ✗ 赤 | ✗ 黙って 0 | ✓ | ✓ |
| `Int` の準拠を外す | ✗ 赤 | △ 赤 (ambiguous) | ✗ 赤 | ✓ |
| 具体の `Float` 版を併置 | ✓ | ✗ 黙って 0 | ✓ | ✓ |
| 併置 + `@_disfavoredOverload` | ✓ | △ 崖あり (下記) | ✓ | ✓ |

**併置は 6-b を直さない** — 整数リテラルの既定型が先に決まるので、総称側が勝つ。`@_disfavoredOverload` を足すと素直な呼び出しでは直るが、`circle(i, i, 1 / 2)` (`i` が `Int` 変数) だけ黙って 0 に戻る。オーバーロード解決は関数まるごとで決まるので、**渡した値が他の引数の型で変わる**ことになり、6-b より読みにくい。**この崖はどんな併置の仕方でも消せない。**

**`ScalarConvertible` に `static var pi` を要求する案は Swift で成立しない。** `some ScalarConvertible` でも `<T: ScalarConvertible>` でも `static member 'pi' cannot be used on protocol metatype` で落ちる。暗黙メンバ参照は具体型が決まっている口でしか解決しないので、protocol に要求を足しても届かない。

**したがって 6-b を新しい罠なしに消せるのは、受け口の型そのものを具体に戻す場合だけである。** それでも戻さない理由は 3 つ:

1. **実害が釣り合わない。** 6-b が動かした絵は 167 枚中 1 枚・不可視である。[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) の秤で、195 引数の巻き戻しと釣り合わない
2. **戻すと #969 の実測された摩擦が戻る。** ローカルモデル実験で全モデルが落ちた形が復活し、[#983](https://github.com/mokume-metal/mokume/pull/983) と [#990](https://github.com/mokume-metal/mokume/pull/990) を巻き戻すことになる
3. **`255 * 50 / 100` は Swift として読めば 127 が正しい。** v0.6.0 の 127.5 のほうが「引数の型が式の型を決めていた」特殊な状態で、そこへ戻すのは「mokume の中でだけ Swift の読み方が変わる」を選び直すことである。決定 4 (混在演算子を定義しない) が同じ理由で断ったのと同じ向きになる

**代わりに、6-b を名乗る。** `ScalarConvertible` の説明文・作者の読む面 (`Documentation/mokume.docc/mokume.md` の「数の型」)・リリースノートの 3 か所で、割り算を含む式は片方を `Float` で書くことを言う。挙動そのものは `Tests/MokumeCoreTests/ScalarConvertibleTests.swift` が固定する — 受け口を将来動かせば赤くなる。

> 破れたとき: 6-b の実害が積み上がっても、この表が「測って断った」と読めるので誰も測り直さない。**新しい実害が出たら、この表に行を足してから決め直す** — 単発の事故で受け口を動かすと、#969 と #1018 のあいだで振り子になる。

## 影響

- **ADR-0033 の影響節が 1 行解消される。** 「`Int` の変数はそのまま渡せない」は本 ADR で消えるので、あちらを改訂する。**決定 1 そのものは動かない** — 避けたのはオーバーロードの罠で、ジェネリックはオーバーロードではない
- 受け口は 38 ファイル・195 の引数が変わる。**Sketch 層と Canvas 層を必ず同じ形にする** — `scripts/api-surface.py` の `check_doc_canon` は `(title, signature)` の組でペアを作るので、片方だけ変えると組が成立せず「Canvas 側の説明文が長い」の診断が黙って効かなくなる
- **説明文の例と参照スケッチの綴りは書き換えない。** `Float(i)` はそのまま通る。書き換えると `// shot:` 台帳の指紋が動き、絵の撮り直しが付いてくる
- 作者に薦める数値型の案内は [#924](https://github.com/mokume-metal/mokume/issues/924) が書く (本 ADR の決定待ちで止めてある)
- **破壊的な影響を持つ変更は、`changelog.d` の `.breaking.md` で名乗る (2026-09-07)。** 本 ADR を実装した [#983](https://github.com/mokume-metal/mokume/pull/983) は 6-a を `.feature.md` の本文に書いたので、`v0.7.0` のノートに `## 破壊的変更` の節が立たなかった。`changelog.d/README.md` は既にそう定めており、規律の不在ではなく従い損ねである ([#1017](https://github.com/mokume-metal/mokume/issues/1017))
- **面の変更の影響を測る標本は、このリポジトリの内側では足りない (2026-09-07)。** 6-a は 6 箇所と測って 23 箇所だった。手本を移す層を持つのは制作トラックの側なので、面を動かしたら [works](https://github.com/mokume-metal/works) の追随結果まで見て初めて影響が数えられる。**これを仕様として引き受けた判断は [ADR-0022](0022-production-track.md) 決定 2 の追補が持つ** — 標本の由来が変わらない以上、上流の台帳を厚くしても塞げない ([#1027](https://github.com/mokume-metal/mokume/issues/1027))
