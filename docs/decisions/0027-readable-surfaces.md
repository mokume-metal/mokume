# ADR-0027: 読める面の規範 (正典の所在・絵の置き方・面の分け方・言語)

## 状態

採用 (2026-08-30) / 改訂 (2026-08-30): 面が名乗る名前の決まり方

## 文脈

いま外から引けるのは README と、版ごとに Release へ載る公開 API の一覧 (`make api-list`) だけである。**使い方の説明はソースの `///` の中にあり、読む人が引ける形になっていない。**

説明を読める形で配るには面を組み立てる必要があり、そこには**面を広げてからでは直せない**決定が 4 つ含まれる。

- **正典の所在** — 一覧も、人が読む参照の面も、どちらも説明文の生成物になる。**同じ知識が 2 つの経路で外へ出る**ので、役割を先に分けないと [ADR-0001](0001-founding-principles.md) 原則 9 (同じ内容の二重管理を作らない) と当たる
- **絵の置き方** — 実行結果の絵は説明の質をほぼ決めるが、原則 7 はリポジトリに生成物とバイナリを置くことを禁じている。外へ置くなら URL がどこかに残らなければならず、その URL は撮り直さないと作れない (GPU と外部サービスの鍵が要る)。**生成物でありながらコミットが要る**ように見える唯一の点で、ここが本 ADR 最大の判断になる
- **面の分け方** — 機械が組み立てる参照と、手で書く入口を、混ぜるか並べるか
- **言語** — 原則 10 は多言語を「必要になった時点で別の ADR」に送っている。1 言語で出すとして、後から足すときに何が制約になるかだけ先に見ておく

### 測ったこと

決定の材料は、手元の道具 (Xcode 26 同梱の `docc`・Swift 6.3) と `make api` が出すシンボルグラフで実測した。**道具の性質がこのうち 3 つを決めている**ので、根拠として残す。

| 問い | 実測結果 |
| --- | --- |
| 参照の面を作る道具は、いくつの入力から組めるか | **カタログは 1 つだけ**。2 つ目を渡すと `Unexpected argument` で拒否される |
| 何がページになるか | **シンボルグラフの置き場にあるモジュールが全部**。product に含まれない開発用の実行ターゲットまでページになった |
| 扱える絵の形式 | PNG ○ / GIF ○ / mp4 ○ (`@Video`) / **WebP は警告も出さずに落ち、参照ごと本文から消える** (周りの文だけ残る) |
| 外部 URL を指せるか | **指せる**。素の Markdown も `@Image` / `@Video` の source も、「見つからない」旨の警告は出るが**参照は生成され、出力にその URL がそのまま載る** |
| 手で書いた文章をどこまで置けるか | 記事・見出し・表・コードブロックは残る。**生の HTML は警告も出さずに落ちる** |
| 記事を置いたら出るか | **入口から辿れる形で載せた記事だけが出る。** どこからも参照していない記事は**警告も出さずに出力から消える** |
| 記事の公開パス | `/documentation/<カタログのディレクトリ名>/…` — **カタログ名がそのまま URL に出る**。ただし**これは記事だけの話である** (次の行) |
| モジュールのページの公開パス | `/documentation/<シンボルグラフの module.name>/…` — **カタログ名は効かない。** 何も手を入れなければ**ターゲット名**がそのまま URL に出る (2026-08-30 追記・[#561](https://github.com/mokume-metal/mokume/issues/561)) |

**「置いても出ない」が、この道具のいちばん多い壊れ方である。** 上の表のうち 3 行 (WebP・生の HTML・辿れない記事) は、ビルドが緑・警告も無し・出力にだけ存在しない、という形で失敗する。以下の決定は、この壊れ方を人の注意力ではなく形で避けることを重く見ている。

## 決定

### 1. 説明文が唯一の入力 — 一覧は機械が読む面、参照は人が読む面 (2026-08-30 改訂)

公開 API の説明の正典は**ソース内の `///` だけ**とする。公開 API の一覧も、人が読む参照の面も、どちらもその生成物であり、正典を名乗らない。

役割は次の線で分ける。

| | 一覧 | 参照の面 |
| --- | --- | --- |
| 読み手 | 機械 (エージェント・道具) | 人 |
| 形 | 1 ファイル。全体を一度に読める | ページに分かれ、相互にリンクする |
| 配り方 | 版ごとに Release の資産 | 公開された面 |

**カタログに手で書いてよいのは、記号に属さない文だけ**である (面の入口・記号の集まりの説明・面をまたぐ案内)。API 1 本の説明をカタログに書くと、その瞬間に同じ知識の置き場が 2 つになる。[ADR-0020](0020-api-naming-and-surface.md) 決定 4 が「説明文の正本は利用者が最初に触る層に置く」と定めているのと同じ規律を、ソースの外側へ延長したものである。

**参照の面に載せるモジュールは名指しで選ぶ。** 実測のとおり、道具は与えられたシンボルグラフのモジュールを区別せず全部ページにする — 開発用の実行ターゲットまで公開される。一覧の側は既に対象モジュールを名指しで受け取っており (`scripts/api-surface.py` の `--module`)、参照の面にも同じ名指しを要求する。**面に何が出るかを、ビルドの副産物に決めさせない。**

**面が名乗る名前も名指しする** ([#561](https://github.com/mokume-metal/mokume/issues/561)・2026-08-30 改訂)。**当初は名前について何も決めていなかった** — 決めたのは「何が出るか」だけで、面が何という名前で出るかは道具に任せていた。任せた先はシンボルグラフの `module.name`、つまり**ターゲット名**である。[ADR-0016](0016-package-structure.md) の層の割り方の産物であって、面の名前として選ばれたものではない。結果、利用者が `import mokume` の 1 行で開く面が `/documentation/mokumecore/` を名乗り、面の入口が「この面の題になっている `MokumeCore` は〜」と**言葉で漏れを埋める**ことになっていた。「面に何が出るかを、ビルドの副産物に決めさせない」は、**名前にも等しく効く**。

素直な形 — アンブレラ (`Sources/mokume/`) のシンボルグラフを渡す — は**道具の側が壊れていて採れない** (実測)。`@_exported import` の再エクスポートはグラフの上で 2 方向に壊れる:

| 壊れ方 | 実測 |
| --- | --- |
| 要らないものが載る | Darwin の記号が **341 ページ**漏れる (`acos` / `cbrt` / `DBL_MAX` …)。三角関数 7 本の名指し再エクスポート ([#193](https://github.com/mokume-metal/mokume/issues/193)) の副産物 |
| 要るものが載らない | `Inlet` / `Outlet` / `Plugin` / `PluginRegistry` / `StartupReads` / `OutputFrame` の **6 記号**がグラフに現れない |

**アンブレラの意味は正しく、それを運ぶ道具が壊れている。** だから意味だけを迂回して実現する — 実体のグラフを、利用者が `import` する名前で名乗らせる (`scripts/reference-graphs.py`)。**書き換えるのは読者に名前として見える欄だけ**で、記号の同一性 (マングル名) は実体を指したままにする — どの欄かと、見落とすと何が読者に漏れるかはスクリプトの冒頭が持つ。書き換え後の名前は実在する公開モジュール名であって、作り出した名前ではない。

**出力は現行と 1 ページも警告も違わない** (938 ページ・警告 16 本。ページの metadata まで突き合わせて、違うのは名前として現れる値だけであることを確かめてある)。

**内部のモジュールが増えても形は変わらない。** 同じ名前を名乗るグラフは 1 つの面にマージされる (実測: 2 本渡して 938 → 940 ページ・警告は増えず)。利用者から見た入口を 1 つに保つ ADR-0016 決定 2 と同じ形に、そのまま伸びる。

**カタログに置いた文は、入口から辿れる形で載せる。** 辿れない文は出力から消え、しかも何も言われない (実測)。置いたことと出ることは別なので、**置いた文が実際に出ていることは機械で確かめる** (完了条件は [#478](https://github.com/mokume-metal/mokume/issues/478) が持つ)。

### 2. 絵は外へ置き、指す 1 行をソースに書く — 台帳ファイルは作らない

実行結果の絵は外部ホスティングへ置き、リポジトリには 1 バイトも入れない。**絵を指す URL は、説明文の中の 1 行として置く** — 実測のとおり、外部 URL は参照として生成され、そのまま出力に載るからである。

これで**独立した URL 台帳は要らなくなる**。URL はソースの一部として存在し、コミットされるのは絵ではなく「どこにあるか」を書いた行である。

- **機械が書き戻す領域は印で区切る。** 印から下だけを機械が書き、印より後ろに人が文章を書かない。人の文章と機械の書き戻しが 1 本の線で分かれていれば、撮り直しが説明を壊しようがない
- **撮影の記録 (指紋・撮った版) は、同じソースファイルの、読み手に出ない側へ置く。** 説明文として拾われるのは `///` だけなので、普通のコメント行に置けば記録は公開される文章を汚さずソースに残る。**別ファイルの台帳は作らない**
- 同じ中身の絵には同じ URL が返る (`.claude/skills/gyazo-evidence/SKILL.md`)。したがって**撮り直して URL が変わったか**が、そのまま**絵が変わったか**の判定になる

#### 原則 7 との関係

原則 7 が禁じているのは 2 つ — **生成できるものをコミットすること**と、**バイナリを置くこと**である。外部資産の URL と撮影時の指紋は、**どちらにも当たらない**。撮影という一度きりの出来事の結果であって再生成できず、バイナリでもない。

したがってこれは**原則 7 の例外ではなく、対象外**である。原則 7 の定義は変えない。

**歯止めを 1 つ置く。** 「再生成できない事実の記録だからコミットしてよい」と名乗れるのは、**外部に置いた資産の識別子**と**撮影時の指紋**に限る。この名乗りを広げたくなったときは、広げる側が本 ADR を改訂する。

#### 形式は面ごとに違う (実測)

| 宛先 | 静止画 | 動き | 落ちるもの |
| --- | --- | --- | --- |
| 参照の面 | PNG | GIF / mp4 (`@Video`) | **WebP — 警告も出ずに参照ごと消える** |
| Issue / PR | PNG | WebP | mp4 |

**同じ「絵を載せる」でも、配信系の能力が違えば答えが違ってよい。** 無理に 1 本へ揃えると、能力の低いほうに合わせて全体が劣化する。ただし違う結論を持つ以上、**なぜ違うかは両方の場所に書く** — 何を載せるかの規律は `AGENTS.md`「描画に影響する変更」が、撮り方は `.claude/skills/gyazo-evidence/` が持つ。

#### 「警告 0」を機械のゲートにするときの条件

外部 URL は**必ず**「見つからない」警告を出す。したがって説明文の質を機械で見る際 ([#479](https://github.com/mokume-metal/mokume/issues/479))、警告 0 を要求するなら**外部資産が解決できない旨の警告だけを除く**必要がある。除かずに警告 0 を課すと、絵を載せた説明文がすべて赤くなる。

### 3. 参照の面は root に置き、手で書く層を丸ごと被せる (2026-08-30 改訂)

参照の面は**公開先の root** に置く。手で書く層 (`Documentation/site/`) は、その上へ**丸ごと被せる**。同じ名前があれば手で書いたほうが勝つ。

当初は逆に決めていた — 参照の面を配下の 1 ディレクトリ (`/reference/`) に閉じ込め、root は入口が丸ごと使う、という形である。**改訂したのは、読者に見える URL が道具の都合で 2 段になるためである** ([#543](https://github.com/mokume-metal/mokume/issues/543))。

| 基準パス | 読者が見る URL |
| --- | --- |
| `reference` (当初) | `/reference/documentation/mokumecore/` |
| 空 (改訂後) | `/documentation/mokumecore/` |

`documentation` の 1 節は**道具の出力に焼き込まれている** (索引の `path`・ページのディレクトリ構造・面のルータがすべてそれを前提にする)。道具が触らせるのは接頭辞だけなので、`/reference/mokumecore/` という形は**選択肢として存在しない**。残る 2 つのうち、接頭辞を空にしたほうが短く、道具の面としても標準の形になる。

#### 元の懸念にどう答えるか

重ねることを避けていたのは、「どちらの生成系のどの資産を公開へ写すか」の**列挙が要るようになり、列挙は漏れる**からである。漏れたときの症状は「そのファイルだけが公開されない」で、ビルドは緑のまま気付く手掛かりが無い。

**だから守るのは「選り分けをしない」ことである。** 面の出力を丸ごと写し、その上に手で書いた層を丸ごと被せる — どちら側にも「どれを写すか」の判断が無いので、列挙は現れない。

**当初はこれを「上書きは `index.html` 1 枚だけ」と枚数で書いていたが、半日で反例に当たったので改めた** ([#549](https://github.com/mokume-metal/mokume/issues/549))。面の道具はモジュールのページしか作らないため、`/documentation/` のような**途中の階層が 404 になる** — URL を後ろから削って上へ行く読者はそこで行き止まりになる。塞ぐには 2 枚目が要り、枚数の上限はそれを禁じてしまう。枚数は本質 (選り分けの有無) の代理にすぎず、代理のほうが先に壊れた。

手で書いた層が増えるほど、生成物の名前を意図せず覆う危険は上がる。**覆ったかどうかは面を引いて確かめる** — 何が出ていなければならないかはカタログから導けるので、この危険は新しい機構ではなく既存の照合 (`scripts/check-published-reference.py`) が受け持つ。

公開の印 ([#483](https://github.com/mokume-metal/mokume/issues/483) の `publish-stamp.txt`) も root に居るが、これは読む面ではなく機械が引く 1 本である。

参照の面の中身は**1 つのカタログに集める** (道具がそれしか受け取らないため、分けたぶんは入力にならない)。カタログのディレクトリ名は**記事の**公開 URL に現れるので、**内部の都合ではなく面の名前として選ぶ**。**モジュールのページの URL はカタログ名では決まらない** — そちらは決定 1 の改訂が持つ (2026-08-30 改訂)。

**公開の起動条件は、公開に使う入力を覆っていなければならない。** 入力の一部が起動条件から漏れると、ビルドは緑のまま公開だけが古くなる。これも人の規律ではなく機械の照合で守る (完了条件は [#478](https://github.com/mokume-metal/mokume/issues/478) / [#483](https://github.com/mokume-metal/mokume/issues/483) が持つ)。

### 4. 当面は 1 言語 — 多言語は別 ADR

面は日本語 1 言語で出す。原則 10 のとおり、多言語化は必要になった時点で別の ADR として判断する。識別子は英語なので、面には日本語の説明と英語の識別子が並ぶ。

後から足すときに効く制約だけを、実測として書き残す。

- **カタログは 1 つしか渡せない。** 1 つのカタログに 2 言語を入れて切り替えることはできないので、言語ごとにカタログを複製して並べる形になる
- **カタログ名が URL に出る。** 複製先のディレクトリ名を変えると、言語間のパスの 1:1 対応が壊れる
- **生の HTML は落ちる。** 言語切替をページの中へ差し込む逃げ道が無く、切替はページの外 (面の入口) が持つことになる

## 影響

- 後続の完了条件がここから書ける。対応は次のとおり:

  | Issue | 本 ADR のどこから来るか |
  | --- | --- |
  | [#478](https://github.com/mokume-metal/mokume/issues/478) 参照の面を組み立てて配る | 決定 1 (モジュールの名指し)・決定 3 (面の置き場・起動条件が入力を覆う) |
  | [#479](https://github.com/mokume-metal/mokume/issues/479) 説明文の質を機械で見る | 決定 2 (外部資産の警告を除いた警告 0) |
  | [#480](https://github.com/mokume-metal/mokume/issues/480) 実行結果の絵を撮って書き戻す | 決定 2 (印で区切る・記録は読み手に出ない側・台帳を作らない) |
  | [#481](https://github.com/mokume-metal/mokume/issues/481) 絵が何かを示していることを測る | 決定 2 (絵が説明の質を決める以上、絵の質も機械で測る) |
  | [#482](https://github.com/mokume-metal/mokume/issues/482) 入口のページと行き来 | 決定 3 (root の `index.html` 1 枚)・決定 4 (切替は面の入口が持つ) |
  | [#483](https://github.com/mokume-metal/mokume/issues/483) 独自ドメインと公開の追随 | 決定 3 (ビルドの緑は公開の緑ではない) |
  | [#543](https://github.com/mokume-metal/mokume/issues/543) 面を root へ移す | 決定 3 の改訂そのもの |
  | [#549](https://github.com/mokume-metal/mokume/issues/549) 中間の経路が 404 | 決定 3 の再改訂 (枚数 → 選り分けの有無) |

- 決定 1 により、公開 API の説明を書く場所は `///` に固定される。参照の面を足しても、説明を書く手順は変わらない。
- 決定 1 の改訂により、面が名乗る名前は名指しで決まる。**内部のターゲットを層の都合で改名しても、読者が見る URL は動かない。** 逆に、面の名前を変えるときは面を指しているところ (README・入口の HTML・中間の 1 枚) が一緒に動く必要がある。
- 決定 2 により、原則 7 は緩まない。リポジトリに入るのは URL と指紋の行だけで、絵そのものも、絵から作れる生成物も入らない。
- 決定 2 の「印で区切る」により、説明文の一部が機械の書き込み対象になる。書き戻しは何度走らせても同じ結果になる形 (べき等) でなければならず、これは #480 の完了条件になる。
- 決定 3 の改訂により、手で書く層は `Documentation/site/` の 1 か所に集まり、枚数の制限は無くなった。入口の設計 (#482) はこの中で自由に組める — 守るべきは選り分けをしないことだけで、面をサブドメインへ分ける判断も引き続き #482 が持つ。
- 決定 3 の改訂により、面の URL から 1 節が消える。公開済みの `/reference/…` は 404 になるが、この形で外に出ていたのは 1 日で、指していたのは README と未リリースの changelog 断片だけである (#543 で同時に直す)。
- 決定 4 により、当面は訳を作らない。将来の多言語化は上の 3 制約を前提に設計することになる。
- 本 ADR は**規範だけを決め、機構は決めていない**。検査・ゲート・ワークフローを足すのは後続の Issue の仕事で、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) の順序 (実害 → Issue → 機構) はそのまま効く。
