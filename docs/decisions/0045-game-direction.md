# ADR-0045: ゲームも書ける方向 — 簡単なスケッチを複雑にせず、足す道として置く

## 状態

採用 (2026-10-14) / 改訂あり (本文の「改訂 (日付)」見出し)

## 文脈

mokume は、Processing の流儀で絵と動きを書く道具として作ってきた。ここに次の要望が出た ([#2580](https://github.com/mokume-metal/mokume/issues/2580))。

- 想定する利用者は、**Mac で開発できる環境にいる学生**である。授業やゲームジャムで、Processing の気楽さのままゲームまで作りたい
- 作ったゲームを、自分の iPhone / iPad でも遊べるようにしたい。配布に Xcode と署名を使う手間は許容する

### 席が空いている

- iOS で一般的な Unity はエディタ中心で重い。Apple 公式の SpriteKit は、保持モードのノードの木で組むので書き味が重い
- Swift で、コードだけで、即時モードで書けるゲームの道具の席が空いている
- Siv3D (C++) は「Processing のように書けて、ゲームも作れる」ことを示している。ゲームでの書きやすさの大部分を担うのは、**値が振る舞いを持つ書き方** (`Circle(…).intersects(enemy)`) である

### いまの mokume で詰まるところ (2026-10-13 に main で調べた)

| 穴 | いま |
| --- | --- |
| 図形の値と当たり判定 | `intersects` / `contains` の公開が 0 件 |
| 押した瞬間の判定 | `keyPressed()` がキーリピートで連射される |
| 修飾キー・窓を離れたときの押下 | `flagsChanged` を拾わない。窓が key でなくなっても押下中のキーを空にしない |
| 時間 | 窓は実時間の時計だけで、`deltaTime` が毎回ばらつく。積み上げた状態は揃わない (ADR-0025 決定 6) |
| 自作の型の中の語彙 | `fill()` や `mouseX` は `Sketch` のメソッドなので、`struct Player` の中から呼べない |
| 置き場 | 窓は `Sketch.main()` が `NSApplication.run()` で持ち、外から埋め込めない (ADR-0012・ADR-0032) |
| 対象 | macOS 専用 (ADR-0001 原則 5)・物理は入れない (ADR-0041) |

### 既存の ADR とぶつかる

上の要望は、既存の ADR の何本かと逆のことを言う。食い違ったまま実装に入ると、並行して作るエージェントは古い ADR に沿って作る。本 ADR は方向を決め、ぶつかる ADR は同じ変更で改訂する (決定 14 の表)。

### 1. 簡単なスケッチを複雑にしない。ゲーム・リリース・外部サービスは、足す道として置く

**この方向で足すものは、どれも `draw()` だけの簡単なスケッチの書き味を変えない。** リリース・外部サービス・ゲーム層は、使う人だけが足す道として置く。メンテナの言葉では「リリースをするのは全員ではない。やりたい人ができる道があることが重要。メインは、Processing のように簡単なスケッチを作る部分が複雑にならないこと」である。[ADR-0001](0001-founding-principles.md) 原則 1 に同じことを書き足した。

- **ゲームエンジンにはしない。** Unity・SpriteKit と機能の数で競わない。GUI のエディタとアセットの制作工程は持たない ([ADR-0041](0041-standard-scope-map.md) のノードエディタの行)
- 書き方は 2 つを同じスケッチの中で混ぜて使える。Processing 流 (`fill()` してから `circle(x, y, d)`) と、値が振る舞いを持つ書き方 (`ball.intersects(paddle)`) である
- 新しい口は、使わないスケッチに何も要求しない (名乗った 0.x の破壊的変更を除く。影響の節)。設定 (`clock: .frames`)・プロトコル (`SketchPart`)・ゲーム層 (`MokumeGame`) は、書いた人にだけ効く

```swift
final class Game: Sketch {
    var settings: SketchSettings { SketchSettings(width: 480, height: 270, clock: .frames) }
    var player = Player()
    var enemies: [Circle] = []

    func draw() {
        player.update()
        for e in enemies where e.intersects(player.body) { gameOver() }   // 値が判定を持つ
        background(20)
        player.display()
        fill(90, 160, 255)                                              // Processing 流
        for e in enemies { e.draw() }
    }
}

struct Player: SketchPart {                                             // 自作の型の中でも語彙が使える
    var body = Circle(x: 240, y: 200, radius: 10, fill: color(242, 115, 51))
    mutating func update() {
        if keyboard.isPressed(.arrowLeft) { body.move(by: Vector2(-4, 0)) }
        if keyboard.justPressed(.space) { jump() }
    }
    func display() { body.draw() }
    mutating func jump() { /* … */ }
}
```

> 破れたとき: ゲームのための設定や型の名乗りが、円を 1 つ描くだけのスケッチにも要るようになる。主な利用者である学生が最初の 1 枚で止まる。

### 2. 目指す品質は、2D は小規模な商用インディー、3D はスタイライズドな小規模まで

| | 目指す | 作風の例 | 目指さない |
| --- | --- | --- | --- |
| 2D | 授業・ゲームジャムから、小規模な商用インディーまで | ローグライク・弾幕・パズル・デッキ構築・横スクロール | — |
| 3D | 授業・ゲームジャムの 3D と、スタイライズドな小規模 3D | ローポリ・トゥーン・PS1 風・箱庭・1 画面のステージ制 | 写実的な PBR・オープンワールド・大規模なアセット運用 |

- **2D の天井は高く置ける。** コードだけで書くフレームワークから商用のヒットが出ている (Balatro は LÖVE、Celeste と Stardew Valley は XNA 系、Vampire Survivors の初版は Phaser)
- **3D の写実は目指さない。** Apple には RealityKit (ECS・物理・PBR・アニメーション) があり、写実の方向では差が付かない。写実はアセットの制作工程とレベルエディタに支えられていて、GUI エディタをやらない方針 ([ADR-0041](0041-standard-scope-map.md)) とぶつかる。スタイライズドな 3D なら、いまの照明・影・HDR で届く

3D の帯に届くまでに足すものは、次の順である。

1. 材質とテクスチャ付きのモデルの読み込み
2. 3D の値型と当たり判定 (`Sphere`・`Box`・`Ray`)
3. キャラクターのアニメーション (下)
4. 空間音響
5. 半透明の並べ替え
6. 3D の剛体物理 (外のリポジトリ)

**キャラクターのアニメーションは、段階的に上げる。**

| 方式 | 中身 | 上げる時 |
| --- | --- | --- |
| A. 部品の階層をコードで動かす | 関節ごとの剛体の部品を `push`・`rotate` で動かす。ほぼ既存の口で書け、AI もコードで書ける | 最初から |
| B. 3D に 2D のスプライトを立てる (ビルボード) | 2D のスプライトアニメを流用する。ドット絵の資産が使える | 最初から |
| C. 頂点アニメーション | glb の骨とクリップを、読み込み時にコマごとの形へ焼いて再生する。描画は既存の形とインスタンスのまま。時刻からコマへの純関数なので揃う | 作例が求めたら |
| D. GPU スキニング | 関節の行列で頂点を曲げる。動きのブレンドや上下半身の合成ができる | ブレンドが要る作例が来たら |

C と D は glb の読み込み (骨・スキン・クリップ) を共有するので、C から D へは描画側を足すだけで移れる。**キャラクターの形式は glb (glTF のバイナリ) を主にする。** Mixamo → Blender → glb は学生に身近な経路で、仕様も公開されている。本体の JSON の読み込みの延長で、外部依存なしに読める。

半透明の並べ替え ([ADR-0021](0021-solid-space-and-frame-assembly.md) 決定 2) と空間音響 ([ADR-0041](0041-standard-scope-map.md) 決定 2 の音の行・[ADR-0042](0042-camera-and-audio-standard.md) 決定 6 の範囲) の改訂は、3D の段で作例が求めたときに行う。本 ADR では改訂しない。

> 破れたとき: 写実の 3D へ寄せて RealityKit と同じ土俵に立ち、アセットの工程とエディタを抱える。逆に天井を低く置けば、授業の課題の先に続く作品が mokume の外へ出ていく。

### 3. 差別化は、機能の有無ではなく仮説として書く

| 仮説 | 中身 |
| --- | --- |
| H1 書き味 | Processing の手軽さのまま、当たり判定と入力を値で書けるので、同じ課題を少ないつまずきで完成できる |
| H2 AI と確かめる | 観測・入力の注入・リプレイが標準で、**追加のコード 0 行で** AI に遊ばせて確かめられる |
| H3 手元で動く | 作ったものが、そのまま Mac のアプリや自分の iPhone で動く |

個々の機能は Pico-8・LÖVE・p5play・Siv3D・Godot にもある。差はその組み合わせと、繋ぐ手間の少なさにある。

**p5.js に負ける軸は、勝負しないと明記する。**

| 軸 | p5.js | mokume |
| --- | --- | --- |
| 導入 | ブラウザで 0 秒 | Xcode のコマンドラインツールと mokume のインストールが要る |
| 書いてから動くまで | 即時 | Swift のビルドを待つ (ホットリロードで和らげる) |
| 友人に遊んでもらう | URL を送るだけ | Mac を持たない友人には渡せない |
| 教材 | 豊富 | まだ無い |

Web への書き出しは、描画が Metal に依るので目指さない。

**退けた案:**

- **段 1 の後に、学生数名で同じ課題を p5.js と比べる評価の段を置く。** メンテナの判断で置かない。そのため「フレームの時計を既定にするか」(決定 9) は、作例か利用者から実害が出たときに判断する
- **遊んだ記録から動画を書き出し、共有の道にする段を置く。** メンテナの判断で置かない。共有の弱さは上の負ける軸に残す

> 破れたとき: 「他に無い一級の特徴」と書いた機能が実は他にもあり、方向の根拠が崩れる。負ける軸を書かないと、勝てない軸 (導入の速さ・共有) に作業を注ぎ込む。

### 4. 置き場は 3 段にする

| 置き場 | 部品 |
| --- | --- |
| **本体の既存の領域を延ばす** | 2D / 3D の値型と当たり判定、押した瞬間・離した瞬間の判定、時間の値 (`Stopwatch`・`Countdown`) とイージング、効果音の重ね鳴らしと音量のバス、書き込み先の解決、スプライトアニメ、ビルボード、glb の読み込み |
| **本体の新しい領域「ゲーム」** (`MokumeGame` ターゲット) | シーン管理、アーケード物理、タイルマップ (Tiled 形式)、セーブスロット、カメラの追従、簡易 GUI (仮置き。`@Param` のつまみとの関係を作例で見てから決める) |
| **外のリポジトリ** | 剛体物理 (2D は Box2D・3D は Jolt) |

- `MokumeGame` は描画コアの上に載る層 ([ADR-0016](0016-package-structure.md) 決定 1 のコア依存) の 1 ターゲットで、アンブレラ `mokume` が再公開する (同決定 2)。ADR-0016 はモジュールの列挙を固定しないので、層の規則のまま足せる
- 地図 ([ADR-0041](0041-standard-scope-map.md) 決定 2) の「ゲーム」の行と、物理を分けた行が正本である
- アーケード物理の範囲 (速度・重力・めり込みの解消・接地の判定まで) と、5 基準の当てはめは地図の行が持つ
- **剛体物理** (積み重ね・関節・回転する衝突) は、作例が求めたときに外のリポジトリで包む。第三者のコードを本体で保守しない (ADR-0041 決定 7 の Syphon と同じ理由)。別リポジトリをバイナリ配布物の拡張に限っていた [ADR-0001](0001-founding-principles.md) 原則 6 は、第三者のコードを抱える拡張にも広げた

**退けた案: ゲーム専用のものは外のパッケージに置く** (#2580 の起票時の推奨)。mokume はすでに `MokumeAudio`・`MokumeCamera`・`MokumeNetwork` を別ターゲットに分け、アンブレラが再公開している。ゲーム層も同じ形にすれば、入口が 1 つ (`import mokume`)・1 リポジトリ 1 版 ([ADR-0001](0001-founding-principles.md) 原則 6)・学生の import が 1 行、の 3 つが同時に保てる。外のリポジトリは版の追随を払う (mokume-syphon と同じ)。それに見合うのは、第三者のコードを抱えるものだけである。

> 破れたとき: ゲーム層を外に出し、本体の版が進むたびにゲーム層が遅れる。学生は 2 つのパッケージの版の組み合わせを気にすることになる。

### 5. 値型は、大きさと基準点をラベルで名乗り、描画モードに依らない

関数は手本どおり残す (`circle` は直径、`sphere` は半径、`rect` は `rectMode` に従う)。値型は次の形にする。

```swift
Circle(x: 100, y: 200, radius: 20)
Circle(x: 100, y: 200, diameter: 40)
Rect(left: 24, top: 48, width: 40, height: 14)   // 左上で置く
Rect(center: p, width: 120, height: 40)          // 中心で置く
paddle.left / .top / .right / .bottom / .center  // 読み出しも同じ語
Ellipse(center: p, width: 80, height: 40)
Sphere(center: q, radius: 1)
Box(center: q, size: Vector3(2, 1, 2))
```

- 円は半径と直径の両方の入口を持ち、中では中心と半径で持つ (`diameter` は読み出しのプロパティ)
- 円・楕円・球・箱は常に中心で表す。ラベル `x:y:` を持つのは `Circle` だけで、意味は中心である
- **`rectMode` / `ellipseMode` の影響を受けない。** 判定も `draw()` も、値に書いたとおりの位置と大きさで働く。値は持ち歩いて別の場所で判定するので、意味を値の中で完結させる
- **数の受け口は `ScalarConvertible` にする** (`Vector2(col * 44, 48)` に `Int` の変数をそのまま渡せる)。理由は [ADR-0035](0035-numeric-reception.md) 決定 1 と同じで、中と GPU は `Float` のまま持つ
- 名前は [ADR-0020](0020-api-naming-and-surface.md) 決定 1 の規則 (描画関数の名前を大文字にしたもの) に従う。隔離は [ADR-0010](0010-concurrency-model.md) 決定 1 の改訂に従う

**退けた案:**

- **`Rect(x:y:width:height:)` で左上を表す** (`rect()` の既定・`CGRect` と同じ)。`rectMode(.center)` を使うスケッチで、読み手が基準点を取り違える。ラベルを読めば基準点が分かる形なら、モードがどうでも誤解が起きない。関数 `rect(x, y, w, h)` とは形がずれるが、関数にはもともとラベルが無いので、値の側で意味を名乗るほうを優先する
- **モードが既定でないときに値型の `draw()` を呼んだら警告する。** 中心指定の `rect()` の背景と `Rect` のボタンを併用する、正しいコードでも鳴る

> 破れたとき: 同じ `Rect` を 2 つのスケッチに持ち込むと、`rectMode` の違いで違う場所に描かれ、違う場所で当たる。

### 6. 値型の見た目は、プロパティで持たせる。描くのは `draw()` だけ

```swift
var brick = Rect(left: 24, top: 48, width: 40, height: 14)
brick.fill = color(239, 83, 80)      // このブロックの塗りを赤にする (描かない)
brick.draw()

bricks.append(Rect(left: x, top: y, width: 40, height: 14, fill: palette[row]))
for b in bricks { b.draw() }

fill(239, 83, 80); brick2.draw()     // 見た目を持たない値は、今の状態に従う
```

| 書き方 | 意味 | 描くか |
| --- | --- | --- |
| `fill(red)` | 全体の塗りを赤にする | 描かない |
| `brick.fill = red` | このブロックの塗りを赤にする | 描かない |
| `brick.draw()` | 描く | 描く |

- **`fill` は、どこで使っても「塗りの色を決める」という意味になる。** 違うのは効く範囲だけである
- **値が持つ見た目が優先し、持たない項目 (`nil`) は今の状態に従う。** `noFill()` の中でも、値が持つ塗りは塗る。描いた後の状態は呼ぶ前と同じである。Processing の `PShape` と mokume の `Shape` が「色は形の中に焼き付く」と決めているのと同じ規則で、形は既存の `Placement` (`fill: LinearRGBA?` のプロパティと、初期化子の `fill:` ラベル) に揃える
- 当たり判定は見た目と無関係である
- 教える順は、関数で描く → 値で判定し、描くときは `fill()` に従わせる → 物体ごとに見た目を持たせる、である。Processing の関数で描く書き方は 1 行も変わらない

**代償:**

- プロパティは引数の形を複数持てないので、`brick.fill = 236` とは書けない (`color(236)` と書く)。名前の付いた色 ([#2595](https://github.com/mokume-metal/mokume/issues/2595)) で和らぐ
- 「値の色が `fill()` より優先する」という規則を、`PShape` と同じものとして覚えてもらう

**退けた案:**

- **値型の `fill(_:)` / `stroke(_:weight:)` がその場で描き、連鎖できる** (`enemy.fill(a).stroke(b)`)。`Sketch` の `fill(_:)` (状態を置く) と同じ名前で意味が違う。`ball.fill(c); ball.draw()` は 2 回描かれ、`let redBall = ball.fill(red)` は赤い値を取っておくように読めるが、その行で描かれる。[ADR-0020](0020-api-naming-and-surface.md) 決定 1 が TCP と WebSocket の `write` で退けた、同じ名前が 2 つの意味を持つ形である
- **描く動詞を `draw(fill:stroke:weight:)` 1 つにする。** 見た目を値と一緒に持てないので、学生が見た目を持つ構造体を自分で作ることになる
- **`filled(_:)` が見た目の付いた新しい値を返す。** p5 から来た人には見慣れない形である。その場限りの描き分けには便利なので、作例が要ったときに足す候補として残す

> 破れたとき: 値型と `Sketch` で `fill` の意味が割れ、`fill` を書いた行で描かれるのかどうかを、呼んだ相手で覚え分けることになる。

### 7. 判定は値どうしの計算で、画面の座標で比べる。値を正本にする

```swift
var button = Rect(left: 100, top: 100, width: 120, height: 40)
button.move(by: Vector2(200, 0)); button.draw()
button.isHovered                 // 値を動かせば、見た目と判定は一致する

translate(200, 0); button.draw() // 見た目だけを変換で動かすと
button.isHovered                 // 値 (100〜220) と画面のマウスを比べる
button.contains(localMouse)      // 今の変換の座標に直したマウスで比べる
```

- `intersects` / `contains` は値どうしの純粋な計算である。描画の状態も座標変換も見ない
- `isHovered` / `justPressed` は、画面の座標のマウスと比べる。どのポインタ (iOS ではどの指) でも中にあれば押された扱いにする ([ADR-0034](0034-input-surface-units.md) 決定 7 の 6)
- **値を正本にする。** 描画と判定がどちらも値を見るので、値を動かせば常に揃う。判定に使う値は、画面の座標で持つのが基本である
- `localMouse` (名前は仮) は、今の変換の座標に直したマウスの位置を返す。2D のスクロールは、ゲーム層のカメラの追従が「画面の座標から世界の座標へ」の変換を持つ
- **変換の中で描いた図形を画面の座標で判定したら、1 度だけ警告する** (仮に W2 と呼ぶ)。引き金は「判定を呼んだ時点で変換がかかっているか」ではなく、「同じ形が、このフレームか前のフレームに変換の中で描かれていたか」である。判定の意味は変えない。これは診断であり、拾えない場面がある (移動 → 判定 → 描画の順では、控えた前のフレームの形と一致しない)
- `localMouse` だけでは直らない場面がある。変換の中で描いたボタンを次の `mousePressed()` で判定すると、コールバックは `draw()` の前に呼ばれて変換は戻っているので、`contains(localMouse)` でもずれは戻らない。保持した変換で明示的に判定する口は、作例が要ったときに決める

`isHovered`・図形の `justPressed`・`localMouse`・W2 は、要る作例が来たときに作る ([ADR-0043](0043-features-start-from-examples.md) 決定 2)。最初の作例 (ブロック崩し) が要るのは `intersects` と `contains` までである。

**退けた案: 呼んだ時点の変換、または描いた時点の変換で、自動で判定する。** 同じ `button.isHovered` が、`draw()` の中 (変換が効いている) と `mousePressed()` の中 (効いていない) で別の答えを返す。描いた時点の変換を使う形では、同じ形を 2 か所で描くと意味が曖昧になる。

> 破れたとき: 判定の答えが、呼んだ場所や描いた場所で変わる。値を動かしたのに当たらない、動かしていないのに当たる、が場所ごとに起きる。

### 8. ベクトルは自前の `struct Vector2` / `Vector3` にし、公開面のベクトルをこれに揃える

```swift
var velocity = Vector2(2.5, -2.5)
velocity = velocity * 1.1 + Vector2(0, 0.4)
let speed = velocity.length                       // Processing の mag() に当たる
let d = player.center.distance(to: enemy.center)
```

- 中身は SIMD で持ち、速さは変えない。SIMD との出入り口 `Vector2(simd)` / `.simd` を残す (Metal のシェーダへ渡す上級者向け)
- 配列リテラル (`[300, 300]`) から作れる。数の受け口は `ScalarConvertible` (決定 5)
- メンバーの名前は Swift の慣行に従い (`length`・`normalized()`・`distance(to:)`・`angle`・`rotated(by:)`・`dot(_:)`)、Processing での名前 (`mag()`・`heading()` など) は説明文で名乗る ([ADR-0020](0020-api-naming-and-surface.md) 決定 1 の規則 3)
- 公開面にいまある `SIMD2<Float>` / `SIMD3<Float>` (カメラ・`Placement.rotation`・`Transform.apply`・`Model` の寸法・文字の輪郭・`@Param` の値など) は、0.x の破壊的変更として `Vector2` / `Vector3` へ移す。移した後、公開シンボルの一覧に SIMD が現れるのは `.simd` と `init(_:)` だけになる

**退けた案: `typealias Vector2 = SIMD2<Float>` に extension でメンバーを足す。**

- 入力補完に SIMD の多数のメンバー (`.replacing(with:where:)`・`&+`・`.scalarCount` など) が並び、初学者には雑音になる
- エラーの表示が `SIMD2<Float>` になり、学生が書いていない型の名前が出る
- 足したメンバーが、利用者や他のライブラリの `SIMD2<Float>` にも漏れる
- リファレンスに独立した頁が作れない
- [ADR-0020](0020-api-naming-and-surface.md) 決定 1 が退けた「別名」の形に当たる。`ScalarConvertible` で受ける初期化子とも曖昧になる

> 破れたとき: ベクトルの型が面に 2 つ並び、作例ごとに `Vector2` と `SIMD2<Float>` の書き分けが混ざる。

### 9. `update()` は足さない。窓でもフレームの時計を選べるようにする

mokume にはすでに 2 つの時計がある。

| 時計 | いまの使われ方 | 振る舞い |
| --- | --- | --- |
| `.wallClock` | 窓の既定 | 実時間で進む。重いフレームでは時刻を進めて絵だけ抜く。`deltaTime` は毎回ばらつく |
| `.frameIndex(frameRate:)` | 書き出し (`render`)・ヘッドレス実行の既定 | `draw()` 1 回がちょうど 1/fps 秒。同じ入力なら同じ絵 |

**窓でもフレームの時計を選べる設定を足す** (`SketchSettings(clock: .frames)`。#2601 で入った)。

```swift
var settings: SketchSettings { SketchSettings(width: 480, height: 270, clock: .frames) }
func draw() {                                   // 1 回 = きっちり 1/60 秒。飛ばさない
    if keyboard.justPressed(.space) { vy = -8 } // 2 回発火も取りこぼしも無い
    vy += 0.4
    ball.move(by: Vector2(0, vy))
    background(20); ball.draw()
}
```

- **既定は `.wallClock` のまま。** フレームの時計は opt-in で、既存のスケッチの振る舞いを変えない。既定を変えるかは、作例か利用者から実害が出たときに判断する
- Pico-8・GameMaker・Processing (`x += 2` を毎フレーム書く文化) と同じモデルである。論理と描画を分けたい人は、`draw()` から自前の `update()` を呼べばよい (Processing の慣用)
- 時計が 1 つなので、コールバック・乱数・`justPressed`・停止・外部入力は、どれも今の「フレームごと」の振る舞いのままでよい
- 時間はすべて秒で数える。`deltaTime` は秒の `Float` である ([ADR-0020](0020-api-naming-and-surface.md) 決定 1)

**代償:**

- 重いとゲームが遅くなる (処理落ち)
- 実時間で動く音・動画・カメラとずれる。実時間が正であるべきゲーム (音楽に合わせるリズムゲームなど) は、`.wallClock` と `deltaTime` を使うと説明文で案内する
- 120 Hz の滑らかさは、論理の速さと引き換えになる

**処理落ちは、起こさない・気付ける・和らげる、の順で扱う。**

| 段 | 対策 |
| --- | --- |
| 起こさない | シェーダの初回の組み立てと観測の撮影で、main が止まらないようにする。`draw()` の中の同期の読み込み (`loadImage` など) は 1 度だけ警告し、`setup()` か `request…` へ案内する |
| 気付ける | フレームの時計のとき、1/fps を越えたフレームの数と、いちばん重かったフレームの番号を観測と窓に出す。リプレイ (決定 10) で重さを再現し、性能の回帰の検査にする |
| 和らげる | コマ落とし (絵を出さずに `draw()` を回して追いつく)・解像度を下げる。どちらも opt-in で、作例で実害が出てから入れる |

**止める口の意味は、どの時計でも今のまま変えない。** 次の表を約束にする。

| 口 | `draw()` | `frameCount` | `time` | `deltaTime` | 入力 |
| --- | --- | --- | --- | --- | --- |
| 何もしない | 毎フレーム | +1 | 進む | 1 フレーム分 | 届く |
| `pauseTime()` の間 | 呼ばれる | +1 | 止まる | 0 | 届く |
| `jumpTime(t)` の枚 | 呼ばれる | +1 | t へ跳ぶ | 0 | 届く |
| 時刻を指定した観測の 1 枚 | 呼ばれる | +1 | その枚だけ指定の秒 (`draw()` の中では。入力のコールバックは作者の時計の秒) | 0 | 届く |
| `noLoop()` の間 | 呼ばれない | 止まる | 止まる | — | コールバックは呼ばれる |
| `redraw()` | 1 回 | +1 | 1 フレーム分 | 1 フレーム分 | 届く |
| 外からの停止 (watch・MCP) | 呼ばれない | 止まる | 止まる | 再開時は 1 フレーム分 | 溜まる |

**`Countdown` は、`time` ではなく `deltaTime` の積み上げで減らす。** 普通のフレームで減り、`pauseTime()` と `noLoop()` の間は止まり、`jumpTime()` の枚と観測の 1 枚では減らない。`time` に従わせると、観測で `time` が差し替わった 1 枚で終わりうる。**観測がゲームの状態を変えてはならない。** フレームの時計では `deltaTime` がちょうど 1/fps なので、決定論も保たれる。

**ゲームの一時停止は「自分の印 + `pauseTime()`」と案内する。** 足して進めるもの (`ball.move(by:)`) は自分の印で止め、`Countdown` と `time` から作る動きは `pauseTime()` で止まる。描画は続くので、止めた画面に「PAUSED」を出せる。Unity の `Time.timeScale = 0` と同じ構図である。全部を凍らせ、画面もそのままでよいなら `noLoop()` / `loop()` を使う。代償として、印だけで止めると `Countdown` は進み続けるので、説明文と作例で示す。

**退けた案:**

- **`update()` を足し、一定の刻み (`updateRate`) で呼ぶ** (#2580 の論点 6 の当初の決定)。`update()` を書いたかどうかを Swift では見分けられない (`Sketch` の口は既定の実装を持つ)。作品にはすでに `draw() { update() }` や `private func update()` の書き方があり、`Sketch` の要件にすると乗っ取るか組めなくなる
- **`GameSketch` という別のプロトコルで `update()` を opt-in にする・`updateRate: Int?` の既定を nil にする・`fixedUpdate()` へ改名する。** どれも時計を 2 つ抱える。`draw()` で `justPressed` を読むと 120 Hz では 2 回発火するか取りこぼす。コールバック・乱数の列・停止・外部入力のそれぞれに、どちらの刻みに属するかの表が要る。時計を 1 つにすれば、どれも要らない。論理と描画を切り離す必要が出たら、そのときに `update()` を上に足せる (フレームの時計の意味はその部分集合なので、後から足しても壊れない)
- **フレームの時計では、`pauseTime()` が描画ごと止める。** 時計ごとに意味が割れ、止めた画面も出せない
- **`Countdown` をフレームの数で数える。** `pauseTime()` で止まらない
- **`Countdown` を利用者が毎フレーム進める (`tick()`)。** 書き忘れが起きる

> 破れたとき: 入力の瞬間・乱数・停止のそれぞれが「どちらの時計の刻みか」で答えを変え、`draw()` に書いた判定がフレームの頻度で 2 回発火するか取りこぼす。

#### 改訂 (2026-10-18) — 時刻を指定した観測の `time` は `draw()` の中だけの値である (#2357)

上の表の「時刻を指定した観測の 1 枚」の `time` の欄は、**`draw()` の中を指す**。観測の秒が `draw()` の外の状態に残ると、「観測がゲームの状態を変えてはならない」が作者のコードと本体の状態から破れる。だから、観測の枚でも次のとおりにする。

- 入力のコールバックが読む `time` は**作者の時計の秒**にする (`pauseTime()` が観測の枚でも作者の時計の秒で止めるのと同じ線)。矢印キーの `jumpTime(time + 0.25)` が、作者の時計を観測の秒へ飛ばさない。`draw()` だけが観測の秒を読む。代償は、同じ枚の中で、コールバックと `draw()` の `time` が食い違うこと
- 本体が持つ状態 (動画の再生位置・録った音の起点・入り口が最後に値を取り出した時刻 `lastArrival.time`) は作者の時計の秒で進み、観測の秒を受けない。映すコマ・読む窓だけは観測の秒で決める。撮った 1 枚は指定の秒に当たる絵を映し、観測の後の枚は作者の時計に沿って続く。`draw()` の中で読む値 (`Movie.time` など) は、映しているものに揃えて観測の秒の側を返す
- **作者のコードが観測の枚の `draw()` の中で `time` から作った秒へ `jumpTime` すると、作者の時計が動く。** `draw()` の中の `time` は観測の秒なので、`jumpTime(time ± x)` はその秒へ飛ぶ。これは作者が書いた飛び先で、動作は変えない (公開 API の意味を新たに選ばない。ADR-0025 の範囲)。入力のコールバックの中で飛ぶ形 (`jumpTime(time ± 0.25)`) は、上のとおり作者の時計の秒から飛ぶ

**代償:** 同じ枚の中で、コールバックと `draw()` の `time` が食い違う。さらに、観測の枚のコールバックでは `time` が作者の時計の秒で進むのに `deltaTime` は 0 のまま (観測の枚の経過は 0 という約束・上の表) で、`time` の前の枚との差と `deltaTime` が一致しない。

**退けた案:** コールバックの `time` を観測の秒のまま説明で名乗る (Q)。「観測がゲームの状態を変えてはならない」に、作者のコード経由の穴が残る。

### 10. リプレイは、同じ機械で絵まで一致すると約束する。記録できないものは検出して名乗る

フレームの時計 (決定 9) のスケッチは、フレーム番号ごとの入力を記録して再生できる。再生は画面を出さず、全速で回せる。AI が遊んだ記録を、そのまま回帰の検査にできる (H2)。

| 区分 | もの |
| --- | --- |
| **記録する** | フレームごとの入力・`@Param` の変更・時刻を指定した観測・`ExternalQueue` の出来事と `ExternalInput` の値 (`Codable` のもの)・OSC / MIDI / シリアル / ゲームパッドのメッセージ・読んだ資源のハッシュ・乱数の種 |
| **使われたら「再現を保証しない」と理由つきで記録に書き、再生でも名乗る** | カメラ・マイク・音の解析・動画・URL からの読み込み・`watch` の作り直し・`Codable` でない外部の値・記録時と再生時で資源のハッシュが違う |
| **検出できないので、説明文に書く** | `Date()`、Swift 標準の乱数 (`Int.random` など)。再現したいなら mokume の `random()` と `time` を使うと案内する |

**合格の確かめ方は、記録したときと再生したときを、同じフレーム番号で照合することである。**

- 毎フレーム: `expose` した値
- 60 フレームごとと、最後の 1 枚: 画素のハッシュ
- 食い違ったら、最初に食い違ったフレームを名乗る (AI が原因を探す手がかりになる)
- 再生どうしを比べるだけの検査には頼らない。同じ誤りが 2 回出ても通ってしまう

- 約束の水準は [ADR-0025](0025-determinism-levels.md) の水準 3 (同じ機械の画素) である。記録した入力を流すのは [ADR-0028](0028-external-inputs.md) 決定 6 の注入の道で、同決定 7 により外から届く入力を持つスケッチも水準を名乗れる
- 記録と再生のやりとりは、[ADR-0018](0018-observation-and-control-surface.md) の面 (`.mokume/` の下のファセット・`Schemas/` の JSON Schema) に、新しいファセットとして載せる
- 全速の再生は、[ADR-0012](0012-view-layer.md) 決定 3 の「同じ入口を別の駆動で叩く」1 つである。新しい駆動の仕組みは要らない

**退けた案:**

- **約束を狭める** (キーボード・マウス・パッドと乱数の種だけで動くスケッチに限る)。つまみの調整や AI の観測が混ざるだけで保証の外になり、H2 の現場を支えられない
- **何でも記録する** (カメラの画素まで)。記録が巨大になる
- **刻みの番号と入力と種だけを記録する** (#2580 の論点 6 の当初の約束)。途中で変えた `@Param`、時刻を指定した観測、`ExternalInput` の最新値が記録に無く、同じ絵にならない

> 破れたとき: 「リプレイで再現した」と言いながら、記録していない値で絵がずれる。食い違ったフレームを名乗らなければ、AI は原因を探す手がかりを持たない。

### 11. iOS / iPadOS へは、埋め込めるビュー `SketchView` で出す

- **iOS:** SwiftUI の `SketchView` に描画面を載せる。アプリの外枠 (`@main struct …: App`) は雛形が出す (決定 12)
- **macOS:** いまの `Sketch.main()` (mokume が窓を持つ形) を既定に残し、`SketchView` で埋め込むこともできるようにする
- **同時に動かすスケッチは、最初は 1 つ。** 描画の関数と値型の `draw()` が「走っているスケッチ」を見るので、2 つ同時に動かすとどちらに描くかが曖昧になる。複数の要望は作例が来てから扱う
- スケッチの持ち主 (SwiftUI が組み直すたびに作り直さない形。`SketchView(Game.self)` など) は、`SketchView` の着手時に決める
- 対象は iOS / iPadOS 26 以降、A14 / M1 以降である ([ADR-0009](0009-platform-floor-and-toolchain.md) 決定 1)。Metal 4 の要件で、iPhone 12 以降・iPad Air (2020) 以降などに当たる

**タッチ:** 1 本目の指をマウスとして扱い (p5.js と同じ)、`touches` で全部の指を読む。マウス向けに書いたコードが iPad でそのまま動く。正本は [ADR-0034](0034-input-surface-units.md) 決定 7 の 6。iPad のハードウェアキーボードとゲームパッドは、同じ `keyboard.` / パッドの口で読む

**画面の大きさと向き:**

- 既定は固定の論理解像度で、縦横比を保って拡大し、余白は帯にする。決定論を保ち、学生が考える解像度を 1 つにする
- 画面いっぱいに使うモード (`width` / `height` が画面に追従する) と、`safeArea` の読み出しを選べる
- 縦向き・横向きの固定は設定で選ぶ

| iOS の既定 | 値 |
| --- | --- |
| 音のカテゴリ | `.ambient` (消音スイッチに従い、他のアプリの音楽を止めない) |
| アプリが裏に回ったとき | 止める。戻ったときに止まっていた時間を 1 枚に乗せない ([ADR-0025](0025-determinism-levels.md) 決定 6 の上限と同じ向き) |
| フレームレート | 60。ProMotion の 120 は設定で選べる |
| ホットリロード・MCP | 実機では使わない。開発は Mac で行い、実機は遊んで確かめる場所にする |

AppKit に依存しているのは約 16 ファイル・約 4,300 行で、本体の約 6% である。ほぼ `Display/` と `Parameters/` に集まっていて、描画の中核 (Metal 4・CoreText・ImageIO) は AppKit を参照しない (2026-10-13 時点)。

**退けた案: iPad の Swift Playgrounds で開発できるようにする。**

- Playgrounds の上では、差別化 (決定 3) のうち書き味しか残らない。MCP・CLI・ホットリロード・ヘッドレスの書き出しは Mac のプロセスで、AI と組む開発は成り立たない
- 代償が恒常的にかかる。サードパーティの macro (swift-syntax) を iPad で組めるという公式の記述が見つからず、`@Param` を本体から外すことになる。Playgrounds の Swift の版を下限にし、その版でビルドする CI を持つことになり、[ADR-0009](0009-platform-floor-and-toolchain.md) 決定 4 (互換ビルドの CI を持たない) の反転にあたる
- 想定する学生は Mac を持っているので、iPad だけで完結する価値が要らない

> 破れたとき: 1 プロセス 1 スケッチの前提のまま iOS へ出ようとして、アプリの外枠と窓を mokume が持つ形を iOS へ持ち込む。SwiftUI のアプリに描画面を置けない。

### 12. 配布は `.xcodeproj` の外枠とし、ゲームのコードは常に Swift パッケージに置く。外部サービスは mokume に入れない

```
MyGame/
├── Package.swift            ← ゲームの本体 (Sketch とロジック)。mokume に依存
└── MyGameApp.xcodeproj      ← iOS アプリの外枠。SketchView の数行と、各サービスの設定
```

- Mac での開発の流れ (ホットリロード・MCP・全速のリプレイ) は `swift build` でパッケージを組むので、ゲームがパッケージにある限りそのまま使える
- entitlement (Game Center・Sign in with Apple・iCloud・プッシュ通知)・Info.plist・他のターゲット・SDK は、外枠の側で Xcode の普通のやり方で扱う
- 外枠は CLI の雛形で出す。固定の雛形に名前を差し込む形にし、Xcode 16 以降のフォルダと同期するグループを使う
- 授業ですぐ試すには、Mac で `mokume-cli run` すれば足りる

**外部サービス:**

- データベース・認証などのサービスを mokume に入れない。地図 ([ADR-0041](0041-standard-scope-map.md)) に無い領域で、各サービスの仕事である
- サービスの結果は、落とさない列 (`ExternalQueue`・[ADR-0028](0028-external-inputs.md) 決定 2) でゲームへ渡す。どのスレッドからでも送れ、フレームの頭で受け取る。`Codable` な値ならリプレイに記録できる (決定 10)
- テストや AI のプレイでは偽物の値を送る。サービスを protocol の向こうに置く書き方を、雛形で示す
- Game Center は将来のゲーム層の候補だが、作例が来るまで入れない ([ADR-0043](0043-features-start-from-examples.md))

**退けた案:**

- **`.swiftpm` (App Playground) の外枠を正式な道にする。** entitlement が要る機能は Playgrounds では使えないと Apple のフォーラムで回答されている。Info.plist も決まった項目しか書けず、他のターゲットも持てない。いずれも完全には確かめていないが、後から必要になったときに詰む恐れのある形式を正式な道にしない。道を 1 本に絞るため、`.swiftpm` の外枠は作らない
- **サービスの結果を `ExternalInput` (最新の 1 つ) で渡す。** 1 フレームに 2 件届くと 1 件が上書きされて消える

> 破れたとき: 外部サービスの SDK と設定が mokume の本体に入り、使わない学生のスケッチまで重くなる。結果の出来事が上書きで消え、リプレイにも残らない。

### 13. 全体が整うのを待たず、段ごとに着手の条件を置く。進める順は作例から

**整うのを待たない。** open の Issue は流入が流出を上回っていて (2026-10-13 時点で流入が流出の約 2.4 倍)、その多くは反証役が兄弟の端の入力を探す仕組み自体が生む Bug である。作るほど見つかるので、件数が 0 に向かう見込みは無い。代わりに、ゲームの作例を「何を直すか」の選別に使う ([ADR-0043](0043-features-start-from-examples.md))。作例が通る経路の Bug と性能の問題を優先して直し、通らない経路は待たせる。

**0.x の間に土台の口を決めるほうが安い。** 時間のモデル・入力の端の判定・埋め込めるビューは公開面の形を変える。公開面が広がってからだと、移すものが増える。

| 段 | 中身 | 着手の条件 |
| --- | --- | --- |
| 0 | 本 ADR と、ぶつかる ADR の改訂 | — |
| 1 | macOS で作例のゲームを 1 本書き (ブロック崩し)、作例が要る分の口をそろえる | 段 0 の後。シェーダの初回の組み立てで窓が止まらないこと。並行するレーンは 1 本 |
| 1.5 | リプレイ (決定 10) | フレームの時計の後。観測の撮影で main が止まらないこと |
| 2 | 埋め込めるビュー (決定 11) | 段 1 の作例が動く |
| 3 | iOS / iPadOS | 段 2 の後。専用機の依存に縮退の道があること (iOS の検査で CI の量が増えるため) |
| 4 | ゲーム層 (`MokumeGame`) | 段 1 の語彙が固まった後 |
| 5 | 3D (決定 2 の順) | 段 1 の 2D の値型の後 |

- **段 1 と 2 は、ゲームの方向をやめてもクリエイティブコーディングに残る。** 賭けになるのは段 3 だけで、その前に段 1 で書き味を確かめられる
- **リプレイを段 1.5 に早めるのは、差別化の H2 の中身だからである**
- 段 1 の範囲は、作例が要る分に絞る。`Line`・`Ellipse`・`Triangle`・`Vector3`・`isHovered`・図形の `justPressed`・`localMouse`・`Stopwatch` は、要る作例が来たときに入れる (決定は本 ADR に残す)
- 効果音のファイルを重ねて鳴らす口と音量のバスは段 4 に置く。最初の作例は、リポジトリにバイナリを置かないため、既存の合成音で鳴らす
- 各段の子の完了条件に「`draw()` だけの既存の作例は書き換えずに動く (名乗った破壊的変更を除く)」を入れる。新しい検査は足さない
- 段の Issue と進み具合は [#2580](https://github.com/mokume-metal/mokume/issues/2580) とその sub-issue が持つ。本 ADR に進捗の台帳を複製しない

> 破れたとき: 「整ってから」と待ち続けて土台の口を決めないまま公開面が広がり、決めた日に移すものが積み上がっている。逆に、作例を持たずに口を先にそろえると、使われない口が面に残る。

## 影響

- **公開面と保守の対象が、iOS の分だけ広がる。** 描画の中核は AppKit を参照しないが、窓・入力・つまみの層は iOS の形を別に持つことになる。iOS のビルドと検査を CI のどこで回すかは、段 3 で決める
- **0.x の破壊的変更がいくつか出る。** `isKeyDown` は `keyboard.isPressed` へ移り、`keyPressed()` はキーリピートで連射しなくなる ([ADR-0034](0034-input-surface-units.md) 決定 7)。公開面の SIMD は `Vector2` / `Vector3` へ移る (決定 8)。語彙の置き場が `SketchPart` へ移り、リファレンスの頁の置き場が変わる ([ADR-0020](0020-api-naming-and-surface.md) 決定 7)
- **書き方が 2 つ並ぶことを、教える順で支える。** 関数で描く → 値で判定する → 物体ごとに見た目を持たせる (決定 6)。入門の文書の組み直しは段 1 の作例と一緒に行う
- **本 ADR は検査・hook・ラベル・ワークフローを 1 つも足さない。** 段ごとの完了条件は、既存の検査 (golden の台帳・`make api`・注入の検査) の範囲を広げて確かめる
- **未実装のものが多い。** 本 ADR は方向と口の形を決めたもので、採用は実装の完了を意味しない。`SketchPart`・値型・リプレイ・`SketchView`・iOS・`MokumeGame` はどれもまだ無い (`clock: .frames` は #2601 で入った)。実装の順と進み具合は #2580 の段が持つ
- 想定する利用者を Mac で開発できる学生に置いたので、Mac を持たない人に遊んでもらう道 (Web・Android) は持たない。この弱さは決定 3 の負ける軸に残す
