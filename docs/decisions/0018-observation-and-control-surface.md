# ADR-0018: 観測と操作の面 — ファイルの往復を 1 つの規約に束ねる

## 状態

採用 (2026-08-27) / 改訂 (2026-08-31): 決定 5 に、表の 2 行目を取り違えた実例を足した

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 3 は、走っているスケッチを外から観測・操作できることを土台の要件に置き、プロセス間の通信形式は schema を正典とすると決めている。[ADR-0016](0016-package-structure.md) 決定 5 は、その機構を描画コアの要件とし、後付けの拡張にしないと決めた。

決まっていないのは**面の形**である。スケッチの外にいる書き手と読み手 — エージェント・コマンドラインの道具・測定のスクリプト — が、何をどこへ置き、いつ読めば「終わった」と言えるのか。

面の形は後から変えると利用者が一斉に壊れる。しかも同じ性質のやりとりは今後も増える (観測のあとに、パラメータの読み書き・作り直しをまたぐ受け渡しが控えている)。1 つずつ設計すると流儀がずれ、読み手は面ごとに別の作法を覚えることになる。**先に 1 つ決めて、各ファセットがそれに乗る**順にする。

### この面で実際に壊れるところ

1. **書きかけを読む** — 書き手が書いている途中のファイルを読み手が開くと、壊れた JSON か、途中までの画像を掴む
2. **応答が返らない** — 要求を出したのに何も起きないとき、読み手には「まだ処理していない」「失敗した」「相手が死んでいる」の区別が付かない
3. **古い成果物を新しいと信じる** — 前回の応答が残っていると、読み手はそれを今回の応答と取り違える。とくに今回が失敗したときに起きる
4. **完成の判定** — 複数のファイルからなる応答は、全部揃ったことをどうやって知るか
5. **置き場が消える** — 相対パスの基準をプロセスの作業ディレクトリに委ねると、起動のされ方 (端末から / アプリケーションとして / ログイン項目から) で書けない場所を向く。そしてそれは書き込み失敗としてしか現れない

### 読み手は Swift とは限らない

この面の主な利用者はエージェントで、JSON を手で組んで置き、応答を読む。**実装の型を共有しても、その読み手にはコンパイル時の保証が届かない**。schema であれば、書き手が出したものと読み手が出したものの両方を、実装言語によらず機械で検証できる。

## 決定

### 1. トランスポートはファイルシステムだけを使う

観測と操作のために socket もポートも新設しない。

走っているスケッチと、それを見る道具は同じ機械の上にいる。面が増えるたびに接続・再接続・生存確認・権限の面倒が増え、そのすべてが「絵が 1 枚欲しい」に対する付随的な複雑さになる。ファイルであれば道具を通さずにエージェントが直接読み書きでき、窓口 (MCP サーバなど) は同じ面に乗る薄い層で済む — **面の能力が窓口の実装に閉じ込められない**。

### 2. 置き場は 1 つの作業ディレクトリに集め、基準を明示的に解決する

やりとりのファイルはスケッチの作業ディレクトリ直下の `.mokume/` に置き、用途ごとにその下のディレクトリ (ファセット) へ分ける。観測は `.mokume/observe/`。

**基準ディレクトリの解決は 1 箇所に置く。** 既定はプロセスの作業ディレクトリで、環境変数 `MOKUME_WORK_DIR` があればそれを基準にする。プロセス起動時に一度だけ評価し、以降は変えない。

文脈の 5 番目がそのまま理由である。基準を外から与えられれば、どんな起動のされ方でも道具が場所を指定できる。

### 3. 要求と応答の規約

すべてのファセットが次に従う。

- **書き込みは必ず原子的に** — 同じディレクトリの一時ファイルへ書き、`rename` で所定の名前にする。読み手が書きかけを掴む隙間を作らない。要求側にも応答側にも等しく効く
- **要求ごとに違う ID を載せ、応答はそれを echo する** — 応答側は同じ ID の要求を二度処理しない。読み手は ID の一致で完了を知る。**壁時計の待ちで完了を判断しない**
- **失敗しても必ず応答する** — 応答できなかった理由を載せた応答を書く。無応答は「相手が死んでいる」と区別が付かない
- **失敗応答では、前回の成果物を先に消す** — 新しい ID の応答と古い画像が組にされると、読み手は古い絵を新しいと信じる。消してから応答を書く
- **複数のファイルからなる応答は、目録を最後に原子的に書く** — 読み手は「目録があり、ID が一致し、数が宣言と合う」で完成を判定する
- **知らないキーは無視する** — 読み手も書き手も、自分の知らないキーがあっても失敗しない

### 4. wire 形式の正典は `Schemas/` の JSON Schema

やりとりする JSON の構造・キー・値域は `Schemas/` 配下の JSON Schema (draft 2020-12) が正典で、実装はそれに従う ([ADR-0016](0016-package-structure.md) 決定 4 のとおり実装ターゲットの外に置く)。

- `Schemas/examples/` に**書き手が出す代表例と読み手が出す代表例の両方**を置き、スキーマで検証する検査を `make ci-check` に持つ
- 実装が例からずれないことは実装側のテストが守る (同じ例を実装で読み書きする)
- スキーマは `additionalProperties: false` を既定にする。**キーを足すときはスキーマの更新が必須**になり、面の変更が黙って起きない

### 5. 版の進め方

応答は `schemaVersion` (整数) を持つ。**要求は持たない** — 書き手が読み手の能力を知る必要がなく、決定 3 の「知らないキーは無視する」で前方互換が閉じるためである。

| 変更 | 判定 |
| --- | --- |
| キーの追加で、読み手が解釈しなくても機能が成立する | 据え置き |
| キーの追加で、読み手が解釈しないと成立しない | 上げる |
| 値域・列挙の拡大 | 据え置き (読み手は知らない値を捨てず素通しする) |
| キーのリネーム・削除・型の変更 | 上げる |
| 名前も型も同じまま**意味が変わる** | 上げる |

最後の行だけは機械検査を素通りする。スキーマも実装のテストも「意味」を見ないので、ここは人と本 ADR が唯一の防壁になる。

#### 改訂 (2026-08-31) — 表の 2 行目を取り違えた実例

`frames` (撮った絵の目録) を足したとき ([#408](https://github.com/mokume-metal/mokume/issues/408))、**この表の 2 行目に当たるのに `schemaVersion` は据え置かれた**。読み手は目録を解釈しないと絵の名前を得られないので、上げるべき変更だった。しかも目録は `required` に入っているので、古い書き手の応答は schema 検証も通らない。

帰結として、**「1 を名乗る応答」が 2 通りになった** — 目録を書くもの (0.4.0 以降) と、書かないもの (それ以前)。実害は [#635](https://github.com/mokume-metal/mokume/issues/635) で、絵が実際に書かれているのに「絵は採れませんでした」と報告された。作品はライブラリの版を固定してコミットし ([ADR-0022](0022-production-track.md) の再現の目印)、道具は独立に新しくなるので、**この食い違いは事故ではなく常態**である。

**いま上げ直さない。** 上げても過去の曖昧さは消えない — 既に出た 0.4.0 / 0.5.0 の応答は目録を書きつつ 1 を名乗っており、書き換えられない。読み手は版ではなく**形**から判定するしかなく、#635 はそう実装した (目録が無ければ単数形へ落ち、**補ったことを名乗る**)。

**表は変えない。** 取り違えたのは表の読み方ではなく、上げる判断そのものである。ただし**上の一文は言い過ぎだった** — 「最後の行だけが素通りする」と書くと他の行は誰かが見張っていると読めるが、実際には表のどの行も機械に見られていなかった。`required` の追加は見張れるので、検査は [#637](https://github.com/mokume-metal/mokume/issues/637) が持つ。

## 影響

- 決定 1 により、観測と操作の能力は窓口の実装から独立する。窓口が無くてもエージェントは同じことができ、窓口は面の薄い包みになる
- 決定 2 により、`.mokume/` は今後増えるファセットの共通の屋根になる。パラメータの読み書きや作り直しをまたぐ受け渡しが要るようになったとき、新しい通信路ではなく新しいファセットとして足せる
- 決定 3 の「失敗しても応答する」により、読み手はタイムアウトを持たなくてよい。読み手の実装が単純になり、遅い機械で誤検出しない
- 決定 4 により、面の変更はスキーマの変更として現れる。実装だけが変わって形式が黙って変わる経路を持たない
- 決定 5 の最後の行は、この ADR が機械にできない仕事を名指ししている。意味を変える提案は PR の説明で明示すること
- 本 ADR が決めるのは**面の形だけ**である。何を観測できるか (応答に載る中身) は観測の実装が決め、その schema が持つ
