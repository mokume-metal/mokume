# ADR-0019: 描画の検証は目と手元の機械で分ける

## 状態

採用 (2026-08-28) / 一部置換 (→ [ADR-0031](0031-triage-as-the-single-gate.md)): 決定 2 / 改訂 (2026-09-15): 決定 4 の画素の期待値を、入口の変換と出力段を経て導く形に書き直す / 改訂 (2026-09-23): 決定 3 の代表シーンに参照スケッチの書き出しを加える / 改訂 (2026-09-25): 決定 3 の台帳で、字形を写す行は採った OS の版でだけ比べ、ほかの行には字形を写さない

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 8 は、検査の入口を 1 本に保ち、そこを通れば安心して merge できる状態を目指すと決めている。ところが**描画を要する検査だけは、その入口の中で走っていない**。CI のランナーが持つ仮想化された GPU はこの世代のコマンド構造を備えておらず ([#180](https://github.com/mokume-metal/mokume/issues/180))、実測ではランナーの更新を待てば解決するという見立ても消えた。

いま描画の正しさを支えているのは「手元で `make ci-check` を通す」という記述だけで、それを守っているかを見る機構は無い。

### 絵の検証は 1 つの問題ではない

「見た目が正しいか」は、性質の違う 2 つの問いが重なっている。

1. **新しく描いた絵が正しいか** — 目でしか判定できない。参照画像を持っていても、その参照が正しいと**人が認めた時点**でしか意味を持たない。機構をどれだけ厚くしてもこの判定は機械へ移らない
2. **触っていない絵が変わっていないか** — 目では担えない。PR に載る証跡は作者が「変えたつもりの絵」だけで、共通部を触った変更が他の絵を変えても、**誰もその絵を見ない**

この 2 つを 1 つの機構で解こうとすると、参照画像の置き場・承認の流れ・環境差の吸収・知覚的な比較器と、機構が際限なく膨らむ。複数の OS とブラウザで動く処理系が、環境差と戦うためにクラスタ解析つきの比較器を必要としているのはその帰結である (p5.js の視覚回帰テスト: https://github.com/processing/p5.js/blob/main/test/unit/visual/visualTest.js)。

**mokume は単一の環境しか対象にしない** ([ADR-0009](0009-platform-floor-and-toolchain.md))。環境差を吸収する複雑さを引き受ける理由が無く、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) に従えば、実害が示されていない機構は建てない。

### 実機を CI へ差し出す道は取らない

自前の機械を CI のランナーとして登録すれば描画を見られるが、public なリポジトリでそれをやると、**他人が書いたコードがメンテナの実機で走る**。得られるのは「絵を機械が見る」ことだが、上のとおり機械が見て判定できるのは退行だけであり、その退行は下記 3 の軽い機構でも捕まえられる。釣り合わない。

### 外部の作法

- **参照画像を持たない検証**は珍しくない。piglit は「この画素がこの色であること」を許容誤差つきで宣言する検査を並べ (https://blogs.igalia.com/siglesias/2015/05/29/piglit-iii-how-to-write-glsl-shader-tests/)、Khronos の適合性テスト群も保存済みの参照画像を持たず、CPU 側で参照をその場で作って突き合わせる (https://github.com/KhronosGroup/VK-GL-CTS)
- **変化の監視**は完全一致を優先し、更新は記録に残る操作にするのが定石 (Skia Gold: https://skia.org/docs/dev/testing/skiagold/ 、Filament はコミットのタグで承認する: https://github.com/google/filament/tree/main/test/renderdiff)
- **回帰を利用者の報告に頼る**体制は避けたい。描画の結果を検証するテストを持たない処理系は実在する (https://github.com/processing/processing4/tree/main/core/test/processing/core)

## 決定

### 1. 判定を 2 つに分け、担い手を分ける

| 問い | 担い手 | 形 |
|---|---|---|
| 新しい絵は正しいか | 人間と AI の目 | PR に before / after の証跡を載せ、レビューで見る |
| 触っていない絵が変わっていないか | 機械 | 代表シーンのハッシュ照合 (下記 3) |

証跡の撮り方・置き方は視覚証跡の作法が正典とし、本 ADR は繰り返さない。

### 2. 見た目を伴う Issue は `verify: human` でトリアージする

**この決定は [ADR-0031](0031-triage-as-the-single-gate.md) 決定 1 に置き換わっている** (状態欄が名乗っているとおり)。`verify: human` は削除され、残るのは `verify: triaged` の 1 つで、`review-gate` が見るのはその**有無だけ**である。**見た目を伴うことに固有の承認は無くなった** — 承認が要るのは重要パスに触れる PR だけで、絵の正しさを担うのは決定 1 の「人間と AI の目」と、そこへ差し出す証跡そのものである。

**当初の決定**は「[ADR-0002](0002-issue-lifecycle-and-merge-approval.md) の既定の機構がそのまま働き、新しい仕掛けは要らない — `review-gate` が『人間の Approve なしに merge できない』を強制する」で、続きに「自己判定テスト (下記 4) が厚くなった領域は `verify: machine` へ戻してよい」を置いていた。ラベルの二分がそのまま承認の有無を決める前提に立った書き方である。**その前提のほうが畳まれた** — 分類が実測で機能していなかったため ([#618](https://github.com/mokume-metal/mokume/issues/618)・ADR-0031)。**決定 1 の「目で判定する」は動いていない**ので、番号は増やさず、担い手が承認という操作ではないことをここに書き足す (2026-09-09・[#733](https://github.com/mokume-metal/mokume/issues/733))。

### 3. 触っていない絵の退行は、代表シーンのハッシュ照合で PR の差分に浮かび上がらせる

決定論 (ADR-0001 原則 2) により、同じ入力からは同じ絵が出る。そこで代表的なシーンを描き、**出力段を通した 8 bit の画素バッファ**([ADR-0011](0011-color-model.md) 決定 6 の量子化点) の sha256 を台帳の行と突き合わせる。

- **画像ファイルのバイトでは取らない。** 符号化器の版に依存させると、絵が 1 画素も変わっていないのに OS の更新で台帳が全滅する
- **台帳はテキストでリポジトリに置く。** 差分で読めて、バイナリを置かない原則 (ADR-0001 原則 7) とも両立する。**画像の実体はコミットしない** — 承認した時点の絵は PR の証跡 (外部の URL) が持つ
- **役割はゲートではなく可視化**である。「どの絵が変わったか」が PR の差分に行として現れ、レビューする目が「この変更でなぜこの絵が変わるのか」を問えるようにする。ADR-0001 原則 8 が予約していた「参照画像の比較を自動検証に育てる」の、この体制における形
- **失敗のメッセージに切り分けを書く**: 台帳と一致しない + 同じシーンを 2 回描くと一致する → 絵が変わった (意図したものなら台帳を更新し、before / after を証跡に載せる) / 2 回描いても一致しない → 決定論が壊れている (**台帳を触ってはならない**)
- 新しいシーンの追加と台帳の更新には「対象を壊して赤を見る」(ADR-0002 決定 5) を適用する。**絵に写っていない要素の退行は画像の比較では捕まらない**という既知の盲点への防壁
- 画像の外部への置き場は同じバイトに同じ URL を返すので、「after の URL が before と同じ = 絵は変わっていない」という機械的な確認も併用できる

#### 改訂 (2026-09-23) — 代表シーンに参照スケッチの書き出しを加える

**当初の決定**では、「代表シーン」は検査の中で組んだシーンだけだった。検査が入力を完全に握れ、シーンごとに経路を 1 つずつ狙って組めるので、動いた行がそのまま動いた経路を名指しする。参照スケッチ (`Sketches/`) は目で見る側に置かれていた — PR の証跡として 1 度見られるもので、検査からその型を import する道も無く、`make ci-check` はビルドするだけだった。同じ前提から、参照スケッチの場所は「台帳が描く絵を動かせない」として手元の実行の覆いから外されていた ([#497](https://github.com/mokume-metal/mokume/issues/497))。

**理由 (触っていない絵は誰も見ない) は動いていない。** 動いたのは、その理由が参照スケッチにも当たるようになったことである。

- 参照スケッチは作者向けの API をほぼすべて、作者が書く形のまま呼ぶようになった ([#1350](https://github.com/mokume-metal/mokume/issues/1350))。それでも絵は PR の時点で 1 度見られるだけで、merge した後に共通部分を触った変更が絵を変えても、誰も見ない
- 走らせる検査も無かった。スケッチから呼ぶと必ず落ちる口が、窓を開いて走らせるまで見つからなかった ([#1367](https://github.com/mokume-metal/mokume/issues/1367))

そこで台帳の検査は、参照スケッチを 1 本 1 行 (`sketch:<名前>@45`) で載せる。描くのは書き出し (`--render`) と同じ 45 フレーム目で、経路も同じ `SketchRuntime` の `advance()` である。これは既存の機構の責務を広げる段 ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) であって、新しい部品ではない。**描く途中で落ちれば、検査ごと赤になる。**

- **標本に新しく入るのは、`Sketch` 層の中継と `SketchRuntime` の経路である** (setup / draw / 時計)。検査の中で組んだシーンは `Canvas` を直に叩くので、この経路を通る行はそれまで無かった
- **外から入る口は閉じて描く。** 観測・入力・つまみの区画と、つまみの保存を読まない。手元に残った保存で絵が動くと、「絵が変わった」の文面が台帳の書き換えを勧めてしまう
- **非同期で読む口は「届く前」の絵が載る。** `requestImage` / `requestModel` の続きは main actor で走り、検査は描き終えるまで main actor を手放さないので、45 フレーム目には必ず届いていない
- **複数フレームは持たない。** 動きのあるスケッチも 45 フレーム目には 45 フレーム分の状態が積み上がっている。取りこぼした実例が出てから足す

変えないこと:

- **役割は可視化のままである。** 動いた行が差分に現れれば足り、`drawing-evidence` の要求は広げない。失敗の文面が before / after の撮り方を示す
- **[ADR-0022](0022-production-track.md) 決定 2 の追補の限界は残る。** 参照スケッチも面の作者が書くので、標本に現れるのは「面の作者が書く綴り」である。この改訂は [#1027](https://github.com/mokume-metal/mokume/issues/1027) の穴を塞がない ([#1377](https://github.com/mokume-metal/mokume/issues/1377))

#### 改訂 (2026-09-25) — 字形を写す行は、採った OS の版でだけ比べる

**当初の決定**は、台帳のすべての行をどの機械でも完全一致で比べていた。前提は決定論 (ADR-0001 原則 2) で、同じ入力からは同じ絵が出るので、手元の機械が違っても行は一致するはずだった。

**理由 (触っていない絵の退行を差分に浮かび上がらせる) は動いていない。** 動いたのは、字形については前提が OS の版の内側でしか成り立たないと分かったことである ([#1559](https://github.com/mokume-metal/mokume/issues/1559))。

- mokume は字形を 1 つずつ CoreGraphics で焼き、四角として置く。**字形を画素にするのは OS である**
- 同じ書体で輪郭と送り幅が同じでも、焼いた画素は macOS 26 と 27 で 1〜3 階調ずれた。既定の書体は字形そのものが変わっていた。書体の引き当ては原因ではなかった
- そのため、文字を含む 16 行は OS を上げるたびに 2 つの値を行き来していた。**OS の下限の内側にある機械なのに、素の `main` で `make ci-check` が通らず、`local-render` を報告できなかった**
- 巻き込まれていた行の多くは、文字が主題ではない。名札や数字を描く参照スケッチで、光・線・粒子を直した PR が、文字と無関係にその行を書き換えていた

そこで台帳の行を 2 つに分ける。これは既存の機構の責務を広げる段 ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) である。

- **文字が主題でない行は、字形の四角を置かずに採る。** 字を引き、送り幅を進める組版は通し、置く手前で止める。名札や数字は人が見るための表示で、突き合わせる絵に混ぜない ([ADR-0025](0025-determinism-levels.md) 決定 5 と同じ向き)。字を測って決める置き場所は、そのまま写る
- **文字が主題の行は、台帳に採った OS の版 (`os=<macOS の major>`) を書く。** その版の機械でだけ比べ、版が違う機械では飛ばす。飛ばした理由 (行名・基準の版・その機械の版) は検査の記録に残す。字形を置いて採るのはこの行だけで、どちらで採るかは台帳の行が決める
- **`os=` の版はすべての行でそろえる。** OS を上げたら、文字が主題の行をまとめて新しい版の機械で採り直す。版が混ざると、どの機械でも比べられない行が残る

失うもの:

- **字と他の絵が重なる所の退行を、参照スケッチの行では見なくなる** (たとえば置き換えの混ぜ方で字の余白が下地を抜く、の種類)。文字が主題の行と、個別の検査で見る
- **文字が主題の行は、基準の版でない機械では誰も見ない。** その行を書き換える変更は、基準の版の機械で採る必要がある。1 台の機械で完結しないのは、この数行に限る

変えないこと:

- **役割は可視化のままである。** 飛ばした行は赤にしない。`local-render` の報告の条件も広げない — 台帳の検査の一部が飛んでも、残りが通れば報告する
- **字形を画素にする所を mokume 自身へ移す手は、ここでは取らない。** 輪郭から塗れば OS の版に依らなくなるが、文字の見た目がすべて 1 度動く工事になり、書体データそのものが変わる場合と絵文字には効かない。字の OS 依存が、この改訂で外した行の外で実害を出したときの次の段とする

### 4. API の仕様は自己判定テストで守る

シーンを構成したテストは、期待値を保存された画像ではなく**仕様から導ける**。

- **画素の直接判定** — 図形の中心は指定色を入口の変換と出力段に通して量子化した値と完全一致・半径の外は背景・縁は滑らかにする領域なので見ない
- **不変条件** — 対称に描いた絵は反転した自分と一致する / 同じ絵を 2 つの経路で描いたら一致する / 2 回描いたら一致する
- **CPU 側の参照** — 行列の合成や擬似乱数のように CPU で同じ計算ができるものは、数点を突き合わせる

失敗が「中心 (400, 300) が (255, 0, 0) のはずが (0, 0, 0)」という言葉で返るので、エージェントが読んでそのまま直せる。**各 API の実装 PR に随伴させる** — `swift test` の領土を広げるだけであり、ADR-0008 の意味での新しい機構ではない。

#### 改訂 (2026-09-15) — 期待値は、打った数そのものではなく変換を経て導く

**当初の文面**は「図形の中心は指定色を量子化した値と完全一致」だった。当時は数値の入口が転送関数しか外していなかったので、打った数がそのまま書き出しの 8 bit に戻り、この文面のままで成り立っていた。[ADR-0011](0011-color-model.md) 決定 3 の改訂 (2026-09-15) で、入口は原色も作業空間へ移すことになった。そのため彩度のある色は打った数に戻らない — `fill(204, 153, 0)` で塗った中心は `196, 155, 51` になる。

変えたのは字面だけである。**期待値を保存された画像ではなく仕様から導く**という決定の趣旨は動いていない。導く道筋が「入口の変換 (sRGB から Display P3 へ) → 出力段のエンコード → 量子化」になった。灰色 (3 成分が等しい色) は原色の取り方に依らないので、打った数と一致したままである。

### 5. AI が絵を確かめるときは、構造化された観測値を一次証拠にする

観測の報告が返す統計値 (平均色・内容の占める割合・内容の外接矩形など。[ADR-0018](0018-observation-and-control-surface.md)) は、まさに「画像を開かずに判定する」ために仕様化されている。画像を読むのは高コストで微細な差に弱いので、補助に回す。

### 6. 長回しの検査は環境変数で選び、入口は 1 本を保つ

多数フレームを回す種類の検査 (確率的にしか出ない破れを数えるもの) は、環境変数で有効になる suite として `swift test` の中に置く。検査の入口は `make ci-check` 1 本のまま保つ (ADR-0001 原則 8)。

### 7. CI は今後も描画を見ない

これを恒久の決定として記録し、[#180](https://github.com/mokume-metal/mokume/issues/180) を閉じる。自前の機械をランナーにする案・台帳の承認をゲートにする機構・環境ごとの許容差は、**実害が出たときに** #180 の記録から読み直す (ADR-0008)。

## 影響

- **CI の緑は「絵が正しい」を意味しない。** 意味するのは「絵以外が正しく、絵は変わっていない (台帳に載っているシーンと参照スケッチについては)」である。この線引きを曖昧にしないために、失敗メッセージと台帳の説明で明示する
- **見た目を伴うことを理由にした承認待ちは無い** ([ADR-0031](0031-triage-as-the-single-gate.md) 決定 1)。エージェントは証跡を載せた PR を出したら、そのまま merge queue へ進める。**当初は「見た目を伴う変更はメンテナの Approve を要する。エージェントは PR を出して証跡を載せるところまでを担い、そこで一度止まる」と書いていた** — 決定 2 が `verify: human` に乗っていた帰結で、前提ごと畳まれた (2026-09-09・[#733](https://github.com/mokume-metal/mokume/issues/733))。**止まる代わりに残るのは記録である** — 証跡が 1 つも無い PR は `drawing-evidence` が今も赤で差し戻すので、絵を見る目が読むものは必ず PR に載る
- ハッシュ照合の最小形は本 ADR の後に別 Issue で実装し、**2D の最初の API 実装より先に入れる**。先に入れないと、台帳の無い状態で面が広がり、後から遡って承認することになる
- 台帳が育つほど、共通部を触る変更のレビューは楽になる (どの絵が動いたかが差分に出る)。逆に**シーンが少ないうちは退行を取りこぼす**ので、フェーズが進むたびに代表シーンを足す
- **ただし、シーンを足しても塞げない種類の穴がある。** 台帳のシーンは面の作者が書くので、標本に現れるのは「面の作者が書く綴り」であって「作者がしうる綴り」ではない — 面の受け口そのものを動かす変更は、絵を動かしうる式が標本の中に無いまま通りうる。これを仕様として引き受けた判断は [ADR-0022](0022-production-track.md) 決定 2 の追補が持つ ([#1027](https://github.com/mokume-metal/mokume/issues/1027))
- **参照スケッチが setup で起こした `Task` の中で落ちると、どのスケッチかが読みにくい。** その `Task` はスケッチの行を描き終えた後に走るので、別の行を描いている最中に検査のプロセスごと落ちる。赤にはなるが、名指しは落ちたときの出力 (ファイルと行) が持つ (#1377)
- 決定論が壊れると台帳は役に立たない。台帳の失敗は「絵が変わった」と「決定論が壊れた」を切り分けて報告する必要があり、そのために同じシーンを 2 回描く経路を検査自身が持つ
