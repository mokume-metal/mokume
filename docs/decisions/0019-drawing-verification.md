# ADR-0019: 描画の検証は目と手元の機械で分ける

## 状態

採用 (2026-08-28)

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 8 は、検査の入口を 1 本に保ち、そこを通れば安心して merge できる状態を目指すと決めている。ところが**描画を要する検査だけは、その入口の中で走っていない**。CI のランナーが持つ仮想化された GPU はこの世代のコマンド構造を備えておらず ([#180](https://github.com/mokume-metal/mokume/issues/180))、実測ではランナーの更新を待てば解決するという見立ても消えた。

いま描画の正しさを支えているのは「手元で `make ci-check` を通す」という記述だけで、それを守っているかを見る機構は無い。

### 絵の検証は 1 つの問題ではない

「見た目が正しいか」は、性質の違う 2 つの問いが重なっている。

1. **新しく描いた絵が正しいか** — 目でしか判定できない。参照画像を持っていても、その参照が正しいと**人が認めた時点**でしか意味を持たない。機構をどれだけ厚くしてもこの判定は機械へ移らない
2. **触っていない絵が変わっていないか** — 目では担えない。PR に載る証跡は作者が「変えたつもりの絵」だけで、共通部を触った変更が他の絵を変えても、**誰もその絵を見ない**

この 2 つを 1 つの機構で解こうとすると、参照画像の置き場・承認の流れ・環境差の吸収・知覚的な比較器と、機構が際限なく膨らむ。複数の OS とブラウザで動く処理系が、環境差と戦うためにクラスタ解析つきの比較器を必要としているのはその帰結である (p5.js の視覚回帰テスト: https://github.com/processing/p5.js/blob/main/test/unit/visual/visualTest.js)。

**mokume は単一の環境しか対象にしない** ([ADR-0009](0009-platform-floor-and-toolchain.md))。環境差を吸収する複雑さを引き受ける理由が無く、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) に従えば、実害が示されていない機構は建てない。

### 実機を CI へ差し出す道は取らない

自前の機械を CI のランナーとして登録すれば描画を見られるが、public なリポジトリでそれをやると、**他人が書いたコードがメンテナの実機で走る**。得られるのは「絵を機械が見る」ことだが、上のとおり機械が見て判定できるのは退行だけであり、その退行は下記 3 の軽い機構でも捕まえられる。釣り合わない。

### 外部の作法

- **参照画像を持たない検証**は珍しくない。piglit は「この画素がこの色であること」を許容誤差つきで宣言する検査を並べ (https://blogs.igalia.com/siglesias/2015/05/29/piglit-iii-how-to-write-glsl-shader-tests/)、Khronos の適合性テスト群も保存済みの参照画像を持たず、CPU 側で参照をその場で作って突き合わせる (https://github.com/KhronosGroup/VK-GL-CTS)
- **変化の監視**は完全一致を優先し、更新は記録に残る操作にするのが定石 (Skia Gold: https://skia.org/docs/dev/testing/skiagold/ 、Filament はコミットのタグで承認する: https://github.com/google/filament/tree/main/test/renderdiff)
- **回帰を利用者の報告に頼る**体制は避けたい。描画の結果を検証するテストを持たない処理系は実在する (https://github.com/processing/processing4/tree/main/core/test/processing/core)

## 決定

### 1. 判定を 2 つに分け、担い手を分ける

| 問い | 担い手 | 形 |
|---|---|---|
| 新しい絵は正しいか | 人間と AI の目 | PR に before / after の証跡を載せ、レビューで見る |
| 触っていない絵が変わっていないか | 機械 | 代表シーンのハッシュ照合 (下記 3) |

証跡の撮り方・置き方は視覚証跡の作法が正典とし、本 ADR は繰り返さない。

### 2. 見た目を伴う Issue は `verify: human` でトリアージする

[ADR-0002](0002-issue-lifecycle-and-merge-approval.md) の既定の機構がそのまま働き、新しい仕掛けは要らない — `review-gate` が「人間の Approve なしに merge できない」を強制する。

自己判定テスト (下記 4) が厚くなった領域は `verify: machine` へ戻してよい。ADR-0002 決定 5 が敷いた路線のままである。

### 3. 触っていない絵の退行は、代表シーンのハッシュ照合で PR の差分に浮かび上がらせる

決定論 (ADR-0001 原則 2) により、同じ入力からは同じ絵が出る。そこで代表的なシーンを描き、**出力段を通した 8 bit の画素バッファ**([ADR-0011](0011-color-model.md) 決定 6 の量子化点) の sha256 を台帳の行と突き合わせる。

- **画像ファイルのバイトでは取らない。** 符号化器の版に依存させると、絵が 1 画素も変わっていないのに OS の更新で台帳が全滅する
- **台帳はテキストでリポジトリに置く。** 差分で読めて、バイナリを置かない原則 (ADR-0001 原則 7) とも両立する。**画像の実体はコミットしない** — 承認した時点の絵は PR の証跡 (外部の URL) が持つ
- **役割はゲートではなく可視化**である。「どの絵が変わったか」が PR の差分に行として現れ、レビューする目が「この変更でなぜこの絵が変わるのか」を問えるようにする。ADR-0001 原則 8 が予約していた「参照画像の比較を自動検証に育てる」の、この体制における形
- **失敗のメッセージに切り分けを書く**: 台帳と一致しない + 同じシーンを 2 回描くと一致する → 絵が変わった (意図したものなら台帳を更新し、before / after を証跡に載せる) / 2 回描いても一致しない → 決定論が壊れている (**台帳を触ってはならない**)
- 新しいシーンの追加と台帳の更新には「対象を壊して赤を見る」(ADR-0002 決定 5) を適用する。**絵に写っていない要素の退行は画像の比較では捕まらない**という既知の盲点への防壁
- 画像の外部への置き場は同じバイトに同じ URL を返すので、「after の URL が before と同じ = 絵は変わっていない」という機械的な確認も併用できる

### 4. API の仕様は自己判定テストで守る

シーンを構成したテストは、期待値を保存された画像ではなく**仕様から導ける**。

- **画素の直接判定** — 図形の中心は指定色を量子化した値と完全一致・半径の外は背景・縁は滑らかにする領域なので見ない
- **不変条件** — 対称に描いた絵は反転した自分と一致する / 同じ絵を 2 つの経路で描いたら一致する / 2 回描いたら一致する
- **CPU 側の参照** — 行列の合成や擬似乱数のように CPU で同じ計算ができるものは、数点を突き合わせる

失敗が「中心 (400, 300) が (255, 0, 0) のはずが (0, 0, 0)」という言葉で返るので、エージェントが読んでそのまま直せる。**各 API の実装 PR に随伴させる** — `swift test` の領土を広げるだけであり、ADR-0008 の意味での新しい機構ではない。

### 5. AI が絵を確かめるときは、構造化された観測値を一次証拠にする

観測の報告が返す統計値 (平均色・内容の占める割合・内容の外接矩形など。[ADR-0018](0018-observation-and-control-surface.md)) は、まさに「画像を開かずに判定する」ために仕様化されている。画像を読むのは高コストで微細な差に弱いので、補助に回す。

### 6. 長回しの検査は環境変数で選び、入口は 1 本を保つ

多数フレームを回す種類の検査 (確率的にしか出ない破れを数えるもの) は、環境変数で有効になる suite として `swift test` の中に置く。検査の入口は `make ci-check` 1 本のまま保つ (ADR-0001 原則 8)。

### 7. CI は今後も描画を見ない

これを恒久の決定として記録し、[#180](https://github.com/mokume-metal/mokume/issues/180) を閉じる。自前の機械をランナーにする案・台帳の承認をゲートにする機構・環境ごとの許容差は、**実害が出たときに** #180 の記録から読み直す (ADR-0008)。

## 影響

- **CI の緑は「絵が正しい」を意味しない。** 意味するのは「絵以外が正しく、絵は変わっていない (台帳に載っているシーンについては)」である。この線引きを曖昧にしないために、失敗メッセージと台帳の説明で明示する
- 見た目を伴う変更はメンテナの Approve を要する。エージェントは PR を出して証跡を載せるところまでを担い、そこで一度止まる
- ハッシュ照合の最小形は本 ADR の後に別 Issue で実装し、**2D の最初の API 実装より先に入れる**。先に入れないと、台帳の無い状態で面が広がり、後から遡って承認することになる
- 台帳が育つほど、共通部を触る変更のレビューは楽になる (どの絵が動いたかが差分に出る)。逆に**シーンが少ないうちは退行を取りこぼす**ので、フェーズが進むたびに代表シーンを足す
- 決定論が壊れると台帳は役に立たない。台帳の失敗は「絵が変わった」と「決定論が壊れた」を切り分けて報告する必要があり、そのために同じシーンを 2 回描く経路を検査自身が持つ
