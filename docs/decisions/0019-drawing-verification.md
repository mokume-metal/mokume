## 文脈

[ADR-0001](0001-founding-principles.md) 原則 8 は、検査の入口を 1 本に保ち、そこを通れば安心して merge できる状態を目指すと決めている。ところが**描画を要する検査だけは、その入口の中で走っていない**。CI のランナーが持つ仮想化された GPU はこの世代のコマンド構造を備えておらず ([#180](https://github.com/mokume-metal/mokume/issues/180))、実測ではランナーの更新を待てば解決するという見立ても消えた。

いま描画の正しさを支えているのは「手元で `make ci-check` を通す」という記述だけで、それを守っているかを見る機構は無い。

### 絵の検証は 1 つの問題ではない

「見た目が正しいか」は、性質の違う 2 つの問いが重なっている。

1. **新しく描いた絵が正しいか** — 目でしか判定できない。参照画像を持っていても、その参照が正しいと**人が認めた時点**でしか意味を持たない。機構をどれだけ厚くしてもこの判定は機械へ移らない
2. **触っていない絵が変わっていないか** — 目では担えない。PR に載る証跡は作者が「変えたつもりの絵」だけで、共通部を触った変更が他の絵を変えても、**誰もその絵を見ない**

この 2 つを 1 つの機構で解こうとすると、参照画像の置き場・承認の流れ・環境差の吸収・知覚的な比較器と、機構が際限なく膨らむ。複数の OS とブラウザで動く処理系が、環境差と戦うためにクラスタ解析つきの比較器を必要としているのはその帰結である (p5.js の視覚回帰テスト: https://github.com/processing/p5.js/blob/main/test/unit/visual/visualTest.js)。

**mokume は単一の環境しか対象にしない** ([ADR-0009](0009-platform-floor-and-toolchain.md))。環境差を吸収する複雑さを引き受ける理由が無く、[ADR-0008](0008-mechanism-needs-demonstrated-harm.md) に従えば、実害が示されていない機構は建てない。

### 実機を CI へ差し出す道は取らない

自前の機械を CI のランナーとして登録すれば描画を見られるが、public なリポジトリでそれをやると、**他人が書いたコードがメンテナの実機で走る**。得られるのは「絵を機械が見る」ことだが、上のとおり機械が見て判定できるのは退行だけであり、その退行は下記 3 の軽い機構でも捕まえられる。釣り合わない。

### 外部の作法

- **参照画像を持たない検証**は珍しくない。piglit は「この画素がこの色であること」を許容誤差つきで宣言する検査を並べ (https://blogs.igalia.com/siglesias/2015/05/29/piglit-iii-how-to-write-glsl-shader-tests/)、Khronos の適合性テスト群も保存済みの参照画像を持たず、CPU 側で参照をその場で作って突き合わせる (https://github.com/KhronosGroup/VK-GL-CTS)
- **変化の監視**は完全一致を優先し、更新は記録に残る操作にするのが定石 (Skia Gold: https://skia.org/docs/dev/testing/skiagold/ 、Filament はコミットのタグで承認する: https://github.com/google/filament/tree/main/test/renderdiff)
- **回帰を利用者の報告に頼る**体制は避けたい。描画の結果を検証するテストを持たない処理系は実在する (https://github.com/processing/processing4/tree/main/core/test/processing/core)

## 決定

現行の範囲は決定 1〜7。台帳は決定 3 の本文に加え、[参照スケッチの採り方](#代表シーンに参照スケッチの書き出しを加える)、[OS ごとの字形の扱い](#字形を写す行は、採った-os-の版でだけ比べる) が効く。CI が描画を見る範囲 (専用機・`merge_group` と同じリポジトリの PR と、既定ブランチの定期の検査) は [決定 7](#7-ci-は、隔離した専用機でだけ描画を見る) が持つ。CI の緑をどこまで読めるかは [影響](#影響) の先頭を見る。文脈は導入前の問題である。

### 1. 判定を 2 つに分け、担い手を分ける

| 問い | 担い手 | 形 |
|---|---|---|
| 新しい絵は正しいか | 人間と AI の目 | PR に before / after の証跡を載せ、レビューで見る |
| 触っていない絵が変わっていないか | 機械 | 代表シーンのハッシュ照合 (下記 3) |

証跡の撮り方・置き方は視覚証跡の作法が正典とし、本 ADR は繰り返さない。

### 2. 見た目に固有の承認は置換済み (→ ADR-0031)

**この決定は [ADR-0031](0031-triage-as-the-single-gate.md) 決定 1 に置き換わっている** (状態欄が名乗っているとおり)。`verify: human` は削除され、残るのは `verify: triaged` の 1 つで、`review-gate` が見るのはその**有無だけ**である。**見た目を伴うことに固有の承認は無くなった** — 承認が要るのは重要パスに触れる PR だけで、絵の正しさを担うのは決定 1 の「人間と AI の目」と、そこへ差し出す証跡そのものである。

### 3. 触っていない絵の退行は、代表シーンのハッシュ照合で PR の差分に浮かび上がらせる

決定論 (ADR-0001 原則 2) により、同じ入力からは同じ絵が出る。そこで代表的なシーンを描き、**出力段を通した 8 bit の画素バッファ**([ADR-0011](0011-color-model.md) 決定 6 の量子化点) の sha256 を台帳の行と突き合わせる。

- **画像ファイルのバイトでは取らない。** 符号化器の版に依存させると、絵が 1 画素も変わっていないのに OS の更新で台帳が全滅する
- **台帳はテキストでリポジトリに置く。** 差分で読めて、バイナリを置かない原則 (ADR-0001 原則 7) とも両立する。**画像の実体はコミットしない** — 承認した時点の絵は PR の証跡 (外部の URL) が持つ
- **役割はゲートではなく可視化**である。「どの絵が変わったか」が PR の差分に行として現れ、レビューする目が「この変更でなぜこの絵が変わるのか」を問えるようにする。ADR-0001 原則 8 が予約していた「参照画像の比較を自動検証に育てる」の、この体制における形
- **失敗のメッセージに切り分けを書く**: 台帳と一致しない + 同じシーンを 2 回描くと一致する → 絵が変わった (意図したものなら台帳を更新し、before / after を証跡に載せる) / 2 回描いても一致しない → 決定論が壊れている (**台帳を触ってはならない**)
- 新しいシーンの追加と台帳の更新には「対象を壊して赤を見る」(ADR-0002 決定 5) を適用する。**絵に写っていない要素の退行は画像の比較では捕まらない**という既知の盲点への防壁
- 画像の外部への置き場は同じバイトに同じ URL を返すので、「after の URL が before と同じ = 絵は変わっていない」という機械的な確認も併用できる

#### 代表シーンに参照スケッチの書き出しを加える

台帳の検査は、検査の中で組んだシーンに加えて、参照スケッチ (`Sketches/`) を 1 本 1 行 (`sketch:<名前>@45`) で載せる。参照スケッチは作者向けの API をほぼすべて、作者が書く形のまま呼ぶ ([#1350](https://github.com/mokume-metal/mokume/issues/1350))。それでも絵は PR の時点で 1 度見られるだけで、merge した後に共通部分を触った変更が絵を変えても、誰も見ない。描くのは書き出し (`--render`) と同じ 45 フレーム目で、経路も同じ `SketchRuntime` の `advance()` である。これは既存の機構の責務を広げる段 ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) であって、新しい部品ではない。**描く途中で落ちれば、検査ごと赤になる。**

- **標本に新しく入るのは、`Sketch` 層の中継と `SketchRuntime` の経路である** (setup / draw / 時計)。検査の中で組んだシーンは `Canvas` を直に叩くので、この経路を通る行はそれまで無かった
- **外から入る口は閉じて描く。** 観測・入力・つまみの区画と、つまみの保存を読まない。手元に残った保存で絵が動くと、「絵が変わった」の文面が台帳の書き換えを勧めてしまう
- **非同期で読む口は「届く前」の絵が載る。** `requestImage` / `requestModel` の続きは main actor で走り、検査は描き終えるまで main actor を手放さないので、45 フレーム目には必ず届いていない
- **複数フレームは持たない。** 動きのあるスケッチも 45 フレーム目には 45 フレーム分の状態が積み上がっている。取りこぼした実例が出てから足す

変えないこと:

- **役割は可視化のままである。** 動いた行が差分に現れれば足り、`drawing-evidence` の要求は広げない。失敗の文面が before / after の撮り方を示す
- **[ADR-0022](0022-production-track.md) 決定 2 の追補の限界は残る。** 参照スケッチも面の作者が書くので、標本に現れるのは「面の作者が書く綴り」である。この改訂は [#1027](https://github.com/mokume-metal/mokume/issues/1027) の穴を塞がない ([#1377](https://github.com/mokume-metal/mokume/issues/1377))

#### 字形を写す行は、採った OS の版でだけ比べる

字形については、決定論の前提 (同じ入力からは同じ絵が出る) が OS の版の内側でしか成り立たない ([#1559](https://github.com/mokume-metal/mokume/issues/1559))。

- mokume は字形を 1 つずつ CoreGraphics で焼き、四角として置く。**字形を画素にするのは OS である**
- 同じ書体で輪郭と送り幅が同じでも、焼いた画素は macOS 26 と 27 で 1〜3 階調ずれた。既定の書体は字形そのものが変わっていた。書体の引き当ては原因ではなかった

そこで台帳の行を 2 つに分ける。これは既存の機構の責務を広げる段 ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 5 の第一段) である。

- **文字が主題でない行は、字形の四角を置かずに採る。** 字を引き、送り幅を進める組版は通し、置く手前で止める。名札や数字は人が見るための表示で、突き合わせる絵に混ぜない ([ADR-0025](0025-determinism-levels.md) 決定 5 と同じ向き)。字を測って決める置き場所は、そのまま写る
- **文字が主題の行は、台帳に採った OS の版 (`os=<macOS の major>`) を書く。** その版の機械でだけ比べ、版が違う機械では飛ばす。飛ばした理由 (行名・基準の版・その機械の版) は検査の記録に残す。字形を置いて採るのはこの行だけで、どちらで採るかは台帳の行が決める
- **`os=` の版はすべての行でそろえる。** OS を上げたら、文字が主題の行をまとめて新しい版の機械で採り直す。版が混ざると、どの機械でも比べられない行が残る

失うもの:

- **字と他の絵が重なる所の退行を、参照スケッチの行では見なくなる** (たとえば置き換えの混ぜ方で字の余白が下地を抜く、の種類)。文字が主題の行と、個別の検査で見る
- **文字が主題の行は、基準の版でない機械では誰も見ない。** その行を書き換える変更は、基準の版の機械で採る必要がある。1 台の機械で完結しないのは、この数行に限る

変えないこと:

- **役割は可視化のままである。** 飛ばした行は赤にしない
- **字形を画素にする所を mokume 自身へ移す手は、ここでは取らない。** 輪郭から塗れば OS の版に依らなくなるが、文字の見た目がすべて 1 度動く工事になり、書体データそのものが変わる場合と絵文字には効かない。字の OS 依存が、この改訂で外した行の外で実害を出したときの次の段とする

### 4. API の仕様は自己判定テストで守る

シーンを構成したテストは、期待値を保存された画像ではなく**仕様から導ける**。

- **画素の直接判定** — 図形の中心は指定色を入口の変換と出力段に通して量子化した値と完全一致・半径の外は背景・縁は滑らかにする領域なので見ない
- **不変条件** — 対称に描いた絵は反転した自分と一致する / 同じ絵を 2 つの経路で描いたら一致する / 2 回描いたら一致する
- **CPU 側の参照** — 行列の合成や擬似乱数のように CPU で同じ計算ができるものは、数点を突き合わせる

失敗が「中心 (400, 300) が (255, 0, 0) のはずが (0, 0, 0)」という言葉で返るので、エージェントが読んでそのまま直せる。**各 API の実装 PR に随伴させる** — `swift test` の領土を広げるだけであり、ADR-0008 の意味での新しい機構ではない。

#### 期待値は、打った数そのものではなく変換を経て導く

入口は原色も作業空間へ移す ([ADR-0011](0011-color-model.md) 決定 3) ので、彩度のある色は打った数に戻らない — `fill(204, 153, 0)` で塗った中心は `196, 155, 51` になる。導く道筋は「入口の変換 (sRGB から Display P3 へ) → 出力段のエンコード → 量子化」である。灰色 (3 成分が等しい色) は原色の取り方に依らないので、打った数と一致する。

### 5. AI が絵を確かめるときは、構造化された観測値を一次証拠にする

観測の報告が返す統計値 (平均色・内容の占める割合・内容の外接矩形など。[ADR-0018](0018-observation-and-control-surface.md)) は、まさに「画像を開かずに判定する」ために仕様化されている。画像を読むのは高コストで微細な差に弱いので、補助に回す。

### 6. 長回しの検査は環境変数で選び、入口は 1 本を保つ

多数フレームを回す種類の検査 (確率的にしか出ない破れを数えるもの) は、環境変数で有効になる suite として `swift test` の中に置く。検査の入口は `make ci-check` 1 本のまま保つ (ADR-0001 原則 8)。

#### 改訂 (2026-10-27) — 図形の大量探索は日次と版の前、既知の回帰は毎回に残す

CPUだけで判定する図形の全探索のうち、#3338で列挙した座標変換・固定seedの交差と穴・橋の角度走査を、毎回の`test`から日次へ移す。入力・seed・許容誤差・判定器を維持し、既知の不具合を検出する固定回帰と境界例は毎回残す。固定回帰は、該当の修正を外す具体的な変異を検出できることを確かめる。日次で新たに見つかった不具合も固定回帰へ加える。

入口はMakefileに置く。`test-geometry-exploration`は元と同じdebugで全探索を実行し、`test-release`と`test-tsan`も全探索を有効にする。GitHubホストの`release.yml`で、**版を出すSHAそのもの**のdebug全探索（並走する`geometry-exploration`）とrelease検査（`release-check`）を通し、どちらかが欠ければ版を出さない（debug全探索は当初`release-check`の中の直列の段だったが、所要が上限を越えて版が出なくなったため別jobにした・#3342。検査の中身と保証は同じ）。出す版がない日も日次で実行する。専用機の`scheduled-debug`も全探索を有効にして、既存の定期debugの全範囲を維持する。ホストと専用機のOS・コンパイラの違いも見続ける。毎回の`render`・`render-pr`では固定回帰を走らせる。

全探索はXMLに対象が揃い、skip・失敗・重複がないことまで照合する。記録欠落・timeoutも成功とは数えず、既存の`release-check-report`で報告する（どちらのjobの赤も同じIssueに載る）。`make hooks-test`が記録照合と報告経路を検査する。SHA・構成・入力とseed・件数・所要を記録し、日次の古い成功を新しい版の保証へ流用しない。

理由は#3190・#3192の毎回の検査時間の増加である。全探索を削除する案や単にケース数を減らす案は、未知の破れを見つける範囲を失うため採らない。別の日次ジョブの成功だけで版を出す案も、その後に入った変更を検査したことにならないため採らない。**代償**は、探索だけで見つかる不具合がmerge後に検出されうること。scheduleの遅延・欠落があるので24時間以内の検出は約束しないが、検査が通っていないSHAの版は出さない。

### 7. CI は、隔離した専用機でだけ描画を見る

描画を要する検査は、GitHub ホストのランナーではなく**隔離した専用機** (メンテナが用意した Apple Silicon の実機) の self-hosted runner で走らせる。走らせるのは次の 3 つに限る。

| 段階 | 対象 | 文脈の却下理由 (「他人が書いたコードがメンテナの実機で走る」) が当たらない理由 |
| --- | --- | --- |
| A | `merge_group` | queue に入るのは write 権限を持つ人が入れたコードだけで、**未承認のコードは専用機に届かない**。残る経路は「悪意あるコードを queue に入れてしまう」ことで、これは merge そのものと同じ信頼の水準である |
| B | 同じリポジトリの PR | そのブランチを作れるのは write 権限を持つ人 (メンテナとそのエージェント) だけである。**このコードは既にメンテナの母艦で `make ci-check` として走っている。** 何も置かない隔離された専用機へ移すのは、攻撃面を増やすのではなく減らす |
| D | `schedule` | 走るのは**既定ブランチ (main) の最新の定義とコードだけ**である (schedule は既定ブランチの定義でしか起動しない)。**main に入ったコードは A の queue を通ったものと同じ**なので、A と同じ信頼の水準で説明できる。入力を差し込む経路も無い |

3 つの理由は独立している。A の理由 (未承認は届かない) は B に使えず、B の理由 (既に母艦で走っている) は A に要らない。D の理由 (main のコードは A を通っている) は、ブランチの上のコードを走らせる B には使えない。どれも他の理由で正当化しない。

**`workflow_dispatch` は足さない。** 書き込み権限を持つ人が任意のブランチで起こせるので、D の理由 (既定ブランチの定義とコードだけ) が当たらず、B に近い別の理由が要る。段階 C が無いのと同じく、要る実害が出たときに改めて決める。

**fork の PR (段階 C) は採らない。** 却下理由がそのまま当たる。しかも同じ機械を共有すると、fork のジョブが残したもの (ビルドの成果物・PATH・常駐するもの) の上で、後から `merge_group` のジョブが走る。必須チェックの結論まで汚せるので、承認のクリック 1 つでは釣り合わない。ジョブごとに使い捨ての VM で隔離する定石も、仮想 GPU がこの世代のコマンド構造を持たないので使えない ([#180](https://github.com/mokume-metal/mokume/issues/180))。採る条件は、信頼するジョブと信頼しないジョブを**別の機械**に分けられるようになることである。

この決定は次の前提の上に立つ。**どれかが外れたら、この決定も外れる。**

- **fork の PR を弾く条件式が、専用機のジョブに付いている** — `github.event_name == 'merge_group' || github.event.pull_request.head.repo.full_name == github.repository`
- **fork の PR のワークフローは、外部の人なら毎回承認を要する** (リポジトリの設定 `approval_policy: all_external_contributors`)。fork の PR はワークフロー自体を書き換えて `runs-on` に専用機を指定できる。上の条件式はこちらのワークフローの中にしか効かないので、その経路を止めるのはこの設定である。この関門は fork に限らず、コラボレータでない bot (`github-merge-queue[bot]` など) が起こした `pull_request` の run にも掛かる ([#1951](https://github.com/mokume-metal/mokume/issues/1951) で実測)。bot が起こすイベントで走らせたいワークフローは、ベース側の定義で走る `pull_request_target` で受け、PR の中身を checkout しない
- **専用機に秘密を置かない。** runner はリポジトリ単位で 1 度だけ登録する常駐のもので、残る秘密は runner 自身の資格情報 (その 1 台としてジョブを受け取る権限) だけである。ジョブごとに登録し直す形 (`--ephemeral`) は、登録の発行に App の秘密鍵を専用機へ置くことになるので採らない。ジョブは secrets を持たず、`permissions: contents: read` で走る
- **専用機は LAN から切り離し、ジョブの間でビルドの成果物を持ち越さない** (ジョブ開始時に作業ディレクトリを消す)。**ネットワークで隔離するのは LAN の側だけで、外向きの通信は開けてある。** 専用機の job から外へ HTTPS が通る ([#2009](https://github.com/mokume-metal/mokume/issues/2009) で `api.github.com` などへの到達を実測) のは想定どおりで、この前提の外れではない。下の mokume-syphon の検査も、外の GitHub から clone と Release の資産を引く (下の改訂 (2026-10-18))
- **`issues: write` を持つのは GitHub ホストの後続ジョブだけで、専用機のジョブは `contents: read`・秘密なしのまま** (D の起票)。後続ジョブは専用機のジョブの結論と記録の artifact を読むだけで、Issue を立てる手続きは既存の `scripts/report-check-failure.sh` が持つ (`ruleset-drift.yml` と同じ形)

文脈の「釣り合わない」の評価も変わった。当時は、決定 3 の軽い機構 (台帳のハッシュ照合) で退行を捕まえられるので、実機を差し出す得は小さいと見た。その後、**軽い機構が手元でしか走らないことの代償**が測られた。

- 手元の実行を merge queue の木へ運ぶ機構 (手元の報告・覆いの判定・描画 PR の番号順・追随の手順) が、スクリプトだけで約 1,100 行、その検査が約 1,600 行に育った
- 描画 PR は 1 本ずつしか merge できない。7 本が並んだ 2026-09-24〜25 には、揃ってから全部が入るまで約 17 時間かかった
- 前の PR が入るたびに手元の検査をやり直す手順が要り、merge の経路に人手の一歩が残った。無人で次々に merge される状態は、原理的に成り立たなかった

#### 定期の検査 (D) の範囲・頻度・歯止め (2026-10-03・[#1983](https://github.com/mokume-metal/mokume/issues/1983))

**塞ぐ実害**: [#1086](https://github.com/mokume-metal/mokume/issues/1086) は GPU を要する release の検査 (`ShapeTests` の速さ) の赤が、誰にも見られないまま 9 日間 main に残った。`ci.yml` の `test-release` (当時。下の「release の赤は merge の前ではなく、版を出す前と定期で止める」で `release.yml` の `release-check` へ移した) は GitHub ホストで走るので GPU の Suite を飛ばし、見ているのは手元で `make test-release` を打つ人だけである。[#1736](https://github.com/mokume-metal/mokume/issues/1736) も、最適化を掛けたときだけ GPU の絵が変わる同じ類の赤で、性能の計測のついでにたまたま見つかった。

**走らせるもの** (専用機は専用なので、夜間に限る理由が無い。広く、頻繁に使う):

- **debug の全部** — `make ci-check` の build・test・gpu-ran。台帳を含む。決定6で毎回から移したCPU全探索も有効にし、専用機の定期検査の範囲を維持する
- **release の全部** — Makefile の `test-release-scheduled`。台帳を含む。release でも debug と同じ台帳に合う ([ADR-0025](0025-determinism-levels.md) 決定 7)。#1736 が決着するまでは、毎回赤になるので台帳だけを外していた (この段の当初の範囲。決着したら戻すと書いてあった約束どおりに戻した)
- 「GPU が見えないので全部飛ばした」まま緑になるのは、`gpu-ran` が止める。代表は debug と同じ台帳
- **例の絵の前後の比較** — 前回までに比べ終えた定期の run の SHA から今の main までの区間を、`scripts/example-shots.py --drift` で描き比べる ([#2706](https://github.com/mokume-metal/mokume/issues/2706)・下の「定期の検査 (D) は退かせない」)。render-pr の名指しは警告で止まらず、merge queue が専用機を待つ間は出ない。そうして main に入った絵のずれが、誰の手元にも残らず 11 日放置されたのが #2705 (13 枚) である。区間に描画のパス (`scripts/drawing-paths.txt`) へ触れた変更が無ければ描かない。名指しがあれば `scheduled-report` が `scripts/report-check-failure.sh` で固定タイトルの Issue にする (`scripts/report-example-drift.sh`・鍵は変わった絵の指紋の集合)。区間の起点は GitHub ホストの門番 (`scheduled-drift-turn`) が API から引き、専用機の job (`scheduled-drift`) に権限も秘密も足さない。**別の job なのは、`scheduled-debug` が 30 分の枠の 28 分を使うから**で、base と head の 2 回の build と render は載らない。却下した案: render-pr の名指しを PR のコメントに残す (書く権限が専用機の job に要り、見送られた PR の分を拾えない) / merge 後に起票する workflow を足す (新しい workflow と権限が増える)。代償: 起票は merge の最大 6 時間後で、比べる区間に描画のパスへ触れた変更があった回だけ専用機の時間が延びる。merge されなかった PR の分は起票されない。**定期の専用機の占有は約 60 分から約 90 分に伸びる** (debug 約 30 分 + release 約 30 分 + 比較の最大 30 分)。`scheduled-report` は `scheduled-drift` を待つので、**debug・release の赤の起票は最大で約 95 分遅れる** (比較の job が門番で最大 60 分待つ分を含む)。起点は `scheduled-drift` の success で進むので、**同じ run の `scheduled-report` が落ちた回の名指しは、artifact と run の要約にしか残らない** (次の区間に入らない)。比べる job が落ちた・切れた回は、debug・release と同じく `scheduled-report` が起票し、区間は次の回へ伸びる。撮り直し込みの PR も区間に入って名指しされる (撮り直したかを見るには `// shot:` の記録の形を変える必要があり、約束の選択として別に決める)

**いつ**: 6 時間おき (`13 2,8,14,20 * * *`・JST の 05:13 / 11:13 / 17:13 / 23:13)。赤が見えるまでの最大は約 6 時間になる。schedule は遅れたり間引かれたりする (`stall-watch.yml` の実測)。毎時 0 分は避ける (このリポジトリの慣習)。

**混雑への歯止め**: 専用機は 1 台で、必須の `render` (queue の期限は 95 分・下の「改訂 (2026-10-30)」) と定期の run が取り合う。そこで 1 本の長いジョブにせず、debug と release の 2 ジョブに分け、release は debug の終了後に、下の門番を通してから queue へ入れる。各ジョブは `timeout-minutes: 30`。初回の run で所要と、直後の `render` の runner 待ちを測り、悪化していれば #1983 に戻って頻度か範囲を選び直す。

**赤を誰が読むか**: GitHub ホストの後続ジョブが `scripts/report-check-failure.sh` で起票する。**赤に数えるのは、専用機の job が落ちた (`failure`) 回と切れた (`cancelled`) 回である** — `timeout-minutes` で切れた job は cancelled で終わり、Actions に灰色で出るだけなので、落ちた回よりさらに見えない。切れる経路 (timeout・人の cancel・run をまたぐ重なりでの concurrency の置き換え) は見分けず、起票の本文がそのどれかと名乗る (代償: 人が定期の run を止めると 1 本立つが、止めた人はそれを知っているので閉じれば済む・下の「切れた (cancelled) 回も赤に数えて起票する」)。却下した案: `stall-watch` が名乗る (赤は Actions に出るだけで、#1086 も publication の赤 (#1295) も「Actions の赤を誰も見ない」形で起きた。夜間の赤は「止まって見える」状態を作らないので、`stall-watch` が読まれる機会も無い) / GitHub の通知メールに任せる (宛先が cron を最後に触った人で決まり、エージェントに届かない)。

**却下した頻度と範囲**: 週に 1 度は #1086 の 9 日間に近い放置を許す。main が動いた日だけ走らせるのは、今の main がほぼ毎日動くので判定の部品を足す理由が弱い。release を台帳ごと全部走らせるのは #1736 が決着するまで毎晩赤になる (決着した後に、台帳ごとへ戻した)。先に #1736 を切り分けるのは、いつ決着するか見えず、それまで #1086 の類が無防備のまま残る。当初の案は「毎日 1 回 (05:13 JST)・release だけ」で、「専用機は専用なので夜間に限らず広く使ってよい」という判断で、頻度と debug を含む範囲に広げた。

#### 切れた (cancelled) 回も赤に数えて起票する

**起票の本文は、job ごとの結論を名乗る** (`scripts/report-scheduled-render.sh`)。記録が無い理由の候補が、落ちた回 (ビルドかジョブの開始で落ちたか、検査のプロセスが記録を残さずに消えた) と切れた回 (走っている途中か、始まる前に止められた) で違うためである。本文は test-log の有無など、材料から分かることだけを名乗り、原因を 1 つに決めつけない。定期の job が cancelled で終わる経路は 3 つある。job の timeout、人の cancel、run をまたぐ重なりである。重なりは、前の回の job が concurrency の group に残っている間に次の回の job が来ると、待っていた job を GitHub が置き換えて cancel する形で起きる (下の「定期の検査 (D) は退かせない」の、run をまたいで重なる場合)。`queue-sweep` は定期の検査を退かせない。

退けた案:

- **timeout だけを起票し、ほかの cancel と見分ける** — 起票の job が job の annotation (`exceeded the maximum execution time`) を読むには `checks: read` が要り、`issues: write` だけだった権限が広がる。見分けて救える実害も無い (上の 14 回の cancelled 7 回は、どれも timeout だった)。timeout でない cancel の起票が実害になったときに改めて決める
- **cancelled は起票せず、起票しないことをここに書く** — 上の「赤を誰が読むか」で却下した形 (赤は Actions に出るだけ) に戻る。切れた job は落ちた job より見えにくいので、却下した案よりさらに見えない

#### 固定タイトルの Issue が開いていれば、黙らずにそこへ追記する

**`scripts/report-check-failure.sh` は、同じタイトルの Issue が開いていれば、二重には立てず、その Issue へコメントで追記する。** 追記には新規起票と同じ本文 (job ごとの結論・落ちた検査・run の URL) を載せる。後から出た赤は前の赤と別物でありうるからである。追記に失敗したら、起票のジョブは赤になる。共通部品の変更なので、定期の検査以外の呼び手 (ルールセットのドリフト・外に置いた証跡の死活・専用機の前検査) にも効く。

**代償** (当初。鍵を渡す呼び手では、下の「改訂 (2026-10-21)」が改めた): 赤が続く間、回ごとに 1 コメント増える。専用機の定期は最大 1 日 4 回で、merge_group で走る前検査の起票 (`render-environment-report`) は、前検査が落ちた group ごとに 1 回である (2026-10-12 に 14 回続けて落ちた事象なら 14 コメント。以前は Issue 1 本で、2 回目以降は黙っていた)。また、追記された赤は前の赤と同じ Issue に載るので、閉じる人は追記された分も同じ直しで解けたかを確かめる (呼び手の本文がそう言う)。

退けた案:

- **開いている Issue を閉じて済ませる** — その時点で開いている 1 件は解けるが、次に着手中の Issue が開いたままになれば同じ形が再び起きる
- **専用機の定期の検査だけ追記する** — 他の呼び手も同じ重複抑止を通り、同じ形で黙る。呼び手ごとに選ばせる口を足すほどの違いが無い

#### 改訂 (2026-10-21) — 同じ落ち方が続く間は、コメントせず本文の区画を書き換える

**呼び手が「同じ落ち方」の鍵 (`--key-file`) を渡し、鍵のハッシュが open な Issue の本文の機械の区画 (連続回数・初めて落ちた日・最後の run・鍵のハッシュ) と同じ間は、コメントせず区画だけを `gh issue edit` で書き換える** ([#2708](https://github.com/mokume-metal/mokume/issues/2708))。鍵が変わった・区画が無いときは、上のとおりコメントで追記し、区画を新しい鍵で作り直す。**鍵を渡さない呼び手・空の鍵は、いままでどおり毎回コメントする** (分からないときは知らせる側に倒す)。書き換えに失敗したら、起票のジョブは赤になる。区画の外 (人が書いた文) は触らない。

**理由**: 上の代償が通知の量で効いた。Actions の通知を切り、機械の信号を Issue で受ける方針にしたので、コメントが失敗の知らせの主な経路になり、同じ原因の赤が続くと、専用機の定期なら最大で 1 日 4 回届く。本文の編集は通知されない。別の赤が黙らない保証 (上の決定) は、鍵が変わればコメントすることで保つ。

**鍵は呼び手が決める。鍵に回ごとに揺れる値 (秒数・時刻・run の ID・全体の件数) を入れない** — 入れると毎回「違う」になって知らせ過ぎ、変わる中身を入れ損ねると別の赤が黙る。

| 呼び手 | 鍵 |
| --- | --- |
| `report-scheduled-render.sh`・`report-release-check.sh` | 呼び手の本文 (結論と落ちた検査の名前・文面。所要を持つ端末出力の末尾は `--log` 側) |
| `report-ruleset-drift.sh` | 検査の出力 (差分) |
| `report-runner-environment.sh` | 前検査の理由 |
| `report-example-drift.sh` | 変わった絵の指紋 (`snippet=`) の集合 (違う画素・最大の差・説明文の行は区間と編集で動く) |
| `report-dead-assets.sh` | 「引けなかった指し先と出所」の節だけ (出力の頭の本数・版数は日次で動く) |

`make hooks-test` が走らせる `report_check_failure_test.py` が、共通部品の振る舞いと、実物の呼び手ごとに「揺れる値だけが違う回は黙り、落ち方が違う回は知らせる」ことを見る。

**代償**: 同じ落ち方の回の出力は、Issue には最後の run の URL としてしか残らない (中身は run のログにある)。「連続 N 回」は同じ鍵で呼ばれた回数で、間に緑が挟まっても数え直さない (自動では閉じず、緑を数える口が無い)。鍵に揺れる値が入ると知らせ過ぎに倒れる (黙る側ではない)。

退けた案:

- **出力の抜粋 (時刻と run の ID を除く) のハッシュで比べる** — 通った検査の所要の秒数が回ごとに揺れ、#2251 の同じ落ち方の 2 件は 6 行違った。直したい場面そのものが直らない
- **呼び手の本文で一律に比べる** — `report-ruleset-drift.sh`・`report-dead-assets.sh`・`report-runner-environment.sh` は、回ごとに変わる中身 (差分・指し先・理由) を `--log` にだけ載せ、本文は固定の文である。落ち方が変わっても「同じ」になり、#2658 が塞いだ「別の赤が黙る」が戻る

#### release の赤は merge の前ではなく、版を出す前と定期で止める

**ホストの release の検査 (`make test-release`・GPU なし・下限 OS の `macos-26`) は merge queue の必須にせず、`release.yml` の `release-check` で、版にする SHA そのものを検査して、緑のときだけタグを打つ** ([#2662](https://github.com/mokume-metal/mokume/issues/2662))。出すものが無い日も走るので、ホストの日次の検査を兼ねる。落ちた・切れた回は、`release-check-report` が `scripts/report-check-failure.sh` で起票する (開いていれば追記する)。権限の分け方は上の D と同じで、検査を走らせるジョブは `issues: write` を持たない。GPU を要する release は、これまでどおり専用機の定期 (`scheduled-release`) が見て、版の関門にはしない。GPU の停止という環境の故障で版が止まり、6 時間おきの SHA も版の SHA と一致しないためである。

あわせて、**GPU の待ちが期限を越えた回は、報告が「環境で成り立たなかった」と先に名乗る** (`scripts/read-test-record.py --failure-messages`)。期限を越えるとプロセスの関所が閉じ、以後の GPU の検査はすべて `gpuNotResponding` で落ちる。2026-10-13 09:20Z の定期の release では 2,108 件がそうなり、要約の先頭 80 件が巻き込みで埋まって、引き金の期限切れも release 固有の赤も載らなかった。関所の分は件数と 1 例に畳み、本物の赤を先に並べ、その周期の保証が欠けていることを言う。

**代償**: release でだけ出る赤は main に入りうる。気付くのは、次の日次の `release-check` (版を出す時) か、専用機の 6 時間おきの定期である。日次の 1 回には前の版からの PR が並ぶので、原因の PR を絞る手間が増える。赤の間は版が出ない (`release:now` の出し直しも関門を通る)。版が出ないと、メンテナが新しい絵を見るリリースノートの「この版の絵」(ADR-0036) も止まる (絵は次の版にまとめて載るので、欠けずに遅れる)。merge queue の中で、合流後の木の検査のターゲットを下限 OS で組むものも無くなる (`ci-check` は merge_group で build と test を外している)。下限 OS でだけ合流後に壊れる形は、日次の `release-check` で気付く。版が出るのは約 15 分遅れる。ホストの macOS の消費は 1 日に約 15 分増え、merge_group ごとの約 12 分が減る。

退けた案 (2026-10-14 にメンテナが比べた):

- **merge queue の必須に残す** — main にも版にも赤が入らないが、queue の律速が残る。いまの形でも GPU を要する release は merge の前に走っておらず、[#1086](https://github.com/mokume-metal/mokume/issues/1086) はこの経路で入った
- **release に効かない変更の group だけ飛ばす** — 2026-09-30 以降の main の 251 コミットのうち、Sources・Tests・Makefile 等に触れるのは 183 で、飛ばせるのは約 27% だけだった。分け方を誤ると穴になる
- **release のビルドを速くする** ([#2596](https://github.com/mokume-metal/mokume/issues/2596)) — 効果は実測まで分からず、キャッシュの誤りは偽の緑になる
- **専用機の merge queue の検査で release も走らせる** — GPU の分も含めて merge の前に止まるが、1 台の専用機の所要が group ごとに約 8 分延びる。下限 OS の分は別に要る
- **`ci.yml` の `test-release` に日次の schedule を足す** (当初の #2662) — 日次の検査の後から版を出すまでに merge された分が、下限 OS の release を通らないまま版に入る

#### 専用機へ積む順番は、GitHub ホストの門番が決める ([#2062](https://github.com/mokume-metal/mokume/issues/2062))

**専用機の runner は、queued の job を先着順に拾わない。** 2026-10-04 の実測では、queue の先頭の `render` が待つ間に、専用機は後から積まれた job を 6 本 (`render-pr` 4・後ろの group の `render` 2) と 7 本 (`render-pr` 2・後ろの group の `render` 5) 拾った。先頭の `render` は一度も拾われないまま queue の期限 (60 分) を越えて弾かれ、後ろの group がまとめて組み直しになった ([#2038](https://github.com/mokume-metal/mokume/issues/2038)・[#2040](https://github.com/mokume-metal/mokume/issues/2040))。

拾う順は GitHub が決めるので変えられない。そこで**専用機に同時に積む job を絞る**。専用機の各ジョブの前に GitHub ホストの門番ジョブ (`render-turn`・判断は `scripts/render-turn.sh`) を置く:

- `render` は、1 つ前の group の run が終わるまで積まない。group は queue の順に 1 本ずつ専用機に載る。**queue の期限の直前 (90 分・当初は 55 分) まで放さない** — 早く放すと後ろの group がそろって積まれ、期限に近い前の group と取り合って元の症状に戻る。上限は門番が自分で終わって守り、job の timeout には任せない
- `render-pr` は、merge_group の run が 1 本でも残っていれば見送る。必須ではないので merge の可否は変わらない (代償: queue が混んでいる間は、PR の時点で早く気付く情報が出ない。**例の絵の前後の比較 (#1986) を持つのは `render-pr` だけ**なので、実装だけが変わって絵が古くなったことの名指しもその間は出ない。見送りは run の要約に名乗る)
- 定期の検査 (D) は、merge_group の run が残っている間は待つ

**門番が判断するのは、専用機へ積む前の 1 回だけである。** merge queue が空いている間に門番を通って専用機の queue に入った job は、後から group ができても引き下がらない。2026-10-04 には 08:38 と 08:50 に積まれた `render-pr` 2 本が、08:53 に積まれた先頭の `render` より先に拾われた。先頭は 37 分待ち、queue の期限の 22 分前に人の手の cancel で解けた ([#2064](https://github.com/mokume-metal/mokume/issues/2064))。そこで、group ができる瞬間と PR が外れる瞬間に走る `queue-sweep` (GitHub ホスト・`actions: write` を既に持つ) が、**専用機でまだ拾われていない `render-pr` の run を cancel する** (判断は `scripts/queue-sweep.sh`)。既に走っている `render-pr` は止めない。cancel するのは `render.yml` の今の group の run が残っているときだけで (門番が見送りに使うのと同じ範囲)、待たせる相手が居なければ触らない。`queue-sweep` の `actions: write` が cancel する相手は、捨てられた group の run から、生きている PR の `render-pr` の run へ広がった。失う情報は、上の「見送る」で既に受け入れたものと同じである。ただし見送りと違い、cancel された PR の run には理由が残らない (`cancelled` とだけ出る)。理由は、その時刻の `queue-sweep` の run の出力に出る。

**見直すのは、group ができた瞬間と外れた瞬間だけである。** その後に門番を通らずに専用機へ積まれた `render-pr` は、次の契機まで残る。門番が API を読めずに通した回や、人が job 単位で rerun した回である。「先頭の `render` が待つ間、専用機の queue に他の job を置かない」を常に守るには、拾われる直前に専用機の job の中で判定し直すしかない。だがそれには専用機の job に token を渡すか、token なしで外の API を引く必要がある (#2064 の案 A)。token を渡すのは、上の「専用機のジョブは権限も秘密も持たない」にぶつかる。token なしでも公開リポジトリの run は読めるが、API の回数の制限 (送り元の IP ごとに 1 時間 60 回) を専用機の job すべてで分け合うことになり、使い切った回は判定できない。外向きの通信は開けてあるので、ネットワークの側は妨げない (上の前提・下の改訂 (2026-10-18))。そこで、取り合いの大半を占める「queue が空いている間に積まれた分」を、GitHub ホストの側で group ができる瞬間に退かせるところで止めた。

**定期の検査 (D) は退かせない。** 1 つの run の中では `needs` の鎖で 1 本ずつ積まれ (debug → 門番 → release → 門番 → 例の絵の前後の比較)、どれも `wait` の門番の後ろにいるので、先頭の `render` と並ぶ定期の job は 1 本までである (`scripts/tests/render_workflow_test.py` が形を固定する)。`wait` は 60 分で通すので、queue が 60 分以上埋まり続ける間は、group がある最中にも 1 本積まれうる。それでも 1 本までである。run をまたいで重なるのは、専用機が 6 時間 (cron の間隔) 以上止まって前の回が queue に残ったときだけである。退かせると、その回の debug・release・起票がまとめて消え、赤が見えるまでの最大が約 6 時間から約 12 時間に延びる。2026-10-04 に先頭を待たせた分の多くは、既に走っていた release (30 分で切れた) で、queued の job を外す手では減らない。release の所要と頻度は [#1983](https://github.com/mokume-metal/mokume/issues/1983) の測り直しで選び直す。

門番は `actions: read` だけを持ち、GitHub ホストで走る。**専用機のジョブは権限も秘密も持たないまま**で、上の前提は動かない。門番が赤でも専用機のジョブは走らせる。`render` が skipped になると、skipped は必須チェックを満たしてしまうので、順番が乱れるほうを軽く取る。門番で待っている間に run を cancel すると `render` は cancelled で終わり、必須を満たさない (skipped にはならない・[#2063](https://github.com/mokume-metal/mokume/issues/2063) の実測)。

#### 改訂 (2026-10-27) — 門番は runner の数 (`RENDER_TURN_SLOTS`) まで group を並走させる ([#2252](https://github.com/mokume-metal/mokume/issues/2252)・[#3319](https://github.com/mokume-metal/mokume/issues/3319))

**門番が守るのは「1 本ずつ」ではなく、「専用機に積まれた job (queued + in_progress) の数が runner の数を越えない」である。** 越えなければ、runner が queued の job を先着順に拾わないこと (上の #2062) は順番を崩さない。そこで `merge_group` の門番は、前の group を base sha の親を辿って N 段まで遡り、終わっていない run を持つ group が N 本未満なら通す。N は render.yml がリポジトリの変数 `vars.RENDER_TURN_SLOTS` から渡し、未設定なら 1 (上の段のとおり 1 本ずつ) である。`yield` (render-pr) と `wait` (定期) は N を見ず、merge_group の run が 1 本でも残っていれば見送る・待つ。

**理由**: 2026-10-20〜27 の実測で、専用機は混む日に 86〜89% 埋まり、`render` は run の作成から専用機で走り出すまで p50 18.4 分・p90 29.5 分を門番の中で待っていた。queue は 2 つの group を同時に組む (`max_entries_to_build: 2`) のに、門番が 1 本ずつにしていたので、2 本目の group は 1 本目の約 22 分をそのまま待った。2026-10-16 に退けた案 3-a (同じ機械に runner を 2 つ) の再開の条件に当たり、メンテナが採った。runner は同じユーザー・同じ画面のセッションで 2 本にする — `scripts/gpu-slot.py` の枠を 2 本で共有し、GPU の同時の検査が枠の数を越えないためである。

**切り替えと戻しは変数で行う。** コードは既定 1 で merge し、2 本目の runner を置いてから変数を 2 にする。基準 (#2252 の完了条件 4: 待ちの p50 が 5 分以下・並走した回の所要が単独の +25% 以内・GPU の打ち切りと窓の検査の赤が増えない) を満たさなければ、変数を 1 に戻す。

**代償**: 専用機の GPU と画面のセッションを 2 本の job が分け合う。1 プロセスの中の並列の幅は 1 のまま (`scripts/gpu-slot.py`「並列の幅」) で、増えるのはプロセスの数 (最大 2) だけだが、専用機で GPU の検査を 2 プロセス同時に走らせた実績は無い。窓を開く検査が同じ画面で重なる。門番の 1 周の API の呼び出しは N=2 で 2 倍 (1 時間 240 件) になる。退けた案: 門番を外して runner の数だけに任せる — group と render-pr が N 本を越えて積まれると、#2062 の取り合いが runner の数だけ緩んで残る。

#### 改訂 (2026-10-30) — queue の期限を 60 分から約 95 分へ延ばす ([#3502](https://github.com/mokume-metal/mokume/issues/3502))

**決定**: 構築数 (`max_entries_to_build`) は 2 のまま、merge queue の期限 (`check_response_timeout_minutes`) を 60 分から **95 分**へ延ばす。門番の `merge_group` の上限は 55 分から **90 分**、`render-turn` の `timeout-minutes` は 65 分から **100 分**へ、同じ並びで動かす。縮退用の ruleset (`.github/rulesets-degraded/`) も同じ 95 分にする (差は必須チェックの `render` だけという固定を保つ)。定期の門番 (`scheduled-release-turn`・`scheduled-drift-turn`) は queue の期限に結び付いておらず、`wait` の 60 分と timeout の 65 分のまま動かさない。`render`・定期の job の `timeout-minutes: 30`・全検査・ALLGREEN は変えない。

**理由**: group が期限内に終わる条件は「前の group の render (最大 30 分) + group の前に割り込みうる専用機の job 1 本 (最大 30 分) + 自分の render (最大 30 分) + 門番の間隔」である。2026-10-21〜28 の 7 日で、期限切れで queue から外れた PR は 13 件あり、全件が専用機の render が間に合わなかった回だった (hosted の検査は 15 分以内に成功。[#2610](https://github.com/mokume-metal/mokume/issues/2610) の測定)。検査時間を縮めても (#3500・#3299・#3010)、割り込み 1 本で 60 分を越える構造は変わらないので、期限の側は短縮を待たずに決めた。

**代償**: 専用機が止まった回 (#2252) は、先頭の group が期限で外れるまでが 60 分から 95 分へ延びる。検査が壊れて止まった回は render の job の `timeout-minutes: 30` が先に赤にするので、故障の検知は遅れない。処理能力 (1 時間に通る group の上限) は変わらない。merge_group が専用機を長く握るので、定期の門番が待ち切れずに割り込む回が増えうる (仮説・未確認)。

**95 分が覆う重なりと、覆わない重なり**: 値の決め方 (前の group の render 30 + 割り込みうる専用機の job 1 本 30 + 自分の render 30 + 門番の間隔) の「1 本」は、走っている `render-pr` か、`wait` の 60 分で放された定期の job の**どちらか 1 本**である。両方が自分の group の前に重なる最悪の形 (前の group 30 + `render-pr` 30 + 定期の job 30 + 自分 30 = 120 分) は、95 分でも覆えず、今までどおり `checks_timed_out` で外れる。`queue-sweep` は走っている `render-pr` を止めず (`scripts/queue-sweep.sh`)、定期の検査は退かせない (上の「定期の検査 (D) は退かせない」の「1 本まで」は定期の job の数で、`render-pr` はそれとは別に走りうる) ので、この重なりは起こりうる。期限を 120 分以上へ延ばすことは、故障した回の先頭の外れがさらに遅れる代償と引き換えになるので、ここでは選ばない。適用後 7 日の測定 ([#3502](https://github.com/mokume-metal/mokume/issues/3502)) で、残った `checks_timed_out` の内訳 (どの job が前に何本入ったか) を数え、この重なりが残りの主因なら期限か重なりの側を選び直す。

**退けた案**: 構築数 1 (単独では時間切れを消さず、群の間の隙間に定期の job や render-pr が入りうる。比較は [#3503](https://github.com/mokume-metal/mokume/issues/3503) の計測の後) / 期限を延ばさず `render-turn` の上限だけを延ばす (期限を越えて待つと自分の render が走る前に弾かれる。`scripts/tests/render_workflow_test.py` が止める) / 期限と同時に render の `timeout-minutes` を延ばす (故障の検知が遅れる)。

#### 外のリポジトリから専用機に届くのは、render-pr が組む mokume-syphon の main だけ

**塞ぐ実害**: [mokume-syphon#26](https://github.com/mokume-metal/mokume-syphon/issues/26) では、本体の振る舞いの変化 (出口へ渡す絵が 1 フレーム遅れた) で mokume-syphon の GPU の検査が 4 件落ちた。気付いたのは mokume-syphon の追随の PR で、本体は壊した版をもう出していた。mokume-syphon の GPU の検査は GitHub ホストでは Suite ごと飛ぶので、専用機の外では誰も見ない。

**決定** ([#1971](https://github.com/mokume-metal/mokume/issues/1971)・[#1973](https://github.com/mokume-metal/mokume/issues/1973)): `render-pr` の最後の段 (`scripts/syphon-check-pr.sh`) が、mokume-syphon の `main` を clone し、依存の mokume を PR の木へ差し替えて組み、GPU の検査まで走らせる。警告だけで merge は止めない (`continue-on-error`)。**mokume-syphon には runner を登録しない。**

届く範囲を延ばしてよい理由は、B (同じリポジトリの PR) の水準を外れないことである。

- mokume-syphon の `main` も PR 必須・bypass なしの ruleset で守られ、書ける人は本体と同じである (2026-10-14 の実測で collaborator は admin 1 人)。「専用機に届くコードは write 権限を持つ人のもの」が保たれる
- 専用機のジョブは token も秘密も持たないままである。clone は公開リポジトリを匿名で引き、Syphon.xcframework は mokume-syphon の Release の資産 (同じ org の成果物) を引く
- 走るのは `render-pr` の中だけで、`render` (A) と定期の検査 (D) には入れない。必須の所要を延ばさず、外のリポジトリの赤が merge や起票を動かさないためである (`scripts/tests/render_workflow_test.py` が形を固定する)
- 届く範囲は `render.yml` 1 枚で言えるまま残る。外の clone 元は `scripts/syphon-check.sh` の既定の 1 つだけである

**却下した案**:
- (a) org 単位の runner に直して、mokume-syphon の PR も専用機で受ける — 別のリポジトリのジョブは門番 (`render-turn.sh`) に見えず、必須の `render` が待たされる
- (b) 同じ機械に 2 つ目の runner を立てる — 1 台に 1 ジョブずつの前提が崩れ、描画の検査と GPU を取り合う

**代償**: mokume-syphon の PR 自身 (Dependabot の pin の張り替えを含む) は、PR の時点では GPU の検査を受けない。(a) へ移るのは、その穴のために壊れた版が出たときである。

**動かさないもの**: 決定 1 (新しい絵の正しさは人間と AI の目が判定する) と、PR に証跡を要求すること。機械が描けるようになっても、新しい絵の判定は移らない。決定 4・5 (仕様から導く自己判定テスト・観測値を一次証拠にする作法) もそのままである。専用機が変えるのは、決定 3 の台帳を含む描画の検査が**どこで走るか**だけである。

実装は [#878](https://github.com/mokume-metal/mokume/issues/878) (専用機の描画ジョブ) と [#879](https://github.com/mokume-metal/mokume/issues/879) (手元の実行を運ぶ機構を消す) が持ち、定期の検査 (D) は [#1983](https://github.com/mokume-metal/mokume/issues/1983) が持ち、#180 はその親として残す。

#### 改訂 (2026-10-18) — 「ネットワークで隔離」は LAN の側だけで、外向きの通信は開けてある

**当初、前提の行は「専用機はネットワークで隔離し」とだけ書き、何を隔離するかを書いていなかった。** そのうえ上の門番の段は、拾われる直前に専用機の job の中で判定し直す案 (#2064 の案 A) を退ける理由に、「token なしで外の API を引く」ことが「ネットワークの隔離にぶつかる」を挙げていた。外向きの通信が閉じていると読める書き方である。

実際に隔離しているのは LAN の側だけで、外向きは開けてある。[#2009](https://github.com/mokume-metal/mokume/issues/2009) で専用機の job から `api.github.com`・`formulae.brew.sh`・`example.com` へ HTTPS が通り (どれも 200)、メンテナはそれを想定どおりと答えた。上の mokume-syphon の段も、専用機の job が毎回外の GitHub から匿名で clone し、Release の資産を引く形で、外向きの通信に依っている。前提の行だけを読むと #2009 の到達が隔離の破れに見え、案 A の理由と mokume-syphon の段は同じ決定の中で食い違っていた ([#2248](https://github.com/mokume-metal/mokume/issues/2248))。

**前提の行に隔離の範囲を書き、案 A を退ける理由から「ネットワークの隔離」を外した。** 案 A は退けたままである。結論は、token を渡せないこと (権限も秘密も持たない) と、token なしの API の回数の制限で支えられる。決定の意味は変えていない — 専用機に届くコードの線 (段階 A・B・D) と、ジョブが権限も秘密も持たないことは、外向きの通信を閉じることに依っていない。

**代償**: 専用機の job が走らせるコードは外へ出られる。持ち出されうるものを小さく保つのは、届くコードを write 権限を持つ人のものに限ることと、専用機に秘密を置かないこと (上の前提) である。外向きを絞るなら、mokume-syphon の検査の取り方 (clone と Release の資産) も一緒に変わる。

## 影響

- **CI の緑は「実行対象の検査が通った」を意味し、「絵が正しい」ことや「絵が変わっていない」ことを保証しない。** GitHub ホストのランナーは描画を走らせない。描画の検査は、専用機の `render` が merge queue の合流後の木で走らせる (決定 7・[#878](https://github.com/mokume-metal/mokume/issues/878))。 定期の検査 (決定 7 の D) は、そこに載らない GPU の検査 (release でしか走らない速さの検査など) も main の最新の木で覆う。以前は、手元の `make ci-check` の記録 (`local-render`) で合流後の木を覆う機構を使っていたが、畳んだ ([#879](https://github.com/mokume-metal/mokume/issues/879))。台帳照合が示すのは、**実行した行が、その版の台帳と一致した**ことだけである。意図した変更に合わせて台帳を更新した回も通るし、OS が違って飛ばした字形の行は一致を確かめていない。参照スケッチには決定 3 の制約 (45 フレーム目・字形の扱い・非同期資源の到着前) も残る。新しい絵の評価は決定 1、API の仕様の検証は決定 4 が担う

  **当初は「絵以外が正しく、絵は変わっていない (台帳に載っているシーンと参照スケッチについては)」と要約していた。** これは台帳の意図した更新と未実施の行を区別せず、検査対象の外まで保証すると読めた。決定 1・3・4 の分担を変えず、その検証範囲へ説明を合わせた (2026-09-27・[#1722](https://github.com/mokume-metal/mokume/issues/1722))。失敗メッセージと台帳の説明でも、この線引きを保つ
- **見た目を伴うことを理由にした承認待ちは無い** ([ADR-0031](0031-triage-as-the-single-gate.md) 決定 1)。エージェントは証跡を載せた PR を出したら、そのまま merge queue へ進める。**当初は「見た目を伴う変更はメンテナの Approve を要する。エージェントは PR を出して証跡を載せるところまでを担い、そこで一度止まる」と書いていた** — 決定 2 が `verify: human` に乗っていた帰結で、前提ごと畳まれた (2026-09-09・[#733](https://github.com/mokume-metal/mokume/issues/733))。**止まる代わりに残るのは記録である** — 証跡が 1 つも無い PR は `drawing-evidence` が今も赤で差し戻すので、絵を見る目が読むものは必ず PR に載る
- **ハッシュ照合の最小形は [#248](https://github.com/mokume-metal/mokume/pull/248) で導入済みである。** 当初は「本 ADR の後に別 Issue で実装し、2D の最初の API 実装より先に入れる」と順序を決めた。台帳の無い状態で面を広げ、後から遡って承認することを避けるためだった。導入後も未実装の計画として読めた説明を、当初の経緯と分けた (2026-09-27・[#1722](https://github.com/mokume-metal/mokume/issues/1722))
- 台帳が育つほど、共通部を触る変更のレビューは楽になる (どの絵が動いたかが差分に出る)。逆に**シーンが少ないうちは退行を取りこぼす**ので、フェーズが進むたびに代表シーンを足す
- **ただし、シーンを足しても塞げない種類の穴がある。** 台帳のシーンは面の作者が書くので、標本に現れるのは「面の作者が書く綴り」であって「作者がしうる綴り」ではない — 面の受け口そのものを動かす変更は、絵を動かしうる式が標本の中に無いまま通りうる。これを仕様として引き受けた判断は [ADR-0022](0022-production-track.md) 決定 2 の追補が持つ ([#1027](https://github.com/mokume-metal/mokume/issues/1027))
- **参照スケッチが setup で起こした `Task` の中で落ちると、どのスケッチかが読みにくい。** その `Task` はスケッチの行を描き終えた後に走るので、別の行を描いている最中に検査のプロセスごと落ちる。赤にはなるが、名指しは落ちたときの出力 (ファイルと行) が持つ (#1377)
- 決定論が壊れると台帳は役に立たない。台帳の失敗は「絵が変わった」と「決定論が壊れた」を切り分けて報告する必要があり、そのために同じシーンを 2 回描く経路を検査自身が持つ
