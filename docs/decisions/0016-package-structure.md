# ADR-0016: パッケージ骨格 — 依存の層をターゲットで表し、アンブレラで気楽さを保つ

## 状態

採用 (2026-08-27)

## 文脈

[ADR-0001](0001-founding-principles.md) 原則 6 は、リポジトリとリリースの単位を既に決めている。

> **単一リポジトリ・単一バージョン・自動リリース** — ライブラリ・CLI・プロジェクトテンプレートは 1 つのリポジトリで開発し、1 つのバージョンタグで常に同時に出荷する。(中略) バイナリ配布物を必要とする拡張だけは別リポジトリに置く。

**本 ADR はこれを再決定しない。** 決めるのはその内側 — 1 つのパッケージの中を、どういう単位に割り、どう依存させるかである。

### 割り方を決めないと依存が絡む

機能を素直に足していくと、音の処理が描画の型を参照し、描画が音の状態を見る、という往復が生まれる。一度絡むと解くのは難しく、**「この機能だけ使いたい」という利用のされ方ができなくなる**。ビルド時間も、変更の影響範囲も、絡んだぶんだけ広がる。

割り方の基準はいくつもありうるが、**依存の向きだけは構造で守れる**。ターゲットを依存の層で分けておけば、逆流したコードはビルドが通らない。文書のルールで守る必要がない。

### しかし利用者に割り方を意識させない

層に分けると、利用者は「どれを import すればよいか」を知る必要が出てくる。これは [ADR-0001](0001-founding-principles.md) 原則 1 (スケッチの気楽さ) に反する。

> スケッチは 1 ファイルから始められ、ボイラープレート・並行性の注釈・ビルド設定をユーザーコードに要求しない。

内部の割り方と、利用者から見た入口は、別に決めてよい。

### ワイヤフォーマットの正典

[ADR-0001](0001-founding-principles.md) 原則 3 は、プロセス間の通信形式について既に方向を持っている。

> プロセス間の通信形式は schema を正典とし、実装が schema に従う (逆ではない)。

これを構造に落とすと、**schema がソースツリーの中で実装から独立した場所を持つ**必要がある。実装の中に埋め込むと、正典が実装になってしまう。

## 決定

### 1. ターゲットは依存の層で分ける

各ターゲットは次のいずれかの層に属し、**依存は必ず下の層へ向かう**。

| 層 | 依存できる先 | 例 |
| --- | --- | --- |
| 基盤 | 何にも依存しない | 診断・ログ |
| 独立領域 | 基盤のみ | 描画コアを必要としない領域 |
| 描画コア | 基盤 | 描画の中核 |
| コア依存 | 基盤・描画コア | 描画コアの上に載る領域 |

**具体のモジュールの列挙は本 ADR では固定しない** — 何が独立領域になるかは、実装してみるまで確定しない ([ADR-0001](0001-founding-principles.md) 原則 4)。固定するのは層の定義と、依存が下へ向かうという規則である。

### 2. アンブレラのターゲットを 1 つ提供する

すべてを再エクスポートするターゲットを用意し、利用者は 1 つの import で全機能に届く。個別のターゲットを直接 import することも妨げない。

**内部の割り方が利用者の書き味に漏れない** ([ADR-0001](0001-founding-principles.md) 原則 1)。

### 3. CLI とテンプレートは同じパッケージに置く

CLI は同じパッケージの別の product とする。プロジェクトテンプレートも同じリポジトリに置き、単一のバージョンタグで同時に出荷する (原則 6)。

### 4. ワイヤフォーマットの schema は実装から独立した場所に置く

プロセス間・ファイル入出力の形式を定義する schema は、ソースツリーの中で**実装ターゲットの外**に置く。実装は schema に従い、検証される側になる ([ADR-0001](0001-founding-principles.md) 原則 3)。

### 5. AI 協調の機構はコアの要件であり、後付けの拡張にしない

実行中スケッチの観測・入力注入・ヘッドレス実行は、描画コアの要件として設計に含める。**別モジュールの拡張として後から差し込む形にしない** ([ADR-0001](0001-founding-principles.md) 原則 3・[ADR-0012](0012-view-layer.md) 決定 1)。

### 6. Examples は 1 つのワークスペースに集約する

作例は個別のパッケージに分けず、1 つのワークスペースの中に置く。リソースを使う作例が**リソースの宣言を書き忘れたらビルドが通らない**構造にする。

**作例そのものは本 ADR では追加しない** — 置き方だけを決める。

### 7. バイナリ配布物を要する拡張は別リポジトリ

原則 6 の決定に従う。本 ADR で再決定しない。

## 影響

- 決定 1 により、`Package.swift` のターゲット定義が層の宣言そのものになる。依存の逆流はビルドエラーとして現れ、検査を別に作る必要がない
- 決定 1 の「列挙を固定しない」により、モジュールの追加・統合は `Package.swift` の変更で行える。層の定義に反する追加だけが議論の対象になる
- 決定 2 により、利用者から見た入口は 1 つに保たれる。層の再編成が利用者のコードに波及しない
- 決定 4 により、ワイヤフォーマットの変更は schema の変更として現れる。実装だけが変わって形式が黙って変わる経路を持たない
- 決定 5 により、観測とヘッドレスの経路は最初から描画コアの中にある。[ADR-0012](0012-view-layer.md) 決定 1 (描画をビューから独立させる) と同じ理由に立つ
- 決定 6 により、作例が増えてもパッケージの数は増えない。ビルドと検査の対象が 1 つに保たれる
- 本 ADR の merge 後、`Package.swift` の骨格を別の PR で入れる。そこで初めて `swift build` / `swift test` が `make ci-check` に加わり、[ADR-0009](0009-platform-floor-and-toolchain.md) が定めたツールチェーンを CI が実際に満たすかが判明する
