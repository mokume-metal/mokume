# ADR-0007: 承認可能性の不変条件

## 状態

採用 (2026-08-27) / 改訂 (2026-08-30): 承認者集合の代理を `author_association` にする / 改訂 (2026-08-30): フックの射程を実態に合わせ、回復手順に rerun を足す

## 文脈

[ADR-0003](0003-agent-identity-separation.md) はエージェントに GitHub App の identity を与え、承認を native の Approve に戻した。「PR の作成者は自分の PR を承認できない」というプラットフォーム制約が効く状態を作ったことが、承認を規約から構造へ変えた。

その構造には、書かれていない前提がある。**承認できる人が author 以外に存在すること**である。

[#88](https://github.com/mokume-metal/mokume/issues/88) でこの前提が破れた。エージェントが App の token を発行できず、素の `gh` — つまりメンテナ本人の identity — で PR を作った。対象 Issue は `verify: human` で、変更は `docs/decisions/` と `.github/` に触れていた。`review-gate` と CODEOWNERS の双方が承認を要求し、唯一の承認者候補は author 本人。**満たす手段が無い PR** ができ、close して作り直すほかなかった。

この失敗には三つの性質がある。

**1. author の種類によらない。** `verify: human` の Issue に**メンテナ自身**が PR を出しても、同じく自己承認になって詰む。CODEOWNERS 対象パスでも同じで、main への直接 push はルールセットが禁じている。つまり単独メンテナ構成では「承認が要る変更を自分名義の PR で入れる」経路が構造的に存在しない。#88 はエージェントの取り違えとして現れたが、根は取り違えではない。

**2. 破れても何も言わない。** 詰みは PR 作成の瞬間には何の警告も出さず、承認を求める段階まで進んで初めて分かる。`ci-gate` は承認を見ないので (ADR-0003 決定 5)、その間 CI は緑である。発見が最も遅い形の失敗になっている。

**3. 回復に前進の道が無い。** PR の author は後から変えられない。close して作り直す以外に無く、それまでのレビューも紐づけも失われる。

原因を「エージェントが鍵を見つけられなかったこと」に置くと対症になる。[#95](https://github.com/mokume-metal/mokume/issues/95) の調査で分かったのは、**鍵が無かったのではなく探し方を知らなかった**ことだった。ADR-0003 は「秘密鍵の中身も、その在処もリポジトリに書かない」と決めており、これは正しい。しかしその決定が「探し方も書けない」と読まれ、エージェントは鍵が無いと誤断してメンテナ名義に落ちた。実際には手元の秘密管理の一覧を引けば分かる状態だった。

## 決定

### 1. 承認可能性を不変条件として置く

> **承認が要る PR の author は、その PR を承認できる集合の要素であってはならない。**

ADR-0003 決定 3 が前提にしていながら書かれていなかったものを、明文の不変条件にする。書くことで、機構が守る対象になる。

「承認が要る」の判定は既に二つあり、新しい分類は作らない — ルールセットの `required_reviewers` が 1 承認を課しているパスに触れること (ADR-0003 決定 4) と、対象 Issue が `verify: human` であること ([ADR-0002](0002-issue-lifecycle-and-merge-approval.md) 決定 1) である。不変条件はその上に乗るだけである。

### 2. 例外を作らない — メンテナも App identity で PR を作る

author が repository admin なら通す、という例外は作らない。理由は二つある。

**判定で区別できない。** 「メンテナが自分で作った PR」と「エージェントがメンテナの認証で作った PR」は、GitHub から見て同一である。token の主体は見えても意図は見えない。ADR-0003 決定 6 が認めているとおり、同じマシンにメンテナの認証が残っている限り、エージェントが認証を切り替える経路は理屈上残っている。例外を明文化すれば、理屈上のものが**既定の経路**になる。

**メンテナにとっても詰みは詰みである。** 文脈の 1 のとおり、単独メンテナでは自分名義の PR を通せない。例外を作って救われるのは「承認が要らない PR」だけで、それは元から不変条件の対象外である。

代償は、メンテナも PR 作成時に installation token を発行する手間を負うことである。鍵は既に手元にあり、発行は 1 コマンドで済む。承認が要らない PR (ルールセットの対象パス外かつ `verify: machine`) は従来どおりでよい。

### 3. 不変条件は 2 段で守る

| 機構 | 効く範囲 | 破れを止める時点 |
| --- | --- | --- |
| PR 作成前のローカルフック | **このリポジトリを主として開いた** Claude Code のセッションのみ | **PR を作る前** — 作り直しが発生しない |
| `review-gate` の検知 | 全エージェント・全経路 | PR 作成後の CI |

どちらも単独では足りない。フックはリポジトリの `.claude/` に置くため、同等のフック機構を持たないエージェント (現状の Codex CLI など) には効かない。`review-gate` は経路を問わないが、赤くなった時点で PR は既にあり、#88 と同じく作り直しになる。**常道はフック、`review-gate` は経路を問わない保険**である。

**フックの射程は「エージェントの種類」より狭い。** 配線は `.claude/settings.json` にあり、読まれるのは**そのセッションが主として開いたディレクトリ**のものだけである。別のリポジトリを主として開いたセッションがこのリポジトリの worktree で作業しても、この配線は効かない (作業中に `cd` で移っても後から有効にはならない)。[#513](https://github.com/mokume-metal/mokume/issues/513) がその形で、[#511](https://github.com/mokume-metal/mokume/pull/511) がメンテナ名義で作られた。

この穴は塞げない。フックを全セッションへ届かせるには個人環境の `~/.claude/` へ置くほかなく、それは [ADR-0017](0017-agent-support-locality.md) 決定 1・2 が禁じている形そのものである — 入れている人にだけ効く支援を前提にすると、規約が環境によって変わる。ルールセット側で author を絞る道も無い (PR の author を制限する rule type が存在せず、`commit_author_email_pattern` は ADR-0003 決定 6 がメンテナ名義に固定した commit の author を見るので代理にならない)。

したがって**並行セッションが増えるほど、保険のほうが常道になる**。この前提で自衛する — 別のリポジトリを主とするセッションからこのリポジトリを触るときは、フックが黙っていることを「安全である」と読まない。

[ADR-0001](0001-founding-principles.md) 原則 8 は検証を規約でなく構造で担わせることを求めるが、**構造が一つである必要はない**。ここでは網羅性 (全経路に効く) と早さ (作る前に止まる) が、別の機構でしか得られない。

#### 改訂 (2026-08-30) — 承認者集合の代理を `author_association` にする

当初この検査は `.github/CODEOWNERS` を承認者集合の代理として読んでいた。collaborator の一覧が `Administration` 権限を要求し、エージェントの App は決定 1 (ADR-0003) によりそれを持たないためである。

**CODEOWNERS は [#530](https://github.com/mokume-metal/mokume/issues/530) で畳んだ** (ADR-0003 決定 4 の改訂) ので、代理を GitHub native の signal へ移す。REST の PR オブジェクトが返す `author_association` が、追加の権限なしに org の中の人か外の人かを答える — App の PR は `CONTRIBUTOR`、[#88](https://github.com/mokume-metal/mokume/pull/88) のメンテナの PR は `MEMBER` だった (実測)。

| | CODEOWNERS 版 | `author_association` 版 |
| --- | --- | --- |
| 承認者集合 | ファイルに書いた名前 | **実際の org 所属** |
| 外部コントリビューター | 集合外なので通る | `CONTRIBUTOR` / `NONE` なので通る |
| 承認が要るパスの判定 | CODEOWNERS のパターン (ルールセットの写し) | **ルールセットの `file_patterns` そのもの** |
| メンテナが 2 人目に増えたとき | owner を数えて自動で緩む | **緩まない** (所属は読めるが人数は数えられない) |

最後の行が失うものである。ただし詰みはしない — 2 人目の Approve が付けば検査を抜ける。それまで赤が出るだけで、これは下の影響が既に述べている「増えたらそのとき別途判断する」の範囲に収まる。写しを 1 つ消すこととの引き換えとして受け入れる ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) — 起きてから直す)。

### 4. 破れたときの回復は close して作り直す

author は後から変えられないので、これが唯一の回復手順である。**差し戻しのメッセージはこの手順を明示し、「承認を待てば済む」と読める書き方をしない** — 待っても承認は永久に来ない。

**close して作り直すだけでは終わらない。** 詰んだ側の run が付けた `review-gate` の赤は**同じ commit に残り続ける**ので、作り直した側の run が全部緑になっても `ci-gate` は赤のままになる ([#513](https://github.com/mokume-metal/mokume/issues/513) で実測 — [#511](https://github.com/mokume-metal/mokume/pull/511) を close して [#512](https://github.com/mokume-metal/mokume/pull/512) を作った後がこの形だった)。**作り直した側の run を rerun して、同じ名前の check を新しい結果で上書きするところまでが回復である。**

ここは間違えやすい方向に間違える。目に見えて赤い run は**詰んだ側**の run なので、[#259](https://github.com/mokume-metal/mokume/issues/259) の一般形 (古い失敗 check run が判定を固定する → その run を rerun する) をそのまま当てると、**同じ赤を再生産する** — その run は詰んだ側の PR のイベントを持っており、何度走らせても判定は変わらないうえ、`human-approval` まで一時的に緑を名乗る。打つ先は逆で、**新しい PR の側**である。

### 5. 秘密は「在処」と「探し方」を区別する

ADR-0003 の「秘密鍵の中身も、その在処もリポジトリに書かない」は維持する。そのうえで、**探す順序はリポジトリに書く**。

書けるのは移植可能な部分だけである — 「手元の秘密管理には自動化から読める秘密の一覧があるのが普通なので、鍵が無いと即断せず、まずその一覧を引く」。どの秘密管理を使うかは環境ごとに違うので書かない。この一段があれば #88 は起きなかった。

在処を書かない目的は、**リポジトリを読める者が秘密へ到達する経路を作らない**ことである。一覧を引く手順にはその性質が無い — 引けるのは、既にその環境の秘密管理へアクセスできる者だけである。目的を損なわずに書ける。

## 影響

- AGENTS.md の「エージェントの identity」節を改訂する。暫定条項「App の作成が済むまでは従来どおりメンテナのアカウントで作業してよい」は移行完了によって事実と食い違っているので削除し、決定 2 と決定 5 を書き足す
- PR 作成前のフックを `.claude/` に置く ([#103](https://github.com/mokume-metal/mokume/issues/103))。`review-gate` に検知を足す ([#104](https://github.com/mokume-metal/mokume/issues/104))
- ~~`.github/CODEOWNERS` は変更不要である。App はユーザーでもチームでもないため CODEOWNERS に書けず、App が作った PR は決定 1 を自動的に満たす~~ (2026-08-30 改訂: CODEOWNERS は #530 で削除した。App が集合の外にある性質は `author_association` が `CONTRIBUTOR` を返すことで引き継がれる)
- ルールセットも変更不要である。`required_approving_review_count` は 0 のまま (ADR-0003 決定 4)
- **不変条件はメンテナが増えれば緩む。** 二人目が入れば「author 以外に承認者がいる」が自然に成り立ち、決定 2 の一本化は必須ではなくなる。ただし決定 2 の第一の理由 (判定で区別できない) は人数に依存しないので、緩めるかどうかはそのとき別途判断する
- 検知の実装は「author が承認者集合の唯一の要素か」を一般形のまま書くことが望ましい。メンテナが一人の現状では「author が人間なら詰む」と同値だが、人数が変わったときに自動で正しくなる。ただし承認者集合を引くには collaborator の権限を読む必要があり、ADR-0003 決定 1 によりエージェントの App は `Administration` 権限を持たない。引けない場合は近似に落とす — 2026-08-30 の改訂で選んだのは `author_association` で、「author が bot でないこと」より狭い (外部コントリビューターを巻き込まない)
