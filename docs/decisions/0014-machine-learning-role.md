# ADR-0014: 機械学習の位置づけ — 4 つの機構の役割分担を先に引く

## 状態

採用 (2026-08-27)

## 文脈

クリエイティブコーディングにおける機械学習の使い道は幅広い — 画風の変換、学習済みの場をリアルタイムに評価する、映像から人物や姿勢を取り出す、テキストや画像を生成する。

プラットフォームが提供する機構も複数ある。[ADR-0009](0009-platform-floor-and-toolchain.md) が Metal 4 世代と macOS 26 を前提に置いたことで、次の 4 つがすべて選択肢に入る。

- **シェーダ内でのテンソル評価** (Metal 4 の ML 統合)
- **モデル単位の推論** (CoreML)
- **画像処理のグラフ** (MPSGraph)
- **生成系** (Foundation Models)

### この領域は「あると良さそう」が最も溜まりやすい

[ADR-0001](0001-founding-principles.md) 原則 4 は、機能を実需で駆動することを求めている。機械学習はこの原則が最も破られやすい領域である — できることが多く、どれも魅力的に見え、しかし実際の作品で使うのはそのうちごく一部だからである。

**したがって本 ADR で作るのは API ではなく地図である。** どの機構が何を担うかを先に決めておけば、実需が現れたときに「どれを使うか」で迷わず、また**別の機構で同じことを二度実装する**ことも避けられる。道を作るのは実需が現れてからでよい。

### 分担を決める軸

4 つの機構は用途が部分的に重なる。切り分ける軸は**「フレームの中で評価するか、フレームの外で走らせるか」**である。

フレームの中で毎回評価するもの (画風の変換、学習済みの場の参照) は、結果を GPU 上に置いたまま描画に使えなければ意味がない。CPU との往復が入った時点でフレーム時間に収まらなくなる。

フレームの外で走るもの (映像からの特徴抽出、生成) は、往復のコストより「モデルをそのまま動かせること」のほうが重要になる。

### 旧世代の画像フィルタ API

画像処理には旧世代の固定機能フィルタ群もあるが、[ADR-0009](0009-platform-floor-and-toolchain.md) が Metal 4 世代への一本化を決めている。**同じことが新しい機構でできる以上、旧世代の API を新規に採用する理由はない。**

### 回避策を持ち込まない

この領域のフレームワークには、Objective-C 由来の API 設計が残っているものがある。メソッドの差し替えや関連オブジェクトによる回避策で不足を埋める書き方は、**動くが後から読めない**。[ADR-0010](0010-concurrency-model.md) 決定 3 と同じ姿勢で、最初から採らない。

## 決定

### 1. 4 つの機構の役割を次のように分担する

| 用途 | 使う機構 |
| --- | --- |
| フレーム内で GPU 上のデータに対して評価する (画風変換・学習済みの場の参照) | Metal 4 のシェーダ内テンソル |
| 学習済みモデルをモデル単位で推論する (特徴抽出・分類・姿勢推定) | CoreML |
| 画像処理を計算グラフとして組む | MPSGraph |
| テキストなどの生成 | Foundation Models |

用途が重なる場合は、**フレーム内で評価する必要があるかどうか**で決める。必要があるならシェーダ内テンソル、無いなら残りから選ぶ。

### 2. 旧世代の固定機能画像フィルタ API を新規採用しない

画像処理は MPSGraph またはシェーダで書く。

### 3. Objective-C runtime を用いた回避策を持ち込まない

メソッドの差し替え・関連オブジェクトによる回避策を使わない。フレームワーク側の制約は、現行の API (async での監視・現行の delegate) の範囲で解く。解けない場合は、その機能を採らない判断も含めて検討する。

### 4. 本 ADR は API を定義しない

決定 1〜3 は境界の宣言であって、公開 API の設計ではない。**実際の作品制作で必要になった経路から実装する** ([ADR-0001](0001-founding-principles.md) 原則 4)。どの機構も「使えるようにしておく」ためだけには実装しない。

### 5. モジュール上の置き場は本 ADR では決めない

機械学習の機能をどのモジュールに置くかは、パッケージ骨格 ([#139](https://github.com/mokume-metal/mokume/issues/139)) の担当とする。

## 影響

- 実需が現れたとき、「どの機構を使うか」の議論を再演しない。決定 1 の表を見て決める
- 決定 1 の軸により、同じ処理を 2 つの機構で二重に実装する事態を避けられる
- 決定 4 により、本 ADR の merge 後もライブラリのコードは 1 行も増えない。これは意図した状態である
- 決定 1 の「フレーム内で評価する」経路は、[ADR-0011](0011-color-model.md) の作業空間 (linear 16F) の上で動く。テンソルと描画が同じ精度・同じ色空間を共有する
- 決定 3 により、回避策で埋めていた不足は「採らない」判断に倒れることがある。これは機能の幅より、後から読めることを優先した結果である
- 決定 1 の表は、新しい機構が増えたときに更新する。表そのものが議論の置き場になる
