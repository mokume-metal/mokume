# ADR-0014: 機械学習の位置づけ — 4 つの機構の役割分担を先に引く

## 状態

採用 (2026-08-27) / 改訂あり (本文の「改訂 (日付)」見出し)

## 文脈

クリエイティブコーディングにおける機械学習の使い道は幅広い — 画風の変換、学習済みの場をリアルタイムに評価する、映像から人物や姿勢を取り出す、テキストや画像を生成する。

プラットフォームが提供する機構も複数ある。[ADR-0009](0009-platform-floor-and-toolchain.md) が Metal 4 世代と macOS 26 を前提に置いたことで、次の 4 つがすべて選択肢に入る。

- **シェーダ内でのテンソル評価** (Metal 4 の ML 統合)
- **モデル単位の推論** (CoreML)
- **画像処理のグラフ** (MPSGraph)
- **生成系** (Foundation Models)

### この領域は「あると良さそう」が最も溜まりやすい

[ADR-0001](0001-founding-principles.md) 原則 4 は、機能を実需で駆動することを求めている。機械学習はこの原則が最も破られやすい領域である — できることが多く、どれも魅力的に見え、しかし実際の作品で使うのはそのうちごく一部だからである。

**したがって本 ADR で作るのは API ではなく地図である。** どの機構が何を担うかを先に決めておけば、実需が現れたときに「どれを使うか」で迷わず、また**別の機構で同じことを二度実装する**ことも避けられる。道を作るのは実需が現れてからでよい。

### 分担を決める軸

4 つの機構は用途が部分的に重なる。切り分ける軸は**「フレームの中で評価するか、フレームの外で走らせるか」**である。

フレームの中で毎回評価するもの (画風の変換、学習済みの場の参照) は、結果を GPU 上に置いたまま描画に使えなければ意味がない。CPU との往復が入った時点でフレーム時間に収まらなくなる。

フレームの外で走るもの (映像からの特徴抽出、生成) は、往復のコストより「モデルをそのまま動かせること」のほうが重要になる。

### 旧世代の画像フィルタ API

画像処理には旧世代の固定機能フィルタ群もあるが、[ADR-0009](0009-platform-floor-and-toolchain.md) が Metal 4 世代への一本化を決めている。**同じことが新しい機構でできる以上、旧世代の API を新規に採用する理由はない。**

### 回避策を持ち込まない

この領域のフレームワークには、Objective-C 由来の API 設計が残っているものがある。メソッドの差し替えや関連オブジェクトによる回避策で不足を埋める書き方は、**動くが後から読めない**。[ADR-0010](0010-concurrency-model.md) 決定 3 と同じ姿勢で、最初から採らない。

## 決定

### 1. 4 つの機構の役割を次のように分担する

| 用途 | 使う機構 |
| --- | --- |
| フレーム内で GPU 上のデータに対して評価する (画風変換・学習済みの場の参照) | Metal 4 のシェーダ内テンソル |
| 学習済みモデルをモデル単位で推論する (特徴抽出・分類。姿勢推定は OS の組み込みの要求で足りないときだけ) | CoreML |
| OS が持つ組み込みの要求で、映像から取り出す (手・顔・体の姿勢・人物の切り抜き。2026-10-23 追加。フレームの外で推論する) | Vision |
| 画像処理を計算グラフとして組む | MPSGraph |
| テキストなどの生成 | Foundation Models |

用途が重なる場合は、**フレーム内で評価する必要があるかどうか**で決める。必要があるならシェーダ内テンソル、無いなら残りから選ぶ。

### 2. 旧世代の固定機能画像フィルタ API を新規採用しない

画像処理は MPSGraph またはシェーダで書く。

### 3. Objective-C runtime を用いた回避策を持ち込まない

メソッドの差し替え・関連オブジェクトによる回避策を使わない。フレームワーク側の制約は、現行の API (async での監視・現行の delegate) の範囲で解く。解けない場合は、その機能を採らない判断も含めて検討する。

### 4. 本 ADR は API を定義しない

決定 1〜3 は境界の宣言であって、公開 API の設計ではない。**実際の作品制作で必要になった経路から実装する** ([ADR-0001](0001-founding-principles.md) 原則 4)。どの機構も「使えるようにしておく」ためだけには実装しない。

### 5. モジュール上の置き場は本 ADR では決めない

機械学習の機能をどのモジュールに置くかは、パッケージ骨格 ([#139](https://github.com/mokume-metal/mokume/issues/139)) の担当とする。

#### 改訂 (2026-10-23) — Vision を持つ。フレームの外の列に置き、結果を入り口で受ける ([#1968](https://github.com/mokume-metal/mokume/issues/1968))

[ADR-0041](0041-standard-scope-map.md) の地図は、Vision (手・顔・体の姿勢・人物の切り抜き) を「標準だが設計が重い」に置き、本 ADR の地図の上で決めるとしていた。前提のカメラ ([#1977](https://github.com/mokume-metal/mokume/issues/1977)) が入ったので決める。前身のライブラリでも、周辺の領域の中で作例が最も多かった。

| 決めること | 決定 |
| --- | --- |
| 本 ADR の地図の上の置き場 | 決定 1 の表に Vision の行を足し、**フレームの外で推論する側** (CoreML と同じ側) に置く |
| ターゲット | [ADR-0042](0042-camera-and-audio-standard.md) 決定 3 のコア依存の層に、`MokumeCamera` と同じ形で別ターゲット (`MokumeVision`) を切る。**MokumeCore だけに依存する** |
| 結果の受け方 | 入り口 (`Inlet`) の「最新の 1 つ」に入れる。元のコマの host time を持たせる |
| 決定論 | 実機は水準 1。書き出しでは、フレームごとに推論を待つ。水準 2 を名乗れるのは、記録した結果を注入するときだけ |
| 決定 4 | 「作品の実需から実装する」を、[ADR-0043](0043-features-start-from-examples.md) (作例から作る) に揃える |
| 最初の範囲 | 手の関節点まで。最初の作例は「手の関節点に円を置き、人差し指で線を描く」 (ml5.js の handPose 型)。顔・体・人物の切り抜きは、次の作例が来てから |

**置き場: フレームの外で推論する側**

- Vision の要求は、OS が持つモデルで画像を読んで値を返す。**結果は GPU 上に置いたまま描画に使う形ではない** (点の列・信頼度) ので、決定 1 の軸 (フレームの中で評価する必要があるか) では「無い」側に落ちる。往復を避けるために GPU 上で評価する理由が無い
- **自前のモデルを動かす口にはしない。** OS が持つ組み込みの要求で足りる姿勢推定・人物の切り抜きは Vision、自前のモデルが要るものは CoreML と分ける。決定 1 の CoreML の行の「姿勢推定」は、この境で読む (表を直した)。利用者のモデルを読み込む口は、作例が来てから別に決める (決定 4)
- 決定 1 の表は、Vision の行を足しただけである。機構の役割分担は変わらない

**ターゲット: MokumeCore だけに依存し、入力は `Image` で受ける**

- [ADR-0016](0016-package-structure.md) 決定 1 は、コア依存の層の中での横の依存を許さない。**`MokumeVision` は `MokumeCamera` に依存できない**ので、カメラの型 (`Capture`) に直に繋がない
- 受ける入力は、外から来た画素が内で作る絵と同じ型になる `Image` ([ADR-0028](0028-external-inputs.md) 決定 5) と、その絵が届いたときの到着の記録 (`Arrival`・MokumeCore の型) である。**カメラ・動画・自作の絵を区別しない**。カメラの `mirrored` で左右を入れ替えた後の絵を受けるので、点は描いた絵の上にそのまま重なる
- 返す点は、**入力の絵の画素の座標** (左上原点・y は下向き) にする。Vision の 0〜1・左下原点を利用者に見せない ([ADR-0020](0020-api-naming-and-surface.md) 決定 6)
- `Image` の画素を CPU へ一括で出す公開の口が MokumeCore に足りなければ、実装の `Feature` が最小のものを足す (`Image.write(DisplayImage)` の逆の向き)。足すなら MokumeCore の `public` に置き、外のパッケージも使えるようにする ([ADR-0042](0042-camera-and-audio-standard.md) 決定 3)。GPU のテクスチャを直に渡す道は、計測で足りないと分かってから足す ([ADR-0042](0042-camera-and-audio-standard.md) 決定 5 の順序)
- 利用者が選んで import する product にはしない。アンブレラが再輸出する。Vision は許可を要らない (カメラの許可は `Capture` が持つ)

**結果の受け方: 最新の 1 つを、元のコマの時刻つきで**

- 結果は `Sendable` で `Codable` な値 (点・信頼度・どの手か) にして、`ExternalInput` の最新の 1 つへ入れる。`supply()` がフレームの開始時に 1 回だけ取り出し、入り口の型の値に書く ([ADR-0042](0042-camera-and-audio-standard.md) 決定 4 の改訂 (2026-10-06)。`AsyncSequence` にはしない)
- **推論は main actor の外で、`Task` で分離して走らせる** ([ADR-0010](0010-concurrency-model.md) 決定 4)。Vision の Swift の口は async なので、待ち行列を OS が決める受け口に当たらず、[ADR-0042](0042-camera-and-audio-standard.md) 決定 7 の例外を足さない
- **溜めない。** 推論の最中に届いた絵は、最新の 1 枚だけを持ち、古いものは捨てる (最新の 1 つの入れ物。[ADR-0028](0028-external-inputs.md) 決定 2)。重くても、描くほうは止まらない
- **結果は元のコマの時刻を持つ。** 持たせるのは推論が終わった時刻でなく、絵が届いた host time である。実機では結果が 1 フレーム以上遅れて届くので、遅れを利用者が時刻から読める。カメラの時刻も MIDI・OSC の時刻も host time に揃える ([ADR-0042](0042-camera-and-audio-standard.md) 決定 4)
- **最初の 1 回は、モデルの用意で待たされる。** 測ると、この機械で初めて走らせた回は 5.0 秒、次のプロセスでは 0.10 秒だった。開くときに用意を始め、用意が済むまでは状態で名乗り (`SourceState`)、フレームを止めない。手が写らないときは空の結果で、落ちない

**決定論 ([ADR-0025](0025-determinism-levels.md))**

- **実機で名乗れるのは水準 1 まで** (フレームの時計を選んだとき) である。カメラの絵も推論の結果も外の時間に依るので、水準 2 は名乗れない ([ADR-0028](0028-external-inputs.md) 決定 7)
- **書き出しでは、フレームごとに推論を待つ。** フレーム N の入力の絵に対する結果が、フレーム N の `draw()` に出る。実機のように遅れて届くことが無いので、回ごとの揺れが 1 つ減る。代償は書き出しの時間で、書き出しは実時間より遅くてよい
- **水準 2 を名乗れるのは、記録した結果を注入して回すときだけである。** 絵を記録して推論をやり直す形では名乗らない — 推論を OS のモデルに任せているので、同じ絵から同じ結果が出ると約束できない。OS の更新でモデルが変わりうるし、機械ごとの実行 (専用回路・GPU・CPU) も選べない
- 結果を `Codable` にしたので、リプレイ ([ADR-0028](0028-external-inputs.md) 決定 6 の改訂 (2026-10-14)) は結果を記録して流し直せる。**結果だけで描くスケッチ** (関節点に円を置く) は、リプレイで水準 2 を名乗れる。カメラの絵も描くスケッチは、カメラが記録の対象外なので名乗れない

**測ったこと** (M3 Max・macOS 27.0.1。使い捨ての計測で、許可に触れない。`VNDetectHumanHandPoseRequest` を手が写らない乱数の絵に 30 回)

- 640×480: 中央値 3.4 ms (2.6〜4.6)。1920×1080: 中央値 5.6 ms (4.9〜6.6)
- **手が写る絵の費用は測っていない** (関節点の段が加わる)。フレームの予算 (60 fps で 16.7 ms) の中で毎フレーム待つ形は採らない理由の 1 つで、実装の `Feature` が手の写る絵で測る

**最初の範囲**

- 手の関節点。1 つの手につき 21 点 (手首と各指 4 点) を、手ごとの信頼度と左右とともに返す。同時に見る手の数は作例が要る分に絞る。名前と形は実装の `Feature` が決める ([ADR-0043](0043-features-start-from-examples.md) 決定 2)
- 作例は点の列で終わり、`Image` を書く道を使わずに済む。**人物の切り抜き (マスク) は `Image` を書く道 ([ADR-0042](0042-camera-and-audio-standard.md) 決定 5) を通るので、次の作例が来てから決める**

**退けた案**

- **フレームの中で推論を待つ。** 手が写る絵の費用を測っていないうえ、実機で 1 枚が重いとフレーム全体が落ちる。書き出しだけが待つ
- **`MokumeCamera` に同居させる。** 動画はカメラと同じ変換 (`FrameConverter`) を共有するので同居したが、Vision が共有するものは無い。`Image` を受ければ、カメラ以外の絵 (動画・自作の絵) にもそのまま効く
- **`Capture` から絵を直に受ける。** 上のとおり ADR-0016 決定 1 に反する。`MokumeVision` が `MokumeCamera` に依存すると、カメラの無い使い方 (動画の絵への推論) もカメラのターゲットを引き込む
- **結果を `AsyncSequence` で流す。** フレームで読む値として持つと決めた ([ADR-0042](0042-camera-and-audio-standard.md) 決定 4 の改訂 (2026-10-06))
- **決定 4 を「作品の実需から」のままにする。** 地図の標準に載った領域は作品を待たずに入れる ([ADR-0041](0041-standard-scope-map.md) 決定 3)。口は作例が要る分だけ作る

**決定 4 を揃える。** 「実際の作品制作で必要になった経路から実装する」は、機能の根拠を ADR-0043 決定 2 (先に置いた作例が要る分だけ作る) が持つ形に直す。**本 ADR が API を定義しない** (本 ADR の決定 4 の前半) ことは変わらない。「使えるようにしておく」ためだけには実装しない、も変わらない。

**決定 5 を決める。** 機械学習の機能の置き場は、本 ADR では決めないとしていた。Vision の置き場は上のとおり `MokumeVision` で、ほかの機構 (CoreML・MPSGraph・Foundation Models) の置き場は、その領域の作例が来たときに決める。

**代償**

- 本体が OS のモデルに頼る。OS の更新で結果が変わりうるので、結果の見た目を突き合わせる検査を書かない。検査は注入した結果で回す (機材も Vision も要らない)
- 実機は結果が遅れて届く。作例では、遅れを許す絵 (関節点の円・指先の軌跡) になる
- 公開の面が増える。口は作例が要る分に絞る

> 破れたとき: 領域ごとに推論の置き場と受け方が分かれ、書き出しの結果が回ごとに揺れる。カメラの型に直に繋いだ推論は、動画の絵に使えず、あとから `MokumeCamera` の中へ積み上がる。

## 影響

- 実需が現れたとき、「どの機構を使うか」の議論を再演しない。決定 1 の表を見て決める
- 決定 1 の軸により、同じ処理を 2 つの機構で二重に実装する事態を避けられる
- 決定 4 により、本 ADR の merge 後もライブラリのコードは 1 行も増えない。これは意図した状態である (2026-10-23 の改訂で、Vision だけは作例から作ると決めた)
- 決定 1 の「フレーム内で評価する」経路は、[ADR-0011](0011-color-model.md) の作業空間 (linear 16F) の上で動く。テンソルと描画が同じ精度・同じ色空間を共有する
- 決定 3 により、回避策で埋めていた不足は「採らない」判断に倒れることがある。これは機能の幅より、後から読めることを優先した結果である
- 決定 1 の表は、新しい機構が増えたときに更新する。表そのものが議論の置き場になる
