# ADR-0010: 並行性規範 — スケッチは MainActor 既定、並列は明示的に分離する

## 状態

採用 (2026-08-27) / 改訂 (2026-09-09): 決定 4 に FileWatcher の例外を追補 ([#733](https://github.com/mokume-metal/mokume/issues/733)) / 改訂 (2026-10-03): 決定 4 の例外を、OS の受け口が待ち行列やスレッドを決めるもの一般へ広げる ([ADR-0042](0042-camera-and-audio-standard.md)) / 改訂あり (本文の「改訂 (日付)」見出し)

## 文脈

[ADR-0009](0009-platform-floor-and-toolchain.md) により Swift 6 言語モードを day 1 から使う。言語レベルの並行性検査はエラーとして働き、隔離されていない可変のグローバル状態や、隔離境界をまたぐ非 `Sendable` な値の受け渡しはコンパイルを通らない。

一方 [ADR-0001](0001-founding-principles.md) 原則 1 は、ユーザーが書くコードの側に注釈を要求しないことを求めている。

> **スケッチの気楽さを最優先する** — スケッチは 1 ファイルから始められ、ボイラープレート・**並行性の注釈**・ビルド設定をユーザーコードに要求しない。(中略) ライブラリ内部の複雑さがスケッチの書き味に漏れ出す設計は、内部がどれほど正しくても採らない。

この 2 つは正面から緊張する。**本 ADR はその緊張を、どちらも降ろさずに解く規範を定める。**

### 緊張の芯にあるもの

スケッチの書き味は「いま描いている対象」への暗黙のアクセスに支えられている。`circle(x, y, d)` と書けるのは、どのキャンバスに描くかを毎回渡さずに済むからで、それは実装から見れば**可変のグローバル状態**である。素朴に書けば Swift 6 では通らない。

通す方法は 2 つある。

1. 状態を隔離する (どのスレッドから触れるかを型で固定する)
2. 検査を黙らせる (`@unchecked Sendable`・`nonisolated(unsafe)` などの escape hatch)

2 は一度使うと必ず増える。使った箇所は「検査を通ったから安全」ではなく「検査を外したから通った」場所になり、数が増えるほど言語モードを有効にしている意味が薄れる。**そして escape hatch を数十箇所抱えた状態から後で剥がすのは、最初から使わないより桁違いに高くつく。** ADR-0009 が言語モードを day 1 に置いたのは、この選択を先送りしないためである。

### 描画は元々ひとつのスレッドの仕事である

隔離先の選択は難しくない。フレームベースの描画ループは、GPU へコマンドを積んで present するまでが一連の順序を持つ仕事で、複数スレッドから同時に触る前提がそもそも無い。**描画とその状態を main actor に置くことは、制約ではなく実態の記述である。**

さらに Swift 6.2 以降には、ターゲット単位で既定の隔離を main actor にする機構がある。これを使うと、ユーザーが書くスケッチには `@MainActor` すら現れない — 原則 1 の要求 (注釈を書かせない) と、言語モードの要求 (隔離を明示する) が同時に満たされる。

### 並列が本当に要る場所は別にある

一方で、すべてを main actor に置くわけにはいかない。GPU コマンドの生成、動画やフレームの書き出し、実行中スケッチの観測 ([ADR-0001](0001-founding-principles.md) 原則 3)、アセットの読み込みは、描画のフレームを止めずに進める必要がある。ここは**明示的に分離する**のが正しく、暗黙に main から外れるのは事故である。

## 決定

### 1. スケッチは main actor 既定とする

ライブラリのターゲットは既定の隔離を main actor に設定する。スケッチを書く人は並行性の注釈を一切書かない。ライブラリの公開 API も、既定では main actor 隔離として提供する。

### 2. 暗黙のアクティブコンテキストは main actor 隔離のグローバルとして正式化する

`circle(...)` のような直接呼べる描画関数が参照する「いま描いている対象」は、隠された裏口ではなく**明示的に main actor 隔離されたグローバル**として設計する。隔離されている以上、それが可変であることは問題にならない。

### 3. escape hatch を既定の道具にしない

`@unchecked Sendable`・`nonisolated(unsafe)` などは、「検査を通せないので黙らせる」用途では使わない。**使うなら、なぜその値が安全なのかをコード上の注釈として残す**。

**この決定に機械検査は付けない** ([ADR-0008](0008-mechanism-needs-demonstrated-harm.md) 決定 1・5)。隔離の検査はコンパイラが既に担っており、自作の lint が見るのは「escape hatch を書いたか」という字面だけである。実際に escape hatch が増え始めたら、そのとき実害を名指しして Issue から機構を足す。

### 4. 並列は actor と structured concurrency で明示分離する

GPU コマンドの生成、書き出し、観測、アセット読み込みなど main actor の外で進める処理は、actor または structured concurrency (`Task` / `TaskGroup`) で明示的に分離する。分離した境界を越える値は `Sendable` を満たす形で設計する。**`DispatchQueue` を新たに導入しない。**

#### 改訂 (2026-10-03) — 例外は 1 本ではなくなった。条件で認める

**現行の扱い: OS の受け口が待ち行列やスレッドを決めるものは、[ADR-0042](0042-camera-and-audio-standard.md) 決定 7 の条件をすべて満たすときに限って認める。** 条件は、受ける点でしかないこと・境界を越えるのが `Sendable` な値か合図だけであること・利用者に漏らさないこと・realtime スレッドで確保もロック待ちも dispatch もしないこと・置くのは本体の上に載る別ターゲットだけであること、の 5 つである。**MokumeCore の中の例外は、下の追補のファイルの見張り 1 本のまま増やさない。**

**下の追補は、ファイルの見張りを「この決定に対する唯一の例外」と数えていた。** カメラと音を標準の機能に入れると ([ADR-0041](0041-standard-scope-map.md))、その数え方が成り立たなくなった。カメラの受け取り (`AVCaptureVideoDataOutput`) は待ち行列を引数に取り、音の入力と出力は OS の realtime スレッドで呼ばれる。どちらも、ファイルの見張りと同じく**並列の設計ではなく OS の受け口の形**で、「渡さない」「呼ばれない」は選べない。

**理由は動いていない。** 禁じているのは自前の並列を待ち行列で組むことで、追補が挙げた守り (受ける点でしかない・値を渡さない・callback を漏らさない) は ADR-0042 決定 7 の条件にそのまま入っている。変わったのは、例外を 1 本ずつ数える形から、条件で認める形にしたことだけである。

#### 追補 (2026-09-09) — 見張りの待ち行列だけは例外である

`Sources/MokumeCore/Drawing/FileWatcher.swift` が `DispatchQueue` を 1 本持っている ([#733](https://github.com/mokume-metal/mokume/issues/733))。**この決定に対する唯一の例外**だった (2026-10-03 の改訂で、条件で認める形へ移った)。ほかの並列は宣言どおり分けてある — `FrameWriter` と `MovieWriter` は待ち方を semaphore に寄せ、コードのコメントで本決定を引いて「`DispatchQueue` は足さない」と名乗っている。

**例外が要るのは、ここが並列の設計ではなく OS の受け口だからである。** ファイルの保存を拾う口は `DispatchSource.makeFileSystemObjectSource(fileDescriptor:eventMask:queue:)` で、**待ち行列を引数に取ることが API の形そのもの**である。actor で包んでも `AsyncSequence` に包んでも、その内側でこの引数を埋めることは避けられない — 選べるのは「どの待ち行列を渡すか」だけで、「渡さない」は選べない。**この決定が禁じた「新たに導入する」— 自前の並列を待ち行列で組む — には当たらない。**

**主キューを渡す形は成立しない。** 主キューが捌かれるのは窓のある実行だけで、検査の実行では捌かれず、**実装が正しくても保存が届かない**ことを実測している (同ファイルの「主キューへ直に載せない」節)。逃げ道が塞がっているという意味でも、ここは選択ではない。

**そして決定 4 が守ろうとしたものは、例外の下でも守られている。** 待ち行列は出来事を受ける点でしかなく、拾った先は `Task { @MainActor in … }` で main actor へ渡る。境界を越えるのは「変化があった」という合図だけで (`@Sendable () -> Void`)、値は渡らないので `Sendable` の要求も自明に満たされる。決定 5 に触れないのも、この口が internal で、callback が利用者へ漏れないためである。

**何が示されたら畳むか**: ファイルの変化を待ち行列なしに待てる口 (`AsyncSequence` を直に返すもの) が使えるようになったとき。そのときはこの例外を消し、決定 4 を例外なしに戻す。

### 5. 継続的な値の流れは AsyncSequence を一級 API とする

時間とともに届き続ける値は、**入り口 (`Inlet`) が `supply()` でフレームごとに渡し、スケッチは `draw()` から読む**。値の性質によって入れ物が 2 つに分かれる (下の表)。新しいものが古いものを上書きして困らない値は最新の 1 つを、1 つでも取りこぼすと意味が変わる出来事の列は前の取り出し以後に届いたものを全部、届いた順に渡す。**見出しの `AsyncSequence` は採択時の選択で、いまは退けている** — 見出しは「ADR-0010 決定 5」の参照を保つために残した。退けた理由は下の 2 つの改訂 (2026-10-06・2026-10-08) にある。

| 値の性質 | 入れ物と出し方 | 例 |
| --- | --- | --- |
| 新しいものが古いものを上書きして困らない。フレームごとに 1 つを取り出せば足りる | 最新の 1 つ (`ExternalInput`) に入れ、入り口が `supply()` で取り出す。スケッチは `draw()` から読む値として持つ | カメラの絵 (`Capture.image`)・音の解析の結果 (`AudioIn.level` ほか) |
| 1 つでも取りこぼすと意味が変わる出来事の列 | 落とさない列 (`ExternalQueue`・[ADR-0028](0028-external-inputs.md) 決定 2) に溜め、`supply()` がフレームごとに、前の取り出し以後に届いたものを全部・届いた順に渡す。スケッチは `draw()` から読む | OSC のメッセージ (`OSCPort.messages`)・MIDI のメッセージ ([#1963](https://github.com/mokume-metal/mokume/issues/1963) の案)・ネットワーク経由の制御 (TCP・UDP・WebSocket — [#2018](https://github.com/mokume-metal/mokume/issues/2018) の案)・シリアルの受信 ([#1961](https://github.com/mokume-metal/mokume/issues/1961) の案) |

```swift
// osc は createOSC(listen:send:) で作った入り口 (OSCPort)
func draw() {
    for message in osc?.messages ?? [] where message.address == "/size" {
        size = message.float(0) ?? size
    }
    circle(width / 2, height / 2, size * height)
}
```

**completion callback を公開 API に置かない。** delegate や callback を要求する下層のフレームワークは、ライブラリ側で包んでから公開する — 届き続ける値は入り口の入れ物 ([ADR-0042](0042-camera-and-audio-standard.md) 決定 4) に受けて上の形にし、読み込みは `async` の口 (決定 6) にする。

#### 改訂 (2026-10-06) — フレームで標本化する値は、フレームで読む値として持つ

届き続ける値を、上の表の 2 つの性質に分けた。この改訂で決めたのは 1 行目 (フレームで標本化する値) で、2 行目 (出来事の列) は `AsyncSequence` のまま残していた (下の改訂 (2026-10-08) で変えた)。

フレームで読む値にする理由は 2 つある。

1. **`draw()` から直に読める。** `AsyncSequence` で出すと、作者は最新の値を預かる変数と、それを埋めるタスクを自分で書くことになる。標本化する値では、その 2 つは毎回同じ形になる
2. **値とフレームの対応を本体が決められる。** `supply()` がフレームの開始時に取り出すので、時刻はフレームの時刻と 1 本になる ([ADR-0042](0042-camera-and-audio-standard.md) 決定 4)。ファイルや標本列を流すときは、フレームの時刻だけで値が決まるので、固定の時計で書き出すと同じフレームが同じ値を受け取る ([ADR-0025](0025-determinism-levels.md) の水準 2)。`AsyncSequence` では対応が届いた順と作者のタスクの進み方で決まり、本体はこれを保証できない

当初の決定は「オーディオ解析の結果」を `AsyncSequence` の例に挙げていた。音の入力の実装 ([#1978](https://github.com/mokume-metal/mokume/issues/1978)) で、この例を外した。カメラ ([#1977](https://github.com/mokume-metal/mokume/issues/1977)) は、この使い分けを書く前に、既にフレームで読む値として入っていた。

#### 改訂 (2026-10-08) — 取りこぼしたくない出来事の列も、フレームで読む値として持つ

**2026-10-06 の改訂は、表の 2 行目 (1 つでも取りこぼすと意味が変わる出来事の列) を `AsyncSequence` で出すとしていた。** 例は「OSC・MIDI のメッセージ、ネットワーク経由の制御、入力イベント」で、当初の決定の冒頭も同じものを挙げ、`for await message in osc.messages { … }` を例にしていた。OSC の実装 ([#1962](https://github.com/mokume-metal/mokume/issues/1962)) で、これを落とさない列 ([ADR-0028](0028-external-inputs.md) 決定 2) に溜めてフレームごとに全部渡す形に変えた。スケッチは `draw()` から `osc.messages` を読む。

**退けた案は `AsyncSequence` である。** 理由は 2 つある。

1. **取りこぼさないことは、落とさない列で満たせる。** 出来事の列をフレームで読む値にしても、最新の 1 つへ標本化するのではない。前の取り出し以後に届いたものを全部・届いた順に渡すので、1 フレームの間に何度届いても失われない。`AsyncSequence` を選んだ理由だった「取りこぼすと意味が変わる」は、出し方ではなく入れ物で守れる
2. **注入で回すときに水準 2 を名乗るには、出来事とフレームの対応を本体が決める必要がある** ([ADR-0028](0028-external-inputs.md) 決定 7)。記録した列を流して書き出すとき、同じフレームに同じ出来事が届かなければ同じ絵にならない。`AsyncSequence` では、どのフレームで読まれるかが届いた順と作者のタスクの進み方で決まり、本体はこれを保証できない。2026-10-06 の改訂がフレームで読む値に挙げた理由 2 と同じもので、出来事の列にもそのまま効く

**代償:**

- 作者が `for await` で 1 つずつ逐次に処理する形は、本体の口からは出ない。届いた瞬間に反応する処理は書けず、反応は次のフレームの `draw()` になる
- 1 フレームの間に届いたものはまとめて渡る。届いた時刻の差は並びの順にしか残らない (入れ物は届いた瞬間の host time を受けるが、面に出るのは最後に届いたもののフレームと時刻 (`lastArrival`) だけで、メッセージごとの時刻は渡さない)
- 列には上限 (既定 4096) があり、超えたら古いものから捨てる。捨てた数は次に読まれたときに診断へ出す ([ADR-0028](0028-external-inputs.md) 決定 2)

入れ物は [ADR-0042](0042-camera-and-audio-standard.md) 決定 4 の共通の土台に並ぶ 2 つ目として MokumeCore に置いた (`ExternalQueue`)。MIDI・TCP・UDP・WebSocket・シリアルも、同じ列を使う案になっている (表の例の Issue)。

窓のマウスとキーの入力イベントは表の例から外し、この改訂では決めない — 窓の入力は既に `mousePressed()` などの呼び出しと `mouseX` などの値として、フレームの頭に届いている。

### 6. 読み込み API は async を正とし、同期版は setup 用の糖衣とする

画像・モデル・フォントなどの読み込みは `async` 版を正式な API とする。フレームループ開始前の初期化 (setup) でだけ使える同期版は、書き味のために提供してよい。同期版をフレーム内で呼べば描画が止まる — これは糖衣の対価であり、**同期版をフレーム内で使えないよう機械で縛ることは今はしない** (決定 3 と同じ姿勢)。

### 7. typed throws は失敗の種類が閉じている箇所で選択的に使う

シェーダのコンパイル、ファイルの読み込みなど、起こりうる失敗を列挙できる API では typed throws を使う。閉じていない箇所へ無理に広げない。

## 影響

- 本 ADR が守られているかの受け入れ検査は「**利用者が書くスケッチに並行性の注釈が現れないこと**」である。ライブラリ内部がどれだけ正しくても、注釈がスケッチ側へ漏れた時点で原則 1 に反する
- 決定 1・2 により、描画順は main actor 上で直列に確定する。これは決定論 ([ADR-0001](0001-founding-principles.md) 原則 2) と同じ方向を向く — 非同期に描画順が乱れる余地を構造的に持たない
- 決定 4 の例外は `FileWatcher` の 1 本だけである。**数が増えたらこの追補を疑う** — 「OS の受け口だから」で通る箇所が積み上がるなら、境界の引き方を決め直す必要があるという合図である
- 決定 4 により、観測・書き出し機構 (原則 3) は「main actor の外から来るもの」として境界を先に設計することになる。ビュー層 ([#135](https://github.com/mokume-metal/mokume/issues/135)) と GPU 応用の設計は、この境界の上に載る
- 決定 5 により、周辺モジュール (ネットワーク・MIDI・オーディオ) の公開 API 形が先に決まる。下層フレームワークが callback を要求しても、それがユーザーへ漏れることはない
- 決定 3・6 により、当面は機械検査を持たない領域が 2 つ残る (escape hatch の使用・同期ローダの誤用)。**どちらも実害が出たら Issue から機構を足す**。この ADR は監視すべき対象を名指ししておく役目も持つ
- パラメータ機構 ([#136](https://github.com/mokume-metal/mokume/issues/136)) は、観測機構との組み合わせが main actor 隔離の下で成立するかを検討対象に含める
