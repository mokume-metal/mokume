# 変更を実物と具体例で報告する

[AGENTS.md](../../../AGENTS.md)「説明と報告」の手順
(理由: [ADR-0036](../../../docs/decisions/0036-unattended-issue-processing.md) 決定 7)。
画像・動画の撮影、出所の記録、公開と表示の検算は [SKILL.md](SKILL.md) を使う。
文字だけの変更でもここから進められる。実際の報告・返答は GitHub に置く。

## 1. 対象と版を固定する

依頼された範囲・期間と対象 Issue を確かめる。報告を作る人が、対象を選ぶところから公開後の
リンク確認までを行う。定期起床の設定はこの手順に含まない。

記録する版は区別する:

- **今回の対象版**: 取得した main の完全な SHA と取得時刻。導入前の PR を報告するなら head SHA と明記する
- **前回報告した版**: 差分を切り出すための版。報告の URL と併記する
- **人が理解したと明示した基準版**: 返答の URL・対象範囲・SHA。返答が無ければ進めない。初回は未設定と書く

```bash
git fetch origin main
git rev-parse origin/main
git log --first-parent --format='%H %s' <前回報告SHA>..<今回SHA>
git diff --stat <前回報告SHA> <今回SHA>
git diff --name-status <前回報告SHA> <今回SHA>
```

first-parent の各コミットを PR と照合し、対象全件の一覧を残す。特定できないコミットも
「PR 未特定」と載せる。実際の merge 日時には PR の `mergedAt` を使う。merge queue では
コミットの時刻と合流時刻が異なるため、日付だけの PR 検索を全件の根拠にしない。
初回や基準版が未設定の回は、遡った範囲と範囲外を明記し、全履歴を覆ったと扱わない。

```bash
gh pr view <番号> --json number,title,url,body,mergedAt,mergeCommit,files,reviews
```

変更ファイルが API の上限等で切れていればローカルの差分と突き合わせる。ファイル名だけで
意味を決めず、テスト・スクリプト・文書も含めて本文と diff を読む。たとえば「テストの変更」
でも、台帳の更新や skip の追加なら緑の意味が変わる。重要パス外でも公開 API の新しいエラーは
利用者の対処を変える。人の基準版が古ければ、今回分とそれ以前の未確認分を分けて残す。

## 2. 各 Issue の具体例を確かめ、意図ごとに束ねる

PR の本数ではなく「作者が何をできるようになるか」「どの約束・代償が変わるか」で束ねる。
ただし全件一覧と対応づけ、束ねた結果、都合の悪い変更が消えないようにする。

各束に、目的、入力・操作、以前/以後の結果、必要な対処または代償、根拠の Issue/PR/ADR を置く。
元の Issue に例が無ければ調査して補う。置き場は AGENTS.md「コメント」の置き分けに従い、
同じ進捗を Issue と PR の両方へ連投しない。

| 変更 | 具体例の形 | 適した実物 |
| --- | --- | --- |
| 描画 | 同じスケッチ・同じ入力で before / after。どこを見るかを1文 | 並べた静止画。保存や操作で動くなら動画/アニメーション |
| API / CLI | `frameRate = 0` で起動 → エラー。止めたいなら `noLoop()` を使う、など入力・出力・対処 | 短いコードと実際の標準出力/終了コード。絵があるなら添える |
| 設計 / 規約 | 「手で起こしたトリアージ済み Issue の着手」で、どの判断・操作が要るかを変更前後で比較 | 読者の操作例、該当する文章の差分。図は説明図と明記 |
| まだ再現できない提案 | 「保存しても窓を消さず、絵だけ入れ替えたい」など期待を示す | 既存動作の実物を参照し、提案の実装を撮ったものとは呼ばない |

画像・動画は可能な範囲で各 Issue にも添える。統合報告では代表的な実物を表示し、残りへリンクする。
出所 (ライブラリ/CLI の版、入力、環境、採取方法・時刻) と検証の限界を併記する。
観測で採った絵は、窓の位置・つまみ・入力操作の実証にはならない。過去の動画を再掲する場合も
「今回の版で再検証した」と扱わない。証跡不足を生成画像や想像の出力で埋めない。

人が新たに選ぶ範囲は [AGENTS.md](../../../AGENTS.md)「説明と報告」で読む
(理由: [ADR-0036](../../../docs/decisions/0036-unattended-issue-processing.md) 決定 8)。採択済みなら根拠と実装を対応づけ、未採択なら選択肢・推奨・移行方法と、
判断を待つ作業の範囲を示す。報告を出しただけで未合意の意味変更を進めない。
たとえば検査の削除なら「CI を速くした」だけでなく、何を確かめなくなるかを示す。
採択済みの仕様を保つ検査の修正なら、同じ選択をもう一度人へ戻さない。

## 3. 短い本文と、辿れる詳細を書く

以下は書き始める形で、空の欄を埋めるために事実を作らない。読み切る時間は本人の評価で記録し、
文字数から「5分で読める」と断定しない。

```markdown
## 今回、何が変わるか

対象: <前回SHA> → <今回SHA> / 取得時刻 / 導入済みか導入前か
人の理解の基準版: <返答URLとSHA・範囲、または未設定>

意図と実物・具体例を示す。残る代償と、今回人に判断してほしい点を先に書く。

## 判断してほしいこと・未確認

選ぶ案と具体的な違い。証跡の欠落、失敗、未確認の範囲、前回から残った項目。
判断が不要なら不要と書く。報告への返答と PR の native Approve を混同しない。

<details>
<summary>対象全件・設計の根拠・検証の詳細</summary>

| Issue / PR・merge SHA | 意図の束 | 具体例・実物 | 設計と代償・検証の限界 |
| --- | --- | --- | --- |
| 全対象を列挙 | 本文との対応 | 出所へのリンク | ADR、検査、未実施 |

</details>
```

基準版から残った項目が多ければ、前の報告をリンクして一覧を保ち、本文では判断に必要なものを
優先する。古い未確認を「今回の対象外」として消さない。新たな設計の採用は ADR を変更する PR へ
つなげ、報告の要約だけで上書きしない。ADR の実装状況は対象版のコードと検査で確かめる。

## 4. 公開し、読めることを確かめる

投稿先は AGENTS.md「コメント」に従う。複数 PR を横断する報告は、その報告を扱う親 Issue
(そこでの独立した作業) に置き、個別の実装途中の話は各 PR に残す。

```bash
bash scripts/comment.sh issue <対象番号> --body-file <一時ファイル>
# PR の検証なら
bash scripts/comment.sh pr <対象番号> --body-file <一時ファイル>
```

投稿した本文を取り直し、全件一覧と版、リンクを確認する。画像は SKILL.md「貼る」のとおり
GitHub 側の配信経路も検算する。機械がバイトを取得できることと、人が表示/再生できることを
区別し、後者を確かめていなければそう書く。実物の表示/再生、分かりにくい具体例、読む時間を
人に尋ねる。返答で明示された対象だけを記録する。

## 5. 欠落や返答を、次の修正と報告につなぐ

| 起きたこと | 次にすること |
| --- | --- |
| 証跡が撮れない/公開できない | 対象、理由、代わりに確認できたこと、未検証範囲を報告する。必要な描画証跡のゲートは省略しない |
| 投稿に失敗した/成否が不明 | 成功と名乗らない。GitHub を取り直して重複投稿を避ける。復旧したら同じ固定版の報告を投稿する。復旧までの一時ファイルは作業用で、正典にしない |
| 報告が溜まった/返答が無い | 最後に公開した報告と、人の基準版を分けて残す。次の報告で未確認分と待っている判断を提示し、委任を広げない。欠けた確認を前提とする採択は待つが、独立した委任済みの修正まで止めない |
| 説明や証跡に誤りが見つかった | 元の投稿に訂正と理由を残し、誤りを引いた報告も直す。誤った版を基準版へ繰り上げない |
| 人が方向を修正した | 対象 Issue の完了条件を更新する。実装の修正は通常の Issue → PR、恒久的な設計変更は ADR へ。次の報告に「返答 → 修正PR → 新しい実物/具体例」を載せる |

報告を続けられるか、本人が方向を把握できたかは別々に評価する。数字は測った日時・母集団・
出所とともに残し、不明なら不明と書く。Issue 作成→merge の時間を、人の読解時間と呼ばない。
